1. tracking-by-detection：范式全流程

现代多目标跟踪（Multiple Object Tracking, MOT）的主流范式是 tracking-by-detection：不做"从像素里找目标再连线"的传统跟踪，而是每一帧都用检测器独立检测，然后把跨帧的检测"缝"成轨迹。检测器（Stage 2）负责"这一帧有什么"，跟踪器只负责"哪帧的哪个和哪帧的哪个是同一个"。

为什么要"先预测再关联"（① 在 ② 前）？因为关联的代价矩阵用的是预测位置：KF 把每条轨迹外推到本帧时刻（顺带解决多传感器的时延差——外推到统一时间戳），再用预测点去和检测算距离。预测把第 2 周的"跟得住"变成了第 3 周"分得清"的前提。

2. track 状态机：杂波的第一道闸门

2.1 三态设计

状态 含义 转入条件 转出条件
tentative（候选） 疑似新目标，还不对外输出 有未匹配检测认领 累计命中 ≥ min_hits → confirmed；连续丢失 → deleted
confirmed（确认） 可信轨迹，对外输出 hits ≥ min_hits（典型 3） 连续丢失 > max_age → deleted
deleted（删除） 释放 ID 与内存 — 不可恢复（新目标 = 新 ID）

2.2 为什么这样设计

  • tentative 挡杂波：真实检测器每帧都有几十个误检，若每个都直接建 confirmed 轨迹，轨迹池瞬间爆炸。杂波是空间随机、时间不持续的——"连续 3 帧出现在可预测位置"对杂波是极小概率事件（本周实验会量化：197 个 tentative 只有 3 个真目标转正；而不做防护时会有 7 条杂波轨迹幸存成 confirmed）。
  • max_age 挡漏检：目标被树荫/车辆遮挡 0.5 s，检测消失但目标还在。KF 纯预测滑行（速度照推、协方差按 Q 膨胀），门控顺带放宽（椭圆大了，马氏距离反而更容易通过），检测一恢复就续上——同一 ID 存活。没有 max_age 的跟踪器，一次遮挡 = 一次 ID 重生。
  • 与 NMS 的配合：检测端 NMS（非极大值抑制，Stage 2）可能把紧邻的两个目标压成一个框（双目标合并漏检），track 会经历"1 条轨迹接 1 个检测 → 突然 2 个检测"的时刻——状态机允许把多余检测开成新 tentative，避免误并入旧轨迹。反过来检测分数低的目标被 NMS 后端滤掉造成漏检，由 max_age 兜底。

3. MOT 指标：怎么量化"跟得好"

多目标跟踪评测的标准指标族来自 CLEAR MOT（Bernardin & Stiefelhagen, 2008），加上身份保持的 IDF1（Ristani et al., ECCV 2016）。逐个看：

3.1 MOTA（Multi-Object Tracking Accuracy）

MOTA=1−FN+FP+IDSW∑tgtMOTA = 1 - \frac{FN + FP + IDSW}{\sum_t g_t} MOTA=1−∑t​gt​FN+FP+IDSW​

这个公式在干什么：数三种错误占真值总量的比例，一次扣完。逐符号拆解：

符号 物理含义 大白话
FNFNFN（false negative） 漏检：真值目标没有对应输出 该报没报
FPFPFP（false positive） 误报：输出没有对应真值 不该报乱报
IDSWIDSWIDSW 身份切换次数：同一真值目标先后被两条不同轨迹认领 认错人
∑tgt\sum_t g_t∑t​gt​ 全部帧的真值目标总数 分母，错误率的基准

为什么可以是负数：输出离谱地多（FP 巨大）时，FN+FP+IDSWFN+FP+IDSWFN+FP+IDSW 可以超过分母，MOTA < 0——指标用线性惩罚明确告诉你"宁可少报不可乱报"。MOTA 主要惩罚检测质量与身份切换，不衡量位置准不准——那是 MOTP 的事。

3.2 MOTP（Multi-Object Tracking Precision）

所有匹配对（真值目标 ↔ 输出轨迹）的平均位置误差（2D 用 IoU 阈值下匹配框的重叠度，3D/点目标用平均距离）。MOTA 高、MOTP 低 = “目标都找对了但框得歪”。注意它衡量的是已配对目标的定位精度，与 MOTA 互补。

3.3 IDF1（Identity F1 Score）

基于身份保持的匹配：把"整条真值轨迹"与"整条预测轨迹"做全局二部匹配（而非逐帧匹配），统计"身份正确识别的检测数 ÷ (真值检测数 + 预测检测数)"。一句话：IDF1 高 = 一条轨迹从头到尾认的是同一个人/车。MOTA 高但 IDF1 低 = “每帧都报到了，但一会儿叫 A 一会儿叫 B”——这正是第 1 周说的 ID 漂移，也是路侧 V2X 最怕的指标组合。

指标工程实现对照 py-motmetrics（其结果与 MOTChallenge 基准对齐）；本周 mini-MOT 按同一口径实现 MOTA/MOTP/IDSW（IDF1 需要轨迹级全局匹配，作为思考题）。更新的 HOTA（Higher Order Tracking Accuracy, Luiten et al., IJCV 2022）把"检测"与"关联"解耦成两个可分别打分的乘法子项，正在成为新基准——概念上记住"MOTA 偏检测、IDF1 偏身份、HOTA 两者都管"即可。

5. SORT 与 DeepSORT：两句话与一条演进线

  • SORT（Simple Online and Realtime Tracking；Bewley et al., arXiv:1602.00763）：本周 mini-MOT 的"官方同款"——强检测器 + KF（状态为框位置尺寸及速度）+ 匈牙利 IoU 匹配，2D MOT 上 260+ Hz，凭这套极简组合就逼近当年的复杂方法。它证明了：tracking-by-detection 时代，检测质量比跟踪算法的精巧更值钱。
  • DeepSORT（Wojke et al., arXiv:1703.07402）：在 SORT 上加一条外观关联——用一个带 ReID（re-identification，重识别）损失的 CNN 从检测框里提出外观向量，级联匹配时"外观近 + 运动近"才算同一目标。专治几何关联治不了的病：遮挡后重现的目标 ID 不换、交叉行人的身份不错乱。

演进线到今天：SORT → DeepSORT（+外观）→ ByteTrack（ECCV 2022，低分检测框二轮关联，不用外观就上台阶）→ 跟踪与检测联合的端到端方案。但骨架全是本周这四步。

6. 轨迹输出怎么喂给下游

mini-MOT 的 output 列表（frame, track_id, pos）在真实系统里长成这样：

下游 拿什么 拿去干什么
预测补帧 confirmed 轨迹的 KF 状态 检测 10 Hz、规控 100 Hz：中间的帧由 KF 纯预测补齐，下游看到平滑连续的目标流（这就是第 1 周时延对齐的续集：输出也统一到下游时间戳）
历史平滑 滑动窗口内的轨迹历史 反推目标意图（变道、刹车）、剔除检测毛刺；输出给 V2X 的轨迹要再做一段历史平滑，避免广播的位置跳变
V2X 广播 TrackID + 状态 + 类别 车端拿 TrackID 对应自己看到的目标——ID 漂移 = 车端全部对不上（第 1 周难点五的闭环）
路侧事件检测 轨迹级统计 逆行、违停、行人闯入都是"轨迹级"模式，不是单帧检测能判断的

一条工程铁律：对下游输出的轨迹，宁可滞后几帧输出"确认过的平滑状态"，不要输出"最新但抖动"的状态——下游（尤其规划）对位置突变的容忍度远低于对延迟的容忍度。这也是 confirmed 态才对外输出、tentative 不输出的原因。

7. 工程权衡与失效模式

  1. min_hits 太大：轨迹出生延迟长，短命目标（窜出的行人）全程没有输出。症状：FN 集中在目标出生帧；修复：min_hits 降为 2，或对高置信检测（score > 0.9）出生即 confirmed。
  2. max_age 太大：杂波轨迹在死亡前多活几十帧（FP 上升），两条并行旧轨迹在目标重现时抢 ID。症状：FP 与 IDSW 同时涨；修复：max_age 与场景遮挡时长匹配（路侧开阔场景 5 帧够，城区 10~30 帧）。
  3. 共线目标误并：前后同车道两车距离近、速度接近，检测合并/交替，轨迹"吞并"了另一个目标。症状：一条轨迹尺寸/速度中途跳变；修复：轨迹尺寸一致性校验 + 外观特征。
  4. 评估口径不对齐：自己算的 MOTA 与 py-motmetrics 对不上，通常是匹配阈值（IoU 0.5 或距离门限）、confirmed 才计入输出、distractor 处理三处口径差异。修复：对照 py-motmetrics 的 CLEAR MOT 实现逐项核对。

8. 延伸思考题（含解析）

Q1：为什么 MOTA 的分母是"真值总数"而不是"输出总数"？
A：MOTA 是"错误率"口径：三类错误都相对"世界上实际发生了多少"来计。若分母是输出数，多输出反而摊薄错误率，会鼓励 FP——与指标的设计意图相反。

Q2：一个跟踪器 MOTA 0.9、IDF1 0.6，说明什么？
A：检测与定位基本到位（每帧都报对了），但身份保持差——轨迹频繁断裂重生或交叉互换。优先查关联（门控/代价）与遮挡处理（max_age/外观），而不是检测。

Q3：本周实验里 IDSW = 0，什么条件下它会变成非零？
A：让两目标交叉时刻更贴近（预测点距离小于门控半径）或加大检测噪声，交叉瞬间马氏距离矩阵出现"互换更优"的格局，全局指派就会换手。可以亲手改 gt_state 验证——这也是面试题"什么参数会影响 ID switch"的实证答案。

Q4：tentative 期间 KF 也在预测和更新，这与 confirmed 后有什么不同待遇？
A：状态更新一样，但 (a) 不对外输出；(b) 门控更紧（本实验的 3 m 欧氏门控）；© 没有宽限红利——本教学版给 tentative 与 confirmed 相同的 max_age，但量产系统通常让 tentative 连丢 1~2 帧即删（confirmed 才享受 max_age 宽限），本实验里杂波 tentative 是被"再吸不到就死"的统计规律自然淘汰的。差别共同保证"杂波进不来、真目标不冤死"。

Q5：为什么预测补帧用 KF 预测而不是"上帧位置直接外发"？
A：直接外发是零阶保持（目标看着一顿一顿），且丢掉了速度信息；KF 预测带速度与加速度趋势，且协方差告知下游"这个预测有多可信"，下游可按不确定度调整代价地图膨胀。

Q6：为什么评估时"tentative 不算 FP"是合理口径？
A：tentative 未对外输出、下游根本看不到；把它算 FP 会惩罚"该有的确认机制"本身，导致调参方向错误（为了压 FP 把 min_hits 调大，反而伤短命目标）。口径必须与"下游真实收到什么"对齐——评估口径是系统接口的一部分。

1. 为什么需要数据关联：多出来的难题是什么

第 2 周的滤波器只面对一个问题：观测已给定，怎么把它的信息融进状态。多目标场景多出一个前置问题：这一帧检测器吐出 5 个框，画面里已有 4 条轨迹，哪个框属于哪条轨迹？这就是数据关联（data association）。

它难在组合爆炸与歧义：

  • 组合爆炸：nnn 条轨迹对 mmm 个检测，可能指派方案是 n!n!n! 量级；真实路口几十条轨迹、上百个检测时不可能穷举。
  • 交叉歧义：两个行人交叉走过，预测位置短暂贴近甚至重叠。此时若用"就近配"，很可能把两条轨迹互换身份——A 的轨迹从此跟着 B 走。这就是 ID switch（身份切换）的最大来源。
  • 杂波与漏检：检测器还可能多报（杂波，clutter）或少报（漏检，miss）。关联算法必须同时回答"这是新目标吗"“这条轨迹断了吗”。

关联错误的代价是灾难性且不可逆的：滤波器再好，喂错了观测也只会把错误精致地平滑掉。所以工程上数据关联的优先级高于滤波精度——先配对，再谈准。

2. 匹配度量之一：IoU 匹配

对 2D 检测框（SORT 的做法），最直观的代价是交并比（IoU, intersection over union）：

IoU(A,B)=∣A∩B∣∣A∪B∣,c=1−IoUIoU(A, B) = \frac{|A \cap B|}{|A \cup B|}, \qquad c = 1 - IoU IoU(A,B)=∣A∪B∣∣A∩B∣​,c=1−IoU

这个公式在干什么：两个框的交集面积除以并集面积（1=完全重合，0=不相交），取 1−IoU1-IoU1−IoU 变成"越小越好"的代价。逐符号拆解：

符号 物理含义 大白话
AAA 轨迹预测出的检测框（KF 把上一帧框推到本帧） “我猜它这个框在这”
BBB 检测器本帧输出的框 “检测器说它在这”
∣A∩B∣|A \cap B|∣A∩B∣ 交集面积 重叠了多少
∣A∪B∣|A \cup B|∣A∪B∣ 并集面积 合起来占多大

IoU 匹配的优点：不依赖任何噪声统计、对框大小自适应（大框允许大位移），SORT 用它做到 260+ Hz。缺点：目标重叠（遮挡）时 IoU 全线下降、互相混淆；不适用于点目标（雷达航迹）或 3D 中心距场景。它回答的是"框重叠不重叠"，不回答"在预测不确定度意义上合不合理"——这就要请出马氏距离。

3. 匹配度量之二：马氏距离门控

3.1 公式

第 2 周已算出预测的残差协方差 S=HP−H⊤+RS = H P^- H^\top + RS=HP−H⊤+R（“预测与测量差多少算正常”）。把残差 y=z−Hx^−\mathbf{y} = \mathbf{z} - H\hat{\mathbf{x}}^-y=z−Hx^− 代入马氏距离（Mahalanobis distance）：

dM2=y⊤S−1yd_M^2 = \mathbf{y}^\top S^{-1} \mathbf{y} dM2​=y⊤S−1y

这个公式在干什么：把普通距离除以"正常波动范围"，得到一个无量纲的"这个偏差有多反常"分数。逐符号拆解：

符号 物理含义 大白话
y\mathbf{y}y 残差向量 预测与测量的分歧
SSS 残差协方差 分歧的"正常尺度"，且含各方向的相关性
S−1S^{-1}S−1 按正常尺度归一 越不确定的方向，同样的偏差越"不算事"
dM2d_M^2dM2​ 归一化偏差平方 无量纲"反常度"分数

和欧氏距离的关键区别：欧氏距离把所有方向一视同仁；马氏距离知道"沿路方向预测误差大（速度不确定）、横向误差小"这类各向异性——一个 8 m 的纵向偏差可能正常，一个 3 m 的横向偏差就异常。第 2 周的协方差椭圆在这里直接兑现价值：椭圆就是马氏距离的等值线。

3.3 手算一个 2D IoU（30 秒建立量感）

轨迹预测框 AAA：4 m × 2 m（轿车），中心 (10, 0)；检测框 BBB：4 m × 2 m，中心 (11.5, 0)。沿 x 方向重叠 10+2−11.5=0.510 + 2 - 11.5 = 0.510+2−11.5=0.5 m，y 方向完全重叠 2 m：

中心只偏了 1.5 m（不足半个车位），IoU 已掉到 0.07——IoU 对平移的敏感度是米级 × 米级平方的，这就是第 1 周难点四"中心 0.5 m + 朝向 5° 让 3D IoU 崩掉"的量感来源，也是高速目标（帧间位移 1 m 量级）必须"先预测后匹配"的原因：拿上一帧的框直接算 IoU，几乎全部为零。

3.2 为什么必须门控（gating）

门控 = 事先给 dM2d_M^2dM2​ 设上限，超限的配对直接禁止参与指派。 两个理由：

  1. 防污染：一个 50 m 外的杂波若不被门控拦住，会以"最反常但唯一"的姿态参与指派，甚至被强行配给某条轨迹，把它的速度状态带崩。门控是杂波的第一道闸门。
  2. 降复杂度与防错配：匈牙利算法对全矩阵运作 O(n3)O(n^3)O(n3)；门控把绝大多数格子置为不可用后，可行指派空间骤减，也避免"全局最优解里出现荒谬配对"。

阈值从哪来：高斯假设下 dM2d_M^2dM2​ 服从自由度为观测维数的卡方分布（chi-square, χ2\chi^2χ2）。设置信水平（如 99%），超限概率 1%，查表得阈值：

自由度（观测维数） 95% 阈值 99% 阈值
2 5.991 9.210
3 7.815 11.345
4 9.488 13.277

2D 位置观测（自由度 2）常用 9.21（99%）：允许 1% 的真观测被误拒，换取 99% 的杂波被拒。阈值调紧→漏配增多、轨迹易断；调松→杂波混入。第 6 节思考题会让你亲手试出这种权衡。

4. 匈牙利算法：全局最优指派

4.1 问题定义

nnn 条轨迹、mmm 个检测，代价矩阵 CCC（CijC_{ij}Cij​ = 轨迹 iii 配检测 jjj 的代价，可以是 1−IoU1-IoU1−IoU、dM2d_M^2dM2​ 或两者组合）。指派问题（assignment problem）：每行最多配一列、每列最多配一行，使总代价最小。

贪心（就近配）：每次挑当前全局最小代价的格子，划掉该行该列，重复。它快（O(nmlog⁡)O(nm\log)O(nmlog)），但局部最优不等于全局最优——先抢了小代价格子可能逼得剩下的行去配代价巨大的格子。

匈牙利算法（Hungarian algorithm）：Kuhn 1955 年提出（方法基于匈牙利数学家 König 与 Egerváry 的工作，故名），保证多项式时间 O(n3)O(n^3)O(n3) 内给出全局最优解。思想一句话：反复"增广"——若当前指派不是最优，沿代价结构找到一条可交换的交替路径，把一个已配对改成另一组配对，总代价严格不增；直到无法再改进，即为全局最优。你不需要会证明，只需要永远用 scipy.optimize.linear_sum_assignment（Munkres 1957 算法的实现），并知道它返回的指派总代价不劣于任何贪心方案。

2×2 手算走一遍算法要解决的问题：代价矩阵 [1224]\begin{bmatrix} 1 & 2 \\ 2 & 4 \end{bmatrix}[12​24​]。贪心拿最小格 (0,0)=1，剩下 (1,1)=4，总代价 5；而 (0,1)+(1,0)=2+2=4。差就出在"行差"上——第 0 行换成 (0,1) 多花 1，第 1 行换成 (1,0) 省下 2，净赚 1。匈牙利算法的所有复杂机制（行列约减、增广路径）本质上就是在系统化地寻找这种"换手净赚"的机会，直到无利可图。

6. 关联失败怎么办：新生与消亡

指派结束后，总有一批行和列没配上。它们是跟踪器"生死逻辑"的输入：

  • 未匹配检测（unmatched detection）：可能是杂波，也可能是新进入视野的目标。不能立刻建轨迹——真实检测器每帧都会吐几十个误检，直接建轨迹会让轨迹池爆炸。标准做法：先建 tentative（候选）轨迹，连续/累计命中若干帧（min_hits，典型 3）才转正——杂波是随机的，连续 3 帧出现在可预测位置上的概率极低。这就是第 4 周状态机的主题。
  • 未匹配轨迹（unmatched track）：可能是目标被遮挡/漏检，也可能真的驶出视野。不能立刻删除——删了，遮挡结束的目标会以新 ID 重生（ID switch）。标准做法：容忍若干帧漏检（max_age，典型 5~10 帧），期间靠 KF 纯预测"惯性滑行"，门控放宽一点等它回来；超过 max_age 才删除。
  • 双向失败的极端情况：目标急转弯导致预测完全偏离，所有检测都被门控拒绝。此时轨迹会滑行到 max_age 死亡，目标以新 ID 重生。这是几何关联的固有局限——外观特征（ReID，第 4 周）就是为它准备的补丁。

动手验证：把 exp4 实验 3 的门控阈值从 5.991 收紧到 3.0，第一个合理检测（dM2=1.25d_M^2=1.25dM2​=1.25）仍通过；再把 PPP 的 y 方向方差从 1 改成 0.04（自信过头），合理检测（横向偏 0.5 m）的 dM2=22/4+0.52/0.04=7.25d_M^2 = 2^2/4 + 0.5^2/0.04 = 7.25dM2​=22/4+0.52/0.04=7.25，超过 5.991 被拒——亲眼看到"协方差太自信会把好观测拒之门外"。门控是概率承诺，不是物理墙。

7. 工程权衡与失效模式

  1. 代价矩阵量纲混搭：把马氏距离²（量级 0~10）与 1−IoU1-IoU1−IoU（0~1）直接相加，前者淹没后者。症状：某类代价完全不起作用；修复：分别归一化再加权，或两阶段匹配（先 IoU 后马氏，SORT/DeepSORT 的做法）。
  2. 门控过紧：Q 调小后椭圆变小，正常机动目标被拒。症状：高速/机动目标 ID 频繁重生；修复：门控阈值随目标速度/状态维数查表，或对 χ2\chi^2χ2 阈值做在线一致性监控。
  3. 轨迹池不清理：tentative 轨迹只进不出，匈牙利矩阵越来越大。症状：帧耗时随时间上涨；修复：max_age + tentative 超时即删（第 4 周实现）。
  4. 全矩阵指派的遮挡崩塌：多目标深度遮挡时一坨检测对应一坨预测，IoU 全体下降，最优指派也开始互换。修复：外观特征、运动方向约束，或分块关联。

8. 延伸思考题（含解析）

Q1：为什么 dM2d_M^2dM2​（而不是 dMd_MdM​）直接和 χ2\chi^2χ2 分位数比较？
A：高斯残差 y∼N(0,S)\mathbf{y} \sim \mathcal{N}(0, S)y∼N(0,S) 时，二次型 y⊤S−1y\mathbf{y}^\top S^{-1}\mathbf{y}y⊤S−1y 严格服从 χk2\chi^2_kχk2​ 分布（kkk = 观测维数），平方量直接查表。用 dMd_MdM​ 还得开方变换分布，多此一举。

Q2：IoU 匹配和马氏门控各自的失效场景？
A：IoU 挂在遮挡（框重叠互相混淆）与点目标（无框可言）；马氏挂在 Q/R 统计失真（协方差不反映真实误差，门控形同虚设）。量产常用级联：先 IoU 粗配（便宜、尺度自适应），再马氏细配。

Q3：检测数比轨迹数多很多时，匈牙利算法会怎么处理多出来的列？
A：linear_sum_assignment 对非方阵自动处理（配 min(n,m) 对）。多余的检测天然"未匹配"，进入新生裁决。工程上也可以把代价矩阵补成方阵并填大数，效果等价。

Q4：为什么说"关联错了，滤波器救不回来"？
A：KF 假设观测来自同一目标。把 B 车的观测喂给 A 车的滤波器，残差被按"正常波动"吸收，A 的速度状态被拉向 B 的运动——错误被平滑地合法化，且 ID 已换，历史不可追溯。这是关联优先级高于滤波的根本原因。

Q5：什么场景下匈牙利算法的全局最优反而有害？
A：当"没有合理指派"时它仍会强行配出 min(n,m) 对（总代价再大也配）。所以门控必须先行——先剪掉荒谬格子，匈牙利只在"合理格子"里做全局权衡。这正是本实验流程"门控→指派→裁决"顺序的原因。

Q6：代价矩阵里 IoU（01）和马氏距离²（0几十）怎么组合到一起？
A：不能直接相加。常规做法有三种：(1) 归一化后加权：c=α(1−IoU)+(1−α) dM2/dgate2c = \alpha(1-IoU) + (1-\alpha)\, d_M^2/d_{gate}^2c=α(1−IoU)+(1−α)dM2​/dgate2​；(2) 级联匹配：先 IoU 粗配，配不上的再用马氏细配（SORT/DeepSORT 的模式）；(3) 门控为"与"、代价取其一：两道门都过，代价用马氏。任何组合都要先各自归一，否则量级大的那个会独自决定指派。

1. 第一性原理：把"深度未知"变成"深度概率"

上周的结论：像素 → 3D 必须指定深度 ddd，而 ddd 无观测。LSS（Lift, Splat, Shoot, Philion & Fidler, NVIDIA, ECCV 2020, arXiv:2008.05711，官方代码 nv-tlabs/lift-splat-shoot）的答案是不要赌一个深度，把所有可能的深度都撒一遍，按概率加权：

不预测 d，而是预测 α=[α1,…,αD],∑iαi=1\text{不预测 } d \text{，而是预测 } \alpha = [\alpha_1, \dots, \alpha_D], \quad \sum_i \alpha_i = 1 不预测 d，而是预测 α=[α1​,…,αD​],i∑​αi​=1

这个式子在说什么：每个像素输出一个离散深度分布（categorical distribution）——D 个深度档各是多少概率。与其说"这个像素是 23.7 m"，不如说"这个像素 20 m 档占 30%、25 m 档占 50%、30 m 档占 20%"。深度估计从回归问题变成分类问题——分类问题好训练（softmax + 交叉熵）、好表达多峰不确定性（玻璃幕墙后面到底是玻璃还是后面的车？两个峰都保留）。

2. Lift 三步全拆解

2.1 第一步：深度分布 α（depthnet + softmax）

图像 backbone（原论文用 EfficientNet-B0）输出每像素特征后，接一个 depthnet（1×1 卷积）输出 D 个深度 logit，再 softmax：

2.2 第二步：上下文特征 c

同一特征图再过一层得到上下文特征（context features） cu,v∈RCc_{u,v} \in \mathbb{R}^Ccu,v​∈RC（原论文 C=64）。它是"这个像素看起来的样子"——颜色、语义、纹理的抽象编码，不含深度信息（深度已被拆到 α 里）。原文就是把 backbone 特征用 1×1 卷积分成 depth（D 通道）和 context（C 通道）两个头。

2.3 第三步：外积得视锥特征（核心公式）

Fu,v,d=αu,v,d⋅cu,v∈RCF_{u,v,d} = \alpha_{u,v,d} \cdot c_{u,v} \quad \in \mathbb{R}^C Fu,v,d​=αu,v,d​⋅cu,v​∈RC

逐符号讲清这个公式在干什么：

  • cu,vc_{u,v}cu,v​：像素的 C 维上下文特征；
  • αu,v,d\alpha_{u,v,d}αu,v,d​：该像素在深度档 ddd 上的概率（标量）；
  • Fu,v,dF_{u,v,d}Fu,v,d​：把上下文特征"复制"到第 ddd 档深度上、再按概率缩放后得到的 C 维向量。对所有 ddd 拼起来，每个像素的 C 维特征膨胀成 D×CD \times CD×C 的块——整个图像物化成 (H,W,D,C)(H, W, D, C)(H,W,D,C) 的四维张量，这就是视锥特征（frustum features）；
  • 几何含义：特征 cu,vc_{u,v}cu,v​ 现在沿整条像素射线"摊开"分布——每个深度档上放一份被 α\alphaα 加权的副本。信息没有被创造或销毁，只是从"深度未知的一维"摊成了"深度概率加权的 D 份"；
  • 原文称之为 outer product（外积）：把 (α∈RD)(\alpha \in \mathbb{R}^D)(α∈RD) 与 (c∈RC)(c \in \mathbb{R}^C)(c∈RC) 做外积得到 D×CD \times CD×C 矩阵，形式上与向量外积 uvTuv^TuvT 同构。

3. Splat：pillar pool + PointPillars 式 encoder

3.1 Pillar pooling

逐符号：Bi,j∈RCB_{i,j} \in \mathbb{R}^CBi,j​∈RC 是第 (i,j)(i,j)(i,j) 根 pillar 的 C 维特征；求和条件是"该视锥特征点的 ego 位置落在 pillar (i,j)(i,j)(i,j) 的 x/y 范围内"。这一步就是第 1 周"反投影 + 网格索引"的批量版，也是 Stage 2 PointPillars 里"点云散落到 pillar"的同款操作——只不过散落的从激光点换成了图像视锥特征。

3.2 BEV encoder

pillar 特征图 (200×200×C) 过一个 ResNet-18 骨干的 encoder（原论文 BevEncode），把稀疏、带洞的特征图补成平滑的 BEV 语义图，输出 BEV 分割。结构上与 Stage 2 PointPillars 的 “pillar feature network + CNN backbone” 完全同型：LSS = 点云入口换成图像视锥的 PointPillars。这个观察很重要：Stage 2 学的 BEV encoder 知识全部平移复用。

3.3 Shoot

原论文的下游任务是 BEV 语义分割 + 规划：在 BEV 特征上卷积出每个格子的占据代价，构成可微代价图，一条候选轨迹的总代价 = 图上采样求和，训练时直接用驾驶数据回传梯度——"shoot"就是让规划器在代价图上"射击"轨迹。注意：LSS 论文本身不做 3D 框检测；把它变成检测框架的是 BEVDet（第 6 节）。

5. BEVDet：把 LSS 变成检测框架的工程课

BEVDet（Huang et al., 2021-12, arXiv:2112.11790）保留 LSS 式 view transformer，框架变成四段：图像视图 encoder → view transformer → BEV encoder → 检测头，检测头直接沿用 Stage 2 的 CenterPoint-style 头。相对原始 LSS 的关键工程改进（论文自述）一句话版：

  • 双空间数据增广：透视图像空间增广（防过拟合）+ BEV 空间增广（弥补视锥导致的 BEV 过拟合），这是 BEVDet 涨点的核心一招；
  • 更精细的 Lift/Splat 实现与 BEV encoder（配合 mmdet3d 工程栈的成熟算子）；
  • 为该范式定制的 NMS：稠密 BEV 头输出大量候选框，NMS 策略按新范式调整。

成绩（论文自报，nuScenes val / test）：BEVDet-Tiny 31.2% mAP / 39.2% NDS（val，计算量约为 FCOS3D 的 1/11）；BEVDet-Base 38.4% mAP / 46.1% NDS（val）；在 nuScenes test 榜（v3）上 42.2% mAP / 48.2% NDS，是当时纯视觉方法第一。后续 BEVDet4D（2022）加上了时序版本——把 LSS 的 Splat 扩到 4D 空间，用前帧 BEV 特征按 ego 运动 warp 后拼接，验证了"稠密 BEV + 时序 warp"的可行版型（第 3 周 BEVFormer 的 TSA 是同一思想的注意力版）。

6. 稠密 BEV 的代价：账单与本质

第 5 节例 6 已给出数字，这里把账单的本质说透：

  1. 算力花在空区域：200×200 pillar 中真正有目标的不过几十格（例 5 实测 6/100），但 BEV encoder 的卷积/后续头对全网格等价计算——感知信息密度与算力开销不成比例，这是稠密路线的原罪。
  2. 视锥中间量巨大：Lift 阶段物化 (H×W×D×C) ≈ 451 MiB 的中间张量（每帧、每 batch），且 6 相机并行——端侧 NPU 对这类大张量的搬运成本高于计算成本。
  3. 分辨率不可局部调节：想要 150 m 远处 0.1 m 分辨率？稠密路线只能全网升到 0.1 m（200→1000 格，25 倍代价），无法"只在前方 30° 精细"。
  4. 深度误差的传播：α 分布尖峰预测错 1 档（1 m），特征整份撒错 pillar——池化不可撤销。这催生了 BEVDepth 类工作用激光监督深度、以及"干脆别撒满"的稀疏路线。

7. 延伸思考题（含解析）

Q1：为什么 LSS 选"分类 D 档深度"而不是"回归 1 个深度"？
A：回归给不了不确定性表达，且深度病态区域（平面、反光）回归会出不可控的离群值；分类分布天然多峰、可稀释、可被激光深度图逐像素监督（BEVDepth 的做法）。代价是 D 档的显存与池化开销。

Q2：视锥特征沿深度求和精确还原 c——那"深度分布还有什么用"？为什么不直接用 c？
A：Splat 之后各 pillar 拿到的是位置加权的证据：同一个 c 若 α 尖，全部质量落在一根 pillar（定位明确）；若 α 平，质量摊在多根 pillar（定位模糊）。池化后的 BEV 图分布完全不同——深度分布的价值体现在空间分配上，而非特征数值上。

Q3：LSS 的 Splat 用 sum pooling，PointPillars 用 max/mean 类池化——选择依据？
A：sum 对"多像素证据累积"友好（远处目标像素少，多档弱证据累加成强证据），且可微、梯度均匀；max 保最强响应但对噪声敏感、多峰信息丢失。工程上两者都有用，BEV 检测框架多随头设计而定。

Q4：为什么 BEVDet 要在 BEV 空间再做数据增广？
A：视锥投影后 BEV 特征的分布与透视域不同（近密远疏 + 池化洞），仅图像域增广无法覆盖 BEV 域的过拟合模式（如对特定 pillar 位置的记忆）。BEV 域旋转/翻转/缩放增广直接对称化 BEV 空间，论文中显著涨点。

1. 方向性反转：从"像素撒"到"格子问"

LSS 的信息流：图像是主体，每个像素带着深度分布撒向 BEV 网格——网格被动接收。BEVFormer（Li et al., ECCV 2022, arXiv:2203.17270，官方代码 fundamentalvision/BEVFormer）把方向反过来：BEV 网格是主体。

1.1 BEV query：可学习的"格栅问句"

定义一组可学习参数 Q∈RHB×WB×CQ \in \mathbb{R}^{H_B \times W_B \times C}Q∈RHB​×WB​×C（nuScenes 惯例 HB=WB=200H_B = W_B = 200HB​=WB​=200，C=256），每个元素对应一根 BEV 柱，称为 BEV query。把它读成一句"问话"：

“我是 ego 系里 (x=20.5 m, y=-15.4 m) 这一格。谁经过这里？长什么样？过去几帧有没有动？”

回答问话的方式不是让像素来投（Lift-Splat），而是每个 query 主动去 6 个相机的特征图上找证据——找哪里、信多少，由注意力机制学出来。这个"主动问"的设计直接继承自 DETR（Carion et al., ECCV 2020）：DETR 用 ~100 个 object query 去图像里"问目标"，BEVFormer 把 query 数量放大到 200×200 = 40000 个、语义从"问目标"换成"问空间格"。所以面试里"BEVFormer 和 DETR 什么关系"的标准答案：同一种 query-based 集合表征，query 从目标级换成空间网格级，注意力从单相机换成多相机 + 多时刻。

2. Spatial Cross-Attention（SCA）公式逐符号

这是 BEVFormer 的视角转换核心。问题：BEV 柱 (i, j) 应该看 6 张图的哪些像素？

2.1 第一步：柱上参考点投影（把"看哪里"定下来）

BEVFormer 沿每根柱取 4 个不同高度的参考点（num_points_in_pillar=4，官方配置值；柱高范围 -5 m 到 3 m，取 4 个采样高度）。参考点 pkp_kpk​（k=1…4）是 ego 系 3D 点：

为什么要在柱上取多个高度而不是柱心一个点：上周反投影公式告诉我们，一个像素对应一条射线；反过来，一个 3D 点只对应图像上一个像素。柱是"竖直的一串空间"，不同高度的物体（车顶、车身、车轮）落在图像的不同行上——只取一个高度会漏掉柱内其他高度的物体。4 个高度就是把柱"竖着采样 4 次"。

每个参考点用标定矩阵正投影到 6 个相机（上周公式反向用）：

  1. 视野 mask：像素落在图像边界外 → 该相机对该参考点不可见，剔除；
  2. 相机 mask：官方实现只保留参考点命中的相机（每个 3D 点通常只被 1~2 个相机看到，环视相机视场互斥大部分区域）。

3. Temporal Self-Attention：时序对齐

3.1 问题：ego 在动，世界也没动

BEV 感知要回答"横穿行人"这类问题必须有速度信息——单帧 BEV 特征里"位置"有、"速度"没有。BEVFormer 的方案：把上一帧算好的 BEV 特征搬进当前帧一起算（recurrent，论文称 temporal fusion 跨 8 帧）。但两帧的 BEV 网格是"贴在车上"的坐标系——车前进 3.4 m 后，同一辆车在网格里的格子索引变了。直接把两帧特征按索引做 self-attention 是错位的。

3.2 解法：ego-motion warp（运动补偿）

失效模式（官方实现注释同款提醒）：ego 高速/大转向时 warp 插值误差大，超出网格范围的格子直接置零；静止目标跨 warp 反而"动"了（对齐的是世界，目标自己也在动——动目标的时序建模是第 4 周稀疏路线用"目标级传播"解决得更好的点）。

6. 工程权衡与失效模式

6.1 权衡速查

  • BEV 分辨率：0.512 m 的格子对 0.6 m 宽的行人只占 1~2 格，BEVFormer 的检测上限受网格分辨率约束——后续工作（如 BEVFormer v2、SOLOFusion）在输入分辨率与网格上继续加码；
  • 3 层编码器：每层都是全量 40000 query 的 TSA+SCA，层数与延迟线性相关；端侧复刻常砍到 1~2 层；
  • warp 依赖定位精度：TSA 的对齐质量受里程计/定位误差直接影响——定位漂移时序融合反而引入拖影（与 Stage 3 第 4 周时间标定呼应：同步误差在 warp 里同样放大）。

6.2 典型失效模式

  1. 视野交界柱信息缺失：两相机边界处参考点恰好在两者边缘出画，柱没有证据 → BEV 图"竖缝"。缓解：相机覆盖重叠区设计 + mask 策略放宽（投影到多相机）。
  2. 大转向帧 warp 错位：yaw 变化大时双线性插值取到错误邻域。症状：转急弯时远处时序拖影。缓解：只用可靠位姿帧、限制跨帧数。
  3. 注意力权重不可解释：没有显式深度分布可监督，深度学错难定位。缓解：加深度辅助监督（如 BEVDepth 思路迁移）或用带显式深度的混合架构。

7. 延伸思考题（含解析）

Q1：SCA 为什么用"参考点附近的 deformable attention"而不是"全图 attention"？
A：全图 attention 的 key 数 = 6×(H’×W’) 数万级，40000 柱 × 3 层根本算不动；且几何上柱的答案只可能在它投影位置附近——参考点投影就是强先验。deformable attention 把计算量压到"每柱 × 每命中相机 × 每高度 × 少数采样点"，同时保留可学习的微调能力。

Q2：TSA 只对"同格子"做注意力，为什么不需要更多历史格子？
A：warp 已把"世界同一位置"对齐到同一格子索引——空间对应关系由几何完成了，注意力只需判断"同一格的内容跨帧是不是同一物体"。运动目标会偏离 warp 预测，这是该设计的已知局限（第 4 周目标级传播的动机之一）。

Q3：BEVFormer 的 40000 个 BEV query 和 DETR 的 100 个 object query，训练上的最大不同？
A：DETR 用匈牙利匹配让 query 与目标 1-1 对应（稀疏集合预测）；BEVFormer 是稠密网格表征——每个 query 固定绑死一个空间格子，不存在匹配问题，检测头再从 BEV 特征出框。所以 BEVFormer 的 query 是"空间问句"，DETR 的 query 是"目标候选"——第 4 周 DETR3D 会把后者搬进 3D。

Q4：为什么 BEVFormer-base 的 test 集 mAP（37.5）比 val（41.6）还低，但 NDS 反而更高（56.9 vs 51.7）？
A：val 和 test 是不同标注子集，难度分布不同；NDS 是 mAP、mATE、mASE、mAOE、mAVE、mAAE 的复合指标，时序融合显著降低速度误差 mAVE，NDS 对"定位准、速度准"的加权让 BEVFormer 的时序优势在 NDS 上放大。教训：比较方法必须同集合同版本，单看 mAP 或单看 NDS 都会被误导。

1.1 病一：尺度随距离剧烈变化

针孔成像里，同一个物理宽度 www 在图像上占的像素数是 w⋅f/dw \cdot f / dw⋅f/d（fff 焦距、ddd 深度）——像素宽度与距离成反比。10 m 处的行人和 60 m 处的行人，在图像上差 6 倍大小。这带来两个后果：

  • 检测器的先验难学：anchor/感受野要同时覆盖"巨大的近处车头"和"几个像素的远处行人"；
  • 同样大小的感受野，在近处覆盖 2 m 世界、在远处覆盖 12 m 世界——同一层特征在空间上语义不均匀。

1.2 病二：遮挡

透视视角沿视线方向投影，前面的车把后面的行人整个挡住。图像是"从眼睛看出去"的投影，沿深度方向的信息被压缩成一层。而驾驶决策恰恰关心被前车挡住的横穿行人——透视表示把最要紧的信息弄丢了（BEV 俯视 + 多传感器能部分救回来）。

1.3 病三：多相机没有统一空间

nuScenes 用 6 个相机（1600×900，12 Hz，前/前左/前右/后/后左/后右，360° 环视；标注关键帧 2 Hz——nuScenes 官方文档数据）。每张图各自是以自己相机为原点的透视投影：

  • 前视图中"左边 100 像素"和左前视图中"右边 100 像素"可能指向同一辆车的同一部分——图像坐标系之间没有公共度量；
  • 想做"前相机看到的行人 + 右相机看到的车 + 激光点云"联合推理，必须先把它们放进同一个坐标系；
  • 更麻烦的是跨相机目标交接：一辆车从前视进入左前视，在两张图里是两个独立的 2D 检测，谁也说不准是不是同一个目标。

一句话总结：透视图的坐标是"角度"，不是"位置"。而下游规划器要回答"我前方 23.4 m 处有个行人"——这个问题在透视图坐标系里根本没法直接表达。

2. BEV 的三个好

BEV（Bird’s-Eye View，鸟瞰图）= 以自车为原点、从天上俯视的 2D 网格表示，格子单位是米而不是像素。

2.1 好 1：统一度量空间

所有相机、激光雷达、毫米波雷达的数据都变换到同一个 ego 车体坐标系（Stage 3 标定 + Stage 1 时序知识的落点）。跨相机交接、跨传感器对齐，在 BEV 里都变成"同一个网格上的同一次加法"。

2.2 好 2：天然适配规划与下游任务

规划器本质在 BEV 里工作："往左打 0.3 m 的车道偏离量"是俯视几何语言。LSS 论文（Philion & Fidler, ECCV 2020, arXiv:2008.05711）证明了一个重要论断：BEV 分割 + 可微代价图可以直接"shoot"出规划轨迹——BEV 表示不是检测的附属品，而是规划的第一公民。同理，高精地图元素（车道线、路沿）在 BEV 里是稳定的矢量形状，在透视图中则随 ego 运动剧烈形变。

2.3 好 3：空间不变性

透视图中"车在左下角"和"车在正中间"需要检测器都认得；BEV 里任何位置的"车"物理形态一致，卷积/注意力算子可以无偏地平移。BEVGridTransform 类的网格定义一旦固定，前后帧之间还能做 ego 运动补偿（第 3、4 周的时序核心）。

代价预告：BEV 不是免费的——把图像特征搬到 BEV 需要"视角转换（view transformation）"，这正是第 2、3 周稠密路线的全部内容，也是第 4 周稀疏路线要绕开的东西。

3. BEV 网格定义：x/y 范围与分辨率

BEV 网格由三元组 (下界, 上界, 分辨率) 定义，惯例沿 x 前、y 左（nuScenes ego 坐标系约定，z 向上）。两个代表性配置（均查证自官方仓库）：

为什么大家都选 200×200？ nuScenes 目标标注范围约 ±50 m（官方 ObjectRangeFilter 常用 [-51.2, 51.2]），0.5 m 分辨率下行人（0.6 m 宽）恰好占 1~2 格、车辆（4.5 m 长）占 9 格——再细显存翻倍，再粗小目标没了。范围 ÷ 分辨率 = 格数：102.4/0.512=200102.4 / 0.512 = 200102.4/0.512=200，这个除法就是 BEV 网格的全部算术。

还有一个隐藏自由度：高度 z。稠密 BEV 最终把 z 维压扁（pillar，柱），但"压扁前"采不采样 z 有讲究——LSS 的 zbound 是 [-10, 10, 20.0]（1 档粗格），BEVFormer 则在每根柱上取 4 个高度参考点（num_points_in_pillar=4，查证自官方配置）。同一个像素对应一条射线（下一节），柱上的多个高度点就是从这条射线上挑的采样点。

4. 2D→BEV 的核心难题：深度未知

4.1 一个像素是一条射线，不是一个点

  • u,vu, vu,v：像素在图像上的列、行坐标（单位：像素）；

4.2 深度 d 是自由度：病的根源

公式里 u,vu, vu,v 是观测（相机给的），R,tR, tR,t 是标定（Stage 3 给的），唯独 ddd 没有观测。同一个像素，ddd 取 10/25/40，得到 ego 系里三个不同的点——但它们共线：都在从光心出发的同一条射线上（方向由 (xc,yc,1)(x_c, y_c, 1)(xc​,yc​,1) 唯一确定）。第 5 节代码会实测打印这一组数。

所以"单目相机 3D 感知"的本质困难可以一句话说死：图像把 3D 世界沿射线方向压缩了，每个像素丢失了 1 个自由度（深度）。BEV 视角转换的全部戏份，就是把丢掉的深度自由度找回来。找法分三派：

派系 找深度的方式 代表
显式离散分布 每像素预测 D 个深度档的概率，全撒出去 LSS（第 2 周）
注意力隐式查 BEV 格子主动去图像上问，深度隐含在注意力权重里 BEVFormer（第 3 周）
只在目标处问 少量 3D query 投影回图像采样，不建网格 DETR3D/Sparse4D/StreamPETR（第 4 周）

4.3 视锥（Frustum）：把所有假设深度一起撒

把一个像素网格（Hu×HvH_u \times H_vHu​×Hv​）和离散深度档（DDD 档）做笛卡尔积，每对 (u,v,d)(u, v, d)(u,v,d) 都反投影出一个 3D 采样点——这些点组成一个从相机张出去的锥体，即视锥（frustum）。这是 LSS 论文里 “view frustum” 的几何来源：视锥 = 像素格 × 深度档的 3D 点云骨架。第 5 节会画俯视图：3×3 像素 × 3 档深度 = 27 个采样点，张成一个随深度变宽的楔形。

数量级直觉：一个 0.5 m 的 BEV 格子在 40 m 远处对应约 0.5×800/40=100.5 \times 800 / 40 = 100.5×800/40=10 个像素（像素宽度 =f⋅w/d= f \cdot w / d=f⋅w/d）——近处一格几十上百个像素来抢，远处一格十来个像素填不满。这就是稠密 BEV 需要精细深度估计、而远处特征天然偏稀的几何根源。

7. 工程权衡与失效模式

7.1 权衡速查

  • BEV 分辨率 vs 显存：200×200@0.5 m 与 400×400@0.25 m 的特征显存差 4 倍（下周代码实测 12.2 → 48.8 MiB/层/通道组），端侧常牺牲分辨率换延迟。
  • 感知范围 vs 分辨率：范围 ±50 m 是 nuScenes 标注惯例；量产前向感知常要求 150 m+，做法是"近处细网格 + 远处粗网格"或前向长焦相机单独一条 BEV 分支。
  • 深度离散档数 D：D=41（LSS 默认 4~45 m 步长 1）是精度/显存的折中；D 翻倍，视锥中间量显存线性翻倍。

7.2 典型失效模式

  1. 外参漂移：相机安装角随载荷/温度变化 → BEV 特征整体错位。症状：车道线在 BEV 里弯、检测框贴地不准。修复：在线自标定（Stage 3 第 4 周）。
  2. 深度档没覆盖目标：dbound=[4,45] 时 45 m 外目标落在最后一档之外。症状：远车"贴"在 45 m 处不动。修复：按感知范围重设 dbound，注意显存代价。
  3. 跨相机拼接错位：环视相机重叠区的外参小误差在拼接缝上放大。症状：BEV 里相邻相机边界出现"双影"。修复：重叠区外参联合精调。

8. 延伸思考题（含解析）

Q1：为什么说"BEV 视角转换本质上是深度估计问题"？
A：反投影公式中唯一无观测的量是深度 ddd。无论 LSS 显式预测深度分布，还是 BEVFormer 用注意力隐式决定"看哪里"，网络都要从数据里学出深度先验（地平线、物体尺寸、上下文）。所以纯视觉 BEV 在"深度病态场景"（均匀大平面、低纹理、雨夜）下必然退化——这也是为什么相机+激光的 BEVFusion 有效。

Q2：一个像素对应一条射线，那"两个相机的同一目标"怎么定出唯一 3D 点？
A：两条射线在 3D 中相交（三角测量，Stage 3 双目原理）。BEV 网络并不显式三角测量，但多相机一致性约束隐含在训练里：BEVFormer 的 SCA 让一个 BEV 柱同时从多个相机采样，DeepInteraction/BEVFusion 类方法在特征层融合——几何上是同一件事的软版本。

Q3：LSS 的深度范围为什么从 4 m 开始而不是 0？
A：相机装在车上，0~4 m 的东西几乎贴脸（自车引擎盖、挡风框），对驾驶决策无价值且深度分辨率极差（近处一格像素太多）。裁掉近距省 10% 的 D 档。教训：dbound 要按"相机实际安装位置 + 有效感知范围"设，不是照搬论文。

Q4：如果把 BEV 分辨率从 0.5 m 提到 0.1 m，哪些模块的代价会变、怎么变？
A：BEV 特征图 200×200→1000×1000（25 倍显存与 BEV encoder 算力）；Splat/池化的写入量不变（视锥点数不变）；但每个视锥点命中的格子更小，"一格多点"的池化平均效果变弱，对深度误差更敏感。分辨率提升是全局代价，这正是第 4 周稀疏路线"算力与分辨率解耦"的卖点铺垫。

Q5：为什么 BEV 网格原点选自车（ego-centric）而不是世界坐标系（world-centric）？
A：自车为中心时网格随车平移，感知范围永远"以我为主"，网格尺寸固定、下游算子（检测头、规划代价图）可复用；世界坐标系的网格会随行驶无限扩张且远处区域永远用不到。工程上 ego-centric 网格 + 每帧按位姿对齐（warp）是标准做法——这也是第 3/4 周时序融合必须先做 ego 运动补偿的原因。

1. 稀疏动机：算力该跟着目标走，而不是跟着格子走

前两周的稠密路线有一个共同动作：为整个感知范围建满 BEV 网格。上周 demo 里的账（重列）：0.5 m 分辨率、±51.2 m 范围 → 200×200 = 40000 格；0.25 m → 400×400 ≈ 160000 格。而一帧 nuScenes 场景里的真实目标（车/行人/骑行者）通常只有几十到几百个。第 2 周例 5 也实测过：72 个视锥特征只点亮 100 根 pillar 中的 6 根。

空区域是纯开销：40000 格里占绝大多数的"路面/天空/远方空格"，在 BEV encoder 里消耗和目标格完全一样的算力与显存，最后的检测头再从这片"空海"里把目标挑出来。而且这个开销随分辨率平方增长——想要远距离细分辨率，代价爆炸。

稀疏路线（sparse query-based）的破法一句话：取消 BEV 网格这个中间表示，直接维护一小撮"目标候选"（3D query），让每个候选自己去多相机图像上取证。算力从 O(网格数) 变成 O(query 数 = 潜在目标数)，与网格分辨率、感知范围解耦。代价是失去一张统一的 BEV 图——检测/跟踪任务收益最大，而 BEV 分割、占据栅格（occupancy）这类全空间任务不适用，这是选型的第一分界线。

2. DETR3D：稀疏路线的开山

DETR3D（Wang et al., CoRL 2021, arXiv:2110.06922）把 DETR 的"query 集合预测"从 2D 图像搬进 3D 驾驶场景，三步：

2.1 第一步：3D query + 投影采样

初始化 N 个可学习的 3D object query（N 取数百量级），每个 query 预测一个 3D 参考点 p∈R3p \in \mathbb{R}^3p∈R3（ego 系 xyz），然后用标定矩阵正投影回每个相机：

(un,vn)∝Kn(Rn⋅p+tn),n=1..6(u_n, v_n) \propto K_n \big( R_n \cdot p + t_n \big), \quad n = 1..6 (un​,vn​)∝Kn​(Rn​⋅p+tn​),n=1..6

逐符号：与第 3 周 SCA 的投影公式完全同形——KnK_nKn​ 内参、Rn,tnR_n, t_nRn​,tn​ ego→相机外参。区别在于：BEVFormer 有 40000 根柱都要投，DETR3D 只有 N 个 query 投。投影落在图像范围内的才做双线性采样（bilinear sampling）取特征，视野外直接跳过——上周 demo 例 1 实测：12 个 query 只算 12 次采样，命中与否不影响其余 query 的计算量。

采样到的特征经 layer norm 后与 query 相加，再过 self-attention/FFN 精化框预测——迭代若干层（论文 layer 数 6），每层重新预测参考点、重新采样（query 的位置越猜越准，采样越聚焦）。

2.2 第二步：集合预测与匈牙利匹配（训练核心）

DETR3D 每个 query 输出恰好一个 3D 框，没有 NMS、没有 anchor——"集合预测（set prediction）"的核心承诺是预测集合与真值集合 1-1 对应。训练时怎么知道哪个预测对应哪个真值？匈牙利匹配（Hungarian matching，二分图最优分配）：

σ^=arg⁡min⁡σ∈SM∑i=1NC(yi,  y^σ(i))\hat{\sigma} = \arg\min_{\sigma \in \mathfrak{S}_M} \sum_{i=1}^{N} \mathcal{C}\big(y_i,\; \hat{y}_{\sigma(i)}\big) σ^=argσ∈SM​min​i=1∑N​C(yi​,y^​σ(i)​)

逐符号：SM\mathfrak{S}_MSM​ 是预测与真值的全部 1-1 分配方案集合；C(⋅,⋅)\mathcal{C}(\cdot,\cdot)C(⋅,⋅) 是配对代价，代价越小越该配对——DETR3D 用的是"类别代价 + 框回归代价（L1 距离加权组合）"，本周 demo 例 3 为演示只用了 3D 中心距离；σ^\hat{\sigma}σ^ 是代价总和最小的唯一分配（匈牙利算法多项式时间求解，scipy 一行）。

匹配定了之后总损失：

L=∑匹配对(i,σ(i))[Lcls+Lbox]+∑未匹配 jLcls(∅,y^j)\mathcal{L} = \sum_{\text{匹配对}(i,\sigma(i))} \big[ \mathcal{L}_{\text{cls}} + \mathcal{L}_{\text{box}} \big] + \sum_{\text{未匹配 } j} \mathcal{L}_{\text{cls}}(\varnothing, \hat{y}_j) L=匹配对(i,σ(i))∑​[Lcls​+Lbox​]+未匹配 j∑​Lcls​(∅,y^​j​)

逐符号：匹配对算"分类交叉熵 + 框 L1 回归"；没匹配上的 query 只算"预测’无目标’类"的分类损失——这是对"多余的预测"的全部惩罚。第 5 节 demo 例 3 实测：5 预测 × 4 真值，最优匹配总代价 13.84，预测 #1 没配对 → 只学"这里没东西"。

免 NMS 的原理：NMS 的存在是因为传统检测器对同一目标出多框；集合预测下每个目标至多被一个 query 负责，重复框在训练中就被抑制。代价是收敛慢、对匹配质量敏感——这是 DETR 家族的共同课。

成绩（官方仓库 README 自报，查证）：nuScenes val，ResNet-101 + DCN：34.7% mAP / 42.2% NDS（+CBGS：34.9/43.4）；test 集 VoVNet 骨干：41.2% mAP / 47.9% NDS。对比 BEVFormer（test 56.9 NDS）差 9 个点——开创性方法被后续超越，但 query→投影采样→集合预测的三件套被所有稀疏路线继承。

3. Sparse4D 系列：把稀疏检测推向端到端

Sparse4D（Lin Xuewu 等，旷视 Megvii 团队，官方仓库曾挂在 megvii-research 组织下）三代演进（均查证）：

3.1 v1：4D 关键点（arXiv:2211.10581，2022-11）

标题 Sparse4D: Multi-view 3D Object Detection with Sparse Spatial-Temporal Fusion。核心改进：每个 3D anchor 不只投影一个中心点，而是分配多个 4D 关键点（4D key points）——3D 空间关键点 + 1 维时间（当前帧与前两帧），投影到多相机、多尺度、多时间戳的特征图上采样，再做层级融合。另加实例级深度重加权（instance-level depth reweight）：上周说过单目深度病态，v1 用实例级的深度重标定缓解"3D→2D 投影的病态性"。论文明确宣称该方法对边缘设备部署友好（无稠密视角转换、无全局 attention）。

3.2 v2：循环时序融合（arXiv:2305.14018，2023-05）

标题 Sparse4D v2: Recurrent Temporal Fusion with Sparse Model。把多帧特征采样改成循环（recurrent）形式：当前帧的 anchor/实例带着历史特征递归传播——时序信息"白拿"（近乎零额外算力），长时序融合不再随帧数堆显存。这是稀疏路线时序化的关键一步，与下节 StreamPETR 同期同思路（2023-05 与 2023-03 相隔两个月）。

3.3 v3：端到端检测 + 跟踪（arXiv:2311.11722，2023-11）

标题 Sparse4D v3: Advancing End-to-End 3D Detection and Tracking。两个辅助训练任务 + 一个结构改动：

  1. 时序实例去噪（temporal instance denoising）：训练时把真值框加噪、按运动外推后混进 query，让模型学会"从带噪历史实例恢复目标"——等于把跟踪的身份延续直接教进网络；
  2. 质量估计（quality estimation）：额外预测框的置信质量（类似 TIDE/GIoU 级别的辅助头），为排序与跟踪稳定性提供信号；
  3. 解耦注意力（decoupled attention）：特征与几何用不同的注意力头处理。

成绩（论文摘要自报，查证）：ResNet-50 骨干下比基线 +3.0% mAP / +2.2% NDS / +7.6% AMOTA，达 46.9% mAP / 56.1% NDS / 49.0% AMOTA；最佳模型 nuScenes test 71.9% NDS / 67.7% AMOTA。跟踪不需要额外 tracker——推理时直接给实例赋 ID，端到端。

仓库坑（实测查证）：官方仓库原在 megvii-research/Sparse4D，现已迁移到 HorizonRobotics/Sparse4D（2025-11 实测旧地址 404）；v1/v2 亦有作者仓库 linxuewu/Sparse4D。搜教程引用旧链接会撞 404，收藏 HorizonRobotics 版。

4. StreamPETR：流式 object query 传播

StreamPETR（Wang et al., 2023-03, arXiv:2303.11926，标题 Exploring Object-Centric Temporal Modeling for Efficient Multi-View 3D Object Detection，官方代码 exiawsh/StreamPETR，ICCV 2023）在 PETR 系（PETR, arXiv:2203.05625，3D position embedding 编码进 2D 特征的稀疏检测器）基础上，把时序做成流（stream）：

4.1 object query 流式传播

第 3 周 BEVFormer 的时序是"网格级"：warp 整张 BEV 特征。StreamPETR 的时序是"目标级"：上一帧的 object query 本身（含全部历史特征）直接传给当前帧当输入——

qt=MotionComp(qt−1)  ⊕  新初始化的 queryq^{t} = \text{MotionComp}\big(q^{t-1}\big) \;\oplus\; \text{新初始化的 query} qt=MotionComp(qt−1)⊕新初始化的 query

逐符号：qt−1q^{t-1}qt−1 是上一帧的 top-k 实例 query（带位置与特征）；MotionComp 用 ego 运动 + 目标速度做运动补偿（demo 例 4 实测：上帧位置 (10, -2) + 目标速度 (10, 0)×0.1s − ego 位移 (3.0, 0.1) → 本帧预期 (8.0, -2.1)——目标自己往前开、车也往前开，两个运动都要补偿，剩下的是"预测残差"交给网络细化）；⊕\oplus⊕ 表示与新增 query 拼接成当前帧 query 集合。传播的是特征而非重建——历史任意长，显存恒定（只存一份 query），这是"流式（online/streaming）"的含义。

与 BEVFormer TSA 的分工差异：网格级对齐对静止/慢目标好（warp 即对齐），目标级传播对动目标好（速度直接建模）——运动补偿后的 query 初始位置几乎就落在真值附近，decoder 只需小幅细化，还天然带实例 ID（跟踪免费）。

4.2 Motion-aware Layer Normalization（MLN）

传播的 query 需要"知道自己动了多少"。MLN 的做法：把运动信息（ego 运动与两帧时间差）经过小网络变成仿射调制参数 (γ,β)(\gamma, \beta)(γ,β)，注入 LayerNorm：

MLN(x∣m)=γ(m)⊙x−μσ+β(m)\text{MLN}(x \mid m) = \gamma(m) \odot \frac{x - \mu}{\sigma} + \beta(m) MLN(x∣m)=γ(m)⊙σx−μ​+β(m)

逐符号：xxx 是 query 特征；μ,σ\mu, \sigmaμ,σ 是常规 LayerNorm 的统计量；mmm 是运动条件（位移/时间差向量）；γ(m),β(m)\gamma(m), \beta(m)γ(m),β(m) 是由 mmm 生成的逐通道缩放与偏移（⊙\odot⊙ 为逐元素乘）。直觉：LayerNorm 本来是"无量纲化"，现在让它按运动量有偏地归一化——同一辆车位移 3 m 和静止两种情形，query 特征被规范化到不同的坐标系，网络不必再用特征容量去"记住"运动差。这是把运动先验塞进归一化层的极廉价设计（几个小 FC），论文强调时序收益"以可忽略的额外计算获得"。

成绩（查证：论文摘要 + 官方 README，均为自报）：论文最佳 67.6% NDS / 65.3% AMOTA（nuScenes val，与激光方法可比的首个纯视觉流式方案）；轻量版 45.0% mAP @ 31.7 FPS（RTX 3090，bs=1，6 视图 FP32，README 口径），超 SOLOFusion 2.3 mAP 且快 1.8 倍；README 模型表：R50（428 query，NuImg 预训练，60ep）val 54.6 NDS / 44.9 mAP / 31.7 FPS。

7. 端侧部署视角：稀疏路线为什么对芯片友好

  1. 算子友好：稀疏路线的主力算子 = 投影（矩阵乘/查表）+ 双线性采样（grid_sample）+ 小规模 attention（N~900 个 query 的 self-attention，序列长度极短）——全是 NPU 编译器熟透的标准算子。稠密路线的大张量 scatter（LSS 池化）与 40000-query 大注意力（BEVFormer）在 NPU 上要么算子不支持要么带宽吃亏。
  2. 算力-分辨率解耦：想要 150 m 感知？稀疏路线只是把 query 的参考点撒得更远，计算量不变；稠密路线网格平方爆炸。感知范围需求（如 AEB 远距）对稀疏路线是"免费午餐"。
  3. 算力-目标数解耦：空旷高速上 5 个目标与闹市 200 个目标，稠密路线算力完全相同（都建满网格）——浪费在空旷场景；稀疏路线算力随 query 数增长，忙时多花、闲时少花，天然负载均衡（query 数上限决定最坏延迟，可做硬实时）。
  4. 免 NMS 后处理：集合预测天然 1-1，后处理只剩阈值过滤——后处理是 CPU 瓶颈的常见来源，砍掉即是延迟。
  5. 端到端跟踪：Sparse4D v3 / StreamPETR 的实例 ID 传播让 tracker 退化成一个滤波器（甚至省掉），跟踪-预测-规划链路的延迟进一步缩短。

稀疏的代价也要记：没有统一 BEV 图 → BEV 分割/占据栅格/在线建图类任务不适配（Occupy 系任务稠密 BEV 仍是主流）；query 数上限硬编码了"最坏同时目标数"，极端场景（超密集人群）可能漏检；训练收敛比稠密慢、对匹配与去噪策略敏感。

8. 选型建议与本阶段收束

选型决策树（按任务 × 平台）：

  • 做检测+跟踪、芯片 ≤ 100 TOPS → 稀疏路线（StreamPETR/Sparse4D 系），精度够、延迟稳、算子友好；
  • 做占据栅格/在线建图/BEV 分割 → 稠密 BEV 表示不可绕开（LSS 系 encoder 或 Transformer 系 BEV 特征），考虑用稀疏检测 + 轻量稠密占据的混合架构；
  • 相机+激光多传感器 → BEVFusion（Liu et al., ICRA 2023, arXiv:2205.13542，mit-han-lab/bevfusion）把相机 BEV 特征与激光 BEV 特征统一进一个 BEV 空间再做融合——BEV 表示的价值在多传感器融合场景最大化，这是 Stage 4 后融合知识的"特征级升级版"；
  • 数据闭环/大模型前处理 → 稠密 BEV 提供的统一空间表征便于跨任务复用（检测/地图/占据共享一张图），工程生态（mmdet3d 系）成熟。

学习路线收束：从第 1 周的"一条射线一个自由度"出发，走过三条找回深度的路——撒满概率（LSS）、主动询问（BEVFormer）、只在目标处问（DETR3D/Sparse4D/StreamPETR）。三条路的共同地基是标定矩阵 + ego 运动补偿：前者决定"空间对不对"，后者决定"时间对不对"。这也为 Stage 6（V2X）铺垫了核心问题——当"ego"从单车扩展成"车-路-车多体"，运动补偿的对象从自车位姿扩展成多节点时空对齐，BEV 的统一空间思想正是 V2X 协同感知的公共语言。

9. 延伸思考题（含解析）

Q1：DETR3D 为什么能免 NMS？什么情况下它仍会出"重复框"？
A：集合预测 + 匈牙利匹配保证训练时每个真值至多被一个 query 负责，模型学会相互谦让；推理时无 anchor 无多框堆叠。但若两个 query 收敛到同一目标（训练不充分或目标极大），推理仍可能出近重复框——所以部分工程实现仍保留一个极低阈值的后处理兜底。

Q2：StreamPETR 的 query 传播和 BEVFormer 的 TSA，对"静止目标"和"匀速横穿行人"分别谁更稳？
A：静止目标：TSA 更稳——warp 后格子索引严格对齐，注意力只判断"同一格还是同一物体"，几何先验最强。匀速横穿行人：目标级传播更稳——速度直接进运动补偿，query 初始位置就贴住真值；TSA 的格子对齐假设"目标随世界静止"，横穿目标跨帧偏离对齐位置，时序证据被稀释。这解释了为什么 StreamPETR 的 NDS 提升集中在 mAVE（速度误差）上。

Q3：motion-aware layer normalization 为什么不用"把运动量拼进特征"这种更直白的方式？
A：拼特征可行但扰动大：运动量纲（米）与特征分布（深层抽象）差异大，拼接后网络需要额外容量学习融合；MLN 把运动变成归一化的仿射条件，等于给特征一个"按运动重标定的坐标系"，不增加序列长度、不扰动主干、参数开销是几个 FC——与 FiLM 类条件归一化同族思想。

Q4：端侧芯片 30 TOPS、内存 8 GB，任务只有 3D 检测+跟踪，你选哪条路线？给三条理由。
A：选稀疏（StreamPETR/Sparse4D 系轻量版）。理由：① 算子全是 NPU 标准件，无大张量 scatter；② 延迟随目标数可预算，硬实时可控（query 上限封顶）；③ 免 NMS + 免 tracker，后处理 CPU 开销小。参考点：StreamPETR R50 轻量版在 RTX 3090 上 31.7 FPS（FP32），30 TOPS 量级 NPU 上同骨架做 INT8 有量产先例。

1. 第一性原理：为什么感知需要 V2X

1.1 单车感知的物理极限：遮挡是测不出来的

前五个 Stage 解决的是"把传感器看到的东西看得更准"——更好的检测（Stage 2）、更准的标定（Stage 3）、更稳的融合（Stage 4）、更全的视角（Stage 5 BEV）。但有一条极限线它们永远跨不过去：光沿直线传播，传感器只能看见视线上没有东西挡住的地方。

经典场景是十字路口的"鬼探头"：

  • 摄像头：被货车挡住，什么都拍不到；
  • 激光雷达：光束同样被挡，点云里那片区域是空的；
  • 毫米波雷达：绕射能力稍强，但对行人（低 RCS、无径向速度分量时）本就吃力。

等行人进入视线的瞬间，30 km/h 的车只剩不到 1 秒反应时间。这不是算法问题，是信息在物理上不存在于这辆车的任何传感器里。解决办法只有一个：从"换一个视角的传感器"那里拿到这份信息——它可能是路侧杆件上的摄像头（比车高、看得见货车后面），可能是对向车，也可能就是行人自己手里的设备。把它们连起来，就是 V2X。

1.2 V2X 是什么：一个总称，四种形态

V2X（Vehicle-to-Everything，车联网/车联万物）是四种通信形态的总称：

形态 全称 典型内容 时延敏感度
V2V Vehicle-to-Vehicle（车-车） 位置/速度/航向广播（BSM 类）、协同感知数据 极高（碰撞预警 ~10 ms 量级）
V2I Vehicle-to-Infrastructure（车-路侧） 路侧感知目标（RSM 类）、信号灯配时（SPAT） 高
V2P Vehicle-to-Pedestrian（车-弱势道路使用者） 行人/骑行者手机或可穿戴设备的位置 极高
V2N Vehicle-to-Network（车-云/网络） 高精地图更新、全局调度、非实时信息 中（百 ms~秒级）

本系列关心的是前三者——它们传输的内容直接参与感知。V2N 走蜂窝上行/下行，本质上和手机上网没有区别，时延与可靠性都撑不起安全类应用，只做"非安全类的大管道"。安全类应用的关键设计约束是：不依赖基站也能工作（见第 4 节的广播特性）。

1.3 感知视角下 V2X 的三句话定位

给后面三周定调，V2X 对感知系统只做了三件事：

  1. 补盲：把"你看不见但我看得见"的目标送过来（第 3 周协同融合的核心收益）；
  2. 校验：同一目标双方都看见了，两份观测融合比一份准（Stage 4 的加权融合在这里复用）；
  3. 预告：把还没进入感知范围的目标提前送过来（超视距，beyond line of sight）。

反过来，感知系统对 V2X 的要求也只有三条：够快（时延预算，第 5 节）、够标准（消息集，第 2 周）、对得上（坐标与时间对齐，第 3 周）。整个 Stage 6 就是围绕这三条展开。

2. 技术路线之争：DSRC vs C-V2X

V2X 的物理层有两条技术路线，打了近十年的"标准战争"。理解这场战争的关键，不是背参数，而是看清两种"出身"带来的设计取舍。

2.1 DSRC：Wi-Fi 家族的直连方案

DSRC（Dedicated Short Range Communications，专用短程通信）的物理层标准是 IEEE 802.11p-2010——对 IEEE 802.11（Wi-Fi）的修正案，名为 WAVE（Wireless Access in Vehicular Environments），2010 年发布，后来并入 IEEE 802.11-2012 基础标准。

它把 Wi-Fi 搬进车里的三个关键改造：

改造 原因
信道带宽 20 MHz → 10 MHz 5.9 GHz 频段总共只有几十 MHz，切出更多正交通道
保护间隔（guard interval）加倍 对抗高速运动带来的多普勒与快速信道变化
免除关联（association）流程 Wi-Fi 连 AP 要先"握手"，车间相遇只有几秒，没时间握手

优点：纯直连、无基础设施也能跑、技术成熟早（美国 2004 年起 FCC 就划了 5.9 GHz 的 75 MHz 给 DSRC）。缺点：Wi-Fi 的 CSMA/CA 机制在车辆密度高时性能退化明显（大家抢同一信道），且没有蜂窝网络的持续演进路线护航。

2.2 C-V2X：蜂窝家族的直连方案

C-V2X（Cellular V2X，蜂窝车联网）由 3GPP 标准化，分两步走：

  • Release 14（LTE-V2X）：2017 年冻结。核心创新是 PC5 直连接口（sidelink，边链路）——车与车、车与路侧不经过基站直接通信，其中的 Mode 4 允许终端自主选资源（基站不在场也能工作）。这一步是"蜂窝技术学会直连"的关键，直接回应了 DSRC 的核心卖点。
  • Release 16（NR-V2X / 5G V2X）：2020 年功能冻结。补充 5G NR 的 PC5 直连（Mode 2 自主资源选择），面向更高级的协同驾驶场景（如编队、协同变道），一句话概括其增强：更低的时延、更高的可靠性与吞吐，为传感器级/特征级数据共享留出空间（本系列第 3 周讲的特征级协同理论上受益于此）。

C-V2X 的优点：物理层基于蜂窝技术，有完整的产业链与演进路线；资源调度机制（半持续调度）在高密度场景下比"纯抢信道"更稳。缺点：起步晚、初期产业链不如 Wi-Fi 成熟。

2.3 频谱：中国的选择

中国的时间线很清晰：

  • 2018 年 10 月，工信部印发《车联网（智能网联汽车）直连通信使用5905-5925MHz频段管理规定（暂行）》（工信部无〔2018〕232号），将 5905-5925 MHz 共 20 MHz 频率规划用于基于 LTE-V2X 技术的直连通信，与国际主流频段保持一致；车载/便携设备参照公众移动通信终端管理，无需频率使用许可和无线电台执照，但须取得型号核准（SRRC）。信道带宽可选 10 MHz（5905-5915）或 20 MHz（5905-5925）。
  • 5.9 GHz 附近用于 ITS（Intelligent Transportation Systems，智能交通系统）也是 ITU 层面的国际共识方向（WRC-19 为 ITS 划定全球协调的频段安排），中国 5905-5925 的选择与国际主流一致，这也是国产车载 C-V2X 模组能兼顾国内外市场的原因之一。

产业结果：美国一度在 DSRC 与 C-V2X 之间摇摆（FCC 2020 年后实际上把 5.9 GHz 上部频段重新分配、转向 C-V2X），欧洲走 ITS-G5（与 802.11p 同物理层）并同步演进 C-V2X；中国是全球最坚定的 C-V2X 阵营，量产车型搭载 C-V2X 模组已成主流配置。对路侧感知工程师的直接含义：你调测的 RSU（Roadside Unit，路侧单元）在国内默认跑 LTE-V2X PC5，工作在 5905-5925 MHz。

2.4 时延/范围量级对照

给感知工程师一个"够用就行"的量级表（同一场景下两类技术实测都会受密度/信道/功率影响，只看量级）：

维度 DSRC（802.11p） LTE-V2X（PC5）
典型时延（直连单跳） 数 ms~数十 ms ~20 ms 量级
典型通信范围 数百 m（可达 ~1 km 视距） 数百 m 量级（直连）
基础设施依赖 无 Mode 4 下无（基站可辅助）
高密度表现 CSMA 退化明显 半持续调度相对稳
演进路线 并入 802.11 后基本止步 Rel-14 → Rel-16 NR-V2X 持续演进

对范围数字要多一分警惕：厂商标称的"数百米"是**视距（LOS）**条件；路口场景里建筑、公交车身都会造成非视距（NLOS）衰减，实际可用范围往往对折——这也是为什么"路口要装 RSU"而不是"靠路边一辆车中继"：固定、高位、供电稳定的 RSU 才能保证盲区覆盖的确定性。

动手验证：不用真设备也能感受量级——第 5 节的脚本把"空口 ~20 ms + 感知/处理 ~80 ms"合成为端到端 100 ms 预算，然后换算成空间位移。

3. 通信栈速览：感知工程师要关心哪几层

不必学完整套通信协议栈，但要知道自己的代码住在哪一层。以中国 C-V2X 为例，从下往上：

层 干什么 与本系列的关系
接入层（PC5 物理层/MAC） 10 MHz/20 MHz 信道、资源选择、调制 决定"时延 20 ms、范围数百 m"这些物理常数；感知工程师当黑盒
网络层/传输层 地理寻址、广播路由 感知工程师当黑盒
消息层（应用层） J2735 / T/CSAE 53 消息定义、ASN.1 编码 第 2 周的主战场——感知输出的对外接口
应用层（感知融合） 感知栈 + 协同融合 Stage 1-5 + 本系列第 3 周的全部产出

一个实用的判断法则：调不通系统时，先确认故障在哪一层——消息层问题用抓包与字段解析定位，感知层问题用 Stage 4 的指标定位，接入层问题看时延/丢包统计。第 2 周的 msgCnt 丢包统计与第 3 周的消息年龄（age）分布，就是连接"通信黑盒"与"感知白盒"的两根探针。

3.1 广播特性：V2X 安全消息是"喊给所有人听"

手机通信是"点对点"：你发微信给一个人。V2X 安全消息是广播（broadcast）：车以固定频率（典型 10 Hz）把"我在哪、多快、朝哪"喊给周围所有节点，谁在射频范围内谁就收到，发端根本不知道（也不需要知道）有谁在听。

这个特性带来三个对感知系统至关重要的推论：

  1. 无基础设施也能 V2V 直连。两辆车在无人区相遇，PC5/802.11p 直连照常工作——这是 V2N 永远做不到的，也是"安全消息"必须走直连的根本原因。
  2. 同一目标的 TrackID 必须跨端可解释。广播是无连接的，接收方连续收到同一 id 的消息才能拼出"这辆车在连续运动"。这正是本库《后融合.md》笔记里"融合后目标 ID 漂移，影响下游跟踪和 V2X 通信"的通信侧含义：ID 漂移会让接收方把同一辆车当成两辆、把两辆车当成一辆。第 2 周展开。
  3. 信道是共享的稀缺资源。大家都在 10 Hz 喊，车一多信道就挤——所以消息必须小（第 2 周的定点量化就是为省字节）、必须分级（不是所有目标都值得广播，ETSI 的 CPM 甚至规定了"生成规则"来抑制冗余）。

3.2 把 1.1 节的鬼探头算出来

第 1.1 节说"等行人进入视线的瞬间只剩不到 1 秒"，把这笔账算清楚（城市路口，ego 30 km/h ≈ 8.33 m/s）：

  • 行人从货车车头边缘出现时，距 ego 横向冲突点约 15 m（典型路口布置）；
  • ego 到冲突点的时间 = 15 m ÷ 8.33 m/s ≈ 1.8 s；
  • ego 自身制动到安全的反应+制动距离对应约 1.0~1.5 s——留给决策的余量不足 0.5 s；
  • 若路侧提前 500 ms 送来行人位置（RSU 视角无遮挡），等效把决策窗口从 0.5 s 扩到 1.0 s——这就是"补盲"的物理价值，也是 V2P/协同感知安全案例的标准论证写法。

4. 时延预算：通信时延怎么变成感知误差

4.1 端到端时延预算

3GPP TS 22.185（Rel-14，V2X 业务需求）对 V2I 类业务给出的要求是：UE 与 RSU 之间消息传输的最大时延 100 ms（并按不同场景给出 90% 可靠性等指标）。注意这是通信段的上限量级；对感知而言，端到端链路是三段串联：

T端到端=T感知+T处理+T通信T_{\text{端到端}} = T_{\text{感知}} + T_{\text{处理}} + T_{\text{通信}} T端到端​=T感知​+T处理​+T通信​

这个公式在干什么：目标从"真实世界发生"到"另一端可用"要经过三道关卡。逐符号拆解：

符号 物理含义 典型量级
T感知T_{\text{感知}}T感知​ 传感器曝光/积分 + 帧同步 20~50 ms（帧率倒数的一半左右）
T处理T_{\text{处理}}T处理​ 检测+跟踪+融合（Stage 2/4 的全流程） 30~100 ms（取决于算力）
T通信T_{\text{通信}}T通信​ 编码 + 空口排队 + 传输 + 解码 ~20 ms（PC5 直连量级）到 100 ms

三段串联意味着每一段都必须把别的段算进去：通信段预算 100 ms，不等于系统可以慢慢处理 200 ms。

4.2 时延 = 空间错位：v·Δt 公式

时延对感知的伤害最终要落到米上：

d=v⋅Δtd = v \cdot \Delta t d=v⋅Δt

这个公式在干什么：消息在路上的 Δt\Delta tΔt 秒里，目标自己也在动。逐符号拆解：

符号 物理含义 例子
vvv 目标速度（m/s） 120 km/h = 33.33 m/s
Δt\Delta tΔt 消息从产生到被使用的总时延（s） 100 ms
ddd 消息里"报的位置"与"目标真实位置"的偏移（m） 3.33 m

结果拿来做什么：3.33 m 意味着什么？一条车道宽 3.5 m——不补偿时延，收到的位置能把邻车道车报成本车道车，足以让任何下游决策（变道、制动）出错。所以协同感知消息必须携带时间戳与速度字段，接收方用 p(tnow)=pmsg+v (tnow−tmsg)p(t_{\text{now}}) = p_{\text{msg}} + v\,(t_{\text{now}} - t_{\text{msg}})p(tnow​)=pmsg​+v(tnow​−tmsg​) 把旧位置外推到当前时刻——这是第 2、3 周的核心公式，本周先把 vΔtv\Delta tvΔt 的数量级算进肌肉记忆。

5. 本周小结

  • V2X 的必要性来自物理遮挡：信息不在你的传感器里，就只能从别的视角拿——四种形态（V2V/V2I/V2P/V2N）中前三者直接服务感知。
  • 技术路线：DSRC（IEEE 802.11p-2010，Wi-Fi 系直连）vs C-V2X（3GPP Rel-14 LTE-V2X PC5 / Rel-16 NR-V2X）；中国把 5905-5925 MHz 规划给 LTE-V2X 直连（工信部无〔2018〕232号），量产生态已倒向 C-V2X。
  • 安全消息是 10 Hz 无连接广播，无基础设施也能 V2V 直连；代价是信道共享与 TrackID 跨端一致性问题。
  • 时延预算三段串联（感知+处理+通信 ≈ 100 ms 量级，3GPP TS 22.185 口径），时延即空间错位 d=vΔtd = v\Delta td=vΔt：120 km/h × 100 ms = 3.33 m——消息必须带时间戳与速度，第 3 周用补偿公式把它修掉。
  • 通信栈分层定位：接入层当黑盒记物理常数，消息层是感知的对外 API（第 2 周），应用层是 Stage 1-5 的全部家当——故障先分层，再动手。

6. 工程权衡与失效模式

  1. 迷信"有 5G 就不需要直连"：V2N 走公网时延百 ms 级且不可控，安全消息必须走 PC5 直连。症状：路侧消息时延抖动到数百 ms；修复：确认 RSU 走 PC5 广播，V2N 只承载非安全类数据。
  2. 时延预算没给处理段留位置：把 100 ms 全当通信预算用，感知+处理超支。症状：消息准时到达但内容已过时 200 ms；修复：按第 4.1 节的三段分解逐段记账。
  3. 假设"广播了就收到了"：无线信道有丢包与干扰（第 4 周仿真里放了 5% 丢包）。症状：协同目标时有时无、轨迹闪断；修复：接收端用 KF 预测撑住丢包间隙（Stage 4 的"漏检几帧椭圆变大但轨迹不丢"），发端控制消息冗余。
  4. 忽视 ID 一致性：本地融合器的 TrackID 每帧漂移，广播出去后对端无法关联。症状：邻车把你的轨迹当成一堆新目标；修复：轨迹管理加确认/保持机制（Stage 4 第 4 周），广播使用稳定 ID。

7. 延伸思考题（含解析）

Q1：为什么 V2V 安全消息必须是广播，而不是"只发给周围相关车辆"的点对点？
A：判断"谁相关"本身需要知道所有人的位置——这个判断的输入正是广播消息本身，逻辑上无法先于广播存在。且无连接广播不需要建链握手，车速 30 m/s 时两车共处通信范围可能只有几十秒，任何建链开销都是浪费。代价是信道共享与冗余接收，用小消息（第 2 周）和生成规则来控制。

Q2：DSRC 输了还是 C-V2X 输了？一句话答。
A：分市场：中国明确 C-V2X（5905-5925 MHz 给 LTE-V2X）；欧洲 ITS-G5（802.11p 系）仍在服役但同步演进 C-V2X；美国实际转向 C-V2X。技术上的分水岭是 Rel-14 的 PC5 Mode 4——蜂窝阵营补上了"无基础设施直连"这块短板后，DSRC 失去了独有卖点。

Q3：120 km/h 下 100 ms = 3.33 m，那把通信时延压到 10 ms 是不是就解决问题了？
A：没有。端到端是三段串联（公式 4.1），通信只占 ~20 ms，感知曝光 + 处理才是大头；且即使时延为零，消息编码时刻到使用时刻之间仍可能有队列等待。正确做法不是无限压时延，而是带上时间戳和速度做外推补偿（第 3 周公式），把"时延"从"误差源"变成"可计算的修正量"。

Q4：路侧 RSU 挂在灯杆上，它算 V2I 里的 I，那它和基站的区别是什么？
A：RSU 是 ITS 专用的路侧通信+计算单元，跑 PC5 广播（发 RSM/SPAT/MAP 等），通常无蜂窝回传或仅有普通宽带回传；基站是运营商网络设备，管蜂窝连接。很多商用 RSU 是"通信模组 + 边缘计算（跑本系列的感知栈）"一体机——你的 Stage 1-5 产出未来就部署在这种盒子里。

Q5：两台 RSU 覆盖同一个路口会不会"互相干扰"？为什么业界还要冗余部署？
A：同频同时隙广播会互相占用信道资源，这是真实存在的工程约束（所以部署规划要做信道/资源分配）。但冗余的价值大于代价：路口是多方向的，单台 RSU 对某些来向天然是非视距；两台高位 RSU 的感知覆盖互补，且互为备份。这与第 3 周的结论同构——多个视角的观测融合，永远好于单视角；通信侧的"干扰"用资源规划管理，感知侧的"盲区"用冗余消灭。

2. 打开 J2735：BSM Part I 逐字段解读

BSM（Basic Safety Message，基本安全消息）是 J2735 中最核心的消息：车辆以 10 Hz 广播自己的状态。Part I（coreData）是必选的核心字段：

字段 含义 分辨率/范围 为什么是它
msgCnt 消息计数器 0~127 循环 接收端据此识别"丢了几条/是否乱序"
id 临时车辆 ID 4 字节（随机分配，非车牌） 跨消息关联同一辆车；随机性防跟踪隐私攻击
secMark 分钟内毫秒标记 0~60999 ms 与 msgCnt 一起确定消息的精确时刻
lat, lon 纬度/经度 0.1 微度（1e-7 度） 绝对位置；1e-7 度 ≈ 1.1 cm，够用
elev, accuracy 高程与定位精度 — 告诉接收方"我的 GPS 多可信"
speed 标量速度 0.02 m/s 步长 时延外推补偿的速度来源
heading 航向 0.0125° 步长 区分方向（速度是标量，没方向）
angle 方向盘转角 1.5° 步长 预判转向

2.1 为什么到处都是"定点数"而不是浮点

J2735 用定点量化（fixed-point encoding）：真实值 = 存储整数 × 分辨率。speed = 565 表示 11.30 m/s。三个理由：

  1. 省字节：speed 范围 0~163.83 m/s，用 0.02 m/s 步长只需 13 bit；float32 要 32 bit。10 Hz 广播 × 道路上每辆车，每个字节都是信道负载（上周第 3 节：信道是共享稀缺资源）。
  2. 误差有界且可解析：定点数的量化误差上界就是半个步长——speed 最大 ±0.01 m/s，heading 最大 ±0.00625°，lat/lon 最大 ±0.05 微度 ≈ ±5.5 mm。接收方精确知道消息里每个数坏了多少。
  3. 无符号解释歧义：浮点跨平台/跨语言解析没有字节序陷阱（ASN.1 编码下尤其如此）。

选择分辨率的逻辑是统一的：分辨率 ≈ 传感器噪声的一半到四分之一——量化误差要小于测量误差才有意义，也没必要细到噪声以下（纯属浪费比特）。0.02 m/s 的速度分辨率对应 GNSS 测速的典型精度量级；0.1 微度位置分辨率（≈1.1 cm）低于车道级定位需求一个数量级，留足了余量。

2.2 中国侧：RSM 才是路侧感知的出口

T/CSAE 53 沿用了 J2735 的风格并做了本土化（坐标系、枚举值等），其中与路侧感知直接相关的是 RSM（Roadside Safety Message，路侧安全消息）：RSU 把自己感知到的目标（车辆/行人/非机动车，含位置、速度、航向、尺寸、TrackID 等）广播出去——字段风格与 BSM 的 coreData 高度同构。RSM 与 RSI（路侧信息，如限速、事故提示等交通事件）、SPAT（信号灯相位与配时）、MAP（路口地图）共同构成中国 V2X 第一阶段的消息家族。工程对应：路侧感知栈的输出适配层，就是"TrackID/类别/位置/速度/尺寸/置信度 → RSM 字段"的映射器；而车端收到 RSM 后的适配层，则是第 3 周的协同融合入口。

欧洲的 CPM（ETSI TR 103 562 分析、后续 TS 103 324 规范化）走的同一条路但更系统：它规定了"哪些目标值得广播、多久广播一次"的生成规则（management container / perception container / per-object container 的分层结构），本质是上周"信道稀缺"问题的标准化解法。

RSI Road Side Information（路侧信息） 交通事件（事故、施工、逆行、异常行人）、标志标牌 事件驱动 + 低频
RSM Roadside Safety Message（路侧安全消息） 路侧感知到的动态目标列表 10 Hz

SPAT + MAP 是一对搭档：MAP 告诉你"这个路口有几条车道、怎么连接"，SPAT 告诉你"哪条车道现在是绿灯还有几秒"——两者合成"绿波引导/红灯预警"类应用。对感知系统的隐含要求：RSM 里的目标要能关联到 MAP 的车道编号（“在进口道 3 上逆行的那辆车”），这需要感知输出带上车道级语义——Stage 2 的语义分割与 BEV（Stage 5）在这里再次兑现价值。

2.4 编码与字节：ASN.1 一句话

J2735 与 T/CSAE 53 的消息都用 ASN.1（Abstract Syntax Notation One）语言编写字段定义，线上传输用 UPER（非对齐紧凑编码）打包。你不需要会写 ASN.1，只需要知道三件事：① 字段定义是标准原文可查的（不用猜）；② 编码是紧凑二进制（教学版脚本用 Python 字典模拟的是"语义层"，真实系统编码后更小）；③ 存在成熟的开源 ASN.1 编译器（如 asn1c）能把标准文件直接编译成 C/Python 编解码代码——工程上手写字段解析是大忌，以标准原文为唯一事实源。

4. 时戳与同步：呼应 Stage 1 的时间对齐

上节的 roundtrip 能精确补偿时延，隐含了一个前提：发端和收端的时钟在同一根时间轴上。回顾 Stage 1/3 讲过的传感器时间同步问题，V2X 场景把它放大到了"设备与设备"之间：

  • 路侧感知栈的时戳来自路侧时钟（GPS 授时，PPS/PTP 同步到 UTC），车端时钟同样来自 GNSS——两端共享同一绝对时基，secMark 才有意义。
  • 若某端时钟漂了 50 ms，上节的补偿公式就会系统性多补/少补 50 ms × 11.3 m/s ≈ 0.57 m——时戳错误不是"消息没用了"，而是更隐蔽的"消息很自信地错了"。
  • 工程检查项（真实联调每周都做）：① 校验 secMark 与本地到达时刻的差是否稳定（漂移的时钟表现为该差值持续增长）；② 用 msgCnt 的连续性算丢包率（10 Hz 广播下，每秒计数应 +10，缺多少补多少）。

这正是广播与单播的哲学差异：单播靠重传与确认保证到达，广播默认会丢、把兜底责任交给接收端的运动模型——Stage 4 那句"漏检几帧椭圆会变大但轨迹不丢"，在 V2X 场景下从性质变成了日常。第 4 周仿真里 5% 丢包被 KF 无声吸收，就是这个设计的实验证明。

5. 本周小结

  • 消息集标准解决"陌生节点互译"问题：SAE J2735（BSM 说"我自己在哪"）+ T/CSAE 53-2020（RSM 说"我看见的东西在哪"——路侧感知的官方出口）+ ETSI CPM（欧洲协同感知消息，含生成规则）。
  • BSM Part I 核心七字段：msgCnt（0~127 循环）、id（4 字节临时 ID）、secMark（分钟内毫秒）、lat/lon（0.1 微度）、speed（0.02 m/s）、heading（0.0125°）、size（cm）；全部定点量化——省带宽、误差有界、无解释歧义。
  • roundtrip 实测：位置编码误差 ≤0.55 cm（解析上界内）、速度 ≤±0.01 m/s——消息集不背感知误差的锅，排查时先跑 roundtrip 排除编码层。
  • secMark + speed + heading 三字段合力把 100 ms 时延的 1.13 m 错位修到 5 mm——时间戳不是元数据，是补偿公式的输入。
  • 时钟同步是隐含前提：50 ms 时钟差 × 11.3 m/s = 0.57 m 系统性偏差，用"消息年龄漂移监控 + msgCnt 丢包统计"两根探针盯住。

6. 工程权衡与失效模式

  1. 编码超范围（overflow）：真实值超出定点范围（如 speed > 163.83 m/s 不可能，但 heading 在 359.99° 边界、lat/lon 在范围边界）会被截断成完全错的值。症状：某个方向的个别目标位置突变到地球另一侧；修复：编码前 clamp + 测试用例覆盖边界值。
  2. 坐标系没写进消息：RSM 有参考点定义，但自研私有消息常常"忘了说原点在哪"。症状：两端各自能跑，联调时目标整体平移/旋转了固定量；修复：消息里显式携带参考坐标系定义或双方约定配置版本号。
  3. conf（置信度）语义不统一：0.94 是 softmax 概率还是校准后的概率？车端如果直接拿它当概率用会翻车。症状：车端融合权重异常；修复：接口文档明确定义并做校准（Stage 2 讲过概率校准）。
  4. TrackID 漂移的直接损失：本地融合器 ID 不稳定（Stage 4 的 ID switch），广播后对端把同一辆车关联成新目标，重复计入碰撞风险。症状：对端目标数量虚高、轨迹抖动；修复：确认态轨迹才广播 + ID 保持策略（min_hits/确认机制），呼应《后融合.md》笔记。
  5. 拿 secMark 当绝对时间戳用：secMark 只在分钟内单调，跨分钟必须配合本地分钟计数。症状：每小时出现一次 59.999→0.000 的"时间倒流"误判；修复：用 msgCnt 连续性做跨分钟消歧。
  6. 频率错配：感知跑 25 Hz 相机、融合器 10 Hz、消息 10 Hz，若未对齐帧率，同一目标的消息时间戳抖动 ±50 ms，下游补偿跟着抖。症状：速度估计的 zigzag、融合残差异常；修复：接口层显式声明频率并做最近邻/插值时间对齐（Stage 1 异步时延问题的通信版）。

7. 延伸思考题（含解析）

Q1：BSM 的 id 是 4 字节随机临时 ID 且会定期更换，为什么不用车牌号/VIN？
A：隐私。安全应用只需要"这几条消息是不是同一辆车"，不需要知道它是谁。固定 ID 会让路侧设备能长期追踪任何人——欧盟 GDPR 与各国隐私法都不允许。定期换 ID（pseudonym）进一步限制追踪窗口。代价是 ID 换新瞬间对端要做轨迹接力（又回到 TrackID 一致性）。

Q2：0.1 微度的经度分辨率，在赤道和在北京（40°N）对应的米数一样吗？
A：不一样。0.1 微度纬度恒为 1.11 cm；经度 1 度对应 111.32 km × cos(纬度)，北京 40°N 时 0.1 微度经度 ≈ 1.11 cm × cos40° ≈ 0.85 cm。所以同样的定点格式，经向误差略小——w2 脚本里 M_PER_DEG_LON 乘 cos(LAT0) 就是在做这个换算。

Q3：路侧感知有 3D 尺寸（长宽高）和朝向（yaw），RSM/BSM 风格消息里只有长宽，朝向信息怎么传？
A：J2735 coreData 只有 width/length（Part I 尽量小）；3D 属性属于扩展部分（Part II 或 CPM 的 per-object container，含 height、yaw、参考点）。教学版脚本只传 L/W 是有意简化——真实工程里目标级消息的字段完整度是"带宽 vs 信息量"权衡的直接体现，CPM 为此设计了一整套可选字段。

Q4：为什么说"消息集不背感知误差的锅"？编码误差和感知误差怎么区分？
A：编码误差有解析上界（半个步长，本例 ≤0.55 cm），感知误差是传感器/算法噪声（分米~米级），两者差两个数量级以上。排查位置误差时先用解析上界排除编码（跑一遍 roundtrip 断言），剩下的全部归因于感知链路——这就是"每层误差可分离"的工程意义。

Q5：路侧感知在隧道/高架下 GNSS 拒止，消息还能用吗？
A：绝对坐标（lat/lon）会漂，但消息结构照样有效——工程对策是把"位置参考点"换掉：RSU 部署时预先标定自己在已知地图坐标系的精确位置（一次性，Stage 3 的标定思想），感知输出走"参考点 + 相对坐标"，GNSS 只需兜住路侧一台设备而不是每个目标。车端同理可以走车道级相对定位。原则：时间同步可以靠共享时基，空间同步要靠"一个精心标定的锚点"而不是"每帧都准的绝对定位"。

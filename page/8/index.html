1. 第一性原理：端侧选型 = 四维预算的联合优化

云端选型只看"精度-成本"，端侧要同时盯四个预算：速度（延迟/吞吐）、内存、功耗、热量。四者互相咬合：

提速→加压提频功耗↑→积热降频→速度回落\text{提速} \xrightarrow{\text{加压提频}} \text{功耗} \uparrow \xrightarrow{\text{积热}} \text{降频} \xrightarrow{} \text{速度回落} 提速加压提频​功耗↑积热​降频​速度回落

这个闭环意味着：端侧的峰值性能没有意义，可持续性能才是指标。一块被动散热的板子，前 30 秒的 tokens/s 和第 5 分钟的可能是两个数字——本报告必须测"持续值"。

3. 工程权衡与失效模式

3.1 权衡

  • 峰值 vs 持续：端侧永远按持续值选型；峰值只在"突发短请求"场景（如唤醒词检测）有意义。
  • 灵活 vs 高效：NPU 快但封闭、CPU 慢但全能——工程上常见"双形态"：正常走 NPU，特殊请求回退 CPU。
  • 报告的可复现性：温度、后台进程、内存压力都会污染数字——每行数据注明环境（室温、锁频状态、后台负载），否则报告三个月后不可信。

3.2 失效模式

  1. 用峰值速度拍板：症状——产品上市后"越用越卡"；根因——热降频，峰值不可持续；修复——持续压测 10 分钟 + 降频悬崖记录（§2.2 表三）。
  2. 内存预算漏算：症状——板端跑大模型 OOM；根因——只算权重，忘了 KV cache + 系统 + 图形栈；修复——预算表四件套：权重 + KV + 运行时 + 系统预留。
  3. 跨平台比 W 不比 mJ/token：症状——得出"慢的平台更省电"的错误结论；根因——功率没归一化到每 token；修复——统一用 mJ/token（§1.3）。
  4. 实验室温度失真：症状——冬天测的数据夏天翻车；根因——被动散热对环境温度极敏感；修复——按产品实际工作温度区间复测（至少 25℃ 与 35℃ 两档）。

4. 延伸思考题（含解析）

Q1：为什么端侧要发明 “mJ/token” 这个指标？
A：端侧的真实约束是电池/散热预算（总能量），不是瞬时功率。快但费电与慢但省电，只有在"每个 token 花多少能量"上才可比。mJ/token = 功率 ÷ tokens/s，是速度与功耗的联合归一——选型报告用它一眼看穿"虚假的省电"。

Q2：降频悬崖出现后，是继续硬扛还是主动降档？
A：主动降档。悬崖后系统会自动在"过热-降频-恢复"间震荡，速度抖动且不可预测；锁定在一个可持续的频率档，换来平稳的 tokens/s——端侧体验要的是稳定而非峰值。这就是 §2.3 决策树里"锁频找收益递减点"的原因。

Q3：同一 1.5B 模型，为什么四平台首 token 延迟的排序可能和 tokens/s 不同？
A：首 token（prefill）吃算力，decode 吃带宽——两个阶段瓶颈不同。NPU 算力相对强、带宽相对弱时，可能"首字快、续写慢"。所以两个指标必须分开测、分开选型，只报一个必然踩坑。

Q4：语音结课项目为什么建议"混合形态"而不是单押一条路线？
A：语音助手是多组件系统：VAD/降噪是固定小模型（NPU 最优）、LLM 对话是变长复杂逻辑（CPU 灵活）、唤醒在极低功耗档。每个组件的最优路线不同——系统级选型天然是异构的，这恰好是本方向四平台的完整用武之地。

Q5：“端侧跑 7B 现实吗？”——用本报告的框架回答。
A：按四预算回答：内存（7B Q4 ≈ 4GB + KV，16GB 板勉强）、速度（decode 带宽账：板级 ~30 GB/s → 个位数 tokens/s）、功耗/热（满速不可持续）。结论：技术上能跑，产品上不现实——端侧应选 1.5-3B + 云端级联（复杂请求上云），这正是 Stage 8 端云一体架构的端侧依据。

1. 第一性原理：KV cache 为什么是显存第一杀手

1.1 KV cache 的由来

自回归解码时，每生成一个新 token，注意力都要看所有历史 token。若每步都重算历史，复杂度是 O(U2)O(U^2)O(U2)。KV cache 把已算过的 key/value 存下来，增量计算，把每步降到 O(1)O(1)O(1)——用显存换计算。

问题：KV cache 随序列长度线性增长，且在请求结束前不能释放。长上下文时代，它比模型权重还吃显存。

1.2 手算 KV cache（本周自测题，必须闭卷）

对单个请求、序列长度 LLL，KV cache 大小：

KV bytes=2×nlayers×nkv_heads×dhead×L×bytes_per_elem\text{KV bytes} = 2 \times n_{\text{layers}} \times n_{\text{kv\_heads}} \times d_{\text{head}} \times L \times \text{bytes\_per\_elem} KV bytes=2×nlayers​×nkv_heads​×dhead​×L×bytes_per_elem

深入拆解：这个公式在干什么

这个公式回答一个问题："每多存一个 token 的历史，我要在显存里多花多少字节？"它是后面一切并发/上下文容量估算的地基。

  • 为什么需要它：规划并发与上下文长度时，你必须先知道 KV 的"单价"（每 token 多少字节），才能算出给定显存能同时养多少请求（交付物②就靠它）；
  • 系数 2：注意力里 K 和 V 是两组独立的张量，各存一份；
  • nlayersn_{\text{layers}}nlayers​：每一层都有独立的注意力、都要存自己的 K/V，层数越多 KV 越大；
  • nkv_heads×dheadn_{\text{kv\_heads}} \times d_{\text{head}}nkv_heads​×dhead​：K/V 每层的"宽度"。GQA（Grouped Query Attention）下 KV 头数远小于 Q 头数——多个 Q 头共享一组 KV 头，这正是省显存的关键（Q 不进 cache，不用管）；
  • LLL：序列长度，KV 与它线性增长；
  • bytes_per_elem：存储精度，FP16=2 字节、FP8=1 字节；
  • 结果拿来做什么：乘上 batch 与序列长度就是总 KV 显存 → 反推"这块卡最多扛多少并发/多长上下文"。

手算小例：假设一个只有 2 层、2 个 KV 头、head_dim=2 的小玩具模型，存 1 个 token 的 FP16 KV：2×2×2×2×2=642 \times 2 \times 2 \times 2 \times 2 = 642×2×2×2×2=64 字节。真实模型只是把这个乘法换成大数字而已。

实例：Qwen2.5-7B（以官方 config.json 为准：28 层、GQA 4 个 KV 头、head_dim=128，由 hidden_size 3584 / 28 个 Q 头 = 128 得出）：

每 token KV 元素数=2×28×4×128=28672 元素/token\text{每 token KV 元素数} = 2 \times 28 \times 4 \times 128 = 28672 \text{ 元素/token} 每 token KV 元素数=2×28×4×128=28672 元素/token

FP16 下 28672×2=5734428672 \times 2 = 5734428672×2=57344 字节 =56= 56=56 KB/token。

8k 上下文、单请求：56 KB×8192=44856 \text{ KB} \times 8192 = 44856 KB×8192=448 MB。

batch=32、8k：32×448 MB=1432 \times 448 \text{ MB} = 1432×448 MB=14 GB。

对比：7B 权重本身（FP16）约 14 GB。batch=32、8k 时 KV cache（14 GB）已与权重（14 GB）相当；上下文再翻倍、或并发再翻倍，KV 就会超过权重——这就是"长上下文时代 KV 是显存第一杀手"的定量直觉：权重是固定开销，KV 随 batch × 序列长度线性膨胀。若换 FP8 KV（元素减半），并发上限直接翻倍，决定单卡能扛多少请求。

动手验证：python -c "from transformers import AutoConfig; c = AutoConfig.from_pretrained('Qwen/Qwen2.5-7B-Instruct'); print(c.num_hidden_layers, c.num_key_value_heads, c.hidden_size // c.num_attention_heads)" 输出 28 4 128。算 KV 必须以目标模型 config 为准——层数、KV 头数随模型型号差异巨大，不要背某个模型的数字。

一句话总结：KV 单价 = 2（K、V）× 层数 × KV 头数 × 头维度 × 字节数；Qwen2.5-7B FP16 下每 token 约 56 KB，8k 上下文单请求 448 MB，batch=32 时 KV 已追平权重——并发与上下文任一翻倍，KV 就反超权重成为显存大头。

2. PagedAttention 实现层

2.1 问题：预分配的浪费

朴素做法：每个请求预留整个最大上下文的连续显存。若请求只用了 200/8192，剩下 97.6% 浪费。高并发下这种"内部碎片"直接拖垮吞吐。

2.2 PagedAttention：把 KV cache 分页

借鉴操作系统虚拟内存：

  • 把 KV cache 切成固定大小的块（block）（如 16 token/块）；
  • 每请求按需分配块，不连续也行；
  • 用**块表（block table）**记录"逻辑块 → 物理块"映射，类似页表。

逻辑 token 位置→block table物理显存块地址\text{逻辑 token 位置} \xrightarrow{\text{block table}} \text{物理显存块地址} 逻辑 token 位置block table​物理显存块地址

注意力计算时通过块表查物理地址。碎片从"整段预留"降到"最多一个块的尾部浪费"，显存利用率逼近 100%。

2.3 块分配器与引用计数

块分配器维护一个空闲块池。分配时取一块、引用计数 +1；释放时 -1，归零则回收。

copy-on-write（写时复制）：并行采样（同一 prompt 出多个回复）或 beam search 时，多个序列共享同一段 KV 块——只复制块表指针，不复制物理数据；只有当某个分支要写入新内容时才真正复制那块。这把并行采样的显存开销从 O(k)O(k)O(k) 降到接近 O(1)O(1)O(1)。

2.4 手写迷你块管理器（交付核心）

预期：20 token 恰好占 2 块；fork 后引用计数为 2 且不分配新块。这就是 PagedAttention 块管理的最小可验证实现。

3. Prefix Caching 与 RadixAttention

3.1 Prefix Caching（vLLM）

多个请求共享同一前缀（如系统提示词）。vLLM 用块内容哈希做键：

hash(block)=H(父块 hash,本块 token ids)\text{hash}(\text{block}) = H(\text{父块 hash}, \text{本块 token ids}) hash(block)=H(父块 hash,本块 token ids)

新请求的前缀块若能命中已有哈希，就直接复用物理块（引用计数 +1），跳过重复的 prefill 计算。逐出用 LRU。

版本注意：V1 引擎（约 v0.8.x 起）中 prefix caching（官方叫 Automatic Prefix Caching，APC）默认开启——不再需要 --enable-prefix-caching；要关掉用 --no-enable-prefix-caching。部分模型（如 Mamba/混合架构）不支持，默认仍关闭。

3.2 RadixAttention（SGLang）

SGLang 用 Radix Tree（基数树） 组织所有缓存的前缀：

  • 树节点 = 一段 token 前缀，边 = token；
  • 共享前缀天然在树的公共路径上；
  • cache-aware 调度：把共享前缀的请求排在一起，最大化命中。

区别：vLLM 的 prefix caching 是"块级哈希命中"，被动复用；SGLang 的 RadixAttention 是"树结构主动管理 + 调度感知"，对多轮对话/共享前缀场景命中率更高。这是两个引擎选型的重要差异点（第 2 周压测会体现）。

4. KV 量化与压缩

4.1 为什么压 KV

第 1.2 节算过，长上下文下 KV 会逼近甚至反超权重。压缩 KV 直接放大并发：

  • FP8 KV：元素 2 字节 → 1 字节，KV 减半，精度损失小（KV 数值范围比权重窄）；
  • KIVI：Key 用 2-bit、Value 用 2-bit 的极端量化（Key 沿通道量化、Value 沿时间量化）；
  • Sliding Window + Sink（StreamingLLM）：只保留最近窗口 + 开头几个"attention sink" token，支持无限长流式。

4.2 在引擎中的位置

这些都作用在"写 KV / 读 KV"的算子上（attention/backends/），对调度器透明。开启方式通常是启动参数（如 --kv-cache-dtype fp8）。

5. 工程权衡与失效模式

5.1 权衡

  • 块大小：小块碎片少但块表开销大；大块反之。16 token 是常见折中；
  • FP8 KV：并发翻倍但精度略降，需验证目标任务；
  • prefix caching：命中省算力，但维护哈希/树有开销，前缀高度重复时才划算。

5.2 失效模式

  1. 块耗尽（OOM-like）：并发高 + 长序列，空闲块归零 → 新请求排队或旧请求被抢占。定位：看块占用时间线波谷；修复：降 max-num-seqs、开 KV 量化、扩容。
  2. 内部碎片误判：以为显存够却排队——其实是块粒度导致的尾部浪费叠加。修复：理解块大小，必要时调整。
  3. prefix caching 命中率低：请求前缀各不相同，缓存形同虚设还添开销。修复：评估前缀重复率再开。
  4. 引用计数泄漏：fork 后未正确释放 → 块永不回收，显存缓慢泄漏。定位：长跑监控空闲块单调下降。

6. 延伸思考题（含解析）

Q1：手算 7B、8k、batch=32 的 KV 显存，并说明它如何逼近权重。
A：以 Qwen2.5-7B 官方 config（28 层、4 KV 头、head_dim=128）为例：每 token KV = 2×28×4×128 = 28672 元素，FP16 约 56 KB；8k 上下文单请求 448 MB，×32 = 约 14 GB，与 7B 权重（约 14 GB）相当。KV 随序列长度与并发线性增长，权重固定，故上下文或并发再翻倍，KV 即反超权重成为显存大头。

Q2：PagedAttention 相比预分配，显存利用率为什么能逼近 100%？
A：预分配按最大上下文整段预留，短请求浪费巨大（内部碎片）；PagedAttention 按需分页，浪费最多是最后一块的尾部（<16 token），碎片从"整段"降到"一块尾部"。

Q3：copy-on-write 在并行采样中省了什么？
A：多个分支共享同一段 KV 物理块，只复制块表指针、引用计数 +1，不复制物理数据；直到某分支要写新内容才真正复制那一块。把并行采样的额外显存从 O(k) 降到接近 O(1)。

Q4：prefix caching 的哈希键怎么构造？为什么含父块哈希？
A：hash = H(父块哈希, 本块 token)。含父块哈希保证"相同后缀但不同前缀"不会误命中——只有从头开始的完整前缀一致才算命中。

Q5：vLLM prefix caching 与 SGLang RadixAttention 的本质区别？
A：vLLM 是块级哈希的被动复用；SGLang 用基数树主动管理所有前缀，且调度器 cache-aware 地把共享前缀请求排一起，命中率与多轮对话场景更优。

1. 第一性原理：NPU 是"算子白名单"硬件，自定义算子是逃生门

1.1 为什么总会撞上算子缺口

NPU 编译器只认固定的算子集（Conv/MatMul/常见激活等）。你的语音模型随时可能带上"新东西"：CIF 积分发射、flow matching 的 ODE 步、自定义归一化。转换报错只是表象，本质是硬件的确定性换来了算子集的封闭性。

逃生门：混合执行——模型图中不支持的算子"落"CPU（用你自己的实现），其余部分仍在 NPU 上跑。运行时在两种执行域之间切换，数据经共享内存传递。

1.2 rknn_custom_op 的注册与执行链

注册三要素：① op 描述（名字、输入输出个数与形状推导）；② compute 回调（拿到输入指针、算、写输出）；③ 内存与格式约定——两个高频坑：

  • 布局：NPU 内部常用 NHWC，框架是 NCHW——自定义算子拿到的可能是 NHWC，按错布局读数据结果全错；
  • 量化参数透传：若自定义算子的输入是量化张量（INT8 + scale/zp），你的 CPU 实现要么先反量化成浮点算、要么在整数域实现并保持 scale 语义——忘了透传 = 输出数值错一个 scale 倍数。

1.3 搬运成本模型（面试高频）

3. 工程权衡与失效模式

3.1 权衡

  • 自定义算子的粒度：算子越小、调用越频繁，搬运占比越高——有时把"一串小算子"打包成一个自定义算子反而更快（一次往返干多件事，融合思想在异构场景的复用）。
  • CPU 实现的优化责任：落 CPU 的算子没人帮你做 SIMD 特化——热点自定义算子要自己上 NEON/AVX（第 2 周技能复用）。
  • 平台锁定成本：RKNN 与 NeuroPilot 的转换脚本、自定义算子互不通用——若产品要双平台，把"模型本体（ONNX）"作为唯一事实源，平台产物全部脚本化再生成。

3.2 失效模式

  1. 布局错乱：症状——自定义算子输出是"有规律的乱码"（通道错位）；根因——NPU 给的是 NHWC、按 NCHW 读了；修复——打印输入 attr 的实际布局，转换期强制统一。
  2. 量化参数没透传：症状——输出整体偏大/偏小固定倍数；根因——把 INT8 输入当数值直接用，没乘 scale；修复——读张量量化参数，先反量化或整数域实现。
  3. 搬运吃掉收益：症状——加了自定义算子后比纯 CPU 还慢；根因——每帧多次小块往返；修复——合并算子、或用 §1.3 的成本模型先算账再动手。
  4. 转换工具与板端运行时版本错配：症状——加载即崩或结果错；根因——厂商工具链版本矩阵严格；修复——锁定版本组合并写进环境文档（RKNN 与 MTK 都有此坑）。

4. 延伸思考题（含解析）

Q1：什么时候"必须"写自定义算子，什么时候应该改写模型绕开它？
A：算子处于热路径且搬运成本可接受 → 自定义算子；算子只在离线/低频路径 → 可忍；算子引发高频小块往返、或实现复杂度过高 → 优先改写模型结构（用支持的算子等价替换）。先算搬运账，再谈实现——顺序不能反。

Q2：自定义算子的 CPU 实现为什么常常要自己写 SIMD？
A：NPU 工具链只对图内算子做编译优化；你的回调函数就是普通 C 代码，编译器不会替你调 NEON 内联。它在热路径上，性能就是你的责任——这是"混合执行"的隐性成本。

Q3：为什么两个平台都坚持从中间格式（ONNX/TFLite）出发？
A：中间格式是训练框架与所有部署工具链的最大公约数——RKNN 走 ONNX、NeuroPilot 主走 TFLite（也支持 ONNX 转换）。以中间格式为唯一事实源，任何平台的产物都可脚本化再生成——平台锁定只锁住转换脚本，锁不住模型资产。这是部署工程的可移植性原则。

Q4：RMSNorm 落 CPU 真的划算吗？什么情况下它应该留在 NPU？
A：RMSNorm 计算轻、但每层每帧都调用——若张量大（长序列），搬运可能超过计算。若 NPU 支持等价结构（多数支持：Mul+ReduceMean+Rsqrt+Mul 可编译融合），就该留 NPU；只有当它带特殊变体（如你的模型自定义的归一化）时才落 CPU。能用原生算子拼出来，就不要自定义。

Q5：对比表的"转换掉点"一列，如果 MTK 明显优于 RK3588，可能的原因有哪些？

1. 第一性原理：decode 为什么慢，投机为什么能快

1.1 decode 的访存瓶颈（回顾）

自回归每生成一个 token 就要加载一次全部权重——生成 kkk 个 token 就要加载 kkk 次。权重加载的显存带宽是瓶颈，计算单元大量闲置。

关键洞察：既然每步都要把权重完整读一遍，不如一次读入、多步共用——这正是投机解码的思路。

1.2 投机解码的循环

每一轮：

  1. 草稿：用便宜的 draft 模型（或免模型的启发式）快速猜出 kkk 个候选 token；
  2. 验证：把 kkk 个候选喂给目标大模型，一次前向并行验证所有位置；
  3. 接受：从左到右比较，接受与目标分布一致的草稿，遇到第一个被拒的位置就停，并从目标分布重采样一个；
  4. 每轮至少产出 1 个（重采样的）、最多 k+1k+1k+1 个 token。

为什么输出分布不变：接受/拒绝规则（rejection sampling）经过精心设计，使得接受的 token 严格服从目标模型分布——加速但不改变生成质量，这是投机解码最漂亮的性质。

1.3 加速比公式推导（本周自测题）

设单步接受率 α\alphaα（草稿被接受的概率），草稿一次猜 kkk 个。每轮接受的草稿数期望为：

E[接受数]=α+α2+⋯+αk=α(1−αk)1−α\mathbb{E}[\text{接受数}] = \alpha + \alpha^2 + \cdots + \alpha^k = \frac{\alpha(1-\alpha^k)}{1-\alpha} E[接受数]=α+α2+⋯+αk=1−αα(1−αk)​

深入拆解：这个公式在干什么

这个公式在算："一轮投机平均能白捡几个 token？"它是决定"投机到底划不划算"的定量依据。

  • α\alphaα 为什么是幂次递增的：第 1 个草稿 token 被接受的概率是 α\alphaα；第 2 个要前 1 个也接受了才轮到它，概率 α2\alpha^2α2；第 jjj 个要求前 j−1j-1j−1 个全部接受，概率 αj\alpha^jαj——拒绝是"从左到右一票否决"的，所以越靠后的草稿越难幸存；
  • 为什么最后还有 +1：遇到第一个拒绝位置时，目标模型会用自己的分布重采样出 1 个正确 token 补上，所以每轮至少产出 1 个、最多 k+1k+1k+1 个 token；
  • 手算小例：α=0.8,k=4\alpha = 0.8, k = 4α=0.8,k=4：E=0.8+0.64+0.512+0.410=2.362\mathbb{E} = 0.8 + 0.64 + 0.512 + 0.410 = 2.362E=0.8+0.64+0.512+0.410=2.362，加上重采样的 1 个，每轮平均产出约 3.36 个 token，而大模型只做了一次前向；
  • 结果拿来做什么：除以"草稿成本 + 验证成本"就得到实测加速比的预测，用来判断该不该开投机。

每轮还额外产出 1 个重采样 token。忽略 draft 开销时，加速比约为"每轮产出 / 验证一次的开销"。理想化公式：

Speedup≈11−α(当 k→∞)\text{Speedup} \approx \frac{1}{1-\alpha} \quad (\text{当 } k \to \infty) Speedup≈1−α1​(当 k→∞)

这条是理论上限：k→∞k \to \inftyk→∞ 时每轮产出趋近 α/(1−α)+1=1/(1−α)\alpha/(1-\alpha) + 1 = 1/(1-\alpha)α/(1−α)+1=1/(1−α) 个 token，而大模型开销仍按"一次前向"计。

直觉：α=0.5\alpha = 0.5α=0.5 → 加速约 2 倍；α=0.8\alpha = 0.8α=0.8 → 约 5 倍。接受率是投机的生命线——草稿越准，加速越猛。

验证开销：验证 kkk 个 token 的一次大模型前向，比单步略贵（算 kkk 个位置）。所以真实加速比还要除以验证开销系数，且 kkk 不是越大越好（kkk 大→草稿开销与验证开销都升，接受数却受 α\alphaα 限制）。

2. 草稿方案家族

2.1 独立 draft 模型（经典）

用一个小的同族模型当草稿（如 7B 目标配 0.5B 草稿）。草稿准但要额外显存与计算。

2.2 EAGLE / EAGLE-2：特征级草稿

不用独立模型，而是在目标模型的特征层接一个轻量头，自回归预测下一特征 → 解码成 token。草稿利用了目标模型自身的特征，接受率显著更高，且几乎不加显存。

2.3 Medusa：多头并行，免草稿模型

给目标模型加多个解码头，每个头独立预测未来不同位置的 token，再用树状注意力一次验证多条候选路径。不需要独立草稿模型，但接受率通常低于 EAGLE。

2.4 n-gram / self-speculative：免模型

用当前上下文里出现过的 n-gram 当草稿（如"刚才说过’机器学习’，后面可能又出现"）。零额外模型、零训练，在重复性文本上有效，接受率依赖文本特性。

3. CUDA Graph：消掉 kernel launch 开销

3.1 问题：launch 开销

decode 每步要发起几十上百个小 kernel。每个 kernel 的 launch（提交）开销在 CPU 侧是固定的（几微秒到几十微秒）。当单 kernel 计算本身很短（访存瓶颈、小 batch），launch 开销占比变得可观，GPU 出现空隙（gap）。

3.2 CUDA Graph 的解法

把一整步的 kernel 序列录制成一张图（graph），之后每步只"回放"这张图——一次提交、整图执行，消掉逐个 launch 的开销。

逐步 launch: [L][k1][L][k2]⋯⏟大量 L 开销    →    Graph: [L一次][k1k2k3⋯ ]\text{逐步 launch: } \underbrace{[L][k_1][L][k_2]\cdots}_{\text{大量 L 开销}} \;\;\to\;\; \text{Graph: } [L_{\text{一次}}][k_1 k_2 k_3 \cdots] 逐步 launch: 大量 L 开销[L][k1​][L][k2​]⋯​​→Graph: [L一次​][k1​k2​k3​⋯]

3.3 为什么主要用于 decode

  • decode：每步结构固定（固定算子序列、固定形状），适合录图；
  • prefill：序列长度多变、形状不固定，难以复用同一张图（要为每个形状单独录，代价大）。

限制：图是静态的——形状必须固定。所以引擎为若干常见形状各录一张图，不在图内的走普通路径。这就是"graph capture 范围与限制"。

4. 其他解码优化

4.1 结构化输出（约束解码 / JSON mode）

让生成严格满足 JSON schema 等。实现：在采样时用有限状态机/文法屏蔽不合法 token（logits mask）。代价：每步要算状态转移与 mask，略增延迟；复杂文法开销更大。

4.2 logits processor 链路

温度、top-k、top-p、重复惩罚等都是作用在 logits 上的 processor，按链式顺序施加。它们本身开销小，但约束解码的文法匹配是主要成本来源。

6. 工程权衡与失效模式

6.1 权衡

  • 草稿方案：EAGLE 接受率高但需加载额外头；n-gram 零成本但吃文本特性；
  • kkk（草稿长度）：大 → 单轮潜在产出多，但草稿+验证开销升、边际收益降；
  • CUDA Graph：省 launch 开销，但要求形状固定、占额外显存存图。

6.2 失效模式

  1. 接受率过低：草稿与目标分布差异大（跨域文本），投机反而变慢（白付草稿开销）。修复：换更贴的草稿方案、或对特定负载关闭投机。
  2. n-gram 在创意文本失效：内容不重复，n-gram 命中率趋零。修复：换 EAGLE 类。
  3. CUDA Graph 形状不匹配：请求形状落在已录图之外，回退普通路径，收益消失。修复：了解引擎录了哪些形状。
  4. 结构化输出拖慢：复杂 JSON schema 的文法匹配成为瓶颈。修复：简化 schema、或用引擎原生优化实现。

7. 延伸思考题（含解析）

Q1：投机解码加速比的理论上限公式？接受率怎么影响？
A：理想上限约 1/(1−α)1/(1-\alpha)1/(1−α)。接受率 α\alphaα 越高，每轮接受的草稿越多，加速越猛：α=0.5\alpha=0.5α=0.5 约 2 倍、α=0.8\alpha=0.8α=0.8 约 5 倍。实测低于理论，因验证开销与有限 kkk。

Q2：投机解码为什么"加速但不改输出分布"？
A：接受/拒绝用 rejection sampling 设计：草稿被目标分布校验，拒绝处从目标分布重采样。数学上保证最终 token 严格服从目标模型分布——纯加速、不损质量。

Q3：EAGLE 和 Medusa 的取舍？
A：EAGLE 用目标特征接轻量头做自回归草稿，接受率高、是当前主流，但需加载草稿头；Medusa 多头并行、免独立草稿模型，实现简单但接受率通常较低。要高质量选 EAGLE，要轻量免模型选 Medusa。

Q4：CUDA Graph 为什么主要用于 decode 而非 prefill？
A：图要求算子序列与张量形状固定。decode 每步形状固定、可复用同一张图；prefill 序列长度多变、形状不固定，需为每形状单独录图、代价大，故主要受益的是 decode。

Q5：什么时候该关闭投机解码？
A：当草稿接受率过低时——草稿开销白白付出，接受数却少，净收益为负。典型是草稿方案与目标负载不匹配（如 n-gram 用于创意文本）。应先实测接受率再决定开关。

1. 第一性原理：量化格式必须与"算子实现"匹配

1.1 量化不只是"存得小"

Stage 2 你学会了把权重压成 4-bit/8-bit。但要在引擎里真正加速，压好的权重必须被专门的 kernel 消费——否则引擎只会把它反量化回高精度再算，白压。

所以核心命题是：

量化格式  ⟷  对应的加速 kernel\text{量化格式} \;\longleftrightarrow\; \text{对应的加速 kernel} 量化格式⟷对应的加速 kernel

格式与 kernel 不匹配，量化只剩"省显存"而失去"提速"。

1.2 权重存储与计算的分离

量化模型在引擎里的典型形态：

  • 权重：低比特存储（省显存、降带宽）；
  • 计算：GEMM 时用反量化或专用 kernel，把低比特权重与激活结合。

这就是为什么"权重 4-bit、激活 16-bit"（W4A16）常见——权重是访存大头，激活保持精度。

2. 各量化格式在 vLLM 中的通路

3. 低比特新前沿

3.1 W4A4：权重激活都 4-bit

比 W4A16 更激进，激活也量化。难点：激活的离群值比权重更难压（回想 SmoothQuant 的动机）。当前仍在探索，精度损失需仔细评估。

5. 多 LoRA 服务（S-LoRA）

5.1 问题：一个底座、很多适配器

实际场景常需同时服务几十上千个 LoRA（每客户/每任务一个）。若每加载一个就复制整个底座，显存爆炸。

5.2 S-LoRA 的解法：共享底座 + 动态挂载

一份底座权重  +  多个轻量 LoRA  →按请求动态挂载  各自适配的输出\text{一份底座权重} \;+\; \text{多个轻量 LoRA} \;\xrightarrow{\text{按请求动态挂载}}\; \text{各自适配的输出} 一份底座权重+多个轻量 LoRA按请求动态挂载​各自适配的输出

  • 底座只存一份，所有请求共享；
  • LoRA 权重很小（低秩），按需加载到显存、可驻留可换出；
  • batch 内混合：同一批里不同请求用不同 LoRA，通过分块计算或 padding 处理。

5.3 热插拔

新 LoRA 上传 → 注册进引擎 → 后续请求即可引用；下线则卸载。无需重启服务、无需动底座。

关键收益：把"每适配器一个服务实例"降为"一个实例 + 动态适配器"，显存与运维成本大幅下降。

6. 工程权衡与失效模式

6.1 权衡

  • 4-bit（Marlin）：显存省、能开大 batch，但精度略降；
  • FP8：精度好、需较新硬件；
  • 多模态预处理：特征配置必须与训练严格一致，否则输出乱。

6.2 失效模式

  1. 量化没走加速路径：静默反量化回高精度，只省显存不提速。诊断：看启动日志与实测吞吐。
  2. 多模态采样率错配：音频未按模型要求重采样，识别/理解全错。修复：预处理强制重采样。
  3. 多 LoRA 显存超限：驻留适配器太多。修复：LRU 换出、控制同时活跃数。
  4. batch 内混合 LoRA 低效：适配器太碎导致计算碎片化。修复：按适配器聚批。

7. 延伸思考题（含解析）

Q1：为什么 4-bit 量化（GPTQ/AWQ）在 batch=1 时可能比 FP16 还快？
A：decode 是访存瓶颈，4-bit 权重体积是 FP16 的 1/4，加载时间大幅缩短；这个带宽收益超过了反量化的计算开销，故单请求延迟反而更低。大 batch 下计算占比上升，优势缩小。

Q2：FP8 量化为什么需要 Hopper/Ada 架构？
A：FP8 的硬件加速依赖 Tensor Core 对 FP8 数据类型的原生支持，对应 CUDA compute capability ≥ 8.9（Hopper H100/H200、Ada L40S 等及更新架构）。Ampere（A100）等老架构无原生支持，无法走 FP8 加速路径。

Q3：多模态输入进引擎前为什么要"重采样到模型要求"？
A：模型的音频编码器在特定采样率（通常 16 kHz）上训练，特征提取（窗口、维度）都基于该采样率。输入采样率不符会导致时间轴与特征全错，输出失真。

Q4：多 LoRA 共享底座为什么能大幅省显存？
A：底座权重是大头，只存一份被所有请求共享；每个 LoRA 只是低秩增量、极小。相比"每适配器复制整个底座"，显存从 O(底座×N) 降到 O(底座 + N×小增量)。

Q5：LoRA 热插拔如何做到不重启服务？
A：底座与适配器解耦。新适配器只是注册一组小的低秩权重并挂载到底座的前向路径，卸载则移除。底座不变、服务不重启，适配器可动态增删。

Q1：达芬奇 Cube/Vector/Scalar 各适合什么计算？举具体算子。

Q2：昇腾和 NVIDIA 架构的本质差异？

A：AscendCL（ACL）对应 CUDA Runtime（运行时 API）；ATC + GE 对应 TensorRT 的模型优化/编译角色（但 ATC 是转换器，把模型转成 OM）。

Q4：为什么 910B 和 310P 要分开用？
A：910B 算力/显存大，适合训练与算子开发验证；310P 低功耗、内存小，适合推理部署。在 310P 上强行训练会内存不足且慢，在 910B 上做端侧部署验证又不真实。

Q5：什么业务值得投入昇腾适配？
A：三维判断：① 国产化/信创要求（政策刚需）；② 成本与供货稳定性（昇腾供应更可控）；③ 生态成熟度（目标模型/算子是否已适配）。有国产化要求且模型在昇腾已适配的业务最值得。

1. 第一性原理：调优是在"显存、吞吐、延迟"三角里找平衡点

1.1 没有万能配置

引擎的默认参数是通用折中，不是你的负载的最优。调优的本质：针对你的负载形状（输入/输出长度、并发、延迟要求），把资源分配调到该形状的最优点。

1.2 调优前先定目标

必须先回答：

  • 优化吞吐（离线批处理）还是优化延迟（在线对话）？
  • 延迟约束是什么（TTFT ≤ ? ms，TPOT ≤ ? ms/token）？

目标不同，最优配置完全不同。吞吐优先可以拉满 batch 牺牲单请求延迟；延迟优先要控 batch 留余量。

2. 关键参数逐一拆解

2.1 gpu-memory-utilization

作用：引擎预留给"模型权重 + KV cache"的显存比例（如 0.9 = 90%）。

调高（→ 0.95）：给 KV cache 更多空间 → 能扛更高并发/更长上下文。但留给激活/临时缓冲的余量小，易 OOM。

调低（→ 0.7）：更安全，但并发上限降低。

经验：在线服务留足余量（0.85-0.9），离线批处理可拉高（0.92-0.95）但需监控。

2.2 max-num-batched-tokens

作用：单步（一个 iteration）处理的最大 token 数——算力预算。

它同时影响：

  • chunked prefill 的块大小（每步最多做这么多 prefill 工作）；
  • 并发（太大 → 单步算太久、延迟抖动）。

调大：prefill 吞吐高，但单步延迟增、干扰 decode；调小：反之。

2.3 swap-space

作用：每卡预留的 CPU 内存，用于抢占时把 KV 换出（第 2 周）。

设为 0：禁用换出，抢占只能 recompute。设为正数：允许 swap。
权衡：换出保留计算但吃 PCIe；空间不足则退回重算。

版本注意：该参数属 V0 时代机制，V1 引擎已移除 swap 抢占（一律 recompute），新版本上调它通常没有效果——排查抢占问题时先确认自己跑的是哪个引擎版本。

2.4 enable-chunked-prefill

作用：开/关把长 prefill 切块（第 2 周）。
影响：开 → TTFT 长尾改善、decode 更平稳；代价是长 prompt 总 prefill 可能略慢。

2.5 参数相互制约

这些参数不是独立的：gpu-memory-utilization 决定 KV 总量 → 影响能开多大 max-num-batched-tokens 和并发；chunked prefill 的块大小又受 max-num-batched-tokens 限制。调优必须成组实验，不能孤立看单参数。

3.1 标准压测脚本

3.2 负载曲线（capacity planning 的核心）

对一组 request-rate 依次压测，画出：

吞吐=f(到达率),延迟=g(到达率)\text{吞吐} = f(\text{到达率}), \quad \text{延迟} = g(\text{到达率}) 吞吐=f(到达率),延迟=g(到达率)

曲线会显示一个拐点：到达率超过某值后，吞吐不再增长、延迟急剧上升——这就是系统的饱和点。生产容量应设在拐点之前（留 20-30% 余量）。

3.3 goodput：SLO 驱动的吞吐

普通吞吐 = 每秒完成的 token 数，不管延迟。但生产关心的是"满足 SLO 的吞吐"：

goodput=满足 (TTFT≤SLO1)∧(TPOT≤SLO2) 的请求吞吐\text{goodput} = \text{满足 } (\text{TTFT} \le \text{SLO}_1) \land (\text{TPOT} \le \text{SLO}_2) \text{ 的请求吞吐} goodput=满足 (TTFT≤SLO1​)∧(TPOT≤SLO2​) 的请求吞吐

高吞吐但大量请求超延迟 = 实际无效。DistServe 等工作的优化目标就是 goodput。容量规划应以 goodput 为准，而非裸吞吐。

5. 故障排查库（交付：三个自造案例）

5.1 OOM

症状：进程崩溃，CUDA out of memory。
排查路径：

  1. 看是否 gpu-memory-utilization 过高、无余量；
  2. 看是否某请求上下文超长（KV 爆）；
  3. 看激活/临时缓冲是否被低估。
    修复：降 gpu-memory-utilization、限制 max-model-len、开 KV 量化。

5.2 请求排队爆炸

症状：吞吐骤降、延迟飙升、大量请求卡住。
排查路径：

  1. 看显存是否耗尽（KV 块不足，新请求进不了 running）；
  2. 看是否到达率超过饱和点；
  3. 看是否有超长请求独占资源。
    修复：降 max-num-seqs、扩容、限流、拒绝超长请求。

5.3 量化精度异常

症状：量化模型输出明显退化（乱码、答非所问）。
排查路径：

  1. 看启动日志是否静默反量化或走错 kernel；
  2. 看量化格式与 --quantization 是否匹配；
  3. 对比离线量化评测（Stage 2）确认是引擎侧问题还是量化本身。
    修复：指定正确 --quantization、换支持的格式、检查量化产物完整性。

5.4 制造并解决（交付）

主动把上述三类故障各制造一次（如把 gpu-memory-utilization 调到 0.99 触发 OOM），走一遍排查路径，记录"现象→定位→修复"。这是把排查清单变成肌肉记忆的最好方式。

6. 工程权衡与失效模式

6.1 权衡

  • 吞吐 vs 延迟：调优的根本矛盾，先定目标；
  • 显存余量：拉满并发高但易 OOM，留余量稳但并发低；
  • 压测代表性：合成负载快但不真实，真实负载（ShareGPT）慢但准。

6.2 失效模式

  1. 只看裸吞吐忽略 SLO：吞吐高但大量请求超时，实际不可用。修复：用 goodput。
  2. 孤立调单参数：忽略参数交互，组合后效果不如预期。修复：成组实验 + 整体复现。
  3. 压测负载失真：用单一长度压测，上线遇真实分布翻车。修复：用真实负载分布。
  4. 不留余量：把资源用到极限，稍有波动就排队爆炸。修复：容量设在拐点前 70-80%。

7. 延伸思考题（含解析）

Q1：gpu-memory-utilization 调高的收益与风险？
A：收益是更多显存给 KV cache，能扛更高并发/更长上下文；风险是留给激活和临时缓冲的余量变小，更易 OOM。在线服务建议 0.85-0.9 留余量。

Q2：goodput 与吞吐的区别？为什么容量规划要看 goodput？
A：吞吐只数完成的 token，不管延迟；goodput 只统计满足延迟 SLO 的请求。高吞吐但大量超时 = 对用户无效。生产关心的是"及时完成"，故以 goodput 规划容量。

Q3：max-num-batched-tokens 影响哪两件事？
A：① chunked prefill 的块大小（每步 prefill 工作量）；② 单步算力预算（太大会让单步变慢、干扰 decode）。它是 prefill 吞吐与延迟平滑度的权衡旋钮。

Q4：服务突然排队爆炸，排查路径？
A：先查显存（KV 是否耗尽导致新请求进不了 running）→ 再查到达率是否超饱和点 → 查是否有超长请求独占 → 对症处理（降并发/扩容/限流/拒超长）。

Q5：为什么调优实验要"每次只变一个参数"？
A：参数间有交互（如显存利用率影响可用 batch）。同时变多个无法归因是哪个参数导致的变化。单变量实验才能建立"参数→效果"的因果，最后再组合验证。

计算单元不能直接高效吃 HBM 数据，要先搬到 UB；搬完才能算。若"搬一块→算一块→搬下一块→算下一块"串行做，搬运和计算互相等待。double buffer 流水就是来解决这个问题的。

Tiling 的取舍：块太小 → 流水启动/收尾开销占比高；块太大 → UB 装不下。要满足 块大小 ≤ UB 容量 且让每个核都有足够活干。

深入拆解：Tiling 公式在干什么（手算小例）

Tiling 的核心约束是一条显存预算不等式：一次流水处理的中间数据必须全部装进片上 UB。对本算子，一次要同时在 UB 里放输入 xxx、残差 rrr 和输出 yyy 三块 FP16 数据：

tileRows×C×2B⏟x+tileRows×C×2B⏟r+tileRows×C×2B⏟y≤UB 容量\underbrace{\text{tileRows} \times C \times 2\text{B}}_{x} + \underbrace{\text{tileRows} \times C \times 2\text{B}}_{r} + \underbrace{\text{tileRows} \times C \times 2\text{B}}_{y} \le \text{UB 容量} xtileRows×C×2B​​+rtileRows×C×2B​​+ytileRows×C×2B​​≤UB 容量

  • 为什么需要：UB（Unified Buffer，片上缓冲）容量有限，装不下就要么溢出报错、要么被迫分成更多小块；
  • 符号含义：tileRows 是每次流水处理的行数，CCC 是每行列数，FP16 每元素 2 字节；UB 容量随芯片型号而异（910B 一代约 256 KB，老型号 192 KB——以官方规格为准）；
  • 手算小例：C=4096C = 4096C=4096（一行 FP16 = 8 KB），UB 取 256 KB：tileRows≤256/(8×3)≈10\text{tileRows} \le 256 / (8 \times 3) \approx 10tileRows≤256/(8×3)≈10，即每次流水最多搬 10 行（再留点余量取 8）；
  • 结果拿来做什么：这个 tileRows 就是写 kernel 时每次 DataCopy 的分块大小，也是 Tiling 结构体要传给 kernel 的关键参数。

6. 工程权衡与失效模式

6.1 权衡

  • 块大小：受 UB 容量约束，太小流水开销大、太大装不下；
  • 累加精度：归约用 FP32 累加防误差累积，但略慢；
  • 半精度：FP16 省带宽但需注意范围。

6.2 失效模式

  1. UB 溢出：块太大装不下。修复：减块大小、核对 UB 容量。
  2. 流水没起来：串行等待、未用双缓冲。修复：核对 EnQue/DeQue 顺序，让搬与算重叠。
  3. 归约误差大：FP16 累加溢出。修复：中间用 FP32 累加。
  4. Tiling 分块不均：某核没活干/越界。修复：处理不能整除的余数行。

7. 延伸思考题（含解析）

Q1：Ascend C 的 Kernel、Tiling、流水各管什么？
A：Kernel 是设备侧每核的计算逻辑；Tiling 在 host 侧决定任务怎么切给多核、每块多大；流水（double buffer）让数据搬运与计算重叠。三者协作：Tiling 定分工，Kernel 定算法，流水定执行节奏。

Q2：double buffer 为什么能隐藏访存延迟？
A：用两块缓冲，搬第 2 块的同时算第 1 块、搬出第 0 块，三个阶段重叠。稳定后每步同时有搬入/计算/搬出在进行，访存延迟被计算掩盖，硬件利用率提高。

Q3：Tiling 的块大小怎么定？
A：上界是 UB 容量（块必须装得下）；下界是让流水启动/收尾开销占比可接受。在两者间选能整除或余数最少、且每核有足够活的值。

Q4：fused Add+RMSNorm 里哪步是归约？为什么它比逐元素难？
A：求每行均方根是归约（把一行压成一个数）。它需要跨元素累加、涉及累加精度（要 FP32 防溢出）和分块时的跨块合并，比纯逐元素复杂。

Q5：为什么归约要用 FP32 累加，即使输入是 FP16？
A：FP16 范围小，长累加易溢出/精度丢失。用 FP32 累加器累计平方和更稳，最后再转回。这是数值稳定性的常见实践。

第 3-4 周教程：前端与 ASR 板端打通——从麦克风到文字

本周要回答的四个问题

  1. ALSA 采集的帧长、缓冲、时间戳怎么配，才能喂好 AEC 又不引入大延迟？
  2. AEC 的参考信号回路怎么接？为什么「没有参考回路的 AEC 等于没做」？
  3. WebRTC APM 交叉编译到 ARM 要注意什么？哪些模块可以裁掉？
  4. SenseVoice-Small 上板先跑 ONNX Runtime CPU，RTF 与云端一致性怎么测才算数？

对应学习计划：第 3-4 周。交付物：板端跑通「说话 → 文字」，实测 RTF 与首字延迟，记录 CPU 利用率；与云端推理一致性差距 < 2%。

1. 第一性原理：前端存在的理由——信噪比决定一切

1.1 链路质量的乘法关系

全链路识别率近似满足：

P识别≈P前端保真⋅PASR∣SNRP_{\text{识别}} \approx P_{\text{前端保真}} \cdot P_{\text{ASR} \mid \text{SNR}} P识别​≈P前端保真​⋅PASR∣SNR​

这个公式在干什么：它把端到端识别成功率拆成两级条件概率相乘——前端把语音「保真地」送过去的概率，乘以「在当前 SNR 下 ASR 能认对」的概率。级联链路的成功率是乘法而不是加法：假设前端丢真 10%（P1=0.9P_1 = 0.9P1​=0.9）、ASR 在该 SNR 下认对 90%（P2=0.9P_2 = 0.9P2​=0.9），端到端只有 0.9×0.9=0.810.9 \times 0.9 = 0.810.9×0.9=0.81，即 五分之一的话在半路就丢了。这也解释了两条工程结论：① 任何一级的提升都被另一级封顶（P2=0.5P_2 = 0.5P2​=0.5 时，P1P_1P1​ 做到 1.0 也只有 0.5）；② 木桶效应——先补短板收益最大。

ASR 模型在干净语音上的能力是固定的，你能动的变量只有前端送进去的 SNR。远场 3 米、电视背景音下，裸麦的 SNR 可能只有 5 dB，AEC+NS+AGC 能拉回 15 dB 以上——这一段的收益比换任何 ASR 模型都大。这是你 Stage 3 的结论，本周让它上板。

1.2 10 ms 帧的物理约束

WebRTC APM 的处理粒度是 10 ms 帧（16 kHz 下 160 样本）。这个数字不可协商——AEC 的滤波器按帧对齐。Silero VAD 的窗口比 APM 粗：它在 16 kHz 下按 512 样本（32 ms）窗推理（sherpa-onnx 会把你喂进来的 10 ms 小块自动缓冲凑窗），所以整条前端的节拍由最细的 APM 锁死在 10 ms，VAD 的 32 ms 窗是叠加在其上的判定粒度。任何模块引入额外缓冲都在直接加延迟：

T前端=T采集缓冲+TAPM 处理≤10 ms+约 5 msT_{\text{前端}} = T_{\text{采集缓冲}} + T_{\text{APM 处理}} \le 10\,\text{ms} + \text{约 5\,ms} T前端​=T采集缓冲​+TAPM 处理​≤10ms+约 5ms

这个公式在干什么：它把「声音进麦克风 → 前端输出干净语音」这段固定延迟拆成两部分——T采集缓冲T_{\text{采集缓冲}}T采集缓冲​ 是攒够一帧才交数据的等待时间（每帧 10 ms，攒几帧就乘几倍）；TAPM 处理T_{\text{APM 处理}}TAPM 处理​ 是 APM 算完这一帧的时间（AEC+NS+AGC 在 16 kHz 10 ms 帧上通常只要几毫秒，量级参考：ARM 大核单帧远低于帧长，否则实时性就破了）。结果拿来做什么：它是全链路延迟预算里「前端」一行的填报依据——手算就是 1 帧 × 10 ms + 约 5 ms 处理 ≈ 15 ms，远小于预算。

采集缓冲取 1 帧（10 ms）而不是常见的 4~8 帧，是端侧与桌面应用的关键差异——桌面要吞吐，端侧要延迟。

2. 采集与 AEC 回路

2.1 ALSA 采集配置

关键参数：16 kHz、单声道（多通道阵列先混音或走波束成形）、16-bit、period 160 样本（10 ms）、缓冲 2~4 periods。用 hw 设备而非 default（避开 PulseAudio 的重采样与缓冲黑箱）。

2.2 AEC 参考回路（本周最易翻车点）

AEC 的原理：已知送往扬声器的信号 sts_tst​（参考），从麦克风信号 mtm_tmt​ 中估计并减去回声 h^∗st\hat{h} * s_th^∗st​：

cleant=mt−h^∗st\text{clean}_t = m_t - \hat{h} * s_t cleant​=mt​−h^∗st​

这个公式在干什么：扬声器播出的声音会经空气反弹回麦克风，这条「回声路径」可以用一个冲激响应 hhh 描述（∗*∗ 是卷积，表示「过去一段时间内播出的声音按各自的延迟与衰减叠加进麦克风」）。AEC 用自适应滤波器在线估计这个 hhh 得到 h^\hat{h}h^，然后从麦克风信号里把回声的预测值减掉，剩下的 cleant\text{clean}_tcleant​ 才是真正的近端人声。符号含义：mtm_tmt​ 是麦克风录到的信号（近端语音 + 回声 + 噪声）、sts_tst​ 是我们自己送出去的参考（已知！）、h^∗st\hat{h} * s_th^∗st​ 是回声的估计。结果拿来做什么：减得越准，ASR 听到的「自言自语」越少。公式的读法本身就是答案——没有 sts_tst​，减法无从谈起，回声只能当噪声盲处理，这就是「没有参考回路的 AEC 等于没做」的数学根源。

参考信号必须与播放严格同源同时间基。两种接法：

  1. 软件回路（首选）：播放缓冲里的 PCM 块同时复制一份给 APM 的 analyze_reverse_stream——零硬件成本，延迟可知；
  2. 硬件回路：从功放输出回采一路——能消掉功放/扬声器的非线性失真，但需要额外 ADC 通道。

无参考回路时的典型症状：助手在播放 TTS 时被自己的声音触发 VAD，产生自我打断或自问自答。

2.3 WebRTC APM 的 ARM 移植与裁剪

交叉编译要点（aarch64-linux-gnu 工具链）：

  • 只编 modules/audio_processing 子集，裁掉视频与网络模块；
  • 保留：AEC3、NS（噪声抑制）、AGC2、VAD（可选，我们用 Silero）；
  • 裁掉：回声消除的实验性配置、多通道处理（单声道场景）；
  • 编译产物是静态库，Python 侧用 pybind11 薄封装或直接用 sherpa-onnx 的 VAD + 系统级 APM。

替代路径：若自编译时间超 3 天，先用 sherpa-onnx 的 Silero VAD + 简化的谱减降噪打通链路，WebRTC APM 作为第 7-8 周回填——打通优先于完美，但接口层保持「前端是黑盒模块」以便替换。

3. ASR 上板：SenseVoice-Small 的部署路径

3.1 为什么是 ONNX 先行

部署路径：FunASR 权重 → ONNX 导出 → (ONNX Runtime CPU 打通) → (RKNN 转换回填)。

ONNX 先行的理由：① 功能正确性验证与性能优化解耦——先证明链路对，再谈快；② RKNN 转换常遇算子不支持，需要逐个修补，不该阻塞链路打通；③ ONNX Runtime 有成熟的 aarch64 轮子。

sherpa-onnx 的角色：它把流式与非流式 ASR、VAD、唤醒词统一成一套 C++/Python API，是端侧语音的「运行时粘合剂」。SenseVoice 走它的非流式接口（短指令场景，NAR 单步解码本就无需流式）。

3.2 RTF 与一致性的定义（测量口径必须先冻结）

RTF=解码耗时音频时长,首字延迟=VAD 端点时刻→文本产出时刻\text{RTF} = \frac{\text{解码耗时}}{\text{音频时长}}, \qquad \text{首字延迟} = \text{VAD 端点时刻} \to \text{文本产出时刻} RTF=音频时长解码耗时​,首字延迟=VAD 端点时刻→文本产出时刻

RTF 在干什么：Real-Time Factor（实时率）衡量「处理 1 秒音频要花多少墙钟时间」——分子是解码一段音频实际花的秒数，分母是这段音频本身的秒数。RTF = 0.1 意思是「每段音频的处理时间只有它时长的 1/10」，<1 才能追上实时。手算小例：5 秒音频解码花 200 ms → RTF =0.2/5=0.04= 0.2/5 = 0.04=0.2/5=0.04；同一模型若换 0.2 → 解码要 1 s，流式场景下必然越攒越多。结果拿来做什么：它是跨音频长度可比较的归一化速度指标，压测表里报 RTF 而不是裸毫秒数。注意首字延迟是另一个口径：端点时刻到文本产出的绝对耗时，对应延迟预算表里的 200 ms——RTF 管吞吐口径，首字延迟管体验口径，两个都要报（Q2 有展开）。

一致性对比：同 100 条测试音频，板端（ONNX）与云端（FunASR 原始权重）各跑一遍，比较：

一致率=转写完全相同的条数100,要求≥98%\text{一致率} = \frac{\text{转写完全相同的条数}}{100}, \qquad \text{要求} \ge 98\% 一致率=100转写完全相同的条数​,要求≥98%

这个公式在干什么：它把「板端部署有没有偷偷劣化」量化成一个整数比——分子是板端与云端逐字相同的条数。手算小例：100 条里 3 条出现个别字差异 → 一致率 97%，触发排查。注意它刻意用「转写是否相同」而不是「字错率」：目的是抓部署差异（量化/预处理漂移），不需要评分级的相似度。

注意口径：一致性比的是「同模型不同运行时」，不是「板端模型与云端大模型的差距」——后者是模型差距，不是部署差距。混淆这两个口径是压测报告最常见的错误。

5. 工程权衡与失效模式

5.1 权衡

  • CPU 先行 vs NPU 直上：本周选 CPU（打通优先）；但 ONNX 模型封装成独立模块，RKNN 回填时只换实现不换接口。
  • int8 vs fp32：int8 内存减半、速度快 ~2 倍，但一致性测试里若差异集中出现（如 >2%），先回 fp32 定位——量化误差与部署 bug 必须分开归因。
  • 帧缓冲取舍：1 帧（10 ms）采集缓冲延迟最低但 CPU 中断频繁；2 帧（20 ms）CPU 负载降 ~30% 延迟 +10 ms。RK3588 上建议 1 帧起步，负载顶不住再放宽。
  • 波束成形要不要：单麦先跑通；若板子是环形阵列，波束成形收益在远场（>2 m）才显著，近场（<1 m）加它纯增加延迟。

5.2 失效模式

  1. 截头（丢首字）：VAD 触发前的音频没保留 → 「今天天气」识别成「天天气」。修复：环形缓冲回看 ≥200 ms（4.1 已内置）。
  2. 自问自答：无 AEC 参考回路，TTS 播放被 ASR 听进去。修复：接参考回路；临时方案——播放期间关闭 ASR 触发（半双工降级，打断功能随之失效，写进风险清单）。
  3. 重采样污染：麦克风 48 kHz，链路里多次重采样引入混叠与延迟。修复：全链路锁定 16 kHz，重采样只在采集入口做一次（高质量 sinc 滤波器）。
  4. 大核未绑定：ASR 线程被调度到 A55 小核，RTF 翻 3 倍。症状：延迟时好时坏；修复：taskset/pthread_setaffinity 绑大核，压测时盯 /proc 验证。
  5. 一致性差异被误判为量化问题：实际是预处理参数不一致。修复：固定一份「预处理契约」（采样率、梅尔参数、归一化方式），板云共用。

6. 延伸思考题（含解析）

Q1：为什么 AEC 需要参考信号，而 NS（降噪）不需要？
A：回声是已知源的干扰（就是自己播出的信号），可以做参考相减；环境噪声源未知，只能靠统计特征估计并抑制。所以 AEC 是确定性减法问题，NS 是统计估计问题——前者没有参考信号就退化成无信息盲减，自然「等于没做」。

Q2：RTF < 0.1 为什么还不够？预算是 200 ms，5 秒音频 RTF=0.1 不就是 500 ms 吗？
A：好问题——预算表里的 200 ms 针对的是典型短句（≤2 s 的指令），长句场景要么超预算要么截断。所以验收要报两个数字：短句（2 s）首字延迟 <200 ms，长句（5 s）RTF <0.1。单一数字会掩盖分布——这是所有延迟指标的通病。

Q3：ONNX Runtime CPU 版与未来 RKNN 版，精度口径应该怎么对齐？
A：以云端原始权重（fp32）的转写为基准，分别测 ONNX 版与 RKNN 版的一致率；两个运行时各自 ≥98% 才算部署无损。若 RKNN 版单独低，问题在转换（算子替换/量化），与 ONNX 无关——基准唯一、逐层归因。

Q4：VAD 尾部静默阈值 400 ms 是从哪里来的？能再短吗？
A：来自「自然停顿」的统计：中文口语中词语间停顿多为 100~300 ms，轮次结束停顿通常 >400 ms。短于 350 ms 会把思考停顿误判为说完（抢话），长于 600 ms 用户会觉得助手迟钝。400~500 ms 是产品甜点——第 7-8 周用真实用户测试微调。

Q5：如果一致性测试板端 95%、云端 100%，但转写错误的 5 条全是带背景噪声的样本，说明什么？
A：说明差异不在模型运行时，而在前端链路：云端测试用的可能是干净音频或不同的前端处理。修复：把板端前端输出的音频（而非原始录音）作为云端对比输入——对比必须在「同一输入」上才有效。

Q6：为什么用 sherpa-onnx 而不是直接写 ONNX Runtime 推理？
A：sherpa-onnx 在 ONNX Runtime 之上封装了端侧语音的全部例行公事——音频特征提取、流式/非流式状态管理、VAD、唤醒词、TTS 的统一 API，且有成熟 aarch64 轮子。自己裸写 ONNX Runtime 意味着重造特征提取与状态机，而这两处恰是预处理契约差异的高发区。原则：通用运行时自己写，领域粘合层用成熟库。

2. 鲁棒性三板斧：离线验证、泄漏排查、高温测试

2.1 完全离线验证

方法：sudo ip link set wlan0 down（物理拔网线/关射频更彻底），跑完整测试集——唤醒、对话、打断全部通过才算「离线」。检查清单：

  • TTS 无云端音色依赖；
  • LLM 无在线词表/缓存回源；
  • 时间戳不依赖 NTP（RTC 本地时钟）；
  • 日志上报全部落本地文件（联网时才批量上传）。

任何一项失败，都说明「离线」只是当前没触发联网路径——写进风险清单并修复。

2.2 内存泄漏长跑

判定标准：连续 24 小时（至少 8 小时）混合负载（对话 + 待机 + 唤醒），RSS 增长 <50 MB/小时且无单调趋势才算通过。

这个标准在干什么：内存泄漏（leak）的定义是「分配了不再归还的内存，且随事件次数无界增长」。它是斜率问题而不是绝对值问题——一条 平稳波动但均值不变的曲线 是健康的，一条斜率恒正的直线 才是泄漏。所以判定用两个量：增速 rate=(RSS末−RSS首)/时长\text{rate} = (\text{RSS}_{\text{末}} - \text{RSS}_{\text{首}}) / \text{时长}rate=(RSS末​−RSS首​)/时长（斜率上限）与趋势检验（末段均值是否显著高于首段）。手算小例：8 小时从 2.1 GB 涨到 2.5 GB → rate =400/8=50= 400/8 = 50=400/8=50 MB/h，恰好压线；若从 2.1 GB 涨到 2.16 GB → 7.5 MB/h，通过。红线 50 MB/h 的来源：按 24 小时连续运行倒推——50×24=1.250 \times 24 = 1.250×24=1.2 GB，是 8 GB 板子可承受的单日漂移上限，再高就会把其他模块的余量吃光。

采样工具链（一个容易踩的坑：别用 ru_maxrss——它是进程历史最高水位，只涨不跌，会把一切正常波动记录成「单调增长」）：

常见泄漏点（按你链路的出现概率排序）：① 音频缓冲/队列只进不出（打断路径没清空）；② 会话历史列表无上限；③ ONNX Runtime session 反复创建不复用；④ 日志句柄。定位用 pmap -x $(pidof assistant) | sort -k3 -n 观察哪个映射段在涨。

2.3 高温降频

RK3588 的温控点（thermal trip point）在大核温度到达 ~85 °C（主线内核里大核簇的 passive 降频点，约 75 °C 先告警）时触发 DVFS 压频，满载且散热一般时很容易触到；降频幅度依散热条件浮动，常见实测掉到标称频率的六七成。所有 CPU 侧延迟随之等比例变慢（RTF 翻倍即首 token 与解码全线上涨）——你的预算表是按冷机测的，热机可能全线破线。防法：

  1. 压测时同时记录 cat /sys/class/thermal/thermal_zone*/temp，把延迟数据按温度分桶；
  2. 主动散热（散热片+风扇）是端侧产品的标配，别省；
  3. 预算表加一行「热机 P95」，与冷机并列报告——面试时主动讲这个，是系统成熟度的证明。

3. 质量压测：分信噪比矩阵

3.1 设计原则

成功率必须按信噪比分层报告，一个总数字没有意义。噪声类型也要覆盖三类真实场景：安静、电视背景（非平稳、含人声）、多人交谈（竞争性人声最难）。

SNR 安静 电视背景 多人场景 判定
30 dB+（近场） ✅ 目标 ≥98% — — 基线
15 dB 目标 ≥95% 目标 ≥85% ≥75% 主力场景
5 dB ≥85% ≥60% 记录即可 边界，报告不承诺

测试集：50 条固定指令 × 每档噪声 3 次重放 = 每档 150 次；噪声按目标 SNR 与指令信号混合（用 pyloudnorm 对齐响度）。

3.2 可运行的压测统计

预期输出：分档成功率 + Wilson 置信区间。

Wilson 区间在干什么：成功率 p=k/np = k/np=k/n 只是点估计——150 次里成功 135 次（90%）的真实成功率可能低到 84.4%，也可能高到 94%，这个「真实值的合理范围」就是置信区间。直接用教科书正态近似 p^±zp^(1−p^)/n\hat{p} \pm z\sqrt{\hat{p}(1-\hat{p})/n}p^​±zp^​(1−p^​)/n​ 在样本少或成功率接近 0/1 时会算出越界的荒谬区间（如 >100%），Wilson 公式通过对分子分母各加一个修正项 z2/(2n)z^2/(2n)z2/(2n) 与收缩因子 1+z2/n1 + z^2/n1+z2/n 把区间约束在 [0,1][0,1][0,1] 内。代码里逐项对应：z=1.96z = 1.96z=1.96（95% 置信）、z2/(2n)z^2/(2n)z2/(2n) 是中心修正、p^(1−p^)/n+z2/(4n2)\sqrt{\hat{p}(1-\hat{p})/n + z^2/(4n^2)}p^​(1−p^​)/n+z2/(4n2)​ 是修正后的标准误。手算小例：n=150,k=135n = 150, k = 135n=150,k=135，p^=0.90\hat p = 0.90p^​=0.90 → 区间约 [84.2%,93.8%][84.2\%, 93.8\%][84.2%,93.8%]；若只测 30 次成功 27 次（同样 90%），区间宽到约 [74.4%,96.5%][74.4\%, 96.5\%][74.4%,96.5%]——样本越少区间越宽，「90%」这个数字本身越没底气，这正是「每档 ≥100 次」纪律的统计学依据。

报告纪律：成功率低于目标的档位不许藏——写明「该档位表现 + 改进方向（前端升级/换阵列）」，诚实的失败分析比虚假的 99% 更值钱。

6. 工程权衡与失效模式

6.1 权衡

  • 压测覆盖度 vs 交付时间：全矩阵（3 噪声 × 3 SNR × 150 次）约一天机时；砍不动的是 15 dB 主力档，可砍的是 5 dB 边界档（只记录不承诺）。
  • 热机预算的取舍：加散热成本 ~20 元 vs 软件降负载（牺牲响应速度）——产品选前者，演示项目两者都记录。
  • 诚实报告的代价：低成功率档位写出来「难看」，但藏着被面试官一问就穿——主动暴露 + 给改进方向才是加分项。

6.2 失效模式（压测阶段特有）

  1. 长跑第 6 小时崩溃：队列泄漏在低负载下不显形。修复：长跑必须混合负载（对话+打断+待机循环），不能只挂机。
  2. 压测数据与演示不一致：压测在安静房间、演示在展厅（嘈杂+回声）。修复：演示前在目标场地跑一遍快速矩阵，备好降噪档位参数。
  3. 置信区间外的结论：30 次样本就写「成功率 90%」。修复：每档 ≥100 次 + Wilson 区间（3.2 已内置断言）。
  4. 埋点本身拖慢系统：日志同步写盘占用大核。修复：埋点只写内存环形缓冲，异步落盘，压测时对比「埋点开/关」的延迟差确认 <5 ms。

7. 延伸思考题（含解析）

Q1：内存泄漏判定为什么用「增速 <50 MB/h 且无单调趋势」而不是「零增长」？
A：真实系统有合法的内存波动（glibc 内存池、音频缓冲随对话长度变化、模型缓存预热）。零增长标准会把正常波动误判为泄漏，也会逼人造假。「增速上限 + 趋势检验」区分的是「无界增长」（真泄漏）与「有界波动」（正常）——24 小时尺度上真泄漏必然露出单调趋势。

Q2：电视背景噪声为什么比同能量的白噪声难？
A：电视噪声是非平稳 + 含人声的：NS 靠统计平稳性估计噪声谱，人声与目标语音频谱高度重叠（都是语音，前端无法区分「哪个人声是主人」）。同能量白噪声反而容易减。这就是多人/电视档成功率天然更低的根因——也是「定向拾音（波束成形）+ 声纹门限」成为下一代前端方向的原因（接上你 Stage 4 的声纹知识）。

Q3：热机测试发现 ASR 段延迟 +40% 破预算，三个修复方向按成本排序？
A：① 加散热（硬件，最便宜，先做）；② ASR 迁 NPU（回填项，降 CPU 负载）；③ 热机时降级策略（如关闭 NS 高阶档）。原则：先物理后算法，先固定项后牺牲体验项。

Q4：「与云端对比」里端侧成功率低 8 个点，怎么向不懂技术的老板/面试官解释这是可接受的？
A：三个事实：① 离线可用（断网/隐私/无月租）是产品前提，云端方案该场景根本不可用，不是同一选项；② 8 个点集中在 5 dB 极端档，主力 15 dB+ 档差距 ❤️ 个点；③ 差距的归因已定位（前端算力），有明确升级路径（NPU 回填）。用「不可用对比」替代「优劣对比」是核心话术。

Q5：如果重做一遍这个项目，最该提前到第 1-2 周做的是什么？
A：埋点与预算校准器。前四周大量时间花在「手工拼凑延迟数据」上——如果第 1 周就把 Trace 类 + 预算校验函数立起来，每周打通一段就自动进表，第 7-8 周的压测报告是自动聚合出来的而非补出来的。可观测性先行，是本项目最大的复盘教训。

1. class vs struct

两者唯一的语法区别：struct 成员默认 public，class 成员默认 private。区别在设计意图：

  • struct：没有不变式要守护的一堆数据（一帧参数包），成员开放、可用聚合初始化 RawConfig c{16000}；
  • class：有不变式要维护（“采样率必须有效”“指针非空”），数据藏起来，只暴露接口。
    语音代码里，配置结构体用 struct；引擎、解码器、缓冲区这类对象用 class。

2. 构造函数与成员初始化列表

构造函数负责"让对象出生即有效"，析构函数是 RAII 的释放点（03 篇）。这里聚焦一个细节：成员初始化列表（冒号后那一段）。它好于在函数体里赋值，因为：

8. 常见坑

  • 写了析构就丢掉隐式移动：编译器不再隐式生成移动构造/赋值，std::move 后退化为深拷贝——要么补齐 Rule of Five，要么 Rule of Zero。
  • 浅拷贝不一定马上崩：两对象共享内存可能"没事"跑很久，直到一方析构、另一方悬空；测试用 -fsanitize=address 当场抓。
  • 拷贝赋值忘记自赋值检查，或先 delete 后 new（分配失败时对象已残废）。
  • 初始化顺序想当然：列表里写 b_(a_ + 1) 不代表 a_ 先初始化——只看声明顺序。
  • explicit 忘加：隐式转换悄悄通过，单位/参数张冠李戴。
  • operator<< 试图写成成员函数：左操作数是流不是本类，必须友元或普通函数。

9. 小结

  • struct 默认 public（数据聚合），class 默认 private（有不变式）；初始化列表是"初始化"不是"赋值"，const/引用成员只能用它，实际顺序 = 声明顺序。
  • 编译器默认逐成员拷贝对裸指针是浅拷贝；手写资源就要凑齐 Rule of Three/Five，能 Rule of Zero 就 Zero。
  • =default/=delete/explicit 是精修工具，const 是调用者能依赖的合同。

10. 自测题

  1. 只手写了析构函数的类，std::move 之后会发生什么？

    答案 编译器不再隐式生成移动构造/赋值，重载决议选中拷贝构造——本想 O(1) 的移动退化成 O(n) 深拷贝。要么补齐 Rule of Five，要么 Rule of Zero。

  2. 拷贝赋值里为什么"先 new 成功、再 delete 旧内存"，而不是反过来？

    答案 若先 delete 再 new，`new` 抛 `bad_alloc` 时数据指针已悬空，对象残废。先分配成功，中途任何异常都不影响原对象完整性（异常安全的基本功）。

  3. 为什么 operator<< 不能写成 Clip 的成员函数？

    答案 成员函数的左操作数永远是本类对象（`*this`），而 `std::cout << clip` 的左操作数是 `std::ostream`。必须是友元/普通函数：`std::ostream& operator<<(std::ostream&, const Clip&)`。

1. 为什么需要移动

05 篇 AudioBuffer 的拷贝构造是：分配新内存 + 复制几百万个采样点，O(n)。但很多场景下源对象马上就要消亡：

临时对象"行将就木"，它手里的堆内存与其复制一份，不如直接把指针抢过来：接管指针、置空对方，几条指令完事，O(1)。这就是移动语义的全部动机。语音引擎里无处不在：音频块沿管道流动（下游接管）、std::vector<AudioBuffer> 扩容搬迁元素（搬指针而非搬数据）、把大缓冲返回给调用者（"上浮"而非深拷贝）。

2. 左值与右值：先建立直觉

值类别初看唬人（glvalue/xvalue/prvalue），先用直觉建地图：

  • 左值（lvalue）：有名字、能取地址、通常能出现在 = 左边——变量 a、*p、返回引用的函数调用。它的"位置"是主角。
  • 右值（rvalue）：临时的、没有名字、即将消亡——字面量 42、表达式 a + b、按值返回的对象、std::move(x) 的结果。它的"内容"是主角，反正马上就没了，随便抢。

再补两个术语（面试用，写代码用不到）：**prvalue（纯右值）**是货真价实的临时对象，如 42、make_buffer() 的返回值；xvalue（将亡值）是本有名字、被标记为"可抢"的对象，如 std::move(a) 的结果。glvalue = lvalue + xvalue（“有位置”），rvalue = prvalue + xvalue（“可移动”）——xvalue 是交点，std::move 干的就是"把左值标成 xvalue"这件事。

3. 右值引用 && 与 std::move 的真相

右值引用 T&&：专门绑定右值的引用——给行将消亡的对象"续命"，并让重载决议能区分"请拷贝我"（const T&）和"请抢走我"（T&&）。

std::move(x) 的真相：它是一个类型转换，一个字节的移动都没做。它只把表达式 x 转成右值，真正"移动"的是随后被选中的移动构造/移动赋值。读代码看到 std::move 应默念：“宣布：我不再需要 x 的内容，可以抢”。

4. noexcept：std::vector 在乎的事

std::vector 扩容时要搬迁所有旧元素。假设搬到一半，某个元素的移动构造抛异常——旧内存里的元素已被掏空，新内存又没搬完，数据损坏且无法回滚。标准库的对策是 std::move_if_noexcept：只有移动构造标了 noexcept，扩容搬迁才用移动；否则退回拷贝（拷贝失败时原 vector 完好）。这就是"移动构造必须写 noexcept"的工程理由——不写，移动语义在容器里形同虚设。

5. 完美转发

问题：包装函数把参数转手给内部函数时，形参 arg 一旦有了名字，它自己就是左值——哪怕调用者传进来的是右值。无脑转发会把所有右值变成左值，白白触发拷贝。解决：万能引用 + std::forward。

  • 万能引用：T&& 出现在模板参数推导语境里时，既能绑左值也能绑右值——传左值 s 时 T 推导为 std::string&，传右值时 T 是 std::string。注意它只在 T 待推导时成立，写死 std::string&& 就是普通右值引用。
  • 引用折叠一句话：& + & = &，& + && = &，&& + && = &&——左值进来 T = string&，T&& 折叠成 string&；右值进来保持 string&&。
  • std::forward<T>(arg)：按 T 里藏的引用信息还原值类别——左值仍转发为左值，右值仍转发为右值。它和 std::move 一样只是类型转换。

8. 常见坑

  • 以为 std::move 会移动：它只是类型转换；类没实现移动操作时，std::move 之后照样走拷贝。
  • 移动构造忘了标 noexcept：容器扩容退回拷贝（第 4 节实测），优化静默失效。
  • 移动构造忘了掏空对方：源指针没置空，两个对象析构时 double-free——比漏拷贝更致命。
  • 对 const 对象 std::move：产生 const T&&，绑不到 T&&，重载决议退回拷贝——白写，编译器可能不警告。
  • 被移动后继续读内容：合法但未指定状态，只能析构或赋新值，读数据是未定义行为。
  • 对右值引用形参再使用时忘了 std::move/std::forward：void f(T&& x) { g(x); } 里 x 是左值；转发场景用 std::forward<T>，确定不要了用 std::move。

9. 小结

  • 移动 = 接管资源而非复制：O(n) 深拷贝变 O(1) 指针偷取；std::move 只是"标记可抢"的类型转换。
  • 移动构造/赋值要 noexcept（否则容器扩容退回拷贝）、要掏空源对象（否则 double-free）；被移动对象是"合法但未指定"状态。
  • 完美转发 = 万能引用 T&& + 引用折叠 + std::forward<T>，emplace_back 是它的头号受益者。
  • 性能要实测：3.8 MB 缓冲区拷贝 ~150 us，移动 ~0 us。

  1. std::move(x) 执行后，x 的内存被释放了吗？

  2. 为什么第 4 节示例 A 中，push_back(CopyOnly(i)) 的第一个操作是"移动"而非"拷贝"？

  3. template <typename T> void f(T&& x); 传入左值 s 时，T 和 x 的类型分别是什么？

2. std::unique_ptr：独占所有权

3. std::shared_ptr：共享所有权

为什么需要它

有些资源确实要共享：ASR 模型的权重加载要几秒，十几个推理任务应该共用同一份，而不是各自加载。“最后一个用完的人负责释放”——这正是引用计数的语义。

控制块与开销（必须心里有数）

shared_ptr 比裸指针多两个东西，合称控制块：

  • 强引用计数：有多少个 shared_ptr 共享这个对象；
  • 弱引用计数：有多少个 weak_ptr 在观察（下一节）。

每次拷贝/析构 shared_ptr 都要对计数做原子操作（加减 + 内存屏障）。所以：

  • 拷贝不是免费的，在极热的循环里按 const& 传 shared_ptr；
  • make_shared<T>(...) 把对象和控制块放进同一次分配，比 shared_ptr<T>(new T(...)) 少一次分配、对缓存也更友好，永远优先用它。

线程安全性（准确表述，面试高频）

  • 引用计数本身是原子的：多个线程同时拷贝/析构各自持有的 shared_ptr 副本，计数不会乱，对象不会提前释放也不会泄漏。
  • 同一个 shared_ptr 对象不是线程安全的：两个线程同时读写同一个 shared_ptr 变量（一个赋新值、一个拷贝）是数据竞争，需要加锁或用 std::atomic<std::shared_ptr<T>>（C++20）。
  • 被管理的对象完全不受保护：shared_ptr<ModelWeights> 只保证"权重在你用的时候活着"，两个线程同时读权重没问题，但一读一写照样要自己加锁。

一句话：shared_ptr 保护"这个对象还存在吗"，不保护"这个对象的内容"。

5. 所有权设计经验法则

  1. 默认 unique_ptr，有理由才升级 shared_ptr。unique_ptr 可以隐式转换成 shared_ptr（反过来不行），先独占后共享的路是通的。
  2. 判断问题只有一个：“这个资源要不要多个主人？” 不需要，就 unique_ptr。语义上"转移"（音频块沿管道流动）是 unique_ptr + std::move。
  3. 接口签名泄露所有权设计：
    • void sink(std::unique_ptr<T> p) —— 接管；
    • T* borrow(...) / const T& borrow(...) —— 只借用，不拥有；
    • void share(std::shared_ptr<T> p) —— 分享一份所有权（按值才计数）。
  4. 函数内部临时计算用 std::vector/值语义即可，不必事事上智能指针。
  5. 看到 shared_ptr 要问一句"这真的需要共享吗"——很多代码库里一半的 shared_ptr 其实只是作者不敢用 unique_ptr；管理 C 接口句柄（如 pa_simple*、FILE*）时给智能指针配自定义删除器，让 RAII 覆盖非内存资源。

6. 常见坑

  • shared_ptr 参数类型不完全一致会偷偷计数：本篇示例里 infer 若声明为 const std::shared_ptr<const ModelWeights>&，传入 shared_ptr<ModelWeights> 会因隐式转换生成一个临时 shared_ptr，use_count 凭空 +1（实测如此）。要么类型写一致，要么直接按值传。
  • 循环引用不报错、不崩溃，只是安静泄漏：ASan 的 LeakSanitizer 通常能报出来，但它依赖"对象不可达"判定——栈上残留指针可能让对象"看起来仍可达"而漏报（本篇泄漏示例因此加了一个冲刷栈的 scrub()）。最可靠的证据永远是：析构函数该跑没跑。
  • use_count() 在多线程下只是近似值：别的线程可能随时增减计数，它适合调试和日志，不适合做业务判断。
  • make_shared 的一个副作用：对象和控制块同一块内存，只要有 weak_ptr 活着，整块内存都不能还——大对象 + 长命 weak_ptr 场景要留意。
  • get() 拿到的裸指针交给别人管理就等于双份所有权：两个主人各自 delete，必然 double-free；shared_ptr<T> a(raw); shared_ptr<T> b(raw); 同理会造出两个独立控制块，双重释放。

7. 小结

  • RAII 的"自动释放"需要载体，智能指针就是标准化的载体：unique_ptr 独占且零开销，shared_ptr 共享但带控制块与原子计数。
  • unique_ptr 表达"转移"，shared_ptr 表达"共用"，weak_ptr 表达"知道但不拥有"，接口签名应当如实反映这三者。
  • shared_ptr 只保证对象存活期，不保护对象内容；引用计数原子，同一个 shared_ptr 变量仍需同步。
  • 循环引用是 shared_ptr 的结构性盲区：所有权单向，回指用 weak_ptr。

自测题

  1. 为什么 unique_ptr 不能拷贝却可以放进 std::vector 并 push_back？

    答案 `push_back` 接收的是右值（临时对象或 `std::move` 的结果），走的是**移动**而非拷贝；容器元素的所有权转移是移动语义，不违反"独占"。直接写 `v.push_back(ptr)`（`ptr` 是左值）才会编译报错，需要 `std::move(ptr)`。

  2. shared_ptr 的引用计数是原子的，那两个线程同时写"同一个 shared_ptr 变量"安全吗？

    答案 不安全。原子性保护的是计数，不保护 `shared_ptr` 变量本身：一个线程赋值、另一个线程同时拷贝它属于数据竞争（未定义行为）。各线程只操作自己持有的副本则完全安全。

  3. 下面的代码泄漏吗？为什么？
    auto w = std::make_shared<int>(42); std::weak_ptr<int> obs = w; w.reset();

    答案 不泄漏。`weak_ptr` 不维持强计数，`w.reset()` 后强计数归零，`int` 的析构函数立即运行、对象宣告死亡，`obs.expired()` 变为 `true`；但注意 `make_shared` 把对象和控制块放在同一块内存里，这块内存要等 `obs` 也析构、弱计数归零后才真正归还。

  4. 音频处理管道中，"采集线程产出的 AudioBlock 交给识别线程，处理完销毁"应该用哪种指针？接口签名怎么写？

    答案 `std::unique_ptr`，队列用 `std::vector>`（或加锁的队列），投递接口 `void enqueue(std::unique_ptr block)`——按值传参表明接管所有权。任何时候不需要两个环节同时"拥有"同一块数据。

detach 为什么危险

detach 之后，你就失去了对这个线程的一切控制：无法等待、无法取消、也不知道它是否还在跑。如果线程还引用着某个已经析构的局部变量或成员，就是悬空引用——比悬空指针更难查，因为它可能"大多数时候恰好没炸"。实战建议：推理引擎里几乎不用 detach()。采集、推理、解码线程的生命周期和引擎一样长，用成员变量持有 std::thread，在析构函数里设置停止标志后 join()；想"启动一个异步任务然后拿结果"，用后面的 std::async 或线程池。

常见坑

  1. 忘记 -pthread：能编译（甚至能链接），但运行时表现怪异或崩溃。凡用了 <thread>/<mutex> 一律加上。
  2. 忘 join 导致 std::terminate；detach + 引用局部变量则造成偶发悬空崩溃，两类都是最难的 bug。
  3. wait 不带谓词：虚假唤醒或通知丢失，消费者永久睡眠。永远写 cv.wait(lock, pred) 两参数版。
  4. 改共享状态没拿锁：状态修改必须在锁内，否则存在"检查-睡眠"窗口丢通知；同理临界区不做重活，推理计算放锁外。
  5. 认为"测试通过 = 没有竞争"：竞争是 UB，-O2 下可能恰好不发作（见第三节真实数据）；用 atomic 保护复合操作同理——两个 atomic 变量的更新合在一起不是原子的，该上锁还是要上锁。

小结

  • 推理引擎 = 采集线程 + 推理线程 + 后处理线程，靠线程安全队列交接数据；音频实时流不容许单线程串行。
  • std::thread 销毁前必须 join() 或 detach()；引擎生命周期线程用成员变量 + 析构时 join，不用 detach。
  • 多线程共享的普通变量并发写是 UB；单变量计数用 std::atomic，复合逻辑用 std::mutex + RAII 锁（lock_guard / unique_lock）。
  • 生产者-消费者：mutex 保队列，wait(lock, pred) 保等待，"队列空 + 收工标志"保退出；多锁场景统一顺序或用 C++17 std::scoped_lock。async/future/promise 是"后台任务 + 取结果"三件套，call_once 保证一次初始化；第 13 篇将把这些与模板、RAII 组装成真正的 RingBuffer。

项目 A：线程安全音频环形缓冲区 RingBuffer

需求与设计

字节对齐的坑：为什么不能闭眼 read 结构体

最直觉的写法是定义一个和文件布局一模一样的结构体（完整定义见下面的 wav_parser.cpp），一次 file.read(&hdr, sizeof(hdr)) 灌进去。

坑在哪：编译器为了让 4 字节成员落在 4 的倍数地址上，会在成员之间塞填充字节。比如把 fmt_size（4 字节）和两个 uint16_t 的排列稍作调整，sizeof 就可能从 44 变成 48——一次读 48 字节，后面所有字段整体错位 4 字节，采样率读出来是个天文数字。

三种对策（按推荐程度）：1. 逐字节组装（本项目采用，完全可移植）——read_u32_le(p) = p[0] | p[1]<<8 | p[2]<<16 | p[3]<<24，自己控制每一个字节，顺带把大小端问题一并解决；2. #pragma pack(1)——告诉编译器禁止填充，sizeof 强制为 44，跨编译器需配合 #pragma pack(push,1) ... #pragma pack(pop) 使用，且某些架构上非对齐访问有性能或崩溃代价；3. memcpy 逐字段搬运——读原始字节缓冲区再 memcpy 到各字段，本质和方案 1 相同。

本项目两个都用：结构体映射做"教学演示"，逐字节组装做"可移植复核"，并让 static_assert(sizeof(WavHeader) == 44) 把"我的编译器没有塞填充"这件事从假设变成编译期事实——一旦某天换编译器/换平台出现填充，程序直接编译不过，而不是运行时读出乱码。

常见坑

  1. 忘了 close() 就结束生产者：消费者在"样本不够"的 wait 里永久睡死。收工协议（标志 + notify_all）必须成对出现。RingBuffer 容量小于帧长同理：size_ + n <= capacity 永远不成立，双方互相等待，容量至少是帧长的若干倍（本例 4096 >> 480）。
  2. 实时线程里 new/vector 扩容：音频回调中堆分配可能带来毫秒级卡顿，RingBuffer 构造时一次分配固定容量的意义就在于此。
  3. 把 WAV 头结构体 read 进去就信了：填充字节、字节序、字段缺失（有些 WAV 的 fmt 块不是 16 字节、头不止 44 字节）都会让解析错位。生产代码要循环解析 chunk（本教程的最小版只处理 44 字节标准头），并保留逐字节组装这条后路。删掉 static_assert 更糟——错误被推迟到运行时的乱码。
  4. 16-bit 样本忘记归一化：直接把 int16_t 当浮点特征喂给模型，数值范围差 3 万倍。先除以 32768。
  5. CMake 忘记链接线程库：链接期报 pthread_create 未定义。find_package(Threads REQUIRED) + Threads::Threads 是标准解法。

  • WAV 头是逐字段定义的二进制格式；解析二进制的两条正路是"逐字节组装（最可移植）“和”#pragma pack(1) / memcpy（要防填充）"，static_assert(sizeof == 44) 把布局假设钉死在编译期。

自测题

  1. RingBuffer 里如果删掉 size_，改用 head_ == tail_ 判断，会遇到什么经典问题？
  2. pop_frame 的 wait 谓词是 size_ >= n || closed_。如果写成只有 size_ >= n，生产者 close() 后消费者会发生什么？
  3. 为什么 WAV 头结构体在某些编译器下 sizeof 会大于 44？本项目用哪两个手段防御？
  4. read_u32_le 为什么要逐字节组装，而不能 *reinterpret_cast<const uint32_t*>(p) 一把读？
  5. 16kHz、16-bit、双声道的 WAV，byte_rate 和 block_align 各是多少？
  6. 本例 16000 个样本只读出 33 帧共 15840 个样本，剩下的去哪了？真实引擎里通常怎么处理？

答案

  1. 空和满时 head 都可能等于 tail，无法区分；要么牺牲一个槽位，要么像本项目一样额外维护 size_。
  2. close() 只会唤醒等待者，但谓词仍为 false，消费者会继续睡死（新样本永远不会来了），程序挂住不退出。谓词里的 closed_ 加上"唤醒后重查"才是完整退出条件。
  3. 编译器会在成员间插入填充字节使成员对齐到自身大小的倍数地址。防御：static_assert(sizeof(WavHeader) == 44)（编译期哨兵）+ 逐字节组装 read_u16_le/read_u32_le（不依赖结构体布局）。
  4. 逐字节组装不受结构体填充、编译器对齐策略影响，还显式定义了字节序（WAV 是小端）；直接指针重解释假定"对齐正确 + 主机是小端"，换平台就可能出错甚至崩溃。
  5. block_align = 2 声道 × 2 字节 = 4 字节/帧；byte_rate = 16000 × 4 = 64000 字节/秒。
  6. 最后 160 个样本不足一个 480 样本的帧，pop_frame 在 closed_ 后因 size_ < n 返回 false 被丢弃。真实引擎通常补零凑满一帧送模型，或在结果侧丢弃该不完整帧。

1. 第一性原理：ASR 的根本矛盾——对齐未知

1.1 问题定义

ASR 要学的是条件分布：给定音频特征序列 x=(x1,…,xT)\mathbf{x} = (x_1, \dots, x_T)x=(x1​,…,xT​)（TTT 帧，每秒约 100 帧），输出文字序列 y=(y1,…,yU)\mathbf{y} = (y_1, \dots, y_U)y=(y1​,…,yU​)（UUU 个字符/子词）。

根本矛盾：TTT 与 UUU 不仅不相等，而且对应关系未知。一句 3 秒的"你好"：T≈300T \approx 300T≈300 帧，U=2U = 2U=2 个字。哪些帧对应"你"、哪些对应"好"？标注数据只给了整句文字，没给逐帧对齐。这个"对齐缺失"问题，是三代技术各自回答的核心。

2. 前代方案：HMM-GMM 为什么被淘汰

2.1 流水线结构

传统 ASR 是三个独立模型的拼接：

w^=arg⁡max⁡wP(w)⋅P(x∣w)\hat{w} = \arg\max_w P(w) \cdot P(\mathbf{x} \mid w) w^=argwmax​P(w)⋅P(x∣w)

  • 声学模型 P(x∣w)P(\mathbf{x}\mid w)P(x∣w)：GMM 估计每个 HMM 状态发射特征的概率；
  • 发音词典：词 → 音素序列的映射；
  • 语言模型 P(w)P(w)P(w)：N-gram 统计。

解码用 WFST（加权有限状态转换器）把三者编译成一张大搜索图，Viterbi 找最优路径。

2.2 被淘汰的三个原因

  1. 模型容量弱：GMM 无法学习深层非线性特征，必须手工设计特征（MFCC——第 3 周讲过它正是为此而生）；
  2. 误差级联：三模块独立优化，接口处损失无法端到端反传；
  3. 工程复杂：对齐、聚类、决策树等大量手工流程。

深度学习的胜利在于：一个神经网络端到端，从原始特征直接学映射。但"对齐未知"仍在——CTC 与 Attention 是两条端到端的破局路线。

3. CTC：用边缘化消灭对齐标注

3.1 核心思想

既然不知道对齐，那就对所有可能的对齐求和（边缘化）。CTC 引入一个特殊的空白符（blank, ϵ\epsilonϵ），允许：

  • 帧可以发射空白（“这一帧不属于任何字符”）；
  • 同一字符可以连续发射多次（“好——好"折叠成一个"好”）。

定义折叠函数 B\mathcal{B}B（collapse）：把一条路径映射成最终文字。例如路径 π=(ϵ,你,你,ϵ,好)\pi = (\epsilon, 你, 你, \epsilon, 好)π=(ϵ,你,你,ϵ,好) 折叠为 B(π)=(你,好)\mathcal{B}(\pi) = (你, 好)B(π)=(你,好)。精确定义见下面的大白话拆解——"合并重复"与"去空白"的先后顺序是 CTC 最容易理解错的地方。

这个折叠规则在干什么？用大白话拆开看：一条"路径"就是每帧各选一个符号（或空白）的完整决定序列。折叠规则回答的是"这串逐帧决定最终念出来是什么"（Graves et al., 2006 的定义：先合并路径上相邻的重复符号，再删掉 blank，例：B(a−ab−)=B(−aa−−abb)=aab\mathcal{B}(a{-}ab{-}) = \mathcal{B}({-}aa{-}{-}abb) = aabB(a−ab−)=B(−aa−−abb)=aab）：

  • blank 是呼吸/静音/过渡帧：这一帧不属于任何字，念出来等于没念；
  • 相邻重复才合并：同一字符连续出现两次视为"一个字拖长了"，折叠成一次；
  • blank 是分隔符：被 blank 隔开的两个相同符号不会合并——想输出"好好"两个字，路径必须写成"好、blank、好"；而相邻的"好好"会折叠成一个"好"。这是 blank 存在的根本理由（思考题 Q1 的答案）。

3.5 解码：贪心与束搜索

训练边缘化所有路径，推理要找出最优路径：

  • 贪心：每帧取 argmax，再折叠。快，但忽略序列整体概率；
  • CTC beam search：保留 top-k 前缀路径，考虑"重复字符合并"与"空白跨越"的概率合并。精度更高。

4. Attention-based Seq2Seq：另一条路

4.1 LAS（Listen, Attend and Spell）

不边缘化对齐，而是用注意力隐式学对齐：Encoder 读音频，Decoder 自回归生成文字，每步用 cross-attention 看向音频的某个区域。对齐由注意力权重自动涌现，无需空白符。

优势：建模标签间依赖（语言模型内置）、无条件独立假设。
劣势：自回归——逐字生成，延迟随句长线性增长；且注意力可能重复/跳字。

4.2 CTC + Attention 联合（Hybrid）

ESPnet 的标准配方：两个损失加权

L=λLCTC+(1−λ)LAtt,λ≈0.3\mathcal{L} = \lambda \mathcal{L}_{\text{CTC}} + (1-\lambda)\mathcal{L}_{\text{Att}}, \quad \lambda \approx 0.3 L=λLCTC​+(1−λ)LAtt​,λ≈0.3

CTC 帮助对齐快速收敛、Attention 负责语言流畅；解码时两者分数融合（shallow fusion）。

5. 非自回归（NAR）：Paraformer 与 CIF

5.1 为什么需要快

自回归每生成一个字都要一次前向。端侧芯片算力有限，一句话 10 个字就是 10 次串行前向——延迟不可接受。**非自回归（NAR）**一步并行输出所有字。

5.2 难题：输出长度未知

并行输出要求预先知道 UUU（输出多少个字），但 UUU 正是未知的。Paraformer 的答案是 CIF（Continuous Integrate-and-Fire）。

5.3 CIF 机制（直觉版）

CIF 给每帧预测一个"发射权重" wt∈[0,1]w_t \in [0,1]wt​∈[0,1]（该帧承载多少字符信息），沿时间累积积分：

acct=acct−1+wt\text{acc}_t = \text{acc}_{t-1} + w_t acct​=acct−1​+wt​

当累积量 acct≥1\text{acc}_t \ge 1acct​≥1 时"开火"（fire）——表示攒够了一个字的信息，触发一次输出，并把累积量减 1 继续。总开火次数 ≈ 字数 UUU。这个公式在干什么：它把"该输出第几个字了"变成了一个积分器——wtw_twt​ 是每帧往水杯里注的水量，水位（累积量）每到 1 就倒出一杯（发射一个字）。对比 CTC：CTC 每帧硬性发射一个符号（离散），CIF 允许信息跨帧连续累积，所以叫"连续积分发射"。

  1. 模型自己预测出输出长度 UUU（开火次数）；
  2. 每次开火位置的声学特征被提取为该字的表示，并行解码。

于是 NAR 一步生成 UUU 个字，速度是自回归的数十倍——这也是 SenseVoice 官方宣称"推理速度约为 Whisper-large 的 15 倍"的根源之一（第 3 周细看官方数据）。

6. 工程权衡与失效模式

6.1 权衡

  • CTC 条件独立：帧间独立假设丢弃了标签依赖，纯 CTC 模型语言流畅度差 → 需要外挂 LM 或换 Attention。
  • AR vs NAR：质量 vs 延迟的直接交换。云端追求质量用 AR（Whisper），端侧追求延迟用 NAR（Paraformer/SenseVoice）。
  • beam 宽度：宽 → 精度↑、延迟↑。端侧常用贪心或极小 beam。

6.2 失效模式

  1. CTC 重复坍缩：模型学会几乎全发射空白或反复同一字符。症状：输出大量重复或缺失；根因：训练初期对齐未收敛或梯度问题；修复：联合 Attention 损失、检查学习率。
  2. Attention 跳字/重复：注意力对齐漂移。症状：漏词或循环重复；修复：注意力约束、联合 CTC。
  3. NAR 长度误差：CIF 开火次数 ≠ 真实字数 → 整句漏/多。症状：特定长度句子系统性错误；修复：长度校准、混合解码。
  4. 长音频幻觉（Whisper 特有）：30 秒窗口下，静音段被"脑补"出文字。修复：VAD 分段、温度回退解码。

7. 延伸思考题（含解析）

Q1：为什么 CTC 要在标签之间强制插入空白符？直接允许重复不行吗？
A：空白符区分"同一字符的连续重复"与"两个独立字符"。没有空白，无法表达"啊啊"（两个字）与"啊"的长音之间的区别——折叠函数无法区分路径 (啊,啊) 该折成一个还是两个。空白提供了必要的分隔符号。

Q2：CTC 前向算法的复杂度是多少？为什么比暴力枚举可行？
A：DP 表格只有 T×(2U+1)T \times (2U+1)T×(2U+1) 个格子（2U+12U+12U+1 为扩展标签长度），每格最多合并 3 条来路，故复杂度 O(T⋅U)O(T \cdot U)O(T⋅U)；暴力枚举是 O((∣V∣+1)T)O((|V|+1)^T)O((∣V∣+1)T)。动态规划利用折叠的最优子结构（前缀路径的折叠只取决于前缀）把指数级压到线性级——与 HMM 前向、注意力 DP 同源的思想。

Q3：为什么实现必须在 log 域？不用会怎样？
A：α\alphaα 是大量小于 1 的概率连乘，几十帧后就下溢为 0（float 最小约 1e-308）。log 域把乘法变加法，避免下溢，且 log-sum-exp 数值稳定。

Q4：Paraformer 的 CIF 如何同时解决"长度未知"和"并行解码"两个问题？
A：积分发射机制让总开火次数自然等于预测字数 UUU（解决长度未知），每个开火点的特征独立解码（支持并行）。一步前向出全句。

Q5：端侧离线助手为什么选 SenseVoice-Small（NAR）而不是 Whisper？
A：① NAR 单步解码延迟近恒定，适配算力受限的 NPU/CPU；② SenseVoice 针对中文优化且附带标点/情感多任务；③ 显存/内存占用小。代价是极端长尾质量略逊，但端侧交互场景可接受。

本周要回答的四个问题

  1. 一段 30 秒音频，如何一步步变成 1500 个 Encoder Token？每一步的 Shape 是什么？
  2. <|transcribe|>、<|zh|> 这些特殊 token 如何用一个模型统一 99 种语言 + 翻译 + 时间戳？
  3. 手写推理循环里，KV cache 到底缓存了什么？为什么必须有它？
  4. Whisper 的尺寸谱系（tiny→large）如何决定云/端的部署边界？

对应学习计划：第 2 周。交付物：不用 pipeline，手写完整 Whisper 推理循环，打印每步 Tensor Shape，与官方输出对齐，记录 CPU/GPU 的 RTF。

1. 第一性原理：用"弱监督大数据"暴力破解鲁棒性

1.1 前代瓶颈

Whisper 之前的 ASR 是"窄而精"：在干净、标注严格的域内数据上做到极致（如 LibriSpeech 2.7% WER），但换域即崩——口音、噪声、专业术语、低资源语言下性能暴跌。根因：训练数据太干净、太单一，模型学到了数据集的偏置而非"听觉能力"本身。

1.2 Whisper 的答案

OpenAI 收集了 68 万小时的多语言、带字幕互联网音频（弱监督：字幕不精确、有噪声；论文为 Radford et al., 2022, arXiv:2212.04356），不做精细清洗，而是用足够大的模型硬吃这些数据。核心洞察：

数据多样性×数据规模  ≫  标注精度\text{数据多样性} \times \text{数据规模} \;\gg\; \text{标注精度} 数据多样性×数据规模≫标注精度

这个式子在说什么：它不是数学等式，而是一句工程判断——对鲁棒性而言，数据的覆盖面（口音、噪声、领域）和总量，比每条标注的精确度重要得多。Whisper 团队有意放弃"清洗到 LibriSpeech 那么干净"，换来的是换域不崩。后缀事实：后续的 large-v3（2023-11 发布）更是用 100 万小时弱标注 + 400 万小时伪标注（用 large-v2 打的标签）继续验证这条路线。

结果是一个对噪声、口音、领域都鲁棒的通用模型。这个"数据工程优先于模型精巧"的思路，与 VLM 时代的大规模弱监督预训练一脉相承。

1.3 多任务统一：用特殊 token 编程

Whisper 不用多个模型，而是用任务控制 token 在解码起始处指定行为。解码总是从 <|startoftranscript|> 开始，随后依次给出：

⟨∣startoftranscript∣⟩  ⟨∣zh∣⟩  ⟨∣transcribe∣⟩  ⟨∣notimestamps∣⟩  →  文字\langle|\text{startoftranscript}|\rangle \;\langle|\text{zh}|\rangle \;\langle|\text{transcribe}|\rangle \;\langle|\text{notimestamps}|\rangle \;\to\; \text{文字} ⟨∣startoftranscript∣⟩⟨∣zh∣⟩⟨∣transcribe∣⟩⟨∣notimestamps∣⟩→文字

这行式子在干什么：它是给解码器的"程序指令行"。Decoder 是自回归的，每一步都在预测下一个 token——把语言、任务、时间戳开关做成词表里的特殊 token，等于让"输出什么"变成生成序列的一部分，模型自己"读"到 <|transcribe|> 就走转写分支，读到 <|translate|> 就走翻译分支：

  • <|en|> <|zh|> 等语言标签（99 种）→ 控制输出语言；
  • <|transcribe|> vs <|translate|> → 转写原语言，还是翻译成英文；
  • <|notimestamps|> 或省略它 → 是否输出 <|0.00|> 形式的时间戳 token。

一个模型、多种行为，全靠前缀 token 条件化——这就是"用 token 编程"。

2. 架构与数据流：逐步追踪 Shape

2.1 整体结构

Whisper 是标准的 Encoder-Decoder Transformer（不是纯 Decoder）：

波形→Log-Mel→CNN 下采样→Encoder→Decoder (AR)文字\text{波形} \xrightarrow{\text{Log-Mel}} \xrightarrow{\text{CNN 下采样}} \xrightarrow{\text{Encoder}} \xrightarrow{\text{Decoder (AR)}} \text{文字} 波形Log-Mel​CNN 下采样​Encoder​Decoder (AR)​文字

2.2 特征提取：30 秒 → (80, 3000)

  • 输入固定 30 秒（不足补零，超过切段）；
  • 16 kHz × 30 s = 480000 样本；
  • 25 ms 窗、10 ms 移（win_length=400、hop_length=160、n_fft=400）的 80 维 Log-Mel → (80,3000)(80, 3000)(80,3000)。

Shape 怎么来的：帧数 = 480000/160=3000480000 / 160 = 3000480000/160=3000——特征提取器把"每 10 ms 一帧"拍平成除法；808080 是 Mel 滤波器组个数（第 1 周 Stage 1 的 Mel 频谱知识在此落地）。tiny 到 medium 都用 80 维；large-v3 改用 128 维，这是 v2→v3 少数的输入侧改动。所以完整的输入 shape 是 (1,80,3000)(1, 80, 3000)(1,80,3000)（batch=1），这就是官方 WhisperFeatureExtractor 输出的形状。

2.3 CNN 下采样 2×：(80, 3000) → (1500, d)

两层一维卷积 + GELU：第一层步长 1（kernel 3），第二层步长 2（kernel 3），整体时间维减半：

(80,3000)→Conv1, stride 1(dmodel,3000)→Conv2, stride 2(1500,dmodel)(80, 3000) \xrightarrow{\text{Conv1, stride 1}} (d_{\text{model}}, 3000) \xrightarrow{\text{Conv2, stride 2}} (1500, d_{\text{model}}) (80,3000)Conv1, stride 1​(dmodel​,3000)Conv2, stride 2​(1500,dmodel​)

这两层卷积在干什么：Transformer 的注意力是 O(L2)O(L^2)O(L2) 的，3000 长度太贵；先用步长 2 的卷积把时间维砍半（3000→1500），同时把 80 维 Mel 通道混合升维到 dmodeld_{\text{model}}dmodel​——相当于"免费"的一层局部特征提取（类比 Stage 1 学过的滤波器组+降采样）。dmodeld_{\text{model}}dmodel​ 随尺寸变化（small=768, large=1280）。

随后加上正弦（sinusoidal）位置编码送入 Encoder——注意这是固定公式生成的正弦表，不是可学习参数（官方 whisper/model.py 中 Encoder 的 positional_embedding 是注册的 buffer；可学习位置编码在 Decoder 那一侧，易混淆，面试常考）。

2.4 Encoder 与 Decoder

  • Encoder：标准 Transformer 块（Pre-LN 前置层归一化 + 末端 LayerNorm），输出 (1500,d)(1500, d)(1500,d)；
  • Decoder：自回归生成，通过 cross-attention 看 Encoder 输出，自注意力带 KV cache。

Shape 链小结（以 small 为例，d=768d=768d=768）：

480000⏟样本→(80,3000)⏟Log-Mel→(1500,768)⏟Encoder 输入→(1500,768)⏟Encoder 输出→Decoder\underbrace{480000}_{\text{样本}} \to \underbrace{(80, 3000)}_{\text{Log-Mel}} \to \underbrace{(1500, 768)}_{\text{Encoder 输入}} \to \underbrace{(1500, 768)}_{\text{Encoder 输出}} \to \text{Decoder} 样本480000​​→Log-Mel(80,3000)​​→Encoder 输入(1500,768)​​→Encoder 输出(1500,768)​​→Decoder

自测题（第 6 周验收原题）：30 秒音频经 2× 下采样后 Encoder 序列长度 = 3000/2=15003000/2 = 15003000/2=1500。

3.1 为什么要手写

pipeline 把特征提取、解码、KV cache 全藏起来了。手写一遍你才能回答面试必问的"KV cache 怎么管理"“解码每步算什么”。下面用 transformers 的模型权重，但自己写循环。

关键观察点（务必在代码里打印验证）：

  1. KV cache 的作用：第一次 generate_step 输入整段起始序列，之后每步 input_ids 只有 1 个新 token——因为历史 key/value 已缓存。若无 cache，每步要重新前向整个已生成序列，复杂度从 O(U)O(U)O(U) 变 O(U2)O(U^2)O(U2)。
  2. cross-attention 的 KV：每步都要看 Encoder 的 1500 帧输出，这部分也被缓存。
  3. 强制解码：前几步按 forced_decoder_ids 锁定语言/任务 token，保证输出是中文转写而非翻译。

3.2 与官方输出对齐验证

4. 尺寸谱系与部署边界

模型 参数量 Mel 维 Encoder 层/宽 典型场景
tiny 39 M 80 4 / 384 极端端侧、唤醒级
base 74 M 80 6 / 512 轻量端侧
small 244 M 80 12 / 768 端侧/边缘（本教程用）
medium 769 M 80 24 / 1024 云端高质量
large-v3 1550 M 128 32 / 1280 云端最高精度

（参数量与层数/宽度出自 Whisper 论文 [Radford et al., 2022] Table 及 large-v3 模型卡。）

large-v3（2023-11 发布）相对 large-v2 的三处变化：① Mel 特征从 80 维换成 128 维；② 词表新增粤语（Cantonese）语言 token；③ 训练数据扩充到 100 万小时弱标注 + 400 万小时伪标注（large-v2 打标）。语言仍为 99 种。若你用 large-v3，processor 会自动用 128 维特征，但自研前端代码要相应改 n_mels——这是迁移时最常踩的坑。

部署边界经验：端侧 NPU/CPU 通常止于 small；medium 以上需要 GPU（2024-10 的 large-v3-turbo 把 decoder 从 32 层砍到 4 层、参数量降到 809M，是云端兼顾速度的新选择）。这也解释了你的结课项目为何选 SenseVoice-Small（NAR，端侧友好）而非 Whisper-medium。

5. 推理细节工程

5.1 长音频处理：VAD + 分段

Whisper 单次只吃 30 秒。长音频需：

  1. VAD 分段：按静音切成 ≤30 秒片段；
  2. 逐段识别 + 时间戳对齐：每段带 timestamps 输出，拼回全局时间轴。

不分段直接滑窗会在窗口边界切断词语，产生拼接错误。

5.2 解码策略

  • 贪心：快，端侧用；
  • beam search：官方 CLI 默认 beam_size=5（且仅在温度为 0 时启用；transformers 的 generate 默认贪心，需手动传 num_beams），更稳，云端用；
  • 温度回退：置信度低时升温重试，抑制幻觉。

5.3 时间戳头

Whisper 用专门的时间戳 token（<|0.00|>…<|30.00|>，0.02 s 粒度）而非回归头。开时间戳模式时解码在文字与时间戳 token 间交替。

6. 工程权衡与失效模式

6.1 权衡

  • 30 秒窗口：固定窗口简化训练与位置编码，但长音频必须分段，引入边界问题；
  • AR 解码：质量高但延迟随长度增长——这正是 NAR（下周）要解决的；
  • 模型尺寸：精度随尺寸单调上升，但端侧算力/内存是硬约束。

6.2 失效模式

  1. 静音段幻觉：无语音输入时，模型"脑补"出重复文字或训练集片段。定位：看输入是否接近静音；修复：VAD 预过滤、温度回退、设置 condition_on_previous_text=False。
  2. 长文本重复循环：自回归陷入重复。修复：repetition penalty、no_repeat_ngram。
  3. 跨语言误判：中英混读时语言检测错误。修复：显式指定 language。
  4. 时间戳漂移：长音频分段拼接后时间戳错位。修复：以 VAD 全局时间为基准对齐。

7. 延伸思考题（含解析）

Q1：30 秒 16 kHz 音频，Encoder 输入序列长度是多少？怎么算？
A：30s×100帧/s=300030\text{s} \times 100\text{帧/s} = 300030s×100帧/s=3000 帧（Log-Mel），经 2× 下采样 = 1500 个 Encoder token。

Q2：KV cache 缓存了什么？没有它解码复杂度如何变化？
A：缓存已生成步的 Decoder 自注意力 key/value 与 cross-attention key/value。有 cache 每步只算新 token（O(1)O(1)O(1) 增量）；没有则每步重算整个前缀，总复杂度 O(U2)O(U^2)O(U2)。

Q3：为什么 Whisper 用固定 30 秒窗口而不是变长？
A：固定长度简化批处理与位置编码、训练高效；代价是长音频需分段。工程上通过 VAD 分段弥补。

Q4：特殊 token 如何做到"一个模型多任务"？如果让你加一个"输出带标点"的任务，怎么设计？
A：在解码起始处增加一个任务控制 token（如 <|punct|>），用带标点的字幕数据微调，让模型学会该前缀下输出标点。本质是条件化生成。

Q5：为什么 Whisper 在噪声下比传统模型鲁棒？
A：68 万小时弱监督互联网数据覆盖了海量真实噪声、口音、领域，模型学到的是泛化的听觉-文本映射而非干净域偏置。数据多样性是鲁棒性的来源。

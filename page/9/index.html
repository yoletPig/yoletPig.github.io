第 2 周教程：调度器与连续批处理状态机

本周要回答的三个问题

  1. vLLM V1 调度器的 waiting/running 队列怎么迁移？抢占（preemption）的 recompute 与 swap 各在什么时候用？
  2. chunked prefill 的"预算"是什么？它为什么能改善 TTFT 长尾，代价又是什么？
  3. Prefill 和 Decode 的计算特性差在哪？为什么这催生了 PD 分离（Disaggregated Serving）？

对应学习计划：第 2 周。交付物：云上压测对比——vLLM vs SGLang，三组负载 {长 prefill 短 decode、短 prefill 长 decode、混合}，测吞吐、TTFT P50/P99、TPOT，解释什么负载形状下谁更强。

1. 第一性原理：调度器是"显存、算力、延迟"三者的仲裁者

1.1 调度器要解决的问题

推理服务同时收到很多请求，每个请求有自己的生命周期（排队→prefill→decode→完成）。调度器要在每一步决定：

  • 哪些请求进 GPU 跑（受显存和算力限制）；
  • 谁先谁后（影响延迟公平性）；
  • 显存不够时牺牲谁（抢占策略）。

这本质是一个在线资源分配问题——请求到达不可预知，决策必须实时做。

1.2 批处理的演进（一条主线）

static batching→continuous batching→chunked prefill→PD 分离\text{static batching} \to \text{continuous batching} \to \text{chunked prefill} \to \text{PD 分离} static batching→continuous batching→chunked prefill→PD 分离

  • Static batching：凑够一批一起跑，全批结束才接新请求。短请求等长请求，浪费严重；
  • Continuous batching：每一步（每个 decode iteration）都可插入新请求、移出完成请求——以 iteration 为粒度动态组批。这是现代引擎的基石；
  • Chunked prefill：把长 prefill 切块，与 decode 混在同一步执行，避免 prefill 阻塞 decode；
  • PD 分离：prefill 与 decode 拆到不同机器池，各自优化。

每一步演进都在解决前一步暴露的干扰或浪费问题。

2. vLLM V1 调度器内部

2.1 两个队列

  • waiting：已到达、还没开始（或等待显存）的请求；
  • running：正在 GPU 上迭代的请求。

每步调度的核心动作：从 waiting 取请求**准入（admit）**进 running，前提是显存（KV 块）和预算够。

2.2 准入判断（能不能进）

一个新请求进 running 需要：

  1. 有空闲 KV 块容纳它的 prompt（prefill）+ 预留的生成空间；
  2. 总 token 数不超过 max-num-batched-tokens（单步算力预算）；
  3. 并发数不超过 max-num-seqs。

任一不满足，请求留在 waiting（排队）。

2.3 抢占（Preemption）

当 running 里的请求持续增长、显存耗尽，而又有更高优先级需求时，调度器会抢占某个请求，把它踢出 running。理论上两种手段：

  • recompute（重算）：直接丢弃该请求的 KV，之后重新 prefill。省显存（立即释放全部块），但浪费已算的计算；
  • swap（换出）：把 KV 块换到 CPU 内存，之后换回。保留计算，但占 PCIe 带宽、有换入换出开销。

版本事实（重要）：V1 引擎里 swap 模式已被移除——抢占一律 recompute（实测 V1 架构下重算的开销反而更低，swap 队列整体删除；--preemption-mode swap 在 V1 不受支持）。swap vs recompute 的权衡仍是理解 V0 与其他引擎（以及面试）的好素材，但在新版 vLLM 上做实验时看到的只会是 recompute。旧版 V0 中的 --swap-space（每卡预留的 CPU 换出空间，默认 4 GiB）只在 V0 生效。

2.4 手写最小调度状态机（帮助理解）

预期：短请求 2 先完成，中途插入的请求 3 也能及时进入——这正是连续批处理相对 static batching 的核心价值。

3. Chunked Prefill：把 prefill 切块

3.1 问题：长 prefill 阻塞 decode

一个 8k token 的 prefill 是算力密集的大矩阵乘，执行时间长（几百毫秒）。若整段执行，期间所有 decode 请求都在等——TPOT 抖动、decode 长尾。

3.2 解法：预算内切块

把长 prefill 切成小块（如每块 ≤ max-num-batched-tokens 的预算），每步只做一块，剩余下一步接着做。这样每步的 prefill 工作量被限制，与 decode 共存：

每步=decode tokens⏟所有 running 请求+一块 prefill⏟≤预算\text{每步} = \underbrace{\text{decode tokens}}_{\text{所有 running 请求}} + \underbrace{\text{一块 prefill}}_{\le \text{预算}} 每步=所有 running 请求decode tokens​​+≤预算一块 prefill​​

3.3 收益与代价

  • 收益：TTFT 长尾改善（没有超长 prefill 独占）；decode 延迟更平稳；
  • 代价：长 prompt 的总 prefill 时间可能略增（被切多步、与 decode 抢算力）；预算调小 → 干扰少但 prefill 更慢。

--enable-chunked-prefill 与 --max-num-batched-tokens 共同控制。这是"延迟平滑度"与"prefill 吞吐"的权衡旋钮。

版本注意：V1 引擎中 chunked prefill 默认开启（旧版 V0 才需要显式传 --enable-chunked-prefill，该开关在 V1 已趋废弃）。V1 里 --max-num-batched-tokens 默认 8192，是控制每步预算的主旋钮。

4. PD 分离（Disaggregated Serving）

4.1 Prefill vs Decode 的根本差异

Prefill Decode
计算特性 大矩阵乘，算力瓶颈 逐 token 生成，访存瓶颈
GPU 利用 算力打满 带宽打满、算力闲置
延迟敏感 TTFT TPOT

两者争抢的资源不同、优化方向相反。混在同一卡上，互相干扰（prefill 吃算力拖慢 decode，decode 吃带宽拖慢 prefill）。

4.2 PD 分离的思路

把两类负载拆到不同的机器池：

  • Prefill 池：算力优化（甚至用不同的批大小/引擎配置）；
  • Decode 池：带宽优化；
  • 中间通过高速网络传 KV cache（prefill 算完的 KV 传给 decode 池）。

代表工作：DistServe（按 goodput 优化分离）、Mooncake（KV cache 为中心的分离架构）。

4.3 收益与代价

  • 收益：两类负载各自最优，整体 goodput（满足 SLO 的吞吐）提升；
  • 代价：需要跨机传 KV（网络带宽/延迟成本）；运维复杂（两套池、调度协同）。

短 prompt 场景 KV 传输开销占比高，分离收益小；长 prompt + 高并发场景收益最大。

5. SGLang 调度器对照：RadixAttention 与 cache-aware

5.1 与 vLLM 的核心差异

第 1 周讲过：SGLang 用 Radix Tree 主动管理前缀，调度器 cache-aware——把共享前缀的请求排在一起，最大化 KV 复用。

5.2 调度差异的实际影响

  • 多轮对话 / 共享系统提示词场景：SGLang 的前缀命中率高，prefill 省、延迟低；
  • 前缀完全随机的场景：两者接近，差异主要在各自实现细节。

这是"什么负载选什么引擎"的关键判据之一（本周压测会量化）。

7. 工程权衡与失效模式

7.1 权衡

  • chunked prefill 预算：小 → 干扰少但 prefill 慢；大 → 反之；
  • 抢占策略：recompute 省显存费算力，swap 反之；按序列长度与 CPU 内存选；
  • PD 分离：长 prompt 高并发才划算，短场景传输开销不划算。

7.2 失效模式

  1. TTFT 长尾：偶发超长 prefill 独占。修复：开 chunked prefill、限制单请求最大 prompt。
  2. TPOT 抖动：decode 被 prefill 干扰。修复：调小 chunk 预算、或 PD 分离。
  3. 排队雪崩：显存耗尽后大量请求卡 waiting，吞吐骤降。修复：降 max-num-seqs、开 KV 量化、扩容。
  4. PD 分离网络瓶颈：KV 传输打满网络。修复：高速互联（RDMA）、减少同时传输量。

8. 延伸思考题（含解析）

Q1：chunked prefill 为什么能改善 TTFT 长尾？代价是什么？
A：它把超长 prefill 切块，避免单个大 prefill 独占多步、阻塞后续请求的首次计算，从而平滑首包延迟。代价是长 prompt 的总 prefill 时间可能变长（被切多步、与 decode 抢算力），预算是权衡旋钮。

Q2：抢占时 recompute 和 swap 怎么选？
A：概念上：序列短 → recompute（重算便宜，立即释放显存）；序列长 → swap（重算太贵，换到 CPU 保留计算），前提是 CPU 内存与 PCIe 带宽够（V0 里 --swap-space 决定能换出多少）。但在 vLLM V1 中 swap 已被移除、抢占一律 recompute——实测 V1 架构下重算开销反而更低，这是"理论权衡要向实现演进低头"的好例子。

Q3：为什么 prefill 是算力瓶颈、decode 是访存瓶颈？
A：prefill 一次处理整个 prompt，是大矩阵乘，算术强度高、吃算力；decode 每步只算一个 token，但要加载整个模型权重和 KV，算术强度低、受显存带宽限制。

Q4：PD 分离什么场景最划算？
A：长 prompt + 高并发。此时 prefill 算力需求大、KV 大，分离后两池各自优化收益显著，且大 KV 传输的相对开销可被长生成摊薄。短 prompt 场景传输开销占比高，不划算。

Q5：vLLM 与 SGLang 调度差异在什么负载下体现？
A：共享前缀场景（多轮对话、统一系统提示词）。SGLang 的 RadixAttention + cache-aware 调度前缀命中率高，省 prefill、延迟低；前缀随机场景两者接近。（用你的压测数据佐证。）

1.3 跨核数据分块

若一行跨多个核（或按行分给不同核），要设计：

  • 按行切：每核独立处理完整的行 → 无跨核通信，优先选；
  • 一行跨核：需跨核归约通信 → 复杂，尽量避免。

设计原则：让归约维度（行）完整落在单核内，把并行度放在行数上。

7. 延伸思考题（含解析）

Q1：Softmax 的在线归约在解决什么问题？
A：数据分块处理时，不能等全部数据到位才求最大值和指数和。在线算法边扫边更新最大值与指数和，最大值变化时用 exp(旧m-新m) 缩放累积量保持正确。这与 FlashAttention 的在线 softmax 同一数学。

Q2：为什么归约维度（行）要尽量落在单核内？
A：跨核归约需要核间通信，代价高且复杂。按行切、让每核处理完整的行，可把并行度放在行数上、避免通信。这是数据分块设计的基本原则。

Q3：怎么用数据证明你的优化有效？
A：msprof 抓优化前后的延迟、Cube/Vector 利用率、各阶段耗时。每步改动对应指标变化（如加双缓冲后流水气泡消失、利用率上升）。有前后对比数据才算数。

Q4：什么场景必须自研算子？
A：① 算子库没有该算子；② 现成算子性能不够、可针对你的形状/场景特化；③ 需要融合多个小算子减少访存。否则优先用现成的。

Q5：fused 算子为什么通常比多个独立小算子快？
A：独立算子之间要经 HBM 读写中间结果，访存往返多；融合后中间结果留在片上（UB），一次搬入、算完一次搬出，大幅减少访存——这正是所有算子融合的核心收益。

利用率 ρ\rhoρ 越高，排队延迟越爆炸。M/M/1 模型（单服务台、泊松到达、指数服务时间）的平均排队等待时间：

深入拆解：这个公式在干什么

这个公式在算："服务台忙到什么程度时，用户要开始等很久？"它是"容量要留余量"的数学出处。

  • 符号含义：λ\lambdaλ 是平均到达率（请求/秒），μ\muμ 是单实例的平均服务率（请求/秒），ρ=λ/μ\rho = \lambda/\muρ=λ/μ 是利用率（服务台忙碌的时间占比）。WqW_qWq​ 是请求在队列里干等的平均时长（不含被服务的时间）；
  • 分母的 (1−ρ)(1-\rho)(1−ρ) 是关键：利用率越接近 1，等待时间发散到无穷——物理含义是"队列排空的速度赶不上新请求到达的速度"，积压无界增长；
  • 结果拿来做什么：给"容量设在拐点前 70-80%、留 20-30% 余量"这条工程经验提供依据——高利用率不是"省了一点机器"，而是"延迟悬崖"。

手算小例：单实例服务率 μ=10\mu = 10μ=10 请求/秒。

利用率只从 50% 提到 90%，排队等待翻了 9 倍；再提到 95% 又翻一倍。这就是"容量设在拐点前 70-80%"的数学依据——不是保守，是排队论必然。

Q1：推理服务要盯哪些普通服务不盯的指标？
A：TTFT、TPOT、吞吐、队列长度、抢占率、GPU 显存/利用率。普通服务盯可用性与 QPS，推理必须盯延迟分布与排队——因为推理的"失败"常表现为"太慢"而非"报错"。

Q2：为什么延迟指标必须看分位数而非均值？
A：推理延迟分布通常长尾。均值会被大量快请求拉低，掩盖少数超慢请求；而用户体验由最慢的那批决定。P99 才能反映真实最差体验。

Q3：线上 TTFT 突增，排查路径？
A：① 看是否过载（队列长度、并发）；② 看是否有超长请求拖慢（大 prompt 独占）；③ 看资源（显存、GPU 利用率）；④ 用分布式追踪定位慢在排队还是计算。分层定位，从最可能到最不可能。

Q4：慢节点为什么用健康检查剔除？
A：慢节点（资源争用/硬件退化）会让打到它的请求长尾。健康检查/慢请求检测能识别并把它移出负载均衡，流量切到健康节点，避免个别节点拖累整体延迟。

Q5：优雅降级为什么必须预先配置？
A：故障时认知带宽被占用、决策质量下降。预先配置好的降级策略（丢低优/切小模型/拒长请求）可一键执行，把"临场决策"变成"执行预案"，恢复更快更稳。

  3. timeout 不一致：云端算得比路由层等得久，白算。修复：请求带 timeout_ms，云端尊重。
  4. 流式断流：网络抖动 SSE 中断。修复：客户端重连 + 断点续传（带已生成偏移）。

6. 延伸思考题（含解析）

Q1：云端侧为什么用"最强配置"而不是省钱配置？
A：云端承载的是端侧答不了的复杂请求，是能力天花板。这里省质量 = 系统上限降低。成本优化靠"把简单请求拦在端侧"，而不是削弱云端。

Q2：API 契约里为什么必须有 request_id？
A：① 去重——级联升级可能重复提交，云端据此幂等处理避免重复计费；② 全链路追踪——贯穿端侧→路由→云端的追踪标识。

Q3：云端过载为什么返回 503 而不是排队？
A：排队会让路由层误以为"正常处理中"，用户无限等待。明确 503 让路由层立即感知并触发降级（切端侧兜底），保住可用性。

Q4：压测定标对路由层有什么用？
A：定标给出"云端满足 SLO 的最大并发/队列阈值"，路由层用它判断云端是否过载、决定是否端侧兜底。没有定标，分流就是盲目的。

Q5：流式转发相比整句返回，端云链路多了什么复杂度？
A：要处理 SSE 的转发缓冲、断流重连、断点续传。换来的是首字延迟大幅降低（边生成边到用户）。体验收益通常值得这个复杂度。

1. 检测任务定义：从分类到定位

1.1 三级跳

图像理解的三个经典任务，输出一个比一个"重"：

任务 输入 输出 输出数量
分类（classification） 图像 类别标签 固定 1 个
分类+定位（classification + localization） 图像 类别 + 1 个框 (x,y,w,h)(x, y, w, h)(x,y,w,h) 固定
目标检测（object detection） 图像 未知数量个（框 + 类别 + 置信度） 未知，0~N 个

检测的困难几乎全部来自最后一行：输出数量未知。分类网络最后接一个固定大小的全连接层就行；检测网络必须对"画面里到底有几辆车"这种问题给出答案，还要保证框得准、类别对、不重复报。整个检测领域 20 年的结构演进，本质上都在回答两个子问题：

  1. 候选框从哪来（region proposal → anchor → anchor-free）；
  2. 重复的框怎么去掉、好坏怎么评（NMS + IoU + mAP）。

1.2 一个预测的完整表示

一个 2D 检测器的每个输出是：

(x1, y1, x2, y2, c, s)(x_1,\ y_1,\ x_2,\ y_2,\ c,\ s) (x1​, y1​, x2​, y2​, c, s)

这行式子在说什么：每个预测框 = 6 元组。(x1,y1)(x_1,y_1)(x1​,y1​) 是左上角、(x2,y2)(x_2,y_2)(x2​,y2​) 是右下角（xyxy 格式；另有 cxcywh 格式，两者可以互转），ccc 是类别（多类时是一个 one-hot/多类概率向量），sss 是置信度分数（score，0~1），表示"我有多确信这个框里真有个目标"。置信度是后面 NMS 排序和 mAP 分档的依据——记住，检测器输出的是"一堆带分数的框"，分数意味着"宁可多报、让后面的指标体系去筛"。

预览一下终点：到第 2 周，这 6 元组会变成 10 元组——3D 框 (x,y,z,w,l,h,yaw)(x, y, z, w, l, h, \text{yaw})(x,y,z,w,l,h,yaw) + 类别 + 置信度。度量衡不变，维度升级。

2. IoU：两个框重合程度的唯一通用语言

2.1 定义

交并比（Intersection over Union, IoU）：

IoU(A,B)=∣A∩B∣∣A∪B∣=∣A∩B∣∣A∣+∣B∣−∣A∩B∣\mathrm{IoU}(A, B) = \frac{|A \cap B|}{|A \cup B|} = \frac{|A \cap B|}{|A| + |B| - |A \cap B|} IoU(A,B)=∣A∪B∣∣A∩B∣​=∣A∣+∣B∣−∣A∩B∣∣A∩B∣​

这个公式在干什么：分子是两个框的交集面积，分母是并集面积（两个框面积之和减去交集——因为交集被加了两遍，要减掉一遍）。取值 [0,1][0, 1][0,1]：

  • IoU = 0：两个框不挨着；
  • IoU = 1：完全重合；
  • IoU = 0.5：业界常用的"算命中"门槛（预测框与某个真值框 IoU ≥ 0.5 才算检出了这个目标；车这类大目标在 KITTI 用 0.7 的更严门槛，第 4 周展开）。

结果拿来做什么：IoU 是整个检测体系的"度量衡"——NMS 用它判断两个框是否重复，mAP 用它判断预测是否命中真值，评测集用它划分难度。它只依赖几何形状，与置信度无关。

2.3 NMS：同一辆车只留一个框

非极大值抑制（Non-Maximum Suppression, NMS）解决"重复框"问题。检测网络（尤其 anchor-based 的）天然会在同一目标上激活多个 anchor，输出三四个几乎一样的框。NMS 的流程：

  1. 按置信度从高到低排序；
  2. 取分数最高的框，保留；
  3. 把它与剩余每个框算 IoU，删除所有 IoU > 阈值（典型 0.5）的"重复框"；
  4. 在剩下的框里重复 2-3，直到处理完。

直觉：真目标只会被报告一次，而且最好的那次报告置信度最高——所以"分数最高的框"大概率是对的，跟它重叠严重的都是它的回声。

动手验证：把 iou_thr 改成 0.95——重复框全被保留（阈值太严）；改成 0.6——结果不变，但若框 1 与框 0 只重叠 0.55 就会漏删。阈值是"宁删勿漏"与"宁漏勿删"的旋钮，行人密集场景常用更低的阈值或后面提到的 Soft-NMS。

一句话总结：IoU 回答"重合多少"，NMS 用它回答"谁在重复报同一个目标"。

3. anchor 机制：为什么先猜再修

3.1 直接回归框难在哪

YOLOv1 最初没有 anchor：每个网格单元直接回归 (x,y,w,h)(x, y, w, h)(x,y,w,h)。问题出在 w,hw, hw,h——它们的变化范围横跨几个数量级（近处的车宽 300 像素，远处的 30 像素），网络要在一个输出神经元上覆盖这么大的动态范围，回归误差会被放大。另外画面里目标数量、位置任意，"每个格子只报一个"的约定在相邻目标场景会丢目标。

3.2 anchor 的想法：把"绝对回归"变"相对修正"

anchor（锚框/先验框）是在每个位置预设一批不同长宽比的参考框，网络不再直接报框，而是对每个 anchor 预测修正量：

bx=σ(tx)+cx,by=σ(ty)+cy,bw=pwetw,bh=phethb_x = \sigma(t_x) + c_x, \quad b_y = \sigma(t_y) + c_y, \quad b_w = p_w e^{t_w}, \quad b_h = p_h e^{t_h} bx​=σ(tx​)+cx​,by​=σ(ty​)+cy​,bw​=pw​etw​,bh​=ph​eth​

这行式子在干什么：把 anchor 中心所在网格坐标记为 (cx,cy)(c_x, c_y)(cx​,cy​)，anchor 的宽高记为 (pw,ph)(p_w, p_h)(pw​,ph​)，网络原始输出是 4 个无约束实数 (tx,ty,tw,th)(t_x, t_y, t_w, t_h)(tx​,ty​,tw​,th​)（YOLOv2 的约定）：

  • bx=σ(tx)+cxb_x = \sigma(t_x) + c_xbx​=σ(tx​)+cx​：σ\sigmaσ 是 sigmoid，把预测压到 (0,1)——框中心只会微微偏离所在格子，不会跑到画面另一头（v1 直接回归 x,yx,yx,y 会预测出离格子很远的框，训练不稳定）；
  • bw=pwetwb_w = p_w e^{t_w}bw​=pw​etw​：宽 = anchor 宽 × 指数修正。tw=0t_w=0tw​=0 时框宽就是 anchor 宽；网络只需输出"大 30% / 小 50%"这类相对量，动态范围问题消失。

结果拿来做什么：anchor 把问题从"从零猜框"变成"在先验上微调"，收敛更快、召回更高。代价是引入一堆超参（几个 anchor、什么尺寸——YOLOv2 用 k-means 在训练集上聚类得到）。第 2 周会看到 PointPillars 在 BEV 空间放 anchor（0° 和 90° 两个朝向），第 3 周会看到 CenterPoint 如何干脆把 anchor 也扔掉（anchor-free）。

4. mAP：从一个个框到一个数字

4.1 precision 与 recall

把所有预测框按置信度降序排列，逐个与真值匹配（IoU ≥ 阈值且该真值未被占用的算命中 TP，否则算误报 FP），然后定义累计量：

P=TPTP+FP=累计命中数累计预测数,R=TPNgt=累计命中数真值总数P = \frac{TP}{TP + FP} = \frac{\text{累计命中数}}{\text{累计预测数}}, \qquad R = \frac{TP}{N_{gt}} = \frac{\text{累计命中数}}{\text{真值总数}} P=TP+FPTP​=累计预测数累计命中数​,R=Ngt​TP​=真值总数累计命中数​

这两个公式在干什么：精确率（precision）回答"我报出来的框里有多少是真的"——低 precision 意味着误报多（把货箱报成行人，刹车事故）；召回率（recall）回答"真目标里我找到了多少"——低 recall 意味着漏报（没看见行人，更糟）。两者随置信度阈值此消彼长：阈值抬高，报得少而准（P↑R↓）；阈值放低，报得多而杂（P↓R↑）。

4.2 AP：PR 曲线下面积

把每个置信度阈值下的 (R,P)(R, P)(R,P) 画成 PR 曲线，平均精度（Average Precision, AP）定义为曲线下面积（带 precision 包络插值）：

AP=∫01Penv(R) dRAP = \int_0^1 P_{\text{env}}(R)\, dR AP=∫01​Penv​(R)dR

这个公式在干什么：Penv(R)P_{\text{env}}(R)Penv​(R) 是"包络"——在任意 recall 处取其右侧出现过的最大 precision（数值上从右往左扫一遍取 max）。加包络是因为 PR 曲线天然锯齿抖动（报错一个框 precision 会突然掉一下再爬回来），包络把锯齿抹平，只保留"在这个召回水平上曾经达到过的最佳精度"。AP ∈ [0,1]，越大越好；mAP 就是把每一类的 AP 平均。不同基准的插值细节不同（VOC 老版 11 点采样、2010 版全点 area、COCO 用 101 点并对多个 IoU 阈值平均），思想一致。

5. YOLO 主线演进：每一代改了什么

YOLO（You Only Look Once）是把检测做成单次前向回归的开山系列，也是工程上最常被问到的一条主线。核心事实（均已对照论文/官方发布核实）：

版本 发表时间/出处 关键创新 一句话评价
YOLOv1 CVPR 2016（arXiv 2015-06） 把检测统一成单网络回归：7×77×77×7 网格，每格预测框+类别，一次前向出全部结果 速度起飞（45 FPS 级），但定位粗、相邻目标易丢

6. 工程权衡与常见坑

  1. IoU 阈值与"Don’t Care"区域：0.5 门槛是惯例而非真理。小目标 IoU 对几个像素的偏移极其敏感（同一偏移量，小框 IoU 掉得多），所以小目标为主的场景要小心解释 AP 的波动。
  2. NMS 必须按类别分别做：一辆车和一个行人可以重叠（车挡着人），跨类别去重会误删。所有框架的 NMS 默认 class-wise，自己实现时最容易漏。
  3. NMS 在置信度过滤之前还是之后：正确姿势是先用低阈值（如 0.01）粗筛再 NMS（省计算），评测时再扫全部分数段算 AP。直接砍掉低分框会高估 precision。
  4. AP 插值口径不一致：比较两个模型的 AP 前先确认是不是同一种插值（VOC11 点 / VOC2010 area / COCO 101 点结果不同）；KITTI 用 R40（第 4 周展开），写论文报数字要标注 R11 还是 R40。
  5. “召回 100% 但 AP 低”：说明都报出来了但排序烂（误报混进了高分段），去查置信度校准而不是查召回。

7. 延伸思考题（含解析）

Q1：为什么 mAP 用"面积"而不用"某个固定阈值下的 precision"？
A：固定阈值只反映一个工作点；部署时阈值可调，不同场景要不同的 P/R 权衡。面积积分覆盖所有工作点，是对整个排序质量的综合评价。

Q2：NMS 的 IoU 阈值设 0.3 和 0.7 分别会怎样？
A：0.3 太激进，靠得近的两个真目标（如并排停车的两个车门区域）会被误删一个，recall 下降；0.7 太宽松，重复框留下来，precision 下降、下游跟踪可能出现同一个车两条轨迹。

Q3：YOLOv2 的 bw=pwetwb_w = p_w e^{t_w}bw​=pw​etw​ 里为什么用 eee 而不是线性修正？
A：宽高恒为正，线性修正会预测出负宽；乘性（对数空间）修正既保证正性，又让"翻倍/减半"在数值上对称（tw=±ln⁡2t_w=±\ln 2tw​=±ln2），且大目标的修正量自然放大、小目标自然缩小，尺度自适应。

Q4：把 4.3 的例子改成"GT=3，预测 4 个全 TP"，AP 是多少？
A：R/P 序列 = (1/3, 1), (2/3, 1), (1, 1)，包络恒为 1，AP = 1.0。AP=1 只需要"真目标排在误报前面"，与报不报误报无关——误报全排在最后即可。

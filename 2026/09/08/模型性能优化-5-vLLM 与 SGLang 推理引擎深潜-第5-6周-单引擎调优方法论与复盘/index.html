第 5-6 周教程：单引擎调优方法论与复盘

本周要回答的三个问题

  1. gpu-memory-utilization、max-num-batched-tokens、swap-space、enable-chunked-prefill 各自控制什么？调高调低的真实影响是什么？
  2. 如何用 benchmark_serving.py 做规范的压测？SLO 驱动的容量规划怎么做？什么是 goodput？
  3. OOM、排队爆炸、量化精度异常这三类故障，排查路径分别是什么？

对应学习计划：第 5-6 周。交付物：《单引擎调优手册》——以 Qwen2.5-7B 为例，从默认配置逐项调优，记录每项参数对吞吐/延迟的影响表，给出"7B 模型单卡 A100 最优配置"并复现；附三个自造故障的排查案例。

1. 第一性原理：调优是在"显存、吞吐、延迟"三角里找平衡点

1.1 没有万能配置

引擎的默认参数是通用折中，不是你的负载的最优。调优的本质：针对你的负载形状（输入/输出长度、并发、延迟要求），把资源分配调到该形状的最优点。

1.2 调优前先定目标

必须先回答：

  • 优化吞吐（离线批处理）还是优化延迟（在线对话）？
  • 延迟约束是什么（TTFT ≤ ? ms，TPOT ≤ ? ms/token）？

目标不同，最优配置完全不同。吞吐优先可以拉满 batch 牺牲单请求延迟；延迟优先要控 batch 留余量。

2. 关键参数逐一拆解

2.1 gpu-memory-utilization

作用：引擎预留给"模型权重 + KV cache"的显存比例（如 0.9 = 90%）。

调高（→ 0.95）：给 KV cache 更多空间 → 能扛更高并发/更长上下文。但留给激活/临时缓冲的余量小，易 OOM。

调低（→ 0.7）：更安全，但并发上限降低。

经验：在线服务留足余量（0.85-0.9），离线批处理可拉高（0.92-0.95）但需监控。

2.2 max-num-batched-tokens

作用：单步（一个 iteration）处理的最大 token 数——算力预算。

它同时影响：

  • chunked prefill 的块大小（每步最多做这么多 prefill 工作）；
  • 并发（太大 → 单步算太久、延迟抖动）。

调大：prefill 吞吐高，但单步延迟增、干扰 decode；调小：反之。

2.3 swap-space

作用：每卡预留的 CPU 内存，用于抢占时把 KV 换出（第 2 周）。

设为 0：禁用换出，抢占只能 recompute。设为正数：允许 swap。
权衡：换出保留计算但吃 PCIe；空间不足则退回重算。

版本注意：该参数属 V0 时代机制，V1 引擎已移除 swap 抢占（一律 recompute），新版本上调它通常没有效果——排查抢占问题时先确认自己跑的是哪个引擎版本。

2.4 enable-chunked-prefill

作用：开/关把长 prefill 切块（第 2 周）。
影响：开 → TTFT 长尾改善、decode 更平稳；代价是长 prompt 总 prefill 可能略慢。

2.5 参数相互制约

这些参数不是独立的：gpu-memory-utilization 决定 KV 总量 → 影响能开多大 max-num-batched-tokens 和并发；chunked prefill 的块大小又受 max-num-batched-tokens 限制。调优必须成组实验，不能孤立看单参数。

3. 规范压测方法学

3.1 标准压测脚本

版本注意：新版 vLLM 中该脚本已废弃，对应命令为 vllm bench serve --backend vllm --model ... --dataset-name sharegpt ...（参数基本同名）。另外续行符 \ 之后不能再跟行内注释（会断裂 shell 命令），注释请单独成行。

关键参数：

  • --dataset：负载分布（真实对话 vs 合成长度）；
  • --request-rate：到达率，扫描它画负载曲线；
  • 记录：吞吐、TTFT P50/P99、TPOT P50/P99。

3.2 负载曲线（capacity planning 的核心）

对一组 request-rate 依次压测，画出：

吞吐=f(到达率),延迟=g(到达率)\text{吞吐} = f(\text{到达率}), \quad \text{延迟} = g(\text{到达率}) 吞吐=f(到达率),延迟=g(到达率)

曲线会显示一个拐点：到达率超过某值后，吞吐不再增长、延迟急剧上升——这就是系统的饱和点。生产容量应设在拐点之前（留 20-30% 余量）。

3.3 goodput：SLO 驱动的吞吐

普通吞吐 = 每秒完成的 token 数，不管延迟。但生产关心的是"满足 SLO 的吞吐"：

goodput=满足 (TTFT≤SLO1)∧(TPOT≤SLO2) 的请求吞吐\text{goodput} = \text{满足 } (\text{TTFT} \le \text{SLO}_1) \land (\text{TPOT} \le \text{SLO}_2) \text{ 的请求吞吐} goodput=满足 (TTFT≤SLO1​)∧(TPOT≤SLO2​) 的请求吞吐

高吞吐但大量请求超延迟 = 实际无效。DistServe 等工作的优化目标就是 goodput。容量规划应以 goodput 为准，而非裸吞吐。

4.1 逐项调优矩阵

以 7B 模型、固定负载（如 ShareGPT 200 条、request-rate 8），逐项实验：

实验 变化参数 吞吐 TTFT P99 TPOT P99 备注
基线 默认
E1 gpu-mem-util 0.9→0.95 并发↑ or OOM?
E2 max-batched-tokens 调大 prefill 吞吐
E3 开/关 chunked-prefill TTFT 长尾
E4 swap-space 0→4 抢占行为（仅 V0 有效，V1 无 swap）
… …

每个实验只变一个参数，其余固定——这是归因的基础。

5. 故障排查库（交付：三个自造案例）

5.1 OOM

症状：进程崩溃，CUDA out of memory。
排查路径：

  1. 看是否 gpu-memory-utilization 过高、无余量；
  2. 看是否某请求上下文超长（KV 爆）；
  3. 看激活/临时缓冲是否被低估。
    修复：降 gpu-memory-utilization、限制 max-model-len、开 KV 量化。

5.2 请求排队爆炸

症状：吞吐骤降、延迟飙升、大量请求卡住。
排查路径：

  1. 看显存是否耗尽（KV 块不足，新请求进不了 running）；
  2. 看是否到达率超过饱和点；
  3. 看是否有超长请求独占资源。
    修复：降 max-num-seqs、扩容、限流、拒绝超长请求。

5.3 量化精度异常

症状：量化模型输出明显退化（乱码、答非所问）。
排查路径：

  1. 看启动日志是否静默反量化或走错 kernel；
  2. 看量化格式与 --quantization 是否匹配；
  3. 对比离线量化评测（Stage 2）确认是引擎侧问题还是量化本身。
    修复：指定正确 --quantization、换支持的格式、检查量化产物完整性。

5.4 制造并解决（交付）

主动把上述三类故障各制造一次（如把 gpu-memory-utilization 调到 0.99 触发 OOM），走一遍排查路径，记录"现象→定位→修复"。这是把排查清单变成肌肉记忆的最好方式。

6. 工程权衡与失效模式

6.1 权衡

  • 吞吐 vs 延迟：调优的根本矛盾，先定目标；
  • 显存余量：拉满并发高但易 OOM，留余量稳但并发低；
  • 压测代表性：合成负载快但不真实，真实负载（ShareGPT）慢但准。

6.2 失效模式

  1. 只看裸吞吐忽略 SLO：吞吐高但大量请求超时，实际不可用。修复：用 goodput。
  2. 孤立调单参数：忽略参数交互，组合后效果不如预期。修复：成组实验 + 整体复现。
  3. 压测负载失真：用单一长度压测，上线遇真实分布翻车。修复：用真实负载分布。
  4. 不留余量：把资源用到极限，稍有波动就排队爆炸。修复：容量设在拐点前 70-80%。

7. 延伸思考题（含解析）

Q1：gpu-memory-utilization 调高的收益与风险？
A：收益是更多显存给 KV cache，能扛更高并发/更长上下文；风险是留给激活和临时缓冲的余量变小，更易 OOM。在线服务建议 0.85-0.9 留余量。

Q2：goodput 与吞吐的区别？为什么容量规划要看 goodput？
A：吞吐只数完成的 token，不管延迟；goodput 只统计满足延迟 SLO 的请求。高吞吐但大量超时 = 对用户无效。生产关心的是"及时完成"，故以 goodput 规划容量。

Q3：max-num-batched-tokens 影响哪两件事？
A：① chunked prefill 的块大小（每步 prefill 工作量）；② 单步算力预算（太大会让单步变慢、干扰 decode）。它是 prefill 吞吐与延迟平滑度的权衡旋钮。

Q4：服务突然排队爆炸，排查路径？
A：先查显存（KV 是否耗尽导致新请求进不了 running）→ 再查到达率是否超饱和点 → 查是否有超长请求独占 → 对症处理（降并发/扩容/限流/拒超长）。

Q5：为什么调优实验要"每次只变一个参数"？
A：参数间有交互（如显存利用率影响可用 batch）。同时变多个无法归因是哪个参数导致的变化。单变量实验才能建立"参数→效果"的因果，最后再组合验证。

2. hooks：把规范固化到机器

钩子是 .git/hooks/ 下的可执行脚本，在特定动作前后被 Git 调用。常用者：

钩子 触发时机 典型用途
pre-commit commit 前 格式化检查、lint、拦截密钥（commit 大文件/疑似密钥即失败）
commit-msg 提交消息写好后 校验 Conventional Commits 格式（09 篇规范的机器化）
pre-push push 前 跑测试（别把红推上去）
post-merge merge 后 自动重装依赖/更新子模块

两个工程事实：

  1. .git/hooks/ 不随 clone 传播（安全考虑）——团队共享钩子的标准做法：钩子放仓库内（如 scripts/hooks/）+ git config core.hooksPath scripts/hooks（2.9+），或用 pre-commit（框架）等工具统一管理；
  2. 钩子是"本地防线"不是"安全边界"：--no-verify 可跳过——强制规范必须同时有服务端/CI 检查（09 篇的立场在此技术落地）。

3. Git LFS：大文件的正确通道

Git 对大二进制（模型权重、设计稿、数据集）天然低效：每次改动都存新对象，clone 全量拉取。Git LFS（Large File Storage，开源项目，GitHub/GitLab/Bitbucket 均支持）的方案：仓库里存指针文件，真实文件放专用存储：

  • .gitattributes 记录 track 规则——必须先 track 再 add（后 track 不会自动转换已提交的大文件）；
  • LFS 配额按流量/存储计费（各平台政策不同），超大模型考虑对象存储 + 下载脚本，而不是塞 LFS；
  • 哪些文件适合 LFS 的判别：大 + 二进制 + 会更新。只 add 一次永不再改的大文件，直接入库也可接受（无 delta 增长的困扰）。

4. rerere：记住你解决过的冲突

之后每次手工解决冲突都会被记录；同样的冲突再次出现（rebase 链上同一改动碰多次，是 rerere 的主场），Git 自动套用上次的解法，标成待确认。长 rebases 与长期维护分支的福音，零成本开启。

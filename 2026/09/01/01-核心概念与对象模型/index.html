01 - 核心概念与对象模型

本篇目标

建立贯穿全系列的三个心智模型：commit 是快照不是 diff、一切皆对象、三个区域两步走。这三个模型一旦建立，后面所有命令都不再需要"背"。

1. Git 是什么：内容寻址的文件系统 + 版本管理用户界面

一个常被忽略的事实：Git 本质上是一个内容寻址（content-addressable）的文件系统——用内容的哈希值作为地址来存取数据。版本管理（branch/merge/log…）是这个文件系统之上的一层用户界面。这个视角解释了 Git 的几乎所有设计：

  • 为什么 commit id 是一串哈希？——因为那是数据的"地址"；
  • 为什么同样的文件内容在仓库里只存一份？——因为同样的内容有同样的地址；
  • 为什么"Git 不会丢你提交过的东西"？——因为只要对象图里还有引用，数据就还在。

2. 心智模型一：commit 是快照，不是 diff

旧的版本控制系统（SVN 等）记录"文件的改动增量"；Git 的每次 commit 是项目全部文件的完整快照（通过下节的对象结构高效实现：未变化的文件不重复存储，只存指向同一 blob 的引用）。

推论（很多"玄学"瞬间变得自然）：

  1. commit id 只由内容决定：相同的快照在任何机器上生成相同的 id——Git 的同步与校验能力由此而来；
  2. “改历史”= 生成新对象：amend/rebase 不是修改旧 commit，而是造出新的 commit 对象、把分支指针挪过去（05/06 篇的机制基础）；
  3. diff 是算出来的，不是存出来的：git diff 临时对比两个快照。

3. 心智模型二：四类对象构成一张图

Git 仓库里只有四种对象，全部用内容哈希（SHA-1，160 位；可选实验性的 SHA-256 支持）寻址：

对象 内容 类比
blob 文件内容（不含文件名！文件名存在 tree 里） “内容本身”
tree 目录：一列（名字 → blob/子 tree）的映射 “目录清单”
commit 指向一个 tree + 父 commit（可多个，合并时）+ 作者/时间/消息 “快照 + 演进脉络”
tag 指向一个 commit 的命名标记（附注标签是对象，轻量标签只是引用） “里程碑”

4. 心智模型三：三个区域，两步走

工作流程的三个区域（注意这是界面概念，底层全是对象与引用）：

  • 暂存区（index/staging）：下一个 commit 的"草稿清单"。为什么要有它？——让你决定"这次提交包含哪些改动"：改了 5 个文件但只想提交其中 2 个相关的，add 精确挑选；
  • git add 把工作目录的文件内容写进对象库（生成 blob）并登记到 index；git commit 把 index 的内容固化成 tree + commit 对象；
  • git status 读的正是两个差集：工作目录 vs index（“未暂存”），index vs HEAD（“已暂存未提交”）。理解了这一点，status 的两种颜色永远不会再混淆。

版本注：git restore（撤工作区改动）与 git switch（切分支）是 Git 2.23（2019 年 8 月）引入的命令，把老的 git checkout 的两类职责拆开了。老教程里的 checkout 用法，多数可按此对应翻译。

5. 引用与 HEAD：图上导航的"书签"

  • 分支 = 指向某个 commit 的可移动引用（41 字节的文本文件！03 篇展开）；
  • HEAD = “当前所在位置”：通常指向某个分支（符号引用），detach 后直接指向某个 commit；
  • tag = 不随开发移动的引用（03/09 篇讲语义化版本时的 v1.2.3 就是它）。

所有历史导航命令本质都在回答一个问题：“从 HEAD 这个位置，沿图怎么走？”——HEAD~1 是父提交、HEAD~2 是祖父、main@{yesterday} 是引用日志里昨天的位置（06 篇的救命符）。

6. 一个完整的图景

记住三层结构：工作目录（你要改的）→ index（你要提交的）→ 对象图（你提交过的），加上"对象不可变、引用可移动"这一条铁律，Git 的全部行为都可以推理出来。

自测

  3. git status 的两组输出分别对比哪两个区域？
  4. amend 后原来的 commit 对象去哪了？（下一章预告：06 篇 reflog 能找到它）

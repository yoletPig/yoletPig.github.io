01 - 对象模型与命名

本篇目标

  1. 建立"一切皆对象"的完整心智模型：值、类型、身份三者分离，会看 id() 和 type()；
  2. 分清可变与不可变对象，解释小整数缓存、字符串驻留这些"玄学行为"；
  3. 理解 Python 的名字绑定（赋值是贴标签，不是装盒子），从而能预判函数传参、赋值、别名的行为；
  4. 了解 CPython 的垃圾回收机制（引用计数 + 分代 GC），知道内存什么时候被释放、什么情况会泄漏。

1. 一切皆对象：值、类型、身份

Python 官方数据模型文档（Data Model, docs.python.org → The Python Language Reference → 3. Data model）的第一句话就是：“Objects are Python’s abstraction for data. All data in a Python program is represented by objects or by relations between objects.”——数字、字符串、函数、类、模块，全部是对象。

每个对象都有三样东西：

  • 身份（identity）：对象在内存中的唯一编号，id(obj) 返回它。CPython 中就是内存地址（这是 CPython 的实现细节，语言规范只保证"同一对象 id 相同"）；
  • 类型（type）：type(obj) 返回，决定这个对象支持哪些操作、不可变对象的值；
  • 值（value）：对象承载的数据。不可变对象的值永不改变，可变对象的值可以原地修改。

is 与 == 是两个完全不同的运算（《Fluent Python》第 8 章的核心论题）：

  • is 比较身份：两个名字是否指向同一个对象（等价于比较 id）；
  • == 比较值：调用左操作数的 __eq__ 方法，由类作者定义什么算"相等"。

经验做法：只有两种场合该用 is——① 与单例比较（x is None，PEP 8 明确要求"Comparisons to singletons like None should always be done with is or is not"）；② 显式想判断"是不是同一个对象"（如 x is self）。其他所有相等判断用 ==。

2. 可变 vs 不可变：一张对照表

不可变对象（immutable）一旦创建，其值不可改变；任何"修改"操作实际是创建新对象。可变对象（mutable）支持原地修改，id 不变而值变了。

常见类型归属：不可变——int、float、bool、str、bytes、tuple、frozenset；可变——list、dict、set、自定义类实例（默认可变）。

有个常被忽略的细节：元组不可变，但它引用的对象可以变。

这也是为什么不可变对象不能成为 dict 键的判断标准是"能否哈希"而不是"可变性"——tuple 可以哈希（当且仅当其所有元素可哈希），所以 (1, 2) 能做 dict 键。dict 的键表依赖"键的哈希值永不改变"，这正是不可变性的价值（《Fluent Python》第 3 章）。

2.1 小整数缓存与字符串驻留：不是魔法，是优化

CPython 对部分不可变对象做了对象复用优化，目的是省内存、让 is 快速比较成为可能：

  1. 小整数缓存：CPython 启动时预创建 -5 到 256 的 int 对象并全局复用（CPython 源码 Objects/longobject.c 中的常量 NSMALLNEGINTS/NSMALLPOSINTS）；
  2. 字符串驻留（interning）：符合"标识符样式"（只含字母、数字、下划线）的短字符串字面量会被驻留复用（CPython 源码 Objects/unicodeobject.c）。

结论要背下来：这些都是 CPython 的实现细节（implementation detail），不是语言保证，且受 REPL/脚本/编译器常量折叠等上下文影响（比如同一行代码里的两个 257 常量折叠后可能共享）。你永远不应该依赖它们——相等判断永远用 ==，身份判断只在 is None 这类单例场合用。

3. 名字绑定：赋值是贴标签，不是装盒子

Python 里变量不是盒子，是贴在对象上的标签（“names are references to objects”，Python 官方教程与《Fluent Python》第 6 章反复强调）。赋值语句 x = expr 做的事是：先求出右边的对象，再让名字 x 绑定到它。名字与对象的关系是引用，且引用永远单向：名字 → 对象。

由此推出三条重要规则：

规则一：函数传参传递的是引用（“按对象共享” call by sharing，《Fluent Python》第 6 章）。 函数拿到的是实参对象的引用，不是副本。对可变对象原地修改，调用方看得见；对参数重新绑定（x = ...），只改了本地名字，不影响调用方。

规则二：a = b 之后改 a，会不会影响 b，取决于对象是可变还是不可变。 不可变对象"改"出来的本来就是新对象，两个名字自然分道扬镳；可变对象原地修改则两个名字一起遭殃（别名 aliasing 问题）。

规则三：+= 对可变/不可变对象行为不同。 对可变对象走 __iadd__ 原地修改（改旧对象）；对不可变对象走 __add__ 创建新对象再重新绑定（换新对象）。

经验做法：想复制可变嵌套结构时想清楚要几层——list(x)/x.copy() 是浅拷贝，嵌套结构用 copy.deepcopy；把 list、dict 当默认值或在 __init__ 里直接存引用前，先问自己"外面还会不会改它"。

4. 垃圾回收：引用计数 + 分代 GC（CPython 实现）

以下均为 CPython 实现细节（语言规范不要求 GC 方式，PyPy 用的是完全不同的机制）。CPython 主要靠两件武器：

武器一：引用计数（reference counting）。每个对象内部记录"有多少引用指向我"，计数归零立即释放（sys.getrefcount 观察；注意该函数本身会临时加一个引用，返回值比你预期的多 1）。这是 CPython 内存回收的主力，优点是即时性——引用一消失对象立刻销毁（这也是 with 块结束、局部作用域退出后资源能较快释放的原因之一）。

武器二：分代垃圾收集器（generational GC），处理引用计数搞不定的循环引用（a.b = b; b.a = a 时两个对象计数永远 ≥1）。gc 模块实现了三代回收：新对象在 0 代，经历一次回收仍存活就升入下一代；代数越高回收越不频繁（经验上大多数对象都是短命的，这个"弱代假说"来自传统 GC 研究文献）。

Python 3.4+ 的补充（PEP 442）：带 __del__ 终结器的循环引用也能被安全回收了；3.13 起 CPython 又引入了选择性禁用分代 GC、纯按引用计数工作的模式（PEP 703 相关的 free-threading 配套工作，07 篇展开）。

经验做法：日常代码几乎不需要碰 gc 模块；真正会造成"内存泄漏体感"的通常是无意的长命引用——全局缓存只增不减、functools.lru_cache 缓存了带 self 的方法结果、异常 __traceback__ 被长期保存、日志 handler 挂了闭包。排查用 tracemalloc（标准库）对比快照，13 篇实操。

5. 命名空间与 LEGB

命名空间（namespace）是"名字 → 对象"的映射，Python 的命名空间主要是 dict（类的 __dict__、模块的 __dict__；CPython 对函数局部变量做了优化，但概念模型不变）。查找一个名字时，解释器按 LEGB 顺序依次查找（《Fluent Python》第 7 章）：

  1. L（Local）：当前函数内部；
  2. E（Enclosing）：外层嵌套函数（闭包）；
  3. G（Global）：当前模块的全局命名空间；
  4. B（Built-in）：builtins 模块（len、print 等）。

常见陷阱

陷阱一：用可变对象做函数默认参数（02 篇展开，这里先埋个种子）——默认值在 def 时求值一次，之后所有调用共享同一个对象，正是本章"名字绑定 + 可变对象"两个知识点叠加的结果。

陷阱二：is 替代 == 判断值相等。

陷阱三：以为 b = a 拿到了副本，然后原地修改污染了原对象。

陷阱四：在遍历列表的同时往里 append，靠 id/is 猜行为而不是看文档。 遍历的是"活的"可变对象，行为未定义化（实际按索引推进，结果是反直觉的），正确做法是遍历副本 for x in list(items): 或用推导式生成新列表。

本篇小结

  • 一切皆对象：每个对象有 身份（id）、类型（type）、值 三要素；is 比身份、== 比值（__eq__）；
  • 可变性决定"改"是原地改（id 不变）还是换新对象；元组的不可变是"槽位不可变"，槽位指向的可变对象仍可改；
  • 赋值是名字绑定：传参按对象共享，浅拷贝只复制一层，嵌套可变结构要 copy.deepcopy；
  • CPython 内存：引用计数即时回收 + 分代 GC 处理循环引用（实现细节，勿依赖）；泄漏多半来自无意的长命引用；
  • 名字查找 LEGB，赋值默认落 Local，跨作用域重新绑定需 global/nonlocal 显式声明。

02 - 项目管理基础

本篇目标

走通 uv 的标准项目闭环：init → add → sync → run，并理解每一步在文件系统上实际发生了什么（本系列风格：不背命令，看懂机制）。

1. 建项目：uv init 的三种形态

以默认应用形态为例，产出：

生成的 pyproject.toml（PEP 621 标准格式，不是 Poetry 的私有格式）：

三个值得注意的设计：

  1. pyproject.toml 是 PEP 621/518 的标准文件——工具无关（pip/build 生态都认），换成别的工具迁移成本低；
  2. .python-version 是独立小文件——它的存在让"这个项目要什么 Python"成为可提交、可版本化的事实（04 篇）；
  3. uv init --lib 的 src/ 布局是打包最佳实践（源码与构建产物分离，测试 import 的是安装后的包）。

2. 加依赖：uv add 做了五件事

uv add 的幕后动作（每一步都可见可查）：

  1. 解析：计算满足版本约束与全部现有依赖的依赖图（解析器是 uv 的心脏，03 篇展开）；
  2. 下载并缓存 wheel（全局缓存去重）；
  3. 更新 pyproject.toml 的 dependencies；
  4. 更新 uv.lock（锁文件首次出现，03 篇的主角）；
  5. 更新 .venv 环境（不存在则先创建）。

3. uv sync：环境与锁文件对齐

uv sync 的语义一句话：让 .venv 精确等于 uv.lock 的内容——多装的删掉、缺的补上、版本不对的换掉。

这就是 01 篇说的"环境是 uv 保证的不变量"：不要再用 pip 往 .venv 里零散装包——那会让环境偏离锁文件，uv sync 会把你手装的包删掉（这是特性不是 bug：环境必须可复现）。

4. uv run：在正确环境里执行一切

uv run 的决策逻辑：项目环境就绪（与锁一致）→ 直接执行；不就绪 → 先自动 sync 再执行。所以新人上手的完整流程只有三行：

对比旧世界：装 Python 版本（pyenv）→ 建环境（venv）→ 激活 → 装 pip 工具 → 装依赖 → 祈祷。每一行的消失都是有原因的（锁文件 + 解释器管理 + 缓存）。

5. 项目文件清单：哪些提交、哪些忽略

文件 提交进 Git？ 理由
pyproject.toml ✅ 必须 事实来源
uv.lock ✅ 必须（应用项目） 可复现的依赖图（03 篇）；库项目可讨论（08 篇）
.python-version ✅ 必须 团队解释器一致性
.venv/ ❌ 永不 本地环境，可由 lock 重建（Git 02 篇"可重建的不入库"）

（uv 不会自动生成 .gitignore，记得手写：.venv/。）

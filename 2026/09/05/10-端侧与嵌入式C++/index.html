10 - 端侧与嵌入式 C++

本篇目标

  • 列出端侧环境的约束清单，建立"桌面 C++ 直觉"到"端侧 C++ 直觉"的转换。
  • 掌握 -fno-exceptions -fno-rtti 下的错误处理风格（错误码/expected）。
  • 会用 objdump -h 规划静态内存（.text/.data/.bss），用 -fstack-usage 估算栈，实现池分配器。
  • 走通交叉编译最小流程与 CMake toolchain 文件，认识 RK3588 用户态接入 NPU 的 rknn_api 骨架（衔接《模型性能优化》Stage 4）。

范围说明：本章的"端侧"覆盖两个层次——MCU 裸机/RTOS（KB 级，禁异常是刚需）与 ARM Linux SoC（RK3588）（MB 级，异常可用但仍受内存/功耗约束）。两者共用的工程习惯是本章主线，差异处分别标注。

1. 端侧约束清单

约束 MCU（如 STM32，Cortex-M4） ARM Linux SoC（RK3588） 对代码风格的影响
内存 RAM 几十 KB–几 MB，Flash 同量级 几 GB，但与其他进程共享 禁止运行期无界分配；静态规划
异常/RTTI 通常 -fno-exceptions -fno-rtti（异常展开表占 Flash，实时性不可控） 可用，但实时路径仍避免 错误码/expected 为主
实时性 硬实时（中断响应 μs 级） 软实时（帧率/延迟预算） 无锁 SPSC（第 05 章）、预算内完成
栈 几 KB 固定，溢出 = 硬故障 8MB 默认但线程多时要规划 -fstack-usage 预估
看门狗 必配，喂狗是代码结构的一部分 进程级 health check 第 6 节
电源 μA 级功耗预算 W 级但受热限制 NPU/DSP offload

桌面习惯里三件"免费"的事在端侧都是事故源：异常（栈展开要几百 KB 代码与不可预测延迟）、堆碎片（长期运行的 malloc/free 使碎片化，最终 OOM）、无界容器（push_back 到内存耗尽）。本章其余部分就是给这三件事换工具。

2. 禁用异常与 RTTI 的代码风格

-fno-exceptions 下 throw 直接变 std::terminate；-fno-rtti 禁掉 dynamic_cast/typeid（省虚表扩展与类型元数据）。STL 不会编译失败（vector::push_back 分配失败时内部 throw 退化成 abort），但依赖异常做错误流的设计全部失效，替代风格：

经验做法：MCU 层 API 用错误码（C 兼容、可预测栈上布局），中间业务层用 expected 串链；-fno-rtti 后需要"类型分发"的地方用 tag/variant（第 06 章）替代 dynamic_cast。注意 std::expected 的 value() 在无值时抛异常——无异常环境下用 value_or/operator*（先判 has_value）。

3. 静态内存规划：链接脚本与 .bss/.data

ELF 可执行/固件的内存画像由段构成（衔接《计算机系统与网络》01）：

段 内容 占 Flash 占 RAM 注意
.text 代码、字面量池 是 否（从 Flash 直接执行/XIP） -Os 瘦身主战场
.rodata 常量、字符串 是 否（或映射） 模型权重放这里（或独立分区）
.data 有初值全局/静态 是（存初值） 是（运行时） 双倍计费
.bss 零初始化全局/静态 否 是 文件小≠内存小，最易翻车

.bss 的 64KB 在二进制文件里只占段头几个字节，烧录文件大小毫无变化，运行内存实打实多吃 64KB——"固件下进去了但跑不起来"的第一大原因。工具链：size mem（GNU size 工具汇总 text/data/bss 三列）、nm --size-sort -S mem | tail（按大小排符号，找内存大户）。**链接脚本（linker script，.ld 文件）**定义这些段落到物理地址的映射（MCU：.text @FLASH、.data 初值 @FLASH + 运行 @RAM、.bss @RAM，启动代码把 .data 从 Flash 拷到 RAM、清零 .bss）；规划 RAM 的流程 = 列出所有全局/静态缓冲（模型输入输出、DMA 缓冲、栈、堆）→ 每项注明尺寸 → 与 RAM 预算核对。经验做法：所有大缓冲用固定长度数组 + static_assert(sizeof) 记录在案，禁止"先 new 了再说"。

要点：union Slot 让"空闲链表指针"与"对象存储"共用内存（free list 的标准技巧）；acquire/release 都是几次指针操作，时序确定——实时性比平均速度重要时，池 > malloc。用完池再往上是"整块 arena + reset"（第 06 章，每帧重置式）。new/delete、malloc/free 在 MCU 上的定位：只在启动阶段用（构造静态结构），运行期禁用（经验做法，MISRA/汽车行业惯例一致）。

5. 栈大小估算：-fstack-usage

栈溢出在 MCU 上是静默的硬故障（踩到别的内存，行为诡异），必须提前算。GCC 的 -fstack-usage 给每个函数生成 .su 文件：

每行 = 函数自身栈用量（字节）；big 的 2080 = 512×4 的缓冲 + 帧开销。总栈 = 调用链上各函数之和（叶子路径）。三个工程工具：链最深路径的分析器（puncover、stack_analyzer 等读 ELF 自动算）；递归函数在端侧基本禁用（栈不可预测，改显式栈）；RTOS 里每线程栈独立配额（FreeRTOS uxTaskGetStackHighWaterMark 运行期校准）。经验做法：估算值 × 1.5 起配，跑真实负载后用 high-water mark 收紧。

6. 看门狗与喂狗模式

看门狗（watchdog）是"不喂就复位"的硬件倒计时，端侧可用性方案的最后防线。设计要点：

  • 喂狗的不是定时器中断，而是主循环/工作线程：中断里喂狗 = 中断活着但主逻辑死了照样不复位，防不住真正的卡死。MCU 模式：主循环每轮喂一次，轮内做"各任务心跳检查"。
  • 多任务用"逻辑与"喂狗：每个关键任务置自己的心跳位/时间戳，监控点检查全部新鲜才喂（FreeRTOS 的 task watchdog、Linux 的 systemd watchdog 同思想）。
  • 喂狗节奏与最坏路径预算绑定：把最慢一轮的执行时间（含最坏分支）测出来，超时时间 > 2× 最坏值；宁可偶尔复位，不可饿死不喂。
  • Linux 侧（RK3588）：systemd 的 WatchdogSec= + 服务内定期 sd_notify WATCHDOG=1；推理进程在"帧处理循环"里喂，处理阻塞（NPU 超时、解码卡死）时由 systemd 拉起服务。

常见误区

  1. .bss 大数组以为"不占空间"：文件小、运行内存大（第 3 节实测 64KB），MCU 上直接链接失败或运行崩溃。内存规划表里它算满额。
  2. -fno-exceptions 下照写依赖异常的代码：throw 编译成 terminate，expected::value() 无值时也是抛（退化 abort）。所有错误路径走错误码/value_or。
  3. 运行期 malloc/free 撒着用：碎片化让"总空闲充足却分不出连续块"。启动期一次性分配 + 池/arena。
  4. 栈按"够用就行"拍脑袋：-fstack-usage 逐函数给数，链最深路径求和 × 1.5；递归与 alloca 禁用。
  5. 中断里喂狗 / 中断里做重活：前者防不住主逻辑卡死，后者破坏实时性。喂狗放主循环 + 心跳聚合；重活放任务/线程。
  6. 在 PC 上测完性能直接报给端侧：交叉编译优化级别、缓存大小（RK3588 无 AVX，只有 NEON）、内存带宽都不同。性能数字必须在目标板上测（第 03 章的跨平台派发同理）。

本篇小结

  • 端侧约束 = MB 级内存 + 无异常 + 实时性 + 看门狗；桌面三件套（异常/无界堆/无界容器）全部换装。
  • 无异常风格：底层错误码 + 业务层 expected；-fno-rtti 用 variant/tag 替代 dynamic_cast。
  • 静态内存：.bss 只占 RAM 不占 Flash（实测 64KB 数组），objdump -h/size/nm --size-sort 三件套规划；链接脚本映射段到物理地址。
  • 容器：vector 必须 reserve 定容；定长环形缓冲与 union 槽位池分配器都是 O(1)、零堆；new 只在启动期。
  • 栈：-fstack-usage 逐函数量化（leaf 96B / big 2080B 实测），最深链 × 1.5 起配。
  • 交叉编译：toolchain 文件四行 + FIND_ROOT 三规则；RK3588 用 rknn_api 的预分配输入输出骨架接 NPU。

练习

  1. 用 size 和 objdump -h 分析第 12 章的 JSON 解析器二进制，把 .text/.data/.bss 记成表格；再把 Arena 的 chunk 从 1MB 改为静态数组 static char g_arena[256*1024]，观察 .bss 变化。
  2. 给 4.3 的 ObjectPool 加 static_assert(sizeof(Slot) >= sizeof(T)) 之外的"耗尽统计"（acquire 失败计数器），并说明为什么 release 不调用 ~T() 时对非 POD 类型是危险的。
  3. 用 -fstack-usage 测第 12 章解析器的 parse_value/parse_object/parse_array 递归链，估算 20 层嵌套 JSON 的栈深，回答"要不要给解析器加深度上限"。
  4. 写 RK3588 的 toolchain 文件（目标 aarch64-linux-gnu），把第 05 章 SPSC 队列测试交叉编译后在板端（或 QEMU）运行；没有板子时说明 file 输出如何证明产物正确。
  5. 设计一个"音频采集 → NPU 推理 → 结果回传"的端侧流水线内存规划表（各缓冲尺寸、所在段、分配时机、喂狗点），用本章工具逐项验证你的估算。

1. 第一性原理：推理服务的"健康"长什么样

1.1 普通服务看"活着"，推理服务看"够快"

Web 服务的核心指标是可用性（成功率）。推理服务即使 100% 成功，也可能慢到不可用——所以推理的可观测性围绕延迟分布与排队展开。

1.2 推理专属指标清单（本周交付的 6 个核心）

指标 含义 为什么重要
TTFT 首 token 延迟 用户感知的响应速度
TPOT 每 token 间隔 流式输出的流畅度
吞吐 tokens/s 容量与成本效率
队列长度 排队请求数 过载的最早信号
抢占率 被抢占请求比例 显存压力指示
GPU 利用率/显存 资源水位 容量规划依据

分位数而非均值：延迟必须看 P50/P95/P99——均值掩盖长尾，而长尾才是用户投诉的来源。

对号入座（vLLM 实际指标名）：vLLM 在 /metrics 暴露 Prometheus 指标，统一 vllm: 前缀。与上表对应：排队请求数 = vllm:num_requests_waiting、运行中请求数 = vllm:num_requests_running、KV cache 占用率 = vllm:gpu_cache_usage_perc（0~1）、吞吐可用 vllm:generation_tokens_total（counter，求 rate）等。TTFT/TPOT 类延迟分位在新版 vLLM 中也有对应的 histogram 指标（如 vllm:time_to_first_token_seconds、vllm:time_per_output_token_seconds，以你所装版本的 metrics 文档为准）。

4.3 优雅降级策略

过载时的主动选择（按优先级）：

  1. 丢弃低优请求（保高优用户）；
  2. 切更小模型（牺牲质量保响应）；
  3. 拒绝长上下文（长请求占资源最多）。

这些要预先配置好，故障时一键生效，而不是临时想。

5. 工程权衡与失效模式

5.1 权衡

  • 告警灵敏度：太灵敏告警风暴（麻木），太迟钝发现晚。按 SLO 分级（warning 早、critical 准）。
  • 追踪开销：全量追踪有性能开销。采样率权衡，慢请求必采。
  • 指标粒度：太粗看不出问题，太细存储成本高。

5.2 失效模式

  1. 只有均值没有分位数：P99 爆了均值还正常，漏报。修复：所有延迟指标看分位数。
  2. 告警疲劳：低价值告警太多，真告警被忽略。修复：告警分级、定期清理无效告警。
  3. 无追踪定位难：慢请求不知道卡哪。修复：接入分布式追踪，关键路径全打 span。
  4. 降级没预案：过载时临时决策手忙脚乱。修复：预先配置降级策略并演练。

6. 延伸思考题（含解析）

Q1：推理服务要盯哪些普通服务不盯的指标？
A：TTFT、TPOT、吞吐、队列长度、抢占率、GPU 显存/利用率。普通服务盯可用性与 QPS，推理必须盯延迟分布与排队——因为推理的"失败"常表现为"太慢"而非"报错"。

Q2：为什么延迟指标必须看分位数而非均值？
A：推理延迟分布通常长尾。均值会被大量快请求拉低，掩盖少数超慢请求；而用户体验由最慢的那批决定。P99 才能反映真实最差体验。

Q3：线上 TTFT 突增，排查路径？
A：① 看是否过载（队列长度、并发）；② 看是否有超长请求拖慢（大 prompt 独占）；③ 看资源（显存、GPU 利用率）；④ 用分布式追踪定位慢在排队还是计算。分层定位，从最可能到最不可能。

Q4：慢节点为什么用健康检查剔除？
A：慢节点（资源争用/硬件退化）会让打到它的请求长尾。健康检查/慢请求检测能识别并把它移出负载均衡，流量切到健康节点，避免个别节点拖累整体延迟。

Q5：优雅降级为什么必须预先配置？
A：故障时认知带宽被占用、决策质量下降。预先配置好的降级策略（丢低优/切小模型/拒长请求）可一键执行，把"临场决策"变成"执行预案"，恢复更快更稳。

07 - Agent 开发常见问题与陷阱

本篇目标

这是本系列最重要的一篇。前面各篇讲了"怎么搭"，本篇讲"为什么会坏"。每个问题给出：症状 → 根因 → 对策。建议当作排查清单（checklist）收藏。

Agent 工程的残酷现实：演示和可靠之间隔着一整条鸿沟。一个 Agent 在 10 次演示里全对，不代表它在 1000 次生产运行里不崩溃。本篇所有内容都围绕把"演示"变成"系统"。

问题 1：死循环与原地打转

症状：Agent 反复调用同一个工具、重复相同的 Thought、或者在第 20 步重新执行第 3 步做过的事。

根因：

  1. 工具返回错误信息太模糊（Error、false），模型不知道怎么改，只能原样重试；
  2. 上下文太长，模型"忘了"自己已经做过（05 篇的 context rot）；
  3. 任务本身没有可验证的完成标准，模型不知道"做完了"长什么样。

对策：

  • MAX_STEPS / token 预算硬上限（02 篇，无条件的保险丝）；
  • 重复检测：记录最近 N 次调用，发现相同工具+相同参数连续出现 ≥2 次，就在观测里注入警告：“你已重复执行相同操作，请改变策略或输出 Answer”；
  • 把错误观测写成可操作的："文件不存在，路径 /a/b.txt，目录 /a 下有：[…]"比"Error: not found"有用十倍；
  • 系统提示中给出完成标准的显式描述：“当所有三个文件都已校验时输出 Answer”。

问题 2：错误级联（error compounding）

症状：第 5 步的一个小错误（读错文件、算错数）没被发现，导致后面 15 步全部建立在错误之上，最终结果面目全非。

根因：Agent 是自反馈系统——每一步的输入包含之前所有步骤的输出。没有纠错机制时，错误概率按步数复利增长。Anthropic 在《Building Effective Agents》中把这作为控制 Agent 自主性的核心论据：自主性越高、链条越长，误差累积越严重。

对策：

  • 在关键节点插入验证器（verifier）：不是每步都查，而是在"错误代价大"的节点查——文件写完校验行数，SQL 执行前先 EXPLAIN，报告生成后跑一遍事实核对 Agent；
  • 断言式工具：工具本身就做校验（比如 save_json 工具内部先验证 JSON 合法性，失败就拒绝执行并回喂原因）；
  • 缩短链条：能用一次确定性代码解决的（正则、SQL、脚本），不要让 Agent 分五步"智能地"做。确定性优先，LLM 只负责决策点；
  • 允许回滚：给关键工具配 undo（写入前备份、事务化操作）。

问题 3：上下文腐化与"长会话变傻"

症状：任务进行到一半，Agent 开始答非所问、忘记最初的约束、忽略系统提示里的规则。

根因：上下文窗口被大量工具输出淹没（05 篇）；无关内容稀释了关键指令的"注意力权重"（context rot 现象，见 05 篇来源）。

对策：

  • 工具输出截断 + 结构化（03 篇执行器）；
  • 周期性摘要/状态外置（05 篇）；
  • 重要约束在观测流中复述：关键规则可以在长任务中途以系统消息形式重申一次（注意不要滥用，重复注入也有成本）。

问题 4：工具选择错误

症状：该用 search_orders 却用了 get_product；该传 order_id 却传了用户名；一次并行调了三个互有依赖的写操作。

根因：工具描述含糊或重叠（03 篇）；工具太多；参数 schema 太松。

对策：回顾 03 篇五准则；描述中写"何时不用本工具"；收窄 enum；工具超过几十个时引入工具检索或按任务分组注册。另外可加一层运行时参数校验（JSON Schema validation），把非法参数在执行前拦下并回喂 schema 摘要。

问题 5：过度自主 / 欠自主（自主性失配）

症状：要么 Agent 疯狂自作主张（删了不该删的目录），要么事事请示（"我可以读这个文件吗？"问 20 次）。

根因：自主性是按工具粒度设计的，而不是按 Agent 整体。你给它的每个工具都该有自己的风险等级，而新手往往"全放开"或"全审批"。

对策：给工具分级（详见 08 篇）：

  • 只读/无副作用 → 自动放行；
  • 可逆写操作（新建草稿文件）→ 放行 + 审计日志；
  • 不可逆/外发操作（删除、发送邮件、支付）→ 必须人审；
  • 并把"何时必须问人"写进系统提示，避免两种极端。

问题 6：没有评测，靠肉眼验收

症状：改一版提示词，测了三个 case 都好，上线，三天后生产事故。

根因：Agent 的行为是多因素复合（提示词×模型版本×工具实现×任务分布），肉眼看几例的结论是噪声。没有评测集，Agent 迭代等于盲改。

对策（最小可行评测，半天能搭好）：

  1. 攒 20~50 个有标准答案或可程序化验证的代表性任务（从真实使用里捞，不凭空编）；
  2. 写自动判分器：能程序化验证的（文件是否创建、数字是否正确）用代码判；开放式的用 LLM-as-judge（用一个模型按 rubric 打分，注意 judge 本身也有偏差，rubric 要具体）；
  3. 每次改动（提示词、工具描述、模型版本）全量跑一遍并记录，观察指标而不是感觉；
  4. 失败 case 归因后回填到评测集，防回归。

这个做法没有高深理论，但恰恰是"演示"与"产品"的分水岭。参考：OpenAI 的 A practical guide to building agents 与 Anthropic 的《Building Effective Agents》均将 evals 列为核心环节。

问题 7：模型/供应商耦合与迁移幻觉

症状：换一个模型，Agent 直接散架——格式不输出了、工具不会用了。

根因：提示词和解析逻辑与特定模型的"方言"绑死（比如依赖某种特定的思考标签格式）。

对策：用 API 原生 Function Calling 而非正则解析自由文本（02 vs 03 篇）；提示词避免引用模型专属行为；核心循环保持模型无关（04 篇 MCP 也降低了宿主与工具的耦合）；评测集（问题 6）正是迁移时的回归保障。

问题 8：把 Agent 用在了错误的问题上

症状：团队花三个月做 Agent，任务其实是一个固定流程，用 50 行工作流代码 + 一次 LLM 调用就能稳定解决。

根因：01 篇讲过——没有先问"这需要动态控制流吗？有可验证的完成标准吗？"

对策：项目立项前用 01 篇的判断标准过一遍；已有 Agent 的系统定期做"降级审计"——哪些环节可以从自主循环改成确定性代码？确定性代码替换 LLM 步骤，永远是可靠性提升。

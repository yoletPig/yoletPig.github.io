08 - 协程

本篇目标

  • 说清协程解决什么问题：异步回调地狱 → 顺序写法，并与 Python async/await 对齐概念。
  • 掌握 co_await/co_yield/co_return 三个关键字与 promise_type、coroutine_handle 的协作机制，逐行读懂最小 generator。
  • 亲手写自定义 awaiter（休眠定时器、线程池任务），理解"挂起 → IO/定时器就绪 → 恢复"的调度循环。
  • 认识协程最危险的陷阱——悬空引用三大现场，以及"生产用成熟库"的现状结论。

环境：C20 协程，g 需要 -std=c++20 -fcoroutines（g++ 10/11 需要该开关，g++ 12 起隐含）；头文件 <coroutine>。出处：标准 [dcl.fct.def.coroutine]（N4861 §9.5.4）。

1. 协程解决什么问题

与 Python 概念对齐：async def ≈ 协程函数、await ≈ co_await、yield ≈ co_yield。一个关键差异：Python 的 async/await 是语言+事件循环的固定搭配（asyncio 提供事件循环与全部 awaitable）；C++20 只给了语言机制（三个关键字 + 编译器生成状态机），事件循环、任务类型、调度器全是库的事——标准库一个 task 都没有。这解释了 C++ 协程"概念简单、上手难"的观感：语言只管"怎么挂起/恢复"，"谁来恢复、何时恢复"要自己（或库）定义。

第二个关键差异：C++ 协程是无栈协程（stackless）——挂起点信息存在堆上的"协程帧"里，函数体被编译器改写成状态机；不像 Python 生成器那样携带整条调用栈，所以 co_await 只能出现在协程函数体内，不能跨普通函数调用传递。

2. 三个关键字与编译器改写

函数体内出现 co_await、co_yield、co_return 任一，该函数就是协程函数，返回类型必须定义 promise_type（编译器靠它定制行为）：

三个关键字的标准语义：

  • co_await expr：expr 必须可转成 awaiter（提供 await_ready/await_suspend/await_resume 三件套，见第 5 节）。await_ready 为真 → 不挂起直接取结果；否则挂起、把控制权交还给调用者/resumer。
  • co_yield v：等价 co_await promise.yield_value(v)——"吐值"只是 await 的一种预设用法。
  • co_return v：调用 promise.return_value(v)（或无值协程的 return_void()），二选一，定义哪个取决于返回类型是 Task 还是 Generator。

协程帧的生命周期：调用协程函数不执行任何函数体代码，只分配协程帧、把参数拷进去、调用 promise.get_return_object() 造出返回值。函数体何时跑、何时销毁，全部由 promise 的 initial_suspend/final_suspend 决定——这就是第 3 节 generator 逐行解读的伏笔。

逐行复盘执行流：main 里 fib() 返回时帧挂起（②）——这就是惰性；g.next() 首次 resume，函数体从头跑到 co_yield a（a=0）→ yield_value 存值并挂起（④）→ next 返回 true；value() 读 promise 字段（⑨）。每次 next 重复"恢复 → 跑到 yield → 挂起"。done() 为真发生在函数体执行完 co_return 之后（final_suspend 把帧挂住，③ 保证句柄仍可读 promise、由 ⑦ 显式销毁）。

两个必记细节：final_suspend 必须 noexcept（标准要求）；它是 suspend_always 时帧不自动销毁（所有者负责，本例析构函数 ⑦），是 suspend_never 时协程帧在 co_return 后自动销毁——两种策略配对的持有方式不同，混用就是双重释放或泄漏（见第 6 节）。

5. 自定义 awaiter 的三件套

任何类型只要提供三个成员就是 awaiter，co_await 即可用：

成员 调用时机 返回值含义
await_ready() 挂起前 true = 已就绪，跳过挂起直接 await_resume
await_suspend(h) 即将挂起 void/bool：false = 别挂了；返回协程句柄 = 恢复"另一个"协程（对称转移）
await_resume() 恢复时 作为 co_await 表达式的值

6. 生命周期陷阱：悬空引用三大现场

协程帧在堆上、生命周期跨过普通函数的作用域——这是 C++20 协程事故的集中地。三大现场（全部真实可复现）：

现场一：协程参数按引用传递，调用方作用域先结束。

修法（经验做法）：协程参数一律按值（string_view 也逃不掉，见现场三），让拷贝进协程帧；大对象移动进帧。

现场二：范围 for 的临时容器挂起后销毁。

修法：先具名 auto items = get_items(); 再 for。

现场三：Task 对象比协程早亡 / final_suspend 策略与所有者错配。 Task 被移动后旧句柄置空是必须的（本例 std::exchange）；如果 promise 用 final_suspend = suspend_never 而析构函数还 h.destroy()，就是双重释放；反过来 suspend_always + 没人 destroy，就是泄漏。结论：要么整体抄成熟库的 Task，要么把这个组合背下来：惰性启动 + final 挂起 + 所有者移动语义销毁（第 4 节代码就是这个组合）。

额外一条工程纪律（经验做法）：协程里不要写 co_await 挂着去等一个"可能被销毁的对象的成员函数结果"——任何跨越挂起点的引用/指针，先问一句"它的所有者活到我 resume 吗"。ASan 对协程悬空的报告质量在 clang 侧较好，gcc 侧常要靠 review 兜底。

7. C++ 协程库现状与选型

标准库只给机制不给任务类型，实际工程在库层选择（2024-2026 现状）：

  • Asio（standalone asio / boost::asio）：as_tuple/use_awaitable + co_spawn，网络 IO 协程化最成熟、文档最全；llama.cpp server、各类网关在用。生产首选（经验做法）。
  • stdexec（std::execution 提案参考实现）：sender/receiver 模型，C26 的方向；与 C20 协程可互操作，但 API 仍在演进。
  • cppcoro：教学与早期参考实现的最大功臣，但 2020 年后基本停止维护——学概念读它，上生产别依赖它。
  • libunifex（Meta）：sender/receiver 先行者，逐渐被 stdexec 吸收。

结论：自己写 generator/task 教学用没问题（本章就写了）；生产中异步 IO 用 Asio 的协程集成，任务编排等 stdexec 稳定，中间态不要自研调度器——调度正确性（线程安全、取消、异常传播）的坑足够淹没任何自研收益。

常见误区

  1. 以为调用协程函数就会执行：默认惰性（initial_suspend 挂起）下，创建 ≠ 运行；忘了 resume/sync_wait 的"空转协程"是常见 bug——什么都没发生，也没报错。
  2. 参数按引用传协程（现场一）：协程帧活多久不确定，引用必然悬空。协程函数签名里少用 const T&。
  3. 在协程里用引用捕获的 lambda 再跨挂起点：lambda 的捕获栈变量同样悬空；跨挂起点只传值。
  4. co_await 出现在普通函数里：编译错误 “co_await only in coroutine”；正确做法是让外层函数也返回 Task（协程不能跨普通函数边界传递挂起，见第 1 节无栈协程）。
  5. 把 detach 线程恢复协程当正常调度：本章演示用 std::thread(...).detach() 是为了零依赖；真实系统里每次挂起起线程是灾难，用事件循环/线程池（第 7 节的库）。
  6. 异常传播没接住：unhandled_exception 里吞掉异常 = 静默丢失错误。库版 Task 会把 exception_ptr 存进 promise，sync_wait 时重抛——手写 Task 时这是必答题。

本篇小结

  • 协程把回调地狱改写为顺序代码；C++20 只给语言机制（无栈协程、状态机改写），调度/任务类型交给库——与 Python asyncio 的本质差异。
  • 三关键字：co_await（挂起点）、co_yield（吐值 = yield_value）、co_return（return_value/return_void 二选一）。
  • 最小 generator：promise 六件套各司其职；initial_suspend 决定惰性，final_suspend 决定帧归谁销毁；协程帧 = 堆上的参数与局部变量。
  • awaiter 三件套（ready/suspend/resume）是扩展点：定时器、切线程、包装回调式 API 都是它；调度循环 = “注册句柄 → 事件就绪 → resume”。
  • 悬空三大现场：引用参数早亡、range-for 临时容器、Task 与 final_suspend 策略错配；纪律是"跨挂起点只传值"。
  • 生产选型：Asio 协程集成首选，stdexec 是 C++26 方向，cppcoro 只用于学习。

练习

  1. 给第 3 节 Generator 加 operator++/operator*，让 for (auto v : fib() | std::views::take(10)) 风格可用（提示：让 Generator 满足 input_iterator 的最小子集，或用 C++23 std::generator 的思路）。
  2. 写 RepeatAwaiter：co_await RepeatAwaiter{n} 挂起 n 次每次被外部手动恢复（配合一个 main 里的循环 resume），体会 await_suspend 返回 void 与句柄生命周期的关系。
  3. 复现现场二：写一个返回 vector<int> 的函数 + 挂起协程的范围 for，用 ASan（-fsanitize=address）观察报错；然后按修法改对。
  4. 把第 4 节 Task 的 sync_wait 改成"条件变量等待"而不是轮询（promise 里加 std::binary_semaphore，final_suspend 的 await_suspend 里 release），对比两种实现的语义差异。
  5. 用 Asio（standalone 版）把本章 pipeline 重写成 asio::co_spawn + asio::steady_timer，对比手写 awaiter 的代码量，回答"为什么要用库"。

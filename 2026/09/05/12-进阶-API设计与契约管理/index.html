12 - 进阶：API 设计与契约管理

进阶篇第 2 章。01 篇讲"面向接口编程"时，接口还是类层面的概念；系统之间（服务间、前后端、对第三方）的接口是架构级资产——它们一旦有人依赖，就进入了"改起来伤筋动骨"的架构决策范畴（07 篇的判别标准）。本章讲：设计一个 API、管理它的版本与兼容性、以及契约如何成为团队协作的枢纽。

1. API 是契约：换位到"被依赖者"思维

写内部函数时，改签名是廉价的（编译器/IDE 帮你改调用点）。发布给他人用的 API 没有这种奢侈：你不知道谁在调用、用的什么语言、什么版本。API 设计的核心转变：

从"我怎么实现方便"转为"调用方怎么用得对、错了怎么被善待、我将来怎么改而不破坏他们"。

由此推出 API 设计的三条元原则：

  1. 向后兼容是默认义务：不破坏现有调用方地演进（§3 详述）；
  2. 错误是产品：调用方与你的交互大部分时间是"出错的时候"（§4）；
  3. 一致性优先于局部最优：同一 API 族内，同类操作长得必须像（§5）。

2. 设计一个 API：资源、操作、参数、返回

以 REST/HTTP 为载体（gRPC/RPC 的原则相通，载体不同）——以"订单导出"为例走一遍完整决策：

2.1 资源建模：名词优先，操作入资源

判别："导出"这类本质是异步过程的操作，建模为"创建任务资源"而不是 GET /get-export?file=x：

  • 创建即返回 202 Accepted + Location: /exports/{id}（HTTP 语义：已受理未完成，RFC 9110）；
  • 过程状态成为可查询资源，天然支持重试与幂等。

动词式端点（/doExport）的代价：无法表达状态、无法分页、无法被通用缓存/网关理解。

2.2 参数设计：必选最少，可选显式

  • 必选参数做减法：每个必选参数都是调用方的失败点。能推导的不要让调用方传（tenant 从鉴权态取，不要 URL 参数传）；
  • 可选参数给显式默认值并在文档写明；布尔参数两值语义必须文档化（include_draft=true 才含草稿，false 不含——含不含历史版本？写清楚）；
  • 单位与格式显式化：时间戳用 ISO 8601 UTC（“2026-11-07T09:30:00Z”），金额带币种字段。隐含本地时区/隐含币种是国际系统最贵的一类事故。

2.3 返回设计：面向消费者裁剪

  • 返回资源视图而非数据库行：内部表加一列，API 不该跟着变；
  • 大对象给"字段选择"或"视图参数"（?view=summary），避免"详情接口返回 3MB"；
  • 列表返回元信息与数据分离：{"items": [...], "next_cursor": "..."}。

2.4 分页：一律游标分页

偏移分页（?page=3）在数据频繁增删时会出现重复/漏项（窗口漂移），且深翻页对数据库代价线性增长。游标分页（?cursor=<opaque>&limit=50）两者皆免：

  • cursor 是不透明 token（服务端编码，调用方不解码不依赖其结构）——这是保持服务端自由度的关键：内部从 created_at+id 换成 id 排序，cursor 结构变了也不破坏调用方；
  • 代价：不能跳页。对"同步浏览"场景可接受，对导出场景应引导用异步任务（2.1）。

3. 版本与兼容性：演进的生命线

3.1 兼容性判别表（必背）

对"已有调用方"来说，改动分三类：

改动 兼容性 说明
新增可选请求字段、新增响应字段 ✅ 兼容 前提：调用方遵循"忽略未知字段"（§3.2）
新增端点、新增可选枚举值 ✅ 兼容 注意：枚举加值对"穷举校验"的旧调用方是破坏，见下
删字段、改字段语义、改错误码含义、必选变必填、收紧校验 ❌ 破坏 需要 §3.3 的破坏性变更流程

最常被低估的一条：服务端给枚举加新值，可能打爆"穷举处理所有值"的旧客户端（switch 无 default 的调用方当场崩）。缓解：文档要求调用方对未知枚举值有兜底分支；服务端加值前先发布"将新增"预告。

3.2 宽进严出原则（tolerant reader）

  • 服务端对请求：宽进——忽略未知字段（不要因为多了个字段就 400）；这是 Postel 健壮性原则在 API 层的应用，但要加边界：类型/格式不合法该拒绝就拒绝（"宽容"指结构性未知，不是脏数据照单全收——对脏数据的宽容只是把失败推迟到更深的地方）；
  • 客户端对响应：严出宽进——只依赖自己用到的字段，未知字段忽略、未知枚举有兜底。

两端都做到，"加字段"才能真的是兼容变更。

3.3 破坏性变更的标准流程

版本策略的取舍：URI 版本（/v2/exports）简单粗暴、缓存友好，是 REST 实践主流；header 版本（X-API-Version）URI 干净但调试不直观。小版本不进 URI（加字段靠兼容性消化），URI 版本号只在破坏性变更时+1——频繁大版本号是设计失败的信号（每次加参数都 v+1 说明 §3.1 没做）。

3.4 幂等性：重试安全的地基

  • 写操作支持 Idempotency-Key 头（客户端生成唯一键，服务端按键去重）：网络重试不会重复下单。支付、导出创建这类操作必备（与 Agent 系列 12 篇的幂等设计同源）；
  • 读操作天然幂等；DELETE 幂等但注意语义（重复删第二次返回 404 还是 200？文档写明）。

4. 错误设计：调用方最常光顾的地方

四条准则：

  1. 状态码用大类表达"谁的错"：4xx 调用方错（改了请求也没用/有用）、5xx 服务端错（可重试）；语义细化到 400/401/403/404/409/422/429 各司其职（RFC 9110）；
  2. 错误体机器可读：稳定 code + retriable 标志——调用方的重试逻辑不该靠解析 message 字符串；
  3. message 面向开发者：写"下一步做什么"（“cursor 过期请重新获取”），不写内部堆栈；堆栈进服务端日志并返回可关联的 request_id；
  4. 错误码目录化：所有 code 在文档中可查、增量不删（老调用方可能依赖旧 code 的字符串值）。

5. 一致性：API 的"风格统一"靠治理不靠自觉

  • 团队级 API 设计指南（写下来，如 Google API Design Guide / Microsoft REST API Guidelines 是公开的成熟范例）：命名、分页、错误、时间格式一次定死；
  • 契约先行（design-first）：先写 OpenAPI/protobuf 定义、评审通过再实现——契约文档从"事后生成的装饰"变成"设计的载体"；
  • 契约测试（contract testing）：实现与契约的自动比对（如 OpenAPI diff 检查破坏性变更进 CI，类似 Dredd/Schemathesis 的思路）——把 §3.1 的判别表交给机器执行；
  • SDK 生成：从契约生成多语言客户端，保证一致性、消灭手写漂移。

6. 内部 API 的"契约管理"：跨团队协作的枢纽

大型组织里 API 契约的隐藏价值：它是团队间异步协作的界面（康威定律的工程化应用，07/08 篇）——

  • 消费方按契约开发 mock，不必等服务方实现（并行开发）；
  • 契约评审即跨团队的架构沟通（评审的不只是字段，还有边界与所有权）；
  • 契约变更是显式通知义务，"我改了下你们调用的接口"不再是可容忍的沟通方式。

自测

  1. 异步操作为什么建模为"任务资源"？202 与 Location 头的配合？
  2. 背出 §3.1 兼容性判别表。枚举加值为什么会破坏旧调用方？
  3. "宽进严出"的边界在哪？对脏数据宽容会发生什么？
  4. 破坏性变更四步流程？为什么频繁大版本是设计失败信号？
  5. Idempotency-Key 解决什么问题？与 Agent 12 篇的幂等设计有何同源关系？
  6. 错误体为什么需要机器可读的 retriable 字段？

第 5-6 周教程：七方案大横评与量化推理落地复盘

本周要回答的问题

  1. 量化格式与推理引擎怎么匹配？为什么"格式不匹配就白量化"？
  2. 4-bit 模型在 batch=1 时为什么能比 FP16 还快？带宽账怎么算？
  3. 量化什么时候反而变慢？（算力瓶颈反转）
  4. 为什么 PPL 只涨 0.2，长文本生成却崩了？评测陷阱怎么防？

对应学习计划：第 5-6 周。交付物：《Qwen2.5-7B 七种量化横评报告》——{FP16, FP8, INT8-SQ, INT8-GPTQ, INT4-GPTQ, INT4-AWQ, INT4-NF4} × {PPL, MMLU 子集, 显存, tokens/s(b=1/32)} 全矩阵 + 引擎映射 + 决策树。

1. 第一性原理：量化的收益最终在"带宽与算力"上兑现

1.1 访存瓶颈下的带宽推导（面试必考）

LLM decode（batch=1）是极端访存瓶颈：每个 token 要把全部权重从显存搬到计算单元一次。以 7B 模型为例（Stage 3 会再精算一遍）：

ttoken≈权重体积显存带宽⇒tokens/s≈BWbytes per param×Nparamst_{\text{token}} \approx \frac{\text{权重体积}}{\text{显存带宽}} \quad\Rightarrow\quad \text{tokens/s} \approx \frac{BW}{\text{bytes per param} \times N_{\text{params}}} ttoken​≈显存带宽权重体积​⇒tokens/s≈bytes per param×Nparams​BW​

FP16：14 GB/2 TB/s≈14314\,\text{GB} / 2\,\text{TB/s} \approx 14314GB/2TB/s≈143 tokens/s 上限；INT4（4.25 bpw ≈ 3.7 GB）：≈540\approx 540≈540 tokens/s 上限。权重体积缩 4 倍 → 带宽上限升 4 倍——这就是 4-bit 在 batch=1 反超 FP16 的根本原因：瓶颈资源是带宽，而量化恰好压缩了瓶颈资源。

1.2 什么时候量化反而变慢

  • 算力瓶颈反转：batch 拉大后，decode 的算术强度（arithmetic intensity）上升，越过 Roofline 拐点变成算力瓶颈——此时 W4A16 的权重反量化开销开始吃算力，收益缩水甚至为负；
  • 内核缺失：格式没有匹配的高效内核（如 NF4 直接用于推理），反量化走通用路径，实际带宽利用率远低于理论；
  • 格式不匹配：模型量化格式与引擎加载器不对齐，引擎回退到"加载后即时反量化成 FP16"——体积省了、速度一分没省。

1.3 格式与引擎匹配表（背下来）

量化方案 格式特征 首选引擎 备注

Marlin：专为 4-bit × FP16 的 GEMM 手写的高性能内核，靠寄存器级流水与异步拷贝把反量化藏进带宽等待里——是"4-bit batch=1 极速"的具体兑现者。

1.4 量化评测陷阱

PPL 是逐 token 的平均损失，对长程一致性不敏感。典型崩法：PPL +0.2 看似无损，但 512 token 以上的生成开始重复、逻辑断裂、指令跟随崩坏——量化误差在自回归循环里复合放大。因此评测必须加两列：

  • 长输出任务：让模型生成 512-1024 token 的连贯文本，人评 + 重复率；
  • 指令跟随：IFBench 或自建指令集，测"让它干什么就干什么"是否保持。

3.3 决策树（报告收尾）

3.4 横评执行纪律：让数字可比、可信、可复现

七方案横评最大的工程风险不是"量化做得不好"，而是"测得不公平"。五条纪律：

  1. 同机同时序：所有方案在同一台机器、同一驱动/框架版本上依次跑，跑前清缓存、重置频率；禁止"FP16 在 A100 测、INT4 在 4090 测"这类跨机对比。
  2. 固定生成配置：温度、max_tokens、prompt 集合完全一致。量化方案之间比的是"同一问题的不同回答速度"，任何采样参数差异都会污染结论。
  3. 预热 + 多次取中位：每个方案先预热 3-5 次（JIT 编译、内核选择、缓存填充），正式计时取 5 次的中位数——均值会被冷启动异常拉偏。
  4. 显存测量标准化：统一在"加载完成、首请求前"与"峰值"两个时点记录 torch.cuda.max_memory_allocated()，并在报告里注明测量点。
  5. 脚注记录一切：框架版本、内核路径（Marlin/vLLM GPTQ kernel/TRT tactic）、量化时的校准集——三个月后复盘时，脚注就是数字的合法性证明。

3.5 报告成文骨架（直接照抄成文）

面试用法：把第 5、6 节压缩成一页，就是"你做过的最有说服力的量化工作"的展示材料——数字、结论、决策树三件套齐全，比任何口头描述都有力。

4. 工程权衡与失效模式

4.1 权衡

  • 位宽越低体积越小，但评测成本越高：3/4-bit 必须跑长输出与指令跟随，不能只看 PPL。
  • 引擎绑定换性能：Marlin/TRT 内核把 4-bit 吃出真加速，但锁死部署栈；自研服务要评估加载器支持。
  • 横评的时效性：vLLM/TRT-LLM 迭代快，数字带版本号记录（如"vLLM 0.6.x, H100"），否则三个月后就失去可比性。

4.2 失效模式

  1. 格式-引擎错配回退：症状——4-bit 模型推理速度 ≈ FP16；根因——引擎不支持该格式，静默反量化；修复——加载后检查内核路径/日志，确认走量化内核。
  2. b=32 误用 b=1 结论：症状——上线后吞吐不升反降；根因——AWQ 在 b=1 是冠军、大 batch 却受反量化拖累；修复——横评必须同时报 b=1 与 b=32。
  3. PPL 假阴性：症状——所有量化方案 PPL 差 < 0.3 就选了最激进的，线上长文本崩；根因——只测短窗口 PPL；修复——加长输出与指令跟随两列。
  4. 跨硬件外推：症状——A100 上的横评结论搬到 4090 全变；根因——带宽/算力比不同、内核支持不同；修复——结论标注硬件，目标硬件上复测前三名。

5. 延伸思考题（含解析）

Q1：为什么"格式不匹配就白量化"？从数据流角度说清楚。
A：量化模型的加速来自"计算全程保持低位宽"（少搬数据、走低位宽内核）。若引擎加载器不认该格式，会在加载或首层就反量化回 FP16——此后带宽、算力全部按 FP16 计，只剩"文件小了"这一个收益，推理速度归零。

Q2：Marlin 凭什么让 4-bit batch=1 比 FP16 快 3-4 倍而不是只快"体积比"那么多？
A：它把反量化与 GEMM 融合，用异步内存拷贝 + 寄存器流水把"解码 4-bit"的开销藏进带宽等待时间；同时 batch=1 是纯访存瓶颈，体积缩 3.76× 几乎 1:1 兑现为延迟收益——内核效率 × 瓶颈兑现，两者相乘。

Q3：INT8-SQ 为什么在 b=32 常常是吞吐冠军，却不是 b=1 冠军？
A：b=32 时 GEMM 算力需求 32×，W8A8 的 INT8 Tensor Core 算力翻倍直接兑现；b=1 时瓶颈是搬权重，INT8 只缩 2× 体积，不如 INT4 的 ~4×，算力优势又用不上——两头不讨好。

Q4：横评里 NF4 推理垫底，是否说明 NF4 方案失败？
A：不是。NF4 的价值在训练（免校准、分布匹配、配双重量化省显存），垫底只是"拿训练格式硬跑推理"的错位。正确用法：NF4 微调 → 转 GPTQ/AWQ/GGUF 部署。评测的是"方案-场景"组合，不是格式本身。

Q5：如果老板只给你一句话的场景"客服机器人、并发高、成本敏感"，你怎么从决策树走到方案？
A：并发高 → 大 batch → 算力瓶颈 → 排除 W4A16；成本敏感 → 压缩位宽 → INT8-SQ(W8A8) + TRT-LLM；有 H 卡则上 FP8 再快一档；客服是短输出，但仍要过一遍指令跟随评测防幻觉。这就是"场景 → 瓶颈资源 → 格式 → 引擎"的四步走，也是横评报告的最终用途。

6. Stage 2 复盘：把六周缝合成一个知识网络

6.1 全阶段知识地图

六周的一句话总结：量化不是"把数变小"，而是"在预算约束下重新分配误差"——每个算法都是一种误差分配策略，横评就是给这些策略发成绩单。

6.2 与前后阶段的接口

  • 向后（Stage 3）：本周的带宽推导（§1.1）会在 Stage 3 第 1 周的 Roofline 中再次出现并推广；"格式不匹配回退"的失效模式会在手写 INT4 GEMV 时变成你的设计约束。
  • 向后（Stage 4）：NF4/INT4 的知识直接变成 GGUF 的 Q4_K 认知；"端侧选 W4A16"的结论会在四平台选型报告里被实测复核。
  • 向前（Stage 1 基线）：横评矩阵已追加进压缩评测基线总表——从今往后任何新方案（Stage 5 的引擎优化、Stage 6 的昇腾部署）都以这张表为对照系。

6.4 横评常见翻车点（前人踩过的坑）

  1. 量化配置没写进报告：group_size、act_order、校准集条数缺一不可——同一方案不同配置，数字能差 20%。
  2. vLLM 版本漂移：0.5 → 0.6 的内核升级可能让同一模型的吞吐变化 30%；每次横评锁定版本，升级后重测全部行。
  3. b=32 测试用了错误的并发方式：必须是一个请求批内 32 条（真 batch），不是 32 个串行请求——后者测的是延迟不是吞吐。
  4. 显存没清干净：上一个方案的 KV cache 残留会让下一方案的显存数字虚高；每方案之间重启进程。
  5. MMLU 子集抽样不一致：500 题抽样的随机种子必须固定，否则两组数字的差异可能来自题目而非模型。

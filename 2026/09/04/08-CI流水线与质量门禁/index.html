08 - CI 流水线与质量门禁：把纪律自动化

本篇目标

  1. 理解 CI 的本质——它不是"跑测试的地方"，是"每次提交对系统可用性的证明"；
  2. 拿走一套完整的 GitHub Actions 工作流（Python + C++ 双矩阵，yaml 全量可用）；
  3. 建立分层策略：PR 上跑什么、nightly 跑什么，以及覆盖率怎么当门禁用而不伤人；
  4. 落地失败处理纪律：红色不可合并 + flaky 测试的追踪与隔离机制。

1. CI 的本质：每次提交证明系统仍可用

持续集成（CI）的最小定义只有一句：每次提交都触发一次全自动化构建与验证，并在失败时让所有人立刻知道。Martin Fowler 与 Matthew Foemmel 的经典文章《Continuous Integration》（2000 年代初成文，持续更新）强调的从来不是工具，而是两条纪律：提交即验证、修复失败优先于一切新工作。

为什么这条纪律值钱？回到 01 篇的账本：没有 CI 时，“系统还能用"靠的是某个人某天想起来跑一次测试——这个间隔以天/周计；有 CI 后，间隔被压到"一次提交”。集成测试左移的极限形态就是 CI：bug 的发现时间从"联调那天"提前到"写坏它的那一次 push"。

由此推出门禁（quality gate）的定位：CI 不是"体检中心"，是"闸机"。闸机的规则必须简单、客观、无歧义：绿的合，红的停。任何"红了但先合吧"的特批，都是在教整个团队"红色可以商量"——这个信号的破坏力比任何单个 bug 都大。

设计说明（每条都是纪律，不是偏好）：

  1. uv sync --frozen：CI 只按 uv.lock 装，锁与 pyproject 不一致就该红——在 CI 里隐式重解析等于放弃可复现性（uv 08 篇的三条 CI 纪律之一）；
  2. 静态检查排在测试前：类型/lint 失败 3 秒可知，没必要等 3 分钟的测试先跑完（09 篇详述这层为什么算"测试"）；
  3. fail-fast: false：矩阵的目的是拿"哪个版本挂了"的全量情报，fast-fail 只省几分钟却丢信息；
  4. C++ 侧 CTest 是 CMake 原生的测试入口：enable_testing() 后 gtest 自动注册为 ctest 用例（11 篇给全 CMake 接线）；clang-tidy 挂在 CMake 变量上，警告即错误；
  5. 密钥零落地：需要真实凭据的用例不进 PR 流水线（用 secrets 注入的 nightly 专属用例跑）。

3. 分层策略：PR 测什么，nightly 测什么

PR 流水线的预算是十以内分钟级——它是每个工程师每天要过几十次的闸门，慢门禁的结局是被绕过（本地 --skip、催 admin merge）。分层按"价值/耗时比"排：

层 内容 时长预算 触发时机
PR 主线 lint + 类型 + 单元 + 轻集成 + 覆盖率门禁 < 10 min 每次 push
PR 补充 矩阵（多 Python 版本 / 多编译器） < 15 min push（并行跑）
nightly 全量：慢集成、testcontainers 真库、property 大样本（max_examples=2000）、Sanitizer 构建、性能基线对比 < 2 h 每日定时 + 周末跑更长

4. 覆盖率：当诊断用，别当 KPI

coverage.py 的最小闭环（实测输出，pyproject.toml 配置同下）：

fail_under 触发时进程退出码为 1（实测），这就是 CI 里的硬门禁。但全局阈值是一把钝刀：新项目从 0 拉到 85 痛苦，老项目历史欠账大、一卡全卡。Google Testing Blog《Code Coverage Best Practices》（2020，Carlos Arguelles 等）给出的工程化答案是：关注增量（absolute coverage of changed lines），别只盯全量——代码评审时看"这次改动新增的行有多少被测试执行"，新代码 100%、老代码自然漂移到高位。

落地工具：diff-cover（对 coverage.xml 与 git diff 求交集，输出"改动行覆盖率"并可与门禁联动）；PR 流水线用 diff 门禁 + 较低全局阈值（如 60），nightly 报全量趋势。误区温习（01 篇）：覆盖率是必要条件不是充分条件——它抓"从未被执行的行"，不抓"被执行但断言为空"的测试。

5. 缓存与提速：让快反馈可持续

三个杠杆，按收益排序：

  1. 工具链缓存（uv 的主场）：setup-uv 的 enable-cache 缓存全局缓存目录（包与 wheel），键绑定 uv.lock 哈希——锁没变，装依赖从分钟级到秒级（细节见 uv 08 篇）。C++ 侧对应 ccache（apt install ccache + CMake -DCMAKE_CXX_COMPILER_LAUNCHER=ccache），增量构建收益巨大；
  2. 测试分片：矩阵多 job 各跑一部分。pytest 生态用 pytest-split（按历史耗时均匀分组）或手工按目录分：

分片的前提是测试相互独立（01 篇 FIRST 的 I）——有顺序依赖的套件分片后必炸，这也是对独立性的免费体检；
3. 并行：pytest -n auto（pytest-xdist）多进程；注意 07 篇的端口/路径隔离是并行化的前置条件。再配合 --durations=10 定期揪最慢的十个测试优化。

6. 失败处理纪律：红色不可合并 + flaky 追踪

红色不可合并是硬规则：main 分支红了，修复优先级高于一切新 PR（Fowler 的 CI 纪律原文如此）。两个机制配套：

  • 分支保护（GitHub：Settings → Branches → Require status checks）：把 python、cpp 两个 job 设为必须通过，"红着合"在机制上不可能；
  • 本地预演：push 前跑与 CI 相同的命令（uv 08 篇的"新人三行命令"扩展为五行，含 lint+mypy）——CI 惊喜应该在 PR 打开前耗尽。

flaky 测试是门禁的天敌。 Google Testing Blog《Flaky Tests at Google and How We Mitigate Them》（John Micco，2016）披露的数据与机制都值得直接借用：flaky 测试在谷歌规模下每天产生大量误报，开发者一旦学会"红色可以点重试"，门禁失效开始连锁。谷歌的处理框架可以搬到任何团队：

  1. 识别：CI 上记录"同 commit 重跑后结果翻转"事件（rerun 日志或专用工具 pytest-rerunfailures 的 --reruns 配合上报——重试只是止血，必须留下记录）；
  2. 隔离（quarantine）：确认 flaky 的测试移入隔离标记（如 @pytest.mark.flaky(runs=3) 上报 + 隔离清单），隔离集不阻塞合并但进每日报告，限时一周内修复或删除；
  3. 归因：07 篇稳定性四清单是第一排查表；仍无头绪的（真并发竞态、时序敏感），给测试加"失败即录环境"（CI 上下文日志）再分析；
  4. 退出机制：隔离超期未修 = 自动删除该测试并开 issue——一个长期 flaky 的测试比没有测试更糟，它持续消耗全队的信任。

经验做法：把"本周新增 flaky / 修复 flaky / 隔离中"三个数字放进团队周报——被看见的数字才会被治理。

常见误区

误区一：门禁越多越好。 每条门禁都有误杀成本。原则：新门禁上线先观察两周（报告不阻塞），误杀率可接受再转硬门禁。

误区二：nightly 红了不管。 nightly 的定位是"主干的体检中心"，连红说明主干在积累债务——比 PR 红更危险，因为它阻塞不了任何人。

误区三：覆盖率阈值定在 100%。 达成成本指数增长（异常处理/兼容分支），且逼出无断言测试。工程实践：全局 60~85 + 改动行 100%，比单看一个数字健康得多。

误区四：缓存把 CI 变成不可复现的。 缓存失效策略不明确（键不含 lock 哈希）会让 CI 偶尔跑在旧依赖上。所有缓存键必须能从仓库内容推导（uv 的键=lock 哈希，ccache 的键=编译输入哈希），并保留"清缓存重跑"的入口。

误区五：--reruns 3 挂上就算治理了。 重试掩盖红色、无记录无归因，等于给每个 flaky 发了永久通行证。重试必须与上报/隔离绑定。

本篇小结

  • CI 本质：提交即验证 + 修复优先；门禁是闸机不是体检中心，规则必须无歧义；
  • 双语言工作流四个锚点：uv sync --frozen、静态先于测试、fail-fast: false 保情报、CTest+clang-tidy 收 C++ 侧；
  • 分层：PR 十分钟内（增量价值/耗时最高），nightly 吃掉慢集成/大样本/Sanitizer/性能基线，必须有通知与责任人；
  • 覆盖率：fail_under 是退出码 1 的硬门禁，但工程正解是 diff-cover 增量门禁 + 全局宽松阈值；覆盖率是必要条件非充分条件；
  • 提速三杠杆：工具链缓存（uv/ccache）、分片（前提是独立性）、xdist 并行；慢门禁必被绕过；
  • 纪律：分支保护让"红着合"机制上不可能；flaky 治理四步——识别、隔离、归因、超期即删；重试必须留记录。

练习

  1. 给本章 yaml 补第三个 job nightly-sanitizer：C++ 侧以 ASan+UBSan 构建并跑 ctest（提示：-DCMAKE_CXX_FLAGS="-fsanitize=address,undefined"，09 篇有完整接法），并设置 schedule。
  2. 为你的项目配置 diff-cover 门禁：生成 coverage.xml → diff-cover coverage.xml --compare-branch=main --fail-under=90，在 PR 流水线接入并记录首轮各 PR 的数字。
  3. 用 pytest --durations=10 找出你的套件最慢 5 个测试，逐个归因（I/O？sleep？夹具过重？），优化两个并记录前后时长。
  4. 给你的套件做一次"独立性体检"：随机打乱执行顺序（pytest-randomly）跑 3 次，记录是否出现顺序相关失败并归因。
  5. 起草你团队的 flaky 治理条款（隔离标记、责任人、时限、退出动作），对照谷歌四步补缺，写成一页 wiki。

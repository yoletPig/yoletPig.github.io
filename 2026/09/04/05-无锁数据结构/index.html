05 - 无锁数据结构

本篇目标

  • 用实测数据回答"锁的代价什么时候不可接受、什么时候被高估"。
  • 亲手实现无锁 SPSC 环形队列（rigtorp/SPSCQueue、folly::ProducerConsumerQueue 同款思想），逐处解释内存序。
  • 理解无锁内存回收为什么难（Hazard Pointer 思想）与 RCU 的读侧零开销。
  • 用"CAS 重试风暴"实验破除"无锁 = 更快"的迷信，建立"99% 用锁 + 少量原子"的工程直觉。

前置：第 04 章（memory_order、happens-before）、《C++》系列 13（线程安全 RingBuffer 的加锁版）。

1. 锁的代价：什么时候不可接受

结论（实测得出，不是背书）：锁的真正代价来自"争抢"而非"加锁"。临界区极短（几十纳秒）且争抢激烈时，锁的睡眠/唤醒开销才不可接受——这正是无锁队列的用武之地：生产者-消费者之间只有一个指针游标，没有临界区可言。反过来，临界区里有任何实际工作（查表、拷贝、计算），锁的开销立刻摊薄到可忽略。

2. 无锁 SPSC 环形队列：逐行讲内存序

先立定义（[intro.progress] 的惯用归纳）：无锁（lock-free） = 任意时刻停下所有线程，至少有一个能取得进展（个别线程卡住不拖累全局）；有界等待更进一步。SPSC（Single-Producer Single-Consumer）是唯一容易做对的无锁结构：每个游标只有一个写者、一个读者，这把同步需求压到最低——一处 release/acquire 配对。

3. MPSC 概览：多个生产者怎么办

SPSC 的极限场景之外，更多是 MPSC（多生产者单消费者：日志聚合、GPU 命令队列）与 MPMC（线程池任务队列）。生产者多于一个后，head_ 变成多个写者——单一 release/acquire 不再够，典型做法：

  • CAS 竞争游标（compare_exchange_weak 抢占 head）+ 两阶段提交：先 CAS 占坑，写完数据再把"就绪序号"发布，消费者只能消费连续就绪区间（folly::MPMCQueue、moodycamel::ConcurrentQueue 的思路）。
  • 每生产者一条 SPSC 队列，消费者轮询（round-robin）多条 SPSC——把 MPMC 问题降维成已解决的 SPSC 问题。实现简单、无 CAS 风暴，代价是消费者公平性需要自己调度。经验做法：生产者数固定且不大时，先选这条。

MPSC/MPMC 的实现复杂度跨过 SPSC 一个数量级，几乎总是应该直接用 folly/moodycamel/boost::lockfree，而不是手写（经验做法，见第 6 节的"该不该"）。

4. Hazard Pointer：为什么无锁回收内存难

SPSC 队列的内存是预分配环形数组，没有回收问题。但无锁栈/链表（如 Treiber stack）把节点 new/delete 混进并发路径，立刻撞上难题：

难点在于：A 持有的只是"一个副本"，B 无法知道"还有人要读"。经典方案 Hazard Pointer（危险指针）：

  1. 每个读者线程有若干"危险指针"槽（公开可见的原子槽位）。
  2. 读者解引用前，先把指针副本发布到自己的 hazard 槽，再回头验证节点还在链上（否则重来）。
  3. 删除者把节点挂到"待删清单"，只有当任何 hazard 槽都不再指向它时才真正 free。

验证-发布之间存在竞争窗口，所以要"发布 → 复查 → 不在则重试"的两步协议。Michael 2004 的论文（Hazard Pointers: Safe Memory Reclamation）是原始出处；C++ 上的成熟实现见 folly 的 hazard 模块。替代思路 Epoch-Based Reclamation（EBR）：读者进入临界区登记"epoch"，回收者等全局 epoch 推进（所有读者都离开旧 epoch）后整批回收——检查 O(1)，代价是回收有延迟。

5. RCU 概念：读侧几乎零开销

RCU（Read-Copy-Update，Linux 内核大规模使用）把上述思想推到极致，服务"读多写极少"的数据（路由表、配置）：

  • 读者：进_rcu → 读指针副本 → 用 → 出_rcu。全程无原子操作、无锁、无内存写（编译器屏障级别）。
  • 写者：复制一份新结构 → 在副本上修改 → 原子地替换根指针 → 等"宽限期"（grace period，所有旧读者离开）→ 释放旧副本。

读者完全不感知写者的存在，读路径开销接近零；代价由写者承担（复制 + 等待 + 写多时副本爆炸）。与 Hazard Pointer 的关系：都是"延迟回收"，RCU 把"谁还在读"的判定从逐指针验证变成全局 epoch 推进。C++ 用户态可参考 liburcu（Userspace RCU）。经验做法：配置/参数表这类"分钟级才改一次、纳秒级读一次"的数据，RCU 或 shared_ptr 原子交换（copy-on-write）都远好于读写锁。

6. 无锁不等于更快：CAS 重试风暴实测

最常见的迷信：“锁有系统调用开销，无锁一定快”。用计数器做反例——三种实现完成同样的"4 线程各 1000 万次 +1"：

读数：CAS 循环比 fetch_add 慢一倍。原因——fetch_add 是硬件原子的读改写（x86 上 lock xadd，一条指令成功）；CAS 循环在 4 线程争抢同一缓存行时反复冲突重试，每次失败都要重新 load 再交换，还制造额外的缓存一致性流量。“手写的乐观并发"在没有硬件原子原语支持时就是这个下场。真正的教训不是"CAS 不行”，而是：

  1. 有硬件原子原语（fetch_add/fetch_or/…）就别手搓 CAS 循环；
  2. 争抢的根源是"共享写热点"，解法是消除热点而不是换同步原语（分片计数再汇总、每线程局部缓冲）；
  3. 无锁结构赢在"临界区为零 + 无系统调用"，不是赢在"用了 atomic"。

7. 什么时候该用无锁（经验做法）

按可维护性与收益排序的决策阶梯：

  1. 默认：std::mutex + RAII 锁。临界区 ≥ 1μs 或每秒次数 < 10 万，锁的成本根本测不出来；可读性、可调试性（死锁能 dump 栈，无锁只能看汇编）完胜。
  2. 单变量协调：atomic 标志/游标/计数。这不算"无锁编程"，是标准工具（《C++》系列 12）。
  3. 生产者-消费者管线：无锁 SPSC 队列。音频采集→推理、采样→渲染这类"每几十微秒过一小块数据"的固定管线，SPSC 是收益最确定的无锁结构（rigtorp/SPSCQueue 可直接用）。
  4. 其余无锁结构（栈/哈希/MPMC）：直接用 folly/boost::lockfree/moodycamel，不要手写。内存回收（Hazard Pointer/EBR）与 ABA 的坑在第 4 节已经看到，手写正确的工程量以月计。

99% 的场景应该用锁 + 少量原子变量；剩下的 1% 里，SPSC 队列又占大头——这是并发工程里少有的可以放心说的经验法则。

常见误区

  1. 以为无锁 = 不用锁 = 快：第 6 节实测 CAS 循环慢 fetch_add 一倍。无锁的收益来自结构设计，不是原子原语的堆砌。
  2. SPSC 队列被两个线程 push：SPSC 的全部正确性建立在"游标单写者"上，生产者多一个，队列立刻变成未定义行为。用 static_assert/类型系统外的纪律（命名、断言、文档）守住这个前提。
  3. 在无锁代码里调用可能异常的代码：placement new 后 T 的拷贝构造抛异常，游标已推进，队列状态损坏。这就是实现里 static_assert 要求 noexcept 构造的原因。
  4. 忙等不用 pause/让出：while (!push(v)) {} 在单核或超线程上空转会拖死伙伴线程。生产环境要么挂 std::this_thread::yield()，要么限制重试次数后退避（经验做法）。
  5. 用 volatile 写无锁：第 04 章讲过，volatile 无原子性无内存序，无锁代码里它唯一的用途是 MMIO（嵌入式），不是线程同步。
  6. 忘测消费者追不上生产者的"满"路径：环形队列的满/空边界是竞争高发区，测试必须同时覆盖"队列空转"与"队列打满"两种稳态。

本篇小结

  • 锁的真实代价 = 争抢成本：无争抢 mutex ≈ 2.5ns（futex 快路径），4 线程争抢短临界区时 mutex/自旋锁都跌进 850-1330ms 量级而原子游标 220ms——短临界区高争抢才需要无锁。
  • SPSC 环形队列是无锁入门标准案例：游标单写者 + 一对 release/acquire 发布 + alignas(64) 防伪共享 + 容量 2 的幂；满/空返回 bool 把等待策略留给调用方。
  • MPSC 优先"每生产者一条 SPSC + 消费者轮询"；MPMC 直接用 folly/moodycamel。
  • 无锁内存回收难在"删除者不知道有没有读者"：Hazard Pointer 逐指针验证、EBR/RCU 用全局 epoch 延迟回收；读多写少用 RCU/copy-on-write。
  • CAS 重试风暴实测（830ms vs fetch_add 452ms）证明无锁不等于更快；99% 用锁 + 少量原子，1% 里优先 SPSC。

练习

  1. 给 SpscQueue 加 try_push_batch(const T* vs, size_t n)（一次 release 发布多个元素），思考为什么要同时限制"n 不超过剩余空间才整体成功"。
  2. 把两个游标的 alignas(64) 去掉重测 spsc_test，观察吞吐变化；再用 perf stat -e cache-misses 对比两次运行。
  3. 实现 Treiber 无锁栈的 push/pop（CAS 头插法），并指出它为什么必须配合 Hazard Pointer/EBR 才能安全 delete。
  4. 把第 1 节 4 线程计数改成"每线程局部累加、结束时原子汇总一次"，测量三种方案的最终耗时，量化"消除共享写热点"的收益。
  5. 阅读 rigtorp/SPSCQueue 源码中 per-slot seq 的用途，回答：教学版在"生产者 resize 到一半"这类不存在的问题之外，seq 还防住了什么？（提示：队列被误用时 push 与 pop 各自的多个读者）

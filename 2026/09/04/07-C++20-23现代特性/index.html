07 - C++20/23 现代特性

本篇目标

  • 掌握四个"马上就能用"的特性：ranges（管道与惰性）、span（零拷贝视图）、concepts 复习应用、三路比较 <=>。
  • 认清两个"工具链门槛特性"的真实现状：std::expected/std::format（需要 g++ 13+，本文给替代方案）与 modules（构建系统支持仍不完善，如实评估）。
  • 与 Python 的对等物对齐概念（生成器表达式 / memoryview / 异常返回值），降低心智负担。
  • 建立"什么时候不用新特性"的决策框架（团队一致性优先）。

环境说明（本篇如实交代）：以下特性的 g++ 可用版本——ranges/span/concepts/<=> g++ 10+（本系列验证环境 g++ 11.4 实测可运行）；std::expected/std::format g++ 13+，验证环境没有，文中代码给出等价的"现在就能编译"的替代并标注出处。

1. ranges：管道语法与惰性求值

《C++》系列 08 的 std::transform/copy_if 每步都生成中间容器；ranges（C++20，[ranges]）用视图（view）+ 管道（|）把整条流水线写成一行，且惰性求值——不遍历就不计算，全程不产生中间容器：

两个关键认知：视图不拥有数据（悬空风险同 string_view，见误区）；惰性意味着 views::iota(1) 这种"无限序列"合法——组合上 take(5) 才有界。与手写循环对比：手写循环最快但样板多；ranges 在 -O2 下与手写循环同性能（每层 view 被内联掉），可读性完胜（经验做法：业务过滤/变换管道直接 ranges，热点内层循环才手写）。

2. span：安全边界 + 零拷贝

std::span（C++20，[views.span]）是"指针 + 长度"的数组视图，填平了"裸指针 + size 参数对"的坑：

与 Python 的 memoryview、ndarray 切片是同一思想：视图不拷贝、边界自知。API 设计规则（经验做法）：接收连续序列的函数参数一律 std::span<const T>，比"两个迭代器"或"const T* + size_t"都更安全；写操作才用非 const span。llama.cpp 的 ggml_tensor 数据指针操作、RKNN 的输入输出缓冲都是"指针+长度"形态，span 是它们的类型安全包装。

3. expected：C++23 的错误处理

《C++》系列 11 讲过三流派：异常 / optional / variant。std::expected<T, E>（C++23，P0323R12）是"要么值要么错误"的专用解——语义比 optional 清楚（失败有原因），控制流比异常明确（错误在签名里），恰好契合端侧 -fno-exceptions 的约束（第 10 章）：

g++ 11 环境的等价替代：tl::expected（单头文件，作者 Sy Brand / TartanLlama，也是 P0323 的评审参与者），API 与标准版一致，#include "tl/expected.hpp" 后把 std::expected 全文替换为 tl::expected 即可，未来升 g++ 13 时一行别名切回（经验做法：项目里 template <typename T, typename E> using expected = tl::expected<T, E>;，收敛在别名上）。再往前的兜底是《C++》系列 11 的 optional<T> + 错误码出参。

4. std::format：类型安全 + 可读

iostream 十余年来的三宗罪（状态化全局 locale、运算符重载可读性差、慢），printf 的不安全（类型与实参脱钩），std::format（C20 文本格式化 P0645，**库版 g 13+ 才有**；fmtlib 是同一 API 的库版，g++ 11 可用）一起解决：

安全性与性能的两个事实：占位符与实参不匹配是编译错误（不是 printf 的运行期 UB/垃圾值）；fmtlib 官方基准显示格式化短字符串比 snprintf 快、比 iostream 快一个量级（数值来自 fmtlib benchmark 页，量级结论跨机器稳定，具体倍数随用例变化）。g++ 11 的替代：直接用 {fmt} 库（FetchContent 拉取，第 01 章），或继续 snprintf + 人工核对类型（经验做法：日志路径尽早切 format/fmt，一次把 %s 类隐患清掉）。

5. concepts 复习：约束放在接口上

第 02 章已讲 concepts 语法与报错对比，这里补它在接口设计上的应用要点：

  • 库 API 的第一行文档就是 concept：template <std::ranges::input_range R> 比注释"R 必须可遍历"强得多——编译器当守门员。
  • 标准库自带的概念优先复用：std::integral/floating_point、std::same_as/convertible_to、std::ranges::range、std::invocable（清单见 cppreference “Named requirements”/“concepts” 页）。
  • 多约束组合：template <typename T> requires std::movable<T> && std::regular<T>——比 SFINAE 嵌套 enable_if 可读一个量级。
  • g++ 11 完全可用（第 02 章实验已验证），是 C++20 特性里最该立刻全量启用的一个（经验做法）。

6. 三路比较：一次写全六个关系运算

C++20 之前，支持 ==,!=,<,>,<=,>= 要写六个函数；<=>（[class.compare.default]）一次 = default 全解决：

要点：<=> 的返回类型（strong/weak/partial ordering）表达相等性与可全序性，浮点字段会让默认推导落到 partial_ordering，< 在遇到 NaN 时为 false——语义由类型携带而非注释。排序场景（std::sort 的比较器）照旧用 lambda，<=> 主要省的是"值类型六件套"。

7. modules：现状如实说

C++20 的 modules（export module、import）承诺解决头文件三大痛：重复解析、宏泄漏、编译墙。但 2024 年的工程现状是不成熟，如实评估：

  • 编译器：g++ 的 modules 支持长期滞后（g++ 11 的 -fmodules-ts 实验性质，C20 标准语义在 g 14/15 才逐步可用）；MSVC 最完整；clang 的 stdlib 模块化进度缓慢。
  • 构建系统：CMake 到 3.28 才提供正式的 target_sources(... FILE_SET CXX_MODULES) 支持（本系列约定的 CMake 3.22 不可用）； Ninja/MSBuild 需要配合"依赖扫描"模式，增量构建复杂度陡增。
  • 生态：主流第三方库（含 gtest、fmt 的 CMake 集成）仍以头文件/传统 TU 为主，纯 modules 项目几乎是孤岛。

结论（经验做法）：2024-2026 的生产项目继续用头文件 + Pimpl（第 11 章）控编译墙；modules 观察到"目标工具链全绿"再动。学习成本不高，值得读一遍 cppreference 的 modules 页面留个印象，等生态到位时能快速跟上。

8. 协程预告

C++20 协程（co_await/co_yield/co_return）值得单独一章：它把"回调地狱"重写成顺序代码，是异步推理服务（llama.cpp server、ASR 流式识别）的核心表达工具。语言机制、promise_type、最小 generator、生命周期陷阱全部在第 08 章展开，此处只立一个路标。

9. 什么时候不用新特性（经验做法）

决策框架，按重要性排序：

  1. 团队一致性 > 个人先进：团队在 C++17，你单方面上 std::span 会让 review 与构建双输。特性迁移是团队决策，用"新文件新标准、旧文件按需迁移"渐进推进。
  2. 工具链门槛算清楚：std::expected/std::format 要求 g++ 13；目标部署机（嵌入式交叉工具链、CentOS 7 的 devtoolset）给不了就别上，或用第 3/4 节的库替代（tl::expected、fmt——库版特性不锁编译器，这是最稳的引入路径）。
  3. 性能敏感路径先测：ranges 与手写循环在热点里同速（内联后），但 std::variant vs 虚函数（第 06 章）这类"特性选择即架构选择"必须带实测数字进 review。
  4. "标准库已有就别引第三方"有例外：g++ 11 拿不到 std::format/expected 时，fmt/tl::expected 就是正确答案——标准是方向，可用性是现实。
  5. 新特性引入时配套写"本仓库用法一页纸"（什么场景用、禁止什么用法），否则每个人各自发挥，一年后没人敢动。

常见误区

  1. view 悬空：auto r = get_vector() | views::filter(...)——临时 vector 在语句末销毁，r 悬空。规则与 span/string_view 相同：视图寿命 ≤ 源寿命。
  2. 把 views::iota(1) 当无穷循环跑：忘了接 take，直接把容器写爆（配合 views::take_while 才有界）。
  3. span 越界当 vector：s[i] 越界是 UB（Release 下），s.at(i) 才抛异常；边界检查逻辑自己写时用 s.size() 显式判。
  4. <=> 与 == 的坑：= default 的 operator<mark> 成员逐字段比较，但基类/数组字段的语义要与手写版本核对；只要定义了 </mark>，!= 自动合成（C++20 重写规则），不用再写。
  5. 拿 modules 当"更快的头文件"：现状是构建系统与编译器协同仍在成熟中，为了编译速度激进切换会先撞上工具链 bug 而不是收益。
  6. expected 链路上仍抛异常：expected 的价值在"错误即值"；组合函数里夹一个会抛的调用，整体异常安全语义就乱了。端侧 -fno-exceptions 项目里所有底层 API 都必须返回 expected/错误码（第 10 章展开）。

本篇小结

  • ranges：管道 + 惰性 + 零中间容器，g++ 10+ 可用；与 Python 生成器表达式概念对齐，警惕视图悬空。
  • span：带长度的零拷贝视图，API 参数一律 span<const T>；静态长度版编译期查界。
  • expected（g++ 13+）/tl::expected（现在就能用）：错误即值，契合端侧无异常约束；fmt/format 同理。
  • <=> 一次写全六比较，ordering 类型携带序语义（浮点自动 partial）。
  • modules 现状：编译器与构建系统支持不完善，生产继续头文件 + pimpl；团队一致性与工具链门槛是"用不用新特性"的第一判据。

练习

  1. 用 ranges 把一个 vector<string> 管道成"去掉空串 → 全部转大写 → 只取前 10 个"，与 Python 的 itertools 链写对照，并验证"中间不产生容器"（打印 r.size() 前后的内存或用 ranges::distance）。
  2. 把第 12 章 JSON 解析器的 parse 接口参数从 std::string_view 改成 std::span<const char>，体会两者适用面的差异；回答：哪种接口能同时接受 vector<char> 与静态数组？
  3. 用 tl::expected 重写《C++》系列 11 的 optional 版文件读取（打开失败给错误码、读不满给字节数），对比两种返回类型在调用方的表达力。
  4. 给 Frame 增加一个 double score 字段，重新 = default，用 static_assert(!std::totally_ordered<Frame>) 验证 partial_ordering 的出现；再把字段改成 int 恢复全序。
  5. 写一页"本仓库 C++20 启用清单"：从本章挑出三个你所在团队（或假想团队）立刻启用的特性与两个暂缓的特性，各写一行理由。

01 - 为什么测试是顶级工程师的加速器

本篇目标

  1. 用一个真实演化案例看清"不测试的真实成本"——改一处坏三处是如何发生的；
  2. 学会算测试的经济账：什么时候值得写、什么时候不值得；
  3. 掌握测试金字塔及其现代修正（Testing Trophy），能对自己的项目分层；
  4. 用 FIRST 原则判断"什么才是一个好测试"。

1. 不测试的真实成本：一个配置解析函数的三次演化

先讲一个故事。它没有虚构的成分——每一行代码都能跑，bug 是真实存在的（本文所有输出均为实测）。

2. 测试的经济账：什么时候值得写

测试不是信仰，是投资。算得清账，才能在该写的地方写够、在不该写的地方果断省略。

成本侧：写一个测试的成本 ≈ 5~15 分钟（熟练后）+ 每次改接口时的维护成本。

收益侧，两项：

  1. 回归成本节省：没有测试时，每次改动的人工回归 ≈ 理解改动影响面 + 手工验证 N 个现场。经验估算公式：节省 = 单次手工回归时间 × 未来回归次数 × 漏测引入新 bug 的概率。对一个会被改 50 次的核心模块，这笔账轻松超过 10 小时；
  2. 缺陷发现成本差：Barry Boehm 在《Software Engineering Economics》（1981）中量化过：缺陷发现得越晚，修复成本越高，需求阶段 vs 发布后可差两个数量级；测试把发现时间从"线上"提前到"提交前"，吃到的正是这个差额。

什么时候不值得写——这和"值得写"同样重要：

场景 建议 理由
一次性脚本（跑完即弃） 不写 投资对象寿命为零
探索性原型（验证想法） 不写，但标注"转正前先补" Beck：原型确认要转正时，第一件事是补测试
纯粘合代码（A 调 B，无逻辑） 少写，交给集成测试 单测收益低于维护成本
核心算法 / 解析器 / 状态机 / 并发代码 写满，甚至 property-based（05 篇） 分支爆炸，人工回归不可能覆盖
报过一次线上 bug 的模块 修之前先写测试 bug 回归测试是性价比之王（06 篇）

经验做法：面对"要不要给这段代码写测试"的犹豫，问一句——这段代码未来三个月会被改几次？改坏了谁最先发现？ 两个答案分别是"好几次"和"用户"，就写。

3. 测试金字塔与现代修正：Testing Trophy

金字塔模型由 Mike Cohn 在《Succeeding with Agile》（2009）提出，Martin Fowler 的博文《TestPyramid》（2012）将其推广成行业标准表述。形状如下：

比例背后的理由是三个量的乘积：反馈速度（单元毫秒级，E2E 分钟级）、失败定位精度（单测直接指向函数，E2E 只说"哪儿坏了"）、维护成本（E2E 对 UI/环境变化最敏感）。经典配比 70/20/10 或"单元 : 集成 : E2E ≈ 10 : 3 : 1"只是经验参考，关键的是形状而不是数字：越往上越少，因为上层每多一个，下层就省不出开发时间。

现代修正：Kent C. Dodds 在《The Testing Trophy and Testing Classifications》（2021）指出，对服务端与前端应用，纯金字塔低估了集成测试的价值——大量线上 bug 不是"函数算错了"，而是"模块拼起来不对"（配置没接上、类型不一致、边界没对齐）。他把形状改成奖杯（Trophy）：集成测试占最大头，单元与 E2E 各居两侧：

经验做法：按项目类型选形状——

  • 写库 / 写算法核心（本仓库读者的主流场景）：金字塔为主，单元 + property-based 是主力，因为代码的复杂度集中在纯逻辑里；
  • 写服务 / 写应用：奖杯为主，集成测试是主力，因为复杂度集中在组装处；
  • 无论哪种：静态类型检查算"免费的测试"（09 篇），底座越厚，上面越省。

4. 好测试的定义与 FIRST 原则

判断一个测试值不值得留下的标准。先说四条朴素定义，再套 FIRST 缩写。

可重复（Repeatable）：任何机器、任何时间、任何顺序跑，结果都一样。依赖本机时间、网络、随机数种子的测试会变成"有时红有时绿"，而 flaky 测试对团队的腐蚀是指数级的——Google Testing Blog 的《Flaky Tests at Google and How We Mitigate Them》明确指出：开发者会开始无视红色测试，整个门禁随之失效。

独立（Independent）：测试之间不共享可变状态，不依赖执行顺序。pytest 默认按文件内定义顺序执行，一旦某个测试改了模块级状态，下游测试就进入"在我机器上是绿的"薛定谔状态。

快速（Fast）：单元测试毫秒级。速度决定的是反馈频率——跑一次要十分钟，你就不会每次改动都跑；不常跑的测试等于没有。08 篇会讲怎么在 CI 里维持速度。

自解释（Self-explanatory）：红了不用调试就知道坏的是什么。对比：

FIRST 原则出自 Tim Ottinger 与 Jeff Langr（收录于《Clean Code》第 9 章"Aclean Tests"一节的测试规约）：

字母 含义 一句话检验
Fast 快 全量单测 10 秒内？
Independent 独立 打乱顺序跑还绿吗？pytest -p no:randomly 之外能否并行？
Repeatable 可重复 换台机器/离线环境还绿吗？
Self-validating 自校验 断言自动判对错，还是靠人眼看输出？
Timely 及时 测试和实现同期写，而不是"以后补"？

其中 T（及时）最有争议：严格 TDD 要求测试先行（红→绿→重构循环），实践中更多团队采用"实现与测试同期、允许小步先行"。本系列的立场：新代码测试先行或同期写；遗留代码 characterization 测试先行（06 篇）——T 评价的是"测试与实现的距离"，不是教条顺序。

常见误区

误区一：覆盖率等于质量。 Google Testing Blog《Code Coverage Best Practices》原话大意：覆盖率是一个诊断指标，不是质量目标；100% 覆盖可能全是 assert True 式的空转，50% 覆盖也可能恰好盖住了所有高风险分支。覆盖率回答"哪些代码从未被执行过"，不回答"测得对不对"。08 篇会讲如何用阈值门禁 + 差异化覆盖率（只卡改动部分）把它用对。

误区二：E2E 万能论。 “我直接在真实环境里点一遍最保险”——单次发现 bug 的概率确实高，但慢、脆、定位难三者叠加，让你无法频繁执行，最终失去回归能力。正确姿势是：E2E 只留几条关键路径冒烟（登录、下单、核心 API），细节下沉到单元与集成。

误区三：测试是 QA 的事。 测试左移的本意不是把 QA 的活抢过来，而是：自动化测试的编写者必须是实现者——因为只有实现者知道哪里容易碎。QA 继续负责探索性测试与场景设计，这是两件互补的事。

误区四：一次性给老项目补 100% 测试再动手。 大爆炸式补测试往往在半途耗尽士气。06 篇给出的是渐进套路：改哪个模块，才给哪个模块补 characterization 测试，让测试随重构同步生长。

本篇小结

  • 不测试的真实成本不是"少写几行代码"，而是人工回归的复利与线上归因的延迟；一个 retry_delay 的案例就能让三个现场三周后爆雷；
  • 测试是投资：用"未来改动次数 × 单次回归成本"算收益；一次性脚本与原型可以不写，但要标注转正条件；
  • 测试金字塔（单元多、集成中、E2E 少）是库项目的默认形状；服务/应用项目改用 Testing Trophy，让集成测试当主力；静态检查是所有人的免费底座；
  • 好测试的四条朴素定义（可重复/独立/快速/自解释）与 FIRST 原则一起构成评审测试的清单；flaky 测试是门禁的头号敌人；
  • 下一章开始动手：pytest 的日常用法。

练习

  1. 把 1 节的 v2 函数抄下来，自己写出至少再暴露一个 v2 隐藏缺陷的参数化用例（提示：大写单位 "5M"？末尾带空格 "5s "？），并给出对应报错输出。
  2. 按经济账模型估算你最近一个项目里"最该写测试的模块"：改动频率、单次手工回归时间、漏测概率，算出期望节省，与写测试的一次性成本对比。
  3. 你的项目当前更接近金字塔还是奖杯？数一数单测与集成测试的数量比，判断形状是否符合项目类型（库 or 服务），写一段 200 字的调整计划。
  4. 在你自己写过的测试里找出一条违反 FIRST 的（比如依赖网络或执行顺序），按四条定义逐条说明它违反了什么，并当场修好。
  5. （开放讨论）"测试先行"和"实现先行、测试同期"各自的适用场景是什么？结合 T（Timely）条款写你的团队约定。

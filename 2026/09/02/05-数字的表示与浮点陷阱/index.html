05 - 数字的表示与浮点陷阱

本篇目标

  • 从补码的动机出发理解整数的机器表示，能预判符号扩展、无符号比较、溢出这三类经典翻车现场。
  • 逐位拆解 IEEE 754：亲手把 0.1f 拆成符号/指数/尾数，从此 float32/float64/fp16/bf16 的位分配不再是背诵内容。
  • 掌握浮点误差的两个工程定律：0.1+0.2 != 0.3 的原因、大数吃小数的累加误差，并用 Kahan 求和实测修复。
  • 建立 fp16/bfloat16 的选型直觉（动态范围 vs 精度），以及 NaN/Inf 的产生-传播-排查路径。

前置：01 章（位与指令层面）；本章是模型性能优化系列量化/混合精度话题的数值基础。

1. 补码：为什么负数要这样存

无符号数没悬念：8 位 b7...b0 值 = Σ bᵢ·2ⁱ。问题是怎么表示负数？三种历史方案里，补码（two’s complement）胜出的原因只有一个：让同一套加法器硬件同时服务有符号与无符号。补码定义：-x 的编码 = ~x + 1（按位取反加一）。验证 8 位下 3 + (-3)：00000011 + 11111101 = 1_00000000，最高位进位丢弃后得 0 ✅——减法直接变成加法，模 2⁸ 算术，01 章辛苦搭的加法器一行不用改（CSAPP 2.2；P&H 数章节 3.4 也从"简化硬件"角度推过）。

补码的边界要背下来：8 位范围 [-128, 127]；32 位 [-2³¹, 2³¹-1]；64 位 [-9.2e18, 9.2e18]。注意范围不对称：负数比正数多一个（-128 没有正伙伴），这是 abs(INT_MIN) 仍为负、INT_MIN / -1 是未定义行为的根源。

另一个必须预判的行为是符号扩展：8 位 -1 是 11111111，扩展到 32 位必须变成 11111111111111111111111111111111（仍是 -1）——高位复制符号位；而无符号 8 位 255 扩展时高位补 0。02 章的 movsbl/movzbl 两条指令正是这两个动作的硬件体现。ARM 注：x86-64 与 ARM64 的补码与扩展行为一致，差异不在表示，而在"溢出是否置标志位"等细节层面。

2. 整数溢出与符号陷阱：三个真实翻车现场

现场一：有符号溢出是未定义行为。 C 标准规定有符号整数溢出为 UB（C11 6.5/5），编译器可以假设它不发生——for (int i=0; i<=INT_MAX; i++) 可能被优化成死循环；无符号溢出则是良定义的（模 2ⁿ 回绕）。经验做法：计数器、循环变量永远用 size_t/long；二进制协议字段长度检查要防 len + 8 < len 式回绕。

现场二：无符号倒序循环死循环。 for (size_t i = n-1; i >= 0; i--)——size_t 永远 ≥0，条件永真，i 从 0 减一变成 SIZE_MAX，数组越界。正确写法 for (size_t i = n; i-- > 0;)。

现场三：有符号/无符号混比。 C 的"通常算术转换"规则：有符号与无符号比较时，有符号一方被转成无符号（C11 6.3.1.8）。于是：

3. IEEE 754：逐位拆解一个真实数字

浮点的目标：用固定 32/64 位表示跨度极大的数。设计思路照搬科学计数法 ±1.M × 2^E，IEEE 754（2008 版，CSAPP 2.4）规定了位布局：

三个设计点：① 尾数省掉前导 1（规格化数恒为 1.xxx），白赚一位精度；② 指数用偏置码（bias）而非补码，使浮点比较可以当整数比较做（对排序/快速比较至关重要）；③ 指数全 0 表示非规格化数（渐近下溢），全 1 表示 Inf/NaN（见 7 节）。

现场一：0.1 + 0.2 != 0.3。 继续用 flt.c 的输出：

二进制视角（flt.c 的位型）：0.1f 和 0.2f 各自带尾数舍入误差，相加后误差叠加并对齐指数时再次舍入，结果落在 0.3 的"下一个"浮点数上。这不是 Python/浮点的 bug，是二进制定点的数学必然（IEEE 754 规定了每一步怎么舍，误差是有界的：|误差| ≤ 0.5 ulp）。工程结论（CSAPP 2.4.4 的建议）：浮点相等判断用 fabs(a-b) < eps（eps 按量级取，如 1e-6·max(|a|,|b|)）；涉及钱用整数分或 Decimal。

5. Kahan 求和：给误差"记账"

Kahan 补偿求和的思想非常朴素：每次舍掉的误差单独存起来，下次加回去（Kahan 1965；《Numerical Recipes》与 Higham《Accuracy and Stability of Numerical Algorithms》有完整误差分析）：

（本篇 4 节输出里同时含两行，此处单独展示对比。）每步多 3 次浮点运算，把 O(n·ε·Σ|x|) 压到 O(ε·Σ|x|) 量级。经验做法：① 求和前把数据按大小排序或分组累加（pairwise 求和，NumPy 的 np.sum 默认用 pairwise，误差远小于朴素循环）；② 混合精度训练里梯度累积用 fp32 累加器（bf16 加数 + fp32 部分和），正是 Kahan 思想的简化版——用高精度"钱包"接住低精度加数的舍入误差；③ 并行归约（torch.sum）天然是 pairwise 树形结构，这也是为什么 GPU 上求和有时反而比 CPU 朴素循环更准。

6. float16 与 bfloat16：深度学习为什么偏爱"残缺"的 bf16

fp32 精度太高、太占带宽（03 章：推理是带宽受限），于是半精度登场。两者的位分配对比（IEEE 754 half 与 Google brain float 2018）：

  • fp16：动态范围 ±65504，最小规格化数 6e-5。精度高（10 位尾数）但范围窄——梯度动辄小于 6e-5 下溢为 0，大值又容易溢出到 Inf，所以 fp16 训练必须配 loss scaling（把 loss 乘大，把梯度拉出下溢区，算完再缩回）。
  • bf16：指数位与 fp32 完全一致，动态范围与 fp32 相同（±3.4e38），只是尾数从 23 位砍到 7 位（相对精度 ~2⁻⁸≈0.4%）。fp32↔bf16 转换就是尾数截断，无下溢/上溢风险，几乎不需要 loss scaling——这是 A100/4090/TPU 上训练的事实标准。
  • 选型口诀（经验做法，与模型性能优化系列量化章互为表里）：要范围选 bf16（训练/推理默认），要精度选 fp16（配 scaling）或 fp32；部署端到 int8/int4 走量化。注意 CPU 上的历史包袱：x86 的 AVX512-BF16 才有原生 bf16，AVX2 只有 fp16 存储转换指令（F16C）——端侧 ARM 的 NEON 原生支持 fp16 向量运算，bf16 要 ARMv8.6+（RK3588 的 A76 是 ARMv8.2，bf16 硬件支持不完整，端侧量化常直接跳 int8）。

常见误区

  1. “浮点误差是随机的、不可控的”：IEEE 754 是确定性标准，每一步舍入都有定义；误差可以用模型分析（Kahan）、可以用算法控制（pairwise/补偿求和）。不可控的错觉来自"没把中间值打印出来看"。
  2. “float 和 double 只差精度，行为一样”：差在 ulp 间距和误差累积速度，float32 累加 1e7 次 1e-7 错 6.5%（4 节实测），同样代码用 double 几乎无感——累加器/统计量的类型比数据类型更值得升精度。
  3. “bf16 是 fp16 的升级版”：不是升级，是取舍反转——bf16 拿 3 位尾数换 3 位指数，精度降 8 倍、范围升 33 个数量级。任务需要哪种，取决于你的数是要"更准"还是"不爆/不消失"。
  4. “整数运算总是精确的”：无符号回绕、有符号 UB、隐式转换（2 节三个现场）都在精确外表下埋雷；Python 的 int 无限精度反而让人失去对固定位宽的警惕，跨到 C/NumPy（np.int32 溢出回绕）时翻车。
  5. “NaN 排查要靠玄学”：NaN 是确定性传播的，从输出往回二分（中间每层 assert isfinite）10 分钟内必定位；detect_anomaly 与逐层打印是标准流程，不是玄学。

本篇小结

  • 补码让一套加法器通吃加减法（模 2ⁿ）；范围不对称（-128 无伙伴）；符号扩展补符号位、无符号扩展补 0——movsbl/movzbl 的分野。
  • 有符号溢出是 UB、无符号回绕良定义；size_t 倒循环与混合比较是两大惯犯；-Wsign-compare 兜底（经验做法）。
  • IEEE 754 = ±1.M × 2^(E-bias)：偏置指数、隐含前导 1、0.1 的二进制无限循环——手拆 0.1f 应成为肌肉记忆。
  • 0.1+0.2 != 0.3 是数学必然；比较用 eps；大数吃小数实测 1.0647675 vs 真值 1.0，Kahan 求和用"误差钱包"修复到 1.0000000。
  • fp16（10 尾数 5 指数）重精度窄范围需 loss scaling；bf16（7 尾数 8 指数）= fp32 截断尾数，范围无忧，是训练事实标准；部署再往下走 int8/int4。
  • NaN 感染一切、比较恒 False、x!=x 判 NaN；loss=NaN 按清单排查：clip → bf16 → 输入校验 → eps（经验做法）。

练习

  1. 手算 8 位补码：-13 的编码、10001101 作为有符号/无符号各自的值、-128 - 1 回绕后的结果。
  2. 把 -6.5f = 0xC0D00000（3 节实测位型）逐位拆解回十进制，验证值确为 -6.5（S=1，E=129→2²，M=1.101₂）。
  3. 用 Python 复现：0.1 + 0.2 与 0.3 的 hex 表示（float.hex()），确认两者确实差 1 ulp；再用 math.fsum([0.1]*10) == 1.0 验证 fsum（Shewchuk 算法，Kahan 的精确版）的效果。
  4. 写一个 float 累加 0.1f 十万次的 C 程序，分别用朴素、Kahan、double 累加器三种方式打印结果与真值 10000 的偏差，比较三种方法的误差量级。
  5. 查一张你手头 GPU/NPU 的规格表（或 PyTorch 文档），列出它支持的 fp16/bf16/int8 TFLOPS 或 TOPS，结合 03 章"带宽受限"账本，写出"该模型在 fp16 下是算力受限还是带宽受限"的判断过程。

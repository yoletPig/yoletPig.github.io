10 - 进程间通信

本篇目标

  • 掌握管道的两种形态：匿名管道（shell 竖线的实体）与命名管道（FIFO），并亲手在 C 里接通它们。
  • 理解信号的机制与陷阱：kill -l 的信号全景、处理函数的正确写法、可重入问题，以及 SIGKILL 不可捕获的铁律。
  • 会用消息队列、共享内存、信号量三种 System V IPC，并用"拷贝次数"的账本解释为什么共享内存最快。
  • 会用 AF_UNIX socket 做本地进程通信，知道它和 TCP socket 的差别。
  • 拿着一张选型对比表，给真实场景挑对 IPC。

前置：第 02 篇的 fork、第 08 篇的 fd 与"一切皆文件"、第 09 篇的事件模型；环境 Ubuntu 22.04 / WSL2。

1. 管道：匿名与命名

匿名管道是 shell 里竖线的实体（man 2 pipe）：一个单向字节流，带两个 fd——pipefd[0] 读端、pipefd[1] 写端。它的亲缘限制是刻在创建方式里的：由父进程 pipe() 创建后经 fork 继承，没有亲缘关系的进程拿不到它。看 shell 怎么把 ls | grep os 接起来：

管道的本质限制：字节流、无消息边界（两条 echo 可能被一次 cat 读出——08 篇的"字节流无结构"在 IPC 里的镜像）、单向、缓冲有限。工程用法（经验做法）：进程间"触发/通知/日志接力"用管道顺手；要传结构化消息请看第 3、4 节。

2. 信号：kill -l、处理函数、可重入陷阱

信号（signal）是内核发给进程的异步通知（man 7 signal）：软件中断（07 篇的"打断"家族在进程层面的投影）。发信人可以是内核（段错误→SIGSEGV、Ctrl-C→SIGINT、子进程退出→SIGCHLD）、也可以是别的进程（kill 命令）。信号生命周期三步：产生（pending）→ 阻塞（block，挂着不递送）→ 递送（deliver，执行默认动作或处理函数）。

先看全景：

必须认识的六个：SIGKILL(9)/SIGSTOP 不可捕获不可忽略（内核保留的最终手段）；SIGTERM(15)“请你退出”（kill 默认发它，优雅退出靠捕获它做清理）；SIGINT(2) Ctrl-C；SIGCHLD(17) 子进程退出（02 篇收尸的正牌触发器）；SIGSEGV(11) 段错误。进程对大多数信号可选三种处置：默认动作、忽略、或注册处理函数（sigaction，man 2 sigaction——比老的 signal() 可靠）：

可重入陷阱是本节的深水区：处理函数可能在任意一条指令之间插入主程序（比如主程序正在 malloc 到一半），所以处理函数里调用 malloc/printf/锁都可能撞上"函数没跑完就被自己再次进入"——不可重入。规则（man 7 signal-safety，POSIX 列出了异步信号安全函数白名单）：

  • 处理函数里只允许：设置 volatile sig_atomic_t 标志、调用白名单函数（write、_exit 等）；
  • 复杂清理全部放到主循环里根据标志执行（上面代码的结构正是"标志 + 主循环"模式）；
  • Python 的信号处理是同一个问题的温柔版：CPython 把 Python 级 handler 排队到主线程的字节码间隙执行，所以 handler 里可以写 Python，但只有主线程收信号且可能延迟到下一个字节码——信号安全在两种语言里都要刻意设计。

经验做法：推理服务/Agent 进程必须捕获 SIGTERM 做"断开新请求、排空旧请求、落盘状态"的优雅退出——K8s 滚动更新发的是 SIGTERM，你的清理代码只有 terminationGracePeriodSeconds 的宽限；赌 SIGKILL 会给你几毫秒的人，都会在下次 OOM 时丢数据。

4. socket 本地通信：AF_UNIX

socket 家族不止是网络工具（12 篇专题）：AF_UNIX（本地）socket 在同一台机器上提供全双工字节流/数据报，支持双向、面向连接、可传 fd（SCM_RIGHTS 附属数据，这是其他 IPC 给不了的能力）：

AF_UNIX vs 管道/共享内存的定位：会话式（有连接、双向、有关闭语义）、可靠有序、可被 epoll 管理（09 篇的事件模型直接适用）。Docker 的 /var/run/docker.sock、推理服务与本地客户端的通信、systemd 的 socket 激活，都是它的地盘；相比 TCP 127.0.0.1 省掉完整网络栈（无路由/无校验和），延迟更低且天然有文件权限做访问控制。

5. 选型对比表

六种 IPC 一张表定选型（依据各 man 手册与《Linux 系统编程》Robert Love 第 5 章的横向对比，量级数据为常见经验值）：

机制 数据形态 方向 拷贝次数 关系要求 典型场景
匿名管道 字节流 单向 2 亲缘 shell 管道、父子通知
命名管道 字节流 单向 2 无（文件权限） 简单跨进程接力
消息队列 离散消息 双向（多条队列） 2 无（key） 小消息、需边界
共享内存 任意（自定协议） 双向 0 无（需自行同步） 大数据高频（权重/KV cache）
信号 无数据（一个编号） 单向 - 无 生命周期管理（kill/SIGTERM）
AF_UNIX socket 字节流/数据报 双向 2 无（文件权限） 会话式通信、传 fd、C/S 本地协议

选型口诀（经验做法）：管数据量，也管关系——传大块高频数据选共享内存（配信号量）；要消息边界选消息队列；要会话与双向选 AF_UNIX；只发通知选信号；父子进程顺手用管道。多网卡多机？那不叫 IPC，叫网络编程（12 篇）。

常见误区

  1. “管道可以当消息队列用”：管道是无边界的字节流，两条消息可能黏在一次 read 里（与 12 篇 TCP 粘包同源）；需要边界自己加长度前缀，或改用消息队列/数据报 socket。
  2. “信号处理函数里可以随意调用库函数”：malloc/printf/锁都可能死锁或破坏堆（不可重入）；只设 sig_atomic_t 标志 + 白名单函数是铁律（man 7 signal-safety）。
  3. “共享内存最快所以全用共享内存”：它把同步、边界、生命周期全甩给你；小数据低频场景，消息队列/AF_UNIX 的省心完胜零拷贝的收益——性能优化只优化账本上真实的大头。
  4. “kill -9 是清理进程的标准流程”：SIGKILL 绕过一切清理逻辑，会留下半写文件、锁、共享内存残骸；标准流程是先 SIGTERM 等待，超时才 SIGKILL（K8s/Kill 全家桶都这么设计）。
  5. “System V IPC 资源会随进程退出自动回收”：不会！消息队列/共享内存/信号量在 ipcs 里一直活着直到显式 IPC_RMID 或重启——调试留下的共享内存段会悄悄吃内存（ipcrm 手动清理，经验做法：IPC 代码必配清理路径与 atexit）。

本篇小结

  • 管道 = 单向字节流（匿名靠亲缘、命名靠文件系统）；shell 竖线的实体是 pipe+dup2+fork；读不到 EOF 的第一嫌疑是写端 fd 没关干净。
  • 信号是异步通知：SIGTERM 捕获优雅退出、SIGKILL/ SIGSTOP 不可捕获；处理函数只设标志调白名单（可重入铁律，man 7 signal-safety）。
  • 三种 SysV IPC：消息队列有边界（2 次拷贝）、共享内存零拷贝但裸奔（配信号量）、信号量是同步原语不是数据通道；零拷贝账本是"共享内存最快"的全部答案。
  • AF_UNIX socket：本机会话式通道，双向可靠、可传 fd、可进 epoll；docker.sock 是它的名片。
  • 选型按"数据形态 × 关系 × 性能需求"三轴走，没有万能 IPC；SysV IPC 资源生命周期独立于进程，用完必须显式回收。

练习

  1. 把 pipe_shell.c 扩展成支持三段管道 ls | grep os | wc -l（两个 pipe、三次 fork），画出你的 fd 接线图；故意不关父进程的写端 fd，观察 wc 的行为并解释。
  2. 写程序验证信号丢失特性：连续发 3 次 SIGUSR1（不做任何等待），处理函数只递增计数器，最后打印收到的次数并解释为什么可能 < 3（提示：信号是"有无"不是"计数"）。
  3. 用共享内存实现一个双进程环形缓冲区（生产者消费者，两个信号量分别表示空槽/满槽），压入 100 万个 64B 消息计时；再用消息队列实现同功能对比耗时，验证 2 次拷贝 vs 0 次拷贝的量级差。
  4. 给第 02 篇的 mini shell 加管道支持（cmd1 | cmd2）；之后用 strace -f 跟踪真实 bash 执行 ls | wc，对照你的实现数 fork/dup2/pipe 的调用序列是否一致。
  5. 部署视角实验：写一个捕获 SIGTERM 的 Python 服务（signal.signal），打印"排空中"后退出；用 docker run --stop-timeout 或直接 kill -TERM 验证优雅退出路径，再用 kill -9 对比——把两种死法的差别写进你将来的部署文档。

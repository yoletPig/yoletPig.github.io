11 - 进阶：上下文工程与提示词架构

进阶篇第 1 章。基础篇（05）讲了"上下文放不下怎么办"，本章升级视角：上下文不是等待被填充的窗口，而是一份需要精心编写的、每轮都在被重读的文档。这是近年业界从 prompt engineering 走向 context engineering 的核心转变。

1. 为什么"提示词工程"这个说法已经不够了

传统 prompt engineering 关注一次调用的提示词写法。Agent 场景里，每轮循环都会重建完整输入：系统提示 + 工具定义 + 历史 + 工具结果 + 检索内容。真正决定 Agent 表现的是这些内容如何被选择、组织、压缩与排布——这就是上下文工程（context engineering）。Anthropic 的工程博客将其概括为"构建动态系统，在每一步提供恰好正确的信息与工具"（Effective context engineering for AI agents, 2025-09）。

一个必须内化的类比（出自该文）：

上下文窗口像有限的 RAM：系统提示是固件，工具/检索内容是按需换页的数据，历史是待管理的内存。装满 ≠ 高性能——RAM 塞满无用数据只会让一切变慢（对应 05 篇 context rot）。

2. 系统提示的架构：五段式

把系统提示当作给新员工的入职文档而不是"性格描述"。工业级系统提示普遍包含五段（以 Claude Code、各类官方 Cookbook 的公开提示词为参照归纳）：

段 内容 反例
① 身份与目标 你是谁、为谁解决什么问题 “你是一个乐于助人的助手”（无信息量）
② 环境事实 OS、工作目录、可用资源、当前时间 让 Agent 猜环境，反复试探浪费步数
③ 行为规范 关键约束（何时必须问人、禁止事项）、输出风格 约束淹没在细节里
④ 工具使用政策 何时用/不用哪个工具、并行调用规则、失败后怎么办 只列工具不给政策，模型乱用
⑤ 完成标准 任务"做完"的可验证定义、何时该停 没有终止定义 → 死循环（07 篇问题 1）

排序原则：把最常违反的约束放在最前和最后（长上下文中间区域利用率最低，这是 “lost in the middle” 系列研究的现象，Liu et al., TACL 2024——模型对超长上下文中部信息的召回显著弱于首尾）。

长度纪律：系统提示是每轮都重读的固定开销。每多 1000 token，100 轮任务就是 10 万 token 的固定税。能写成一条规则的不写三句背景；给约束编号（“规则 3”），便于后续轮次引用纠错。

3. 工具定义与检索内容的精细化

3.1 工具定义是最被低估的"提示词"

03 篇讲过描述写法，进阶视角补充三点：

  1. 工具描述参与语义检索：MCP 等场景下工具量大时，检索是按描述匹配的——描述里写清楚领域词（“订单”“退款”），工具才被召回；
  2. 用 schema 表达意图，而不是描述：enum、minimum、format 让模型在结构层面无法犯错；
  3. 工具返回值也要"设计"：返回字段命名对模型友好（order_id 而不是 o#）、错误返回包含下一步建议（03 篇的可操作错误）。

3.2 检索内容注入：不要把"找到的"都塞进去

RAG 注入的进阶做法：

  • 压缩后注入：检索回的文档先做一次"面向当前任务的摘要"再入上下文（用小模型做预压缩，通常比塞原文便宜且效果好）；
  • 结构化标记：用明确的定界与来源标记包裹检索内容（<doc source="...">...</doc>），既帮模型区分知识与任务，也是 09 篇注入防御（spotlighting）的日常应用；
  • 时机注入优于常驻注入：不是开场就把所有资料放进上下文，而是按需（某轮需要时才检索注入）。Claude Code 的"按需读文件"取代"整仓注入"就是这个思路。

4. 历史管理进阶：写入、压缩、重写的组合拳

基础篇（05）给了截断/摘要/状态外置/检索四种手段。进阶篇给出组合编排——一个真实 Agent 上下文管线的伪代码：

工程要点逐条拆解：

  1. 压缩工具结果是收益最高的一层。工具输出是上下文膨胀的主因（05 篇），而大多数工具结果在"下一轮看一眼"之后价值就急剧衰减——按"摘要 + 保留关键数值/ID"压缩，任务推进几乎无损；
  2. 摘要触发用预算驱动而不是轮数驱动：token 预算是硬约束，按它触发摘要才能保证永不溢出；
  3. "工作笔记"是压缩的锚点：摘要丢信息不可避免，但只要关键状态（已完成什么、还差什么、已知约束）在结构化笔记里，摘要丢掉过程细节就无关紧要。这是"状态外置"与"滚动摘要"配套使用的根本原因；
  4. 上下文预算要显式分配：像内存管理一样给每层划 quota，而不是无序堆叠后祈祷不溢出。

5. 多轮纠错：把错误变成上下文资产

Agent 的自纠错能力 = 错误信息的上下文质量。三个进阶手法：

  1. 错误不删除：失败的尝试（报错的工具调用）不要从历史里删掉——保留它并附上"此路不通"的标记，模型就不会再走一遍。删掉失败历史是新手最常见的"好心办坏事"（这正是 06 篇提到的记忆/历史设计的反面）；
  2. 纠错提示升级机制：同类错误出现第 2 次时，把纠错信息从"观测"升级为"系统消息"（更高注意力权重）；第 3 次直接终止并报告——避免无限消耗；
  3. 负面清单回写：任务结束后把"该类任务的坑"写入长期记忆（05 篇语义记忆层），下次同类任务开场注入"历史教训"。

6. 上下文工程的评测：怎么知道你的改法有效

上下文改动极易"感觉变好了"。用 07 篇的最小评测框架专门评测上下文策略：

  1. 固定任务集 + 固定模型 + 温度 0；
  2. 只改一个上下文变量（如"工具结果压缩开/关"），跑全量对比；
  3. 同时记录质量指标（通过率）与成本指标（平均 token/任务、步数/任务）；
  4. 警惕"质量不变、成本降一半"的假优化——检查是否只是把错误提前了（在评测集之外的任务上失败）。

自测

  1. "上下文窗口像 RAM"类比里，系统提示、工具结果、历史分别对应什么？为什么要管理而不是填满？
  2. 五段式系统提示是哪五段？为什么约束要放在首尾？
  3. 上下文管线的五层预算分配里，哪一层的压缩收益最高？为什么？
  4. 为什么失败的尝试要保留在历史里？
  5. 如何设计实验验证"压缩工具结果"真的有效？

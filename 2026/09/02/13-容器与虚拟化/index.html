13 - 容器与虚拟化

本篇目标

  • 用一张对比图讲清虚拟化与容器的本质差异： hypervisor 虚拟硬件 vs 内核共享 + 视图隔离。
  • 亲手用 unshare 制造出"看不见外面的进程"，逐个理解六种 namespace 各隔离什么。
  • 用 cgroup 实测限制一个进程的 CPU 与内存，看到超限后的真实反应（throttle 与 OOM）。
  • 理解 Docker 镜像分层与 overlayfs 的"层叠视图"机制，以及它带来的镜像/启动速度优势。
  • 搞懂容器里 PID 1 的两个特殊职责（收僵尸、转发信号），解释"docker run 里 Ctrl-C 没反应"这类现象。
  • 认识你正在用的 WSL2 的真实架构：轻量虚拟机 + 完整 Linux 内核，而非传统容器。

前置：第 02 篇的进程/僵尸、第 05 篇的 OOM、第 10 篇的信号；环境 Ubuntu 22.04 / WSL2（namespace/cgroup 实测在 WSL2 上直接可做，个别需要 sudo）。

1. 虚拟化 vs 容器

两种"把一台机器切成多份"的思路（容器与虚拟化的系统比较见《Understanding the Linux Kernel》相关章节与内核文档；Docker 的官方定位文档也以此为纲）：

一句话定位：VM 虚拟的是硬件，容器虚拟的是"机器的视图"。容器 = 普通进程 + 两层 OS 机制：namespace（让它看不见不该看见的）+ cgroup（让它用不了不该用的）。Docker/containerd 不提供隔离，它们是这两层机制的管理界面——所以第 2、3 节不装 Docker 也能全部实测。这也解释了容器生态的边界：容器不能跑 Windows（内核必须匹配），VM 可以；容器的"安全边界"弱于 VM（共享内核，内核漏洞可逃逸）——生产部署的安全分级依据（Agent 生产部署篇的运行环境选择在此落地）。

2. namespace：六种"视图"隔离（实测 unshare）

namespace 让进程看到不同的世界（man 7 namespaces）。六种（还有两种较新的 time/cgroup ns 共八种，先记主六种）：

namespace 隔离什么 你看得见的效应
PID 进程号空间 容器里 ps 只有自己，你的 PID 是 1
NET 网络栈（网卡/路由/端口） 容器有自己的 IP、端口不与宿主冲突
MNT 挂载点 容器看到的根目录是镜像的 rootfs
UTS 主机名与域名 hostname 在容器里可独立设置
IPC System V IPC 与 POSIX MQ 容器间共享内存互不可见（10 篇）
USER 用户 ID 映射 容器内 root ≠ 宿主 root（rootless 容器）

逐行解读两个魔法：--pid 创建新 PID namespace，进入者被重新编号（$$ = 1）；--mount-proc 挂载一份新的 /proc——ps/$$ 读的都是 /proc，视图换了，世界就换了。这正是 Docker 容器内 ps 只有一个进程、你容器里 PID 常常是 1 的全部原理。再实测 NET/UTS：

经验做法：排查容器网络/进程问题时，先确认你在哪个 namespace 里——ls /proc/self/ns/（每个 ns 一个 inode 号，号相同即同一 namespace）；nsenter --target PID --all 可以"进入"指定进程的全部 namespace，是容器调试的标准入口（宿主上 nsenter 进容器等价于 docker exec 的底层动作）。

3. cgroup：资源限额实测

namespace 管"看得见什么"，cgroup 管"能用多少"（cgroup v2 手册 man 7 cgroups；LKD 第 3 章末尾有 cgroup 简史）。v2 把控制器统一挂在一个层级树下，对进程真正起作用的两个：

  • cpu.max：CPU 配额，格式 周期 微秒配额，如 100000 50000 = 每 100ms 用 50ms → 0.5 核；超限被 throttle（限流压着跑），不是杀。
  • memory.max：内存上限；超限时内核先回收 page cache，救不回来就对这个 cgroup 内进程触发 OOM kill（05 篇 OOM killer 的 cgroup 版）。

两个决定性细节：throttle vs OOM——CPU 超限是"变慢"（100000/50000 的节奏被扣住），内存超限是"被杀"（没有"慢下来的内存"）；cpu.max 与 nice 的层级差异——03 篇的 nice 只影响"抢占优先级"，cgroup 影响的是"配额本身"，生产上限制推理服务 CPU 用 cgroup 而不是 renice。docker 的 --cpus=0.5 --memory=100m 就是帮你写这两个文件。WSL2 注：.wslconfig 的 processors=/memory= 是 VM 级总闸（WSL2 虚拟机的总资源），容器级配额在其下再分配——两层是乘法关系。

4. Docker 镜像分层与 overlayfs 概念

镜像不是一个大压缩包，而是只读层的堆叠（Docker 官方文档 image spec 与 overlayfs 内核文档 Documentation/filesystems/overlayfs.rst）：

overlayfs 的三个目录角色：lowerdir（只读下层，可多层）、upperdir（可写上层）、merged（联合视图）。写时复制规则：读文件直接读 lower；第一次改一个 lower 层的文件，先把它复制到 upper（copy-up）再改；删除文件只在 upper 放一个"白名单"遮住 lower。实测本机（WSL2 里装了 docker 的话）：

这套设计的工程价值（也是为什么"镜像瘦身"有标准操作）：层可共享——多个镜像基于同一 ubuntu 层，磁盘只存一份；构建可缓存——Dockerfile 指令顺序决定缓存命中，把"常变的"放后面是构建提速第一原则；层不可变——改过文件就 copy-up，删了也不会让镜像变小（rm 大文件再提交，层反而叠加）。经验做法：AI 项目的 Dockerfile 把"装 PyTorch/CUDA"这类重且少变的层放最前，COPY . .（代码）放最后；.dockerignore 排除数据集与 venv——三条合计能省几个 GB 和几十分钟构建时间。

5. 容器里的 PID 1 问题

第 2 节实验里你的 bash 是 PID 1——这带来两个真实问题（Docker 官方文档与大量事故复盘的标准议题）：

职责 1：收僵尸。普通进程的孤儿由 PID 1 领养收尸（02 篇）；容器内的孤儿只能由容器内的 PID 1 收。如果 PID 1 是个不管闲事的程序（比如 nginx worker 的父进程退出逻辑不完整、或你 docker run 起的是个 shell 包裹的应用），容器内僵尸会无限堆积：

职责 2：转发信号。宿主对 PID 1（容器的 init）发的 SIGTERM 有特殊语义——PID 1 若没有注册该信号的处理函数，内核对它的 SIGTERM/SIGINT 默认动作是"忽略"（POSIX 对 PID 1 的特殊规定）。这就是"docker stop 卡 10 秒后 SIGKILL 强杀"的头号原因：你的程序没处理 SIGTERM（10 篇的优雅退出），docker stop 等满宽限期直接 -9。同理 docker run -it 时 Ctrl-C（SIGINT）打不到没处理的 PID 1。修法（经验做法）：①应用自己处理 SIGTERM/SIGINT（10 篇的 signal 模板）；②启动命令用 exec 形式（CMD ["python", "app.py"] 而不是 CMD python app.py——后者会多套一层 shell，shell 才是 PID 1）；③兜底用 --init（docker 自带 tini，专职收僵尸+转信号）。

6. WSL2 架构：真虚拟机，不是传统容器

最后回到你每天敲命令的地方。WSL2 的架构（微软官方文档 “Comparing WSL 1 and WSL 2”）：

判定与含义：uname -r = 6.6.87.2-microsoft-standard-WSL2——这是一颗真正的 Linux 内核跑在 Hyper-V 轻量虚拟机里，不是 WSL1 那种系统调用翻译层（WSL1 把 Linux syscall 翻译成 Windows NT 调用，行为差异大；WSL2 是真内核，本系列全部实验直接可用）。三个日常推论：文件系统性能断层——/mnt/c 是 9P 网络协议挂载的 Windows 盘，IO 慢一个数量级，编译/训练/数据集务必放 WSL 内的 ext4（08 篇的 WSL2 注在此给出架构原因）；内存动态——WSL2 的内存是 VM 配置（.wslconfig），空闲时 Windows 侧看到 vmmem 进程占内存大是虚拟机的账，wsl --shutdown 可回收；GPU 直通——WSL2 走 GPU-PV 虚拟化给 Linux 侧 CUDA（nvidia-smi 能在 WSL2 里工作），PyTorch 训练在此环境真实可用（模型性能优化系列的 CUDA 章节在 WSL2 上同样成立）。

常见误区

  1. “容器是轻量虚拟机”：机制完全不同——容器是 namespace+cgroup 的进程沙箱（共享内核），VM 是硬件虚拟化（独立内核）。容器进程在宿主 ps 里看得见（PID 不同而已），这是 docker top 能工作的原因。
  2. “容器里 root 就是宿主 root，随便来”：有 USER namespace 映射时不是（rootless 模式）；即便映射后提权风险仍低于裸机但高于 VM——容器安全分级低于 VM 的根源在共享内核。
  3. “Dockerfile 里 rm 大文件镜像就小了”：rm 只发生在新层（copy-up 后的白名单/删除标记），历史层的文件还在；瘦身必须重排指令或多阶段构建，让大文件根本进不了任何层。
  4. “docker stop 没杀掉是 Docker 的 bug”：十有八九是应用没处理 SIGTERM（或 shell 包裹导致信号打在 shell 上）；先修容器内 PID 1 的信号处理，再谈 stop-timeout。
  5. “WSL2 里 /mnt/c 和 WSL 内文件系统差不多”：差一个数量级（9P vs 原生 ext4）；WSL2 第一性能铁律是"数据与工作目录放 WSL 文件系统内"（经验做法，微软官方也如此建议）。

本篇小结

  • VM 虚拟硬件（强隔离、启动慢、跨 OS），容器 = 进程 + namespace（视图）+ cgroup（配额）；Docker 是这两层机制的管理界面，不是隔离本身。
  • 六种 namespace 一张表：PID/NET/MNT/UTS/IPC/USER；unshare --pid --mount-proc 亲手复现"容器里的 ps"；ns inode 号（/proc/self/ns/）判定同属一个 namespace。
  • cgroup v2：cpu.max 超限 throttle（变慢）、memory.max 超限 OOM kill（死亡）；docker 的 --cpus/–memory 就是写这两个文件；nice 与 cgroup 是抢占优先级与配额两层，别混用。
  • 镜像 = 只读层堆叠 + overlayfs 联合挂载（lower/upper/merged，写时 copy-up）；层共享、缓存命中、rm 不瘦身是三条工程推论；Dockerfile 重层在前、COPY 在后。
  • 容器 PID 1 两职责：收僵尸（否则 defunct 堆积）与转信号（未处理 SIGTERM 会被内核忽略 → docker stop 强杀）；修法 = exec 形式 + 信号处理 + --init 兜底。
  • WSL2 = Hyper-V 轻量 VM + 真 Linux 内核 + ext4 虚拟盘；/mnt/c 的 9P 断层与 .wslconfig 内存是日常两大陷阱来源。

练习

  1. 依次实测 sudo unshare --pid --fork --mount-proc、--net、--uts、--mount 四种组合，每次进入后记录 echo $$、ps aux、ip link、hostname 的输出；回答"最接近完整容器的组合差什么"（提示：rootfs 与 cgroup）。
  2. 用 cgroup v2 复现第 3 节：分别限 0.2 核与 1 核跑同一个 busy-loop，用 top 记录 CPU%；再限 100MB 跑吃内存 Python，抓取 memory.events 与 dmesg 的 OOM 行，写出"throttle 与 OOM 的现场指纹"对照表。
  3. 验证 PID 1 信号特性：在 unshare 的 PID ns 里跑一个"不处理信号的 sleep"，从宿主 kill -TERM 它（注意找到宿主视角的真实 PID），对比"处理了 SIGTERM 的 Python 脚本"的行为差异，用 POSIX 对 PID 1 的规定解释。
  4. 用 docker（或 podman）复现第 5 节的僵尸实验；再用 docker run --init 重跑对比 defunct 是否消失，并用 ps -ef 找出 tini 进程的位置（它才是 PID 1）。
  5. 给你的训练/推理项目写一个"WSL2 就绪"检查清单脚本：检查 uname 是否 WSL2 内核、工作目录是否在 ext4（df -T .）、nvidia-smi 是否可见、.wslconfig 的 memory/processors 值——把 13 篇的三个坑变成跑一次的体检。

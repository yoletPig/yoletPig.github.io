05-记忆与上下文管理

05 - 记忆与上下文管理

本篇目标

  1. 区分"上下文窗口"与"记忆"两个经常混用的概念；
  2. 掌握会话内上下文管理的四种工程手段；
  3. 理解跨会话长期记忆的常见设计与风险。

1. 两个概念，先分清楚

  • 上下文窗口（context window）：模型单次推理能"看到"的 token 上限，是模型能力属性。不同模型差异很大，常见量级从几十万到百万 token 以上（以各厂商官方文档为准，且实际可用量还受输出预留、多模态占位等因素影响）。
  • 记忆（memory）：系统层面让信息跨轮次、跨会话可用的工程机制，是应用架构属性。上下文窗口放不下的、历史会话里的，都要靠记忆机制。

一个类比：上下文窗口是"你的工作台大小"，记忆是"你的笔记本 + 档案柜"。工作台永远只有这么大，关键是什么放在台面上、什么收进档案柜、何时取回。

3. 会话内管理：四种基本手段

手段一：截断（truncation）

最简单：超限时丢掉最旧的消息。优点是零成本；缺点是可能丢掉任务目标或关键约束。改进：永远保留系统提示和最初的目标设定，从中间截断。

要点：摘要的 prompt 要明确"保留什么"——任务目标、已做的关键决定、失败尝试（避免重蹈覆辙）、未完成事项。只说"总结一下"会丢掉 Agent 最需要的信息。

手段三：结构化状态外置（state outside context）

不让"对话历史"充当唯一状态，而是维护一份显式的任务状态（如计划清单、当前进度），每轮只把当前状态注入 prompt。这正是 Anthropic 在《Building Effective Agents》与 Claude Code 等产品中反复出现的手法（如任务列表/计划文件）：用一份不断更新的"工作笔记"替代完整历史。优点是 token 消耗恒定、状态可审计；代价是需要设计状态格式与更新时机。

手段四：检索式按需取回（RAG over history）

把工具结果、历史会话写入向量库/数据库，需要时检索取回。适用于"知识多于窗口"的场景。代价：检索本身可能失败或召回噪声，等于把"上下文问题"转化成"检索质量问题"。

选择建议：短会话（<几十轮）什么都不用做；中等长度用摘要或状态外置；跨项目、跨会话的知识才需要检索式长期记忆。不要一上来就上向量数据库。

4. 跨会话长期记忆

跨会话记忆的常见分层（工程实践中的通行做法，各产品实现命名不同）：

层 内容 生命周期 实现举例
工作记忆 当前会话上下文 会话内 对话历史
情景记忆 用户与 Agent 的交互事件 跨会话 会话日志 + 检索
语义记忆 从交互中提炼的"事实"（偏好、背景） 跨会话 "用户偏好简洁回答"这类条目
程序记忆 学到的操作经验 跨会话 可复用的技能/脚本（如 Anthropic 的 Agent Skills 思路）

典型流程：会话结束（或 periodically）→ LLM 提炼值得记住的条目 → 去重合并入库 → 下次会话按需检索注入。

两个必须正视的风险

  1. 记忆污染：错误信息一旦入档，会持续影响后续所有会话（“用户喜欢被称呼为王总”——其实提取错了）。防御：记忆条目带来源与时间戳、支持用户查看/编辑/删除、低置信度条目降权。
  2. 记忆与注入的叠加（09 篇伏笔）：间接注入的内容若被存入长期记忆，会从"一次攻击"变成"持久后门"。防御：记忆写入前做清洗，注入类内容不落盘。

论文参考：MemGPT: Towards LLMs as Operating Systems（Packer et al., arXiv:2310.08560, 2023）系统提出了把 LLM 当作操作系统、在有限上下文外管理分层记忆的思路，是这一方向的代表作。开源生态中 Mem0、Letta（MemGPT 团队商业化后的项目）、Zep 等都是实现长期记忆的库/服务，选型时请以各自当前文档为准。

5. 上下文"腐化"：长上下文不等于好上下文

一个重要事实：塞得满 ≠ 用得好。业界与研究者反复观察到（如 Chroma 的 “context rot” 研究，2025；以及各家长上下文评测如 RULER、NoLiMa），随着上下文变长或结构变乱，模型对关键信息的利用效率会下降——即使信息"在窗口内"也可能被忽略。对 Agent 的实际启示：

  1. 上下文是稀缺资源，要像内存一样管理，而不是"反正有 1M token"地挥霍；
  2. 无关信息（失败的工具输出、冗长日志）不仅费钱，还会降低回答质量；
  3. 定期"清理台面"：摘要、状态外置、截断，都是让台面上只留当前需要的东西。

08 - 迁移、CI 与团队落地

本篇目标（uv 系列收官）

三件事：把老项目迁到 uv（requirements.txt / Poetry 两条路径）、把 uv 装进 CI（含缓存与发布）、以及团队层面的落地决策清单。

1. 路径 A：requirements.txt 项目 → uv

最常见的存量形态。两步走：

迁移中的判断（不是无脑转换）：

  1. requirements.txt 里的传递依赖（当年 pip freeze 导出的快照）不该进 pyproject.toml——只挑你直接 import 的包；传递依赖交给解析器与锁（03 篇两个文件的角色分工）；
  2. uv add -r 之后跑测试再提交——锁文件与旧环境可能有差异（旧锁来自旧解析），先验证再切换；
  3. 过渡期可以双轨：CI 同时跑 uv sync 与旧流程一个迭代周期，稳定后删旧文件。

uv pip compile 的补充定位：如果项目要继续用 pip但想要跨平台锁，uv pip compile requirements.in -o requirements.txt --universal 可单独作为"更快的 pip-tools"使用——这是 01 篇说的 pip 兼容接口的正经用途。

2. 路径 B：Poetry 项目 → uv

Poetry 的 [tool.poetry] 段是私有格式，迁移 = 翻译成 PEP 621 标准：

机械工作可以用社区转换脚本（如 migrate-to-uv 一类工具，以各自文档为准），但迁移后必须人工核对三处：版本约束的语义等价（^3.11 → >=3.11,<4 是 uv 文档给出的对应）、extras 的转换、以及 poetry.lock → uv.lock（重新生成而不是转换——解析器不同，锁没有可比性）。

3. CI 集成：标准流水线模板

GitHub Actions 形态（GitLab/Jenkins 同理，改命令来源即可）：

三个 CI 纪律（都是可复现性的收口）：

  1. uv sync --frozen：CI 只许按锁装，禁止在 CI 里隐式重解析——锁过期就应该红，而不是悄悄解析出新版本；
  2. 锁版本的解释器矩阵：uv python install 3.10 3.11 3.12 + 矩阵策略（04 篇库项目组合的兑现）；
  3. 缓存键用 uv.lock 的哈希——锁变了缓存自然失效（setup-uv 已内置该逻辑）。

4. 发布：uv build / uv publish

库项目的最后一步也收编了（替代 build/twine）：

发布前自检三件套：pyproject.toml 元数据完整（description/readme/classifiers）、requires-python 与实际测试矩阵一致、版本号按 SemVer 升过（Git 09 篇的 tag 流程衔接：打 tag v1.2.0 → CI 按 tag 构建 → uv publish）。

5. 私有源与镜像配置

企业内网/国内加速的标准配置（写在项目 pyproject.toml，随仓库分发）：

  • 环境变量方式：UV_DEFAULT_INDEX（替换旧 UV_INDEX_URL 的现代写法，具体以 uv 文档 ENV 页为准）；
  • 凭据不进仓库：走环境变量或 keyring（与 Git 04 篇凭据纪律同构）。

6. 团队落地决策清单

uv 系列收官

八篇地图：定位与映射（01）→ 项目闭环（02）→ 依赖工程（03-04）→ 工具与脚本（05-07）→ 落地（08）。最后强调本系列的方法论：uv 的一切便利都来自把"环境"从手工状态变成"锁文件的可再现实例"——理解这一点，遇到任何环境问题都问一句"锁文件是否是事实来源"，答案自然浮现。

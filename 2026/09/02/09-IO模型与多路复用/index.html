09 - IO模型与多路复用

本篇目标

  • 按 POSIX 的口径分清五种 IO 模型：阻塞、非阻塞、IO 多路复用、信号驱动、异步，并理解它们在"等待数据"与"拷贝数据"两个阶段上的差别。
  • 讲清 select → poll → epoll 的演进动机：fd 上限、每次全量拷贝、O(n) 扫描这三个坑是怎么被逐个填掉的。
  • 手写一个最小的 epoll echo server（C，~80 行），搞懂水平触发（LT）与边缘触发（ET）的行为差异与 ET 的正确写法。
  • 掌握 Reactor 模式的结构，明白 Redis、Node、asyncio 的并发能力全部源自同一个 OS 机制。

前置：第 07 篇的上下文切换成本、第 08 篇的 fd；环境 Ubuntu 22.04 / WSL2，gcc。

1. 五种 IO 模型：两个阶段定乾坤

一次网络读（recv）从发起拿到数据，内部有两个阶段（POSIX 对同步/异步 IO 的定义见 POSIX.1-2008 aio_read 相关章节；经典两阶段框架出自 Stevens《UNIX 网络编程 卷1》第 6.2 节，五种模型图源出于此）：

五种模型按"谁在等、怎么等"划分：

模型 阶段 1（等数据） 阶段 2（拷数据） 谁阻塞 POSIX 分类
阻塞 IO 一直阻塞等待 阻塞拷贝 调用线程全程阻塞 同步
非阻塞 IO 立即返回 EWOULDBLOCK，反复轮询 阻塞拷贝 不等数据但拷贝时阻塞 同步
IO 多路复用 select/poll/epoll 阻塞等"任一就绪" 阻塞拷贝 阻塞在多路复用调用上 同步
信号驱动 IO SIGIO 通知"数据到了" 阻塞拷贝 不阻塞，靠信号 同步
异步 IO（AIO/io_uring） 内核全包，完成后通知 内核完成拷贝 全程不阻塞 异步

关键区分（面试与选型都吃这口）：前四种在阶段 2 都要自己拷贝，所以 POSIX 意义上都算同步 IO；只有异步 IO 连拷贝都不用你管（Linux 传统 AIO 支持面窄，现代方案是 io_uring，本文不展开，记住它是"第五种的正统实现"）。IO 多路复用的本质是用一次系统调用同时监视大量 fd，让"等"这件事集中化——它是本篇绝对主角。

为什么多路复用对服务端如此重要？一个 10000 连接的服务器：阻塞 IO 需要 10000 线程（07 篇算过切换成本）；非阻塞轮询烧 CPU；而 epoll 让一个线程盯着 10000 个 fd，只在有事的瞬间醒来。

2. select / poll / epoll 演进

三代接口的接力（man 2 select、man 2 poll、man 7 epoll）：

select（1983，BSD）——用 fd_set 位图传"我关心哪些 fd"：

三大痛点：fd 数量上限 FD_SETSIZE=1024（硬编码位图长度）；每次调用要把整个 fd_set 从用户态拷进内核再拷回（就绪状态就地改写，每次还得重置）；返回后要O(n) 全量扫描找就绪 fd。连接一多，扫描开销压倒一切。

poll（1997）——改成 pollfd 数组，去掉 1024 上限与就地改写问题，但"全量拷贝 + O(n) 扫描"依旧。

epoll（2002，Linux 2.5.44，Davide Libenzi）——把"注册"与"等待"拆开：

  • epoll_create1()：内核建一个 epoll 实例（红黑树组织注册的 fd）；
  • epoll_ctl()：增/删/改注册的 fd（只做一次，不随等待重复）；
  • epoll_wait()：只返回就绪的 fd 列表，不是"哪些有戏"而是"哪些有事"。

两个内核机制支撑 O(1)：回调注册——每个注册 fd 的就绪事件发生时，驱动回调把它挂进 epoll 实例的就绪链表（rdllist）；epoll_wait 只需检查这个链表是否非空，把链表内容返回给用户。于是：拷贝量 = 就绪数（不是总数），扫描量 = 就绪数（不是总数）。连接 10 万、活跃 100 的场景，epoll 干 100 的活，select/poll 干 10 万的活——这就是"C10K 问题"在 Linux 上的标准答案（C10K 术语出自 Dan Kegel 的著名文章）。

select poll epoll
fd 上限 1024（FD_SETSIZE） 无硬限 无硬限
每次等待的拷贝 全量 全量 无（注册一次）
就绪检测 O(n) 扫描 O(n) 扫描 O(1) 就绪链表
跨平台 全平台 全平台 Linux 专属（macOS 是 kqueue）

经验做法：写跨平台库用 poll（或库内封装 kqueue/epoll/io_uring）；写 Linux 服务直接 epoll；连接数不过百、就绪率极高的场景，select/poll 的简单性反而占优——epoll 的收益来自"连接多、活跃少"的不对称性，没有不对称就没有收益。

3. epoll LT vs ET：手写最小 echo server

epoll 有两种触发模式（man 7 epoll 的 “Two levels of triggering”）：

  • 水平触发（LT，默认）：只要缓冲区还有数据没读完，每次 epoll_wait 都持续报告。宽容：读到哪算哪，没读完下次再报。
  • 边缘触发（ET，EPOLLET）：只在状态变化的瞬间报告一次（从无到有）。高效但苛刻：必须一次性把数据读到 EAGAIN，否则残留数据永远不会再通知你——漏读 = 连接假死。

4. Reactor 模式

epoll 是 OS 机制，Reactor 是用它搭出来的并发设计模式（名称出自 Douglas Schmidt 的 ACE 论文 “The Reactor: An Object Behavioral Pattern for Concurrent Multiplexing and Event Handler Demultiplexing”，POSA2 卷有完整章节）。结构一句话：一个事件循环 + 一组回调，fd 就绪哪个就调哪个的 handler：

三条纪律（违反任何一条都会毁掉单线程事件驱动的底线）：handler 绝不阻塞（不睡、不同步读磁盘、不调慢接口——一个阻塞调用冻结全部连接）；handler 快进快出（重活扔给线程池/GPU 队列）；状态机化（半包、半写都记录在连接对象里，下次事件接着处理）。这正是 12 篇"事件驱动服务器"的原型，Redis/Node/asyncio 的骨架由此复制。

5. 为什么 Node/Redis/asyncio 都建在这上面

三个你天天用的系统，扒开外衣是同一个 epoll 事件循环：

  • Redis：单线程事件循环 + epoll（源码 ae.c，aePoll.c 是 epoll 后端）——单线程无锁，命令天然原子，10 万 QPS 的底气是"事件循环处理速度"而不是多线程。这也解释了 Redis 的著名禁忌：*一条慢命令（KEYS 、大 KEY）冻结所有连接（Reactor 纪律第一条被违反）。
  • Node.js：libuv 事件循环封装 epoll（Linux）/kqueue（macOS）/IOCP（Windows）；JS 回调 = handler。所以 Node 的性能天花板与天花板陷阱和 epoll 完全同构——同步 CPU 密集代码阻塞整个循环。
  • asyncio：Python 标准库的事件循环，默认选择器封装 selectors 模块（Linux 上自动挑 epoll）。用 30 行验证它真的在你机器上跑 epoll：

一张总表收束本篇（选型视角，经验做法）：

场景 推荐模型 理由
万级连接、IO 密集（网关/代理/推理服务的 HTTP 层） epoll + Reactor 不对称性收益最大
少量连接、逻辑简单 阻塞 + 每连接线程 代码最简单，切换成本可承受
磁盘文件 IO 阻塞 + 线程池 文件不进 epoll 就绪模型（普通 fd 无 O_NONBLOCK 语义），io_uring 除外
CPU 密集 事件循环没优势 该并行的是计算（多进程/多线程/GPU）

常见误区

  1. “epoll 一定比 select/poll 快”：收益来自"连接多、活跃少"的不对称；几十个连接全活跃时三者相差无几，epoll 的红黑树维护反而添乱。先看连接规模再选接口。
  2. “ET 更高级，应该默认用”：ET 把"必须读干净 + 处理半包半写"的正确性责任全推给你，Nginx/Redis 那样的团队写出的循环才配得上 ET；日常服务 LT 足够且稳（man 7 epoll 明确建议 LT 为默认心智模型）。
  3. “异步 IO = aio_read 那几个函数”：Linux 传统 POSIX AIO（glibc 线程模拟版/内核 kaio）覆盖面与性能都不理想；真正改变格局的是 5.1+ 的 io_uring。面试说"Linux 的异步 IO 生态以 io_uring 为现代主流"更准确。
  4. “普通文件 fd 也能塞进 epoll”：磁盘文件不参与 socket 那套就绪通知（读写基本总"就绪"），epoll_ctl 会报 EPERM；文件 IO 用线程池或 io_uring，这是事件循环里 handler 严禁同步读大文件的原因。
  5. “事件循环是万能并发方案”：它解决"大量 IO 等待"不解决"计算排队"；CPU 密集任务进 Reactor 会把所有连接冻住（Redis 的 KEYS * 事故是标准案例）。混合架构（事件循环收包 + 工作池算活）才是生产形态。

本篇小结

  • 五种 IO 模型按"阶段 1 谁等、阶段 2 谁拷"划分；前四种都是同步 IO（拷贝自己做），io_uring/异步 IO 才是全托管。
  • select（1024 上限、全量拷贝、O(n) 扫描）→ poll（去上限）→ epoll（注册一次、就绪链表 O(1)）；收益本质 = 连接多/活跃少的不对称性。
  • 手写 echo server 的要点：epoll_create1/ctl/wait 三件套、accept 与 read 分流、非阻塞 + 半写循环；ET 必须读到 EAGAIN，LT 是默认正解（经验做法）。
  • Reactor = 事件循环 + 回调分发的模式化封装，三条纪律：handler 不阻塞、快进快出、状态机化。
  • Redis/Node/asyncio 同构于 Reactor；它们的天花板与陷阱（慢命令阻塞一切）也同构——IO 并发归事件循环，CPU 并行归并行单元。

练习

  1. 编译跑通 epoll_echo.c，用 3 个终端同时 nc 测试；把 .events 改成 EPOLLIN | EPOLLET 并把 read 循环改成"只读 1 字节"，观察连接行为差异，写下 LT/ET 的体感结论。
  2. 补全 ET 正确写法：read 循环到 r <mark> -1 && errno </mark> EAGAIN 为止（注意 r==0 关闭连接的分支），重新验证；再给 write 也写半写循环（维护待发缓冲）。
  3. 写一个 Python 的 select 版 echo server（selectors.DefaultSelector 也算），与 epoll 版对比 strace 系统调用形状（strace -c -f），数一数每接受 10 条消息两者各花多少次 syscall。
  4. 压测对比：用 ab -n 10000 -c 100 http://localhost:9000/（echo server 改 HTTP 应答）或简单 TCP 压测脚本，比较 LT/ET 与 select 版的 QPS；解释"不对称性"在你机器上是否成立。
  5. 读 Redis 源码 ae.c 的 aeMain/aeProcessEvents（约 100 行），画出它的主循环与第 4 节 Reactor 图的对应关系；找出它在 handler 里如何避免阻塞（提示：时间事件分片、lazyfree）。

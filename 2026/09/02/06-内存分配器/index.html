06 - 内存分配器

本篇目标

  • 讲清 malloc/free 的分层结构：库的分配器（arena/空闲链表）建在内核原语（brk/mmap）之上，并用 strace 亲眼看到两层的行为差异。
  • 写一个 mini malloc，理解 first-fit/best-fit 与空闲链表；由此自然引出内部/外部碎片的定义。
  • 概览 tcmalloc/jemalloc 的设计思想：线程缓存、大小类、arena——知道它们解决什么、什么场景值得换。
  • 理解 Python 的内存管理三层结构：pymalloc 对象池、arena、退回系统 malloc；解释"为什么大对象特殊"、“内存为什么涨了不回”。
  • 掌握一套内存泄漏排查思路：从 RSS 曲线到 valgrind/tracemalloc 的完整路径。

前置：第 04/05 篇的虚拟内存、mmap、RSS 概念；环境 Ubuntu 22.04 / WSL2。

1. malloc/free 如何工作：brk/mmap 之上有分配器

malloc 不是系统调用，是 libc 里的库函数。它和内核的分工（CSAPP 第 9.9 节的分配器模型；Linux 实现细节见 glibc malloc 内部文档，man 3 malloc 与 mallopt(3)）：

malloc(64) 在系统调用层没有任何痕迹（分配器自给自足），malloc(256*1024) 则直接多出一条 mmap。这个分层解释了大量现象：小块分配快（用户态链表操作，几十纳秒）；大块走 mmap（进内核，微秒级）但 free 时立即归还系统（munmap）；128KB 阈值是可调的性能旋钮（mallopt 的 M_MMAP_THRESHOLD，glibc 还有动态调整逻辑）。

分配器内部如何记账？把空闲内存组织成链表（free list），分配时找一块够大的切下。最简单的两种策略（OSTEP 第 17 章《Free-Space Management》）：

  • first-fit：从链表头找第一块够大的。快，但低地址端容易剩下一堆小碎屑。
  • best-fit：找能装下的最小块。浪费少，但每次要扫全表，且会攒下大量"刚好差一点"的残余小块。

分配时还要"顺手"记下块大小（通常放在块头 header 里，CSAPP 第 9.9 节的隐式空闲链表正是这么设计的），free 才知道还多少。

2. 内存碎片：内部与外部（配 mini allocator）

内部碎片：给你的块比你要求的大（header、对齐、大小类取整），浪费在块里面。外部碎片：空闲内存总量够，但被切成不连续的小块，找不到一块连续的够用的。

d 没有复用 b 的洞——外部碎片诞生：总空闲量够（100），但最大连续块不够（100 < 200）。真实分配器还做合并（free 时把相邻空闲块并起来）和分离适配（按大小分桶的空闲链表，CSAPP 第 9.9 节的 malloc lab 就教到这），但碎片的根源已经在这 60 行里了。经验做法：长时间运行的服务出现 RSS 涨了不回，第一嫌疑是碎片（释放的块太小、位置不连续，合并不了还给内核），第二才是泄漏——两者现象相似，工具能区分（见第 5 节）。

3. tcmalloc/jemalloc 设计思想概览

ptmalloc（glibc 默认）诞生于单核时代，多核多线程下有两个先天短板：所有线程抢同一堆的锁（arena 数量有限），锁内操作链表在 NUMA 上跨节点访存。两个现代分配器给出同一思想的两种实现（Tcmalloc 论文：Sanfilippo/Google per-thread cache 设计；jemalloc 设计文档：Evans, “A Scalable Concurrent malloc Implementation for FreeBSD”）：

  • 线程缓存（thread cache / tcache）：每个线程私有一组小对象缓存，分配/释放小块完全无锁、访问全在本地——大并发的第一加速器。攒多了再批量归还中心区。
  • 大小类（size class）：不按任意字节切，而是按固定档位（8B、16B、32B…2MB），同档位对象复用。牺牲一点内部碎片，换来 O(1) 定位与极低的合并需求。
  • arena 分区：中心内存划成多个 arena（按 NUMA 节点对齐），线程绑定各自的 arena，减少跨节点流量与锁竞争。
  • 页级管理： jemalloc/tcmalloc 都把内存当"页（4KB）+ span/chunk"管理，大对象直接页分配、small object 从页里切。

什么时候值得换（经验做法，可查证的方法是压测对比）：多线程高频小对象（请求处理、KV cache 管理）用 jemalloc/tcmalloc 常有 10%~30% 吞吐提升；单线程或分配不频繁的场景收益接近零。在推理服务里验证极简单：LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2 ./server 前后各跑一遍基准——不写一行代码。

4. Python 的内存管理：pymalloc/arena

CPython 有自己的三层分配体系（依据：CPython 源码 Modules/obmalloc.c 的注释与官方 Dev Guide “Memory Management”）：

  • ≤512 字节的小对象（绝大多数 PyObject：小整数、短字符串、元组）由 pymalloc 管理：arena(256KB) → pool(4KB) → block（与对象大小匹配的固定档位）。释放的 block 回池复用，不归还 C 层。
  • >512 字节直接 malloc——这就是"大对象特殊"的原因：它绕过对象池，直接暴露在 glibc 分配器的碎片逻辑下。NumPy 数组的数据区、大字节串、模型 tensor 都在这里。
  • arena 整体归还的苛刻条件：一个 arena 里所有 pool 全空才能还给 OS。而小对象散布在不同 arena 时"某个 pool 总有活着的对象"——这就是 Python 常见现象"内存涨了不回"的主因（不是泄漏，是池化+arena 碎片），官方文档 “Memory Management” 明确记载此行为。

5. 内存泄漏排查思路

一套由粗到细的通用流程（C 与 Python 各有工具，思想共用；经验做法——先确认"泄漏的是哪一层"再选工具）：

  1. 现象确认：RSS 随时间/请求量单调增长且不回。ps -o rss,vsz -p PID 每分钟采样，或 pidstat -r -p PID 60。注意区分：VIRT 涨不叫泄漏（05 篇），RSS 涨才查。
  2. 分界定位：cat /proc/PID/smaps_rollup 看 Anonymous（新分配）与 Shared（映射共享库）哪边在涨。Anonymous 涨 → 堆/大对象问题；FilePmdMapped/Shared 涨 → mmap/页 cache 行为。
  3. C/C++ 层定罪：valgrind memcheck（valgrind --leak-check=full ./prog，慢 10 倍但精确到行）；常驻服务用 AddressSanitizer（gcc -fsanitize=address，运行时拦截）；分配热点用 heap profiler（gperftools 的 pprof / jemalloc 的 prof）。
  4. Python 层定罪：tracemalloc 快照 diff（下面代码）；gc 模块查引用环；第三方扩展（NumPy/CUDA）的泄漏要用 CUDA-MEMCHECK/compute-sanitizer 或 py-spy dump。
  5. 长跑服务：压测 + 灰度观察曲线；区分"泄漏"与"碎片虚高"——重启后 RSS 立即回落的模式更支持碎片（第 2 节），对象数不降的才支持泄漏。

常见误区

  1. “malloc(100) 就精确拿到 100 字节”：至少 112+（对齐与 header），大块可能按大小类取整到 256KB 级页。别拿 malloc 返回值当内存审计依据。
  2. “free 之后内存就还给 OS 了”：小块进分配器空闲链表复用，RSS 不变是正常且正确的；只有大块（mmap 路径）和触发 trim 时机才归还。用 RSS 判断"free 有没有生效"会冤枉代码。
  3. “Python 没有内存问题，有 GC”：GC 管引用回收，不管池归还（arena 保留）与 C 扩展的泄漏；del 之后 RSS 不降多半不是 bug，是池设计。判断泄漏要看对象层（tracemalloc），不是 RSS。
  4. “碎片和泄漏是一回事”：碎片是"空了但没合并/没归还"，泄漏是"没空"。前者换分配器（jemalloc）或改分配模式可能解决，后者必须改代码——处置完全不同。
  5. “128KB 阈值是官方钦定的最优”：它是 glibc 的默认值（历史经验值），glibc 自己还会动态调整它；把 mallopt 调优当玄学抄配置不如压测验证（经验做法）。

本篇小结

  • malloc 是"库的仓库管理"叠在"内核的批发"（brk/mmap）上：小块用户态链表直达，≥128KB 直接 mmap；strace 一看便知两层边界。
  • 分配策略 first-fit 快、best-fit 省，共同制造外部碎片；块内对齐与 header 制造内部碎片；合并与分桶是对抗碎片的两大武器。
  • tcmalloc/jemalloc 的三板斧：线程缓存（无锁）、大小类（O(1)）、arena（NUMA 友好）；LD_PRELOAD 十分钟完成 A/B 验证（经验做法）。
  • CPython 三层：pymalloc 池（≤512B）、C malloc（大对象）、arena 归还门槛高——"RSS 涨不回"多为池化行为；大对象直通 mmap 所以立还。
  • 排查漏-碎之争：RSS 曲线 → smaps_rollup 分界 → C 用 valgrind/ASan、Python 用 tracemalloc diff；先定位层再选工具。

练习

  1. 给 mini_malloc.c 的 my_free 加"相邻空闲块合并"（只处理 next 相邻的情形即可），重跑 main 验证 d 能复用 b 的洞；再思考为什么"向后合并"容易、"向前合并"需要 header 里的前驱信息（CSAPP 第 9.9 节边界标记）。
  2. 用 strace -e trace=brk,mmap,munmap 分别观察 python3 -c "x=[0]*10**7" 与 python3 -c "x=[str(i) for i in range(10**6)]" 的系统调用形状，对照本篇解释哪个走 pymalloc、哪个惊动了内核。
  3. 把 pymalloc_demo.py 的小对象数量从 50 万逐步加到 500 万，记录 RSS 增幅与 tracemalloc 的差值曲线；用 arena 结构解释差值为何越来越大。
  4. LD_PRELOAD jemalloc 前后跑同一个多线程 C 小程序（8 线程各 malloc/free 100 万次 32B），用 time 对比总耗时；没有 jemalloc 的机器可用 apt install libjemalloc2 装上再试。写 3 行结论。
  5. 构造一个真实的"碎片 vs 泄漏"对比实验：程序 A 每轮 malloc/free 一对 1MB+16B 的块；程序 B 每轮只 malloc 1MB 不 free。各跑 10 轮后用 cat /proc/PID/smaps_rollup 与 valgrind 分别观察，写下你区分两者的判据。

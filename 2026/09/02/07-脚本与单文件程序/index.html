07 - 脚本与单文件程序

本篇目标

大量 Python 使用形态根本不是"项目"，而是单个脚本：数据清洗脚本、运维小工具、教学示例。它们过去面临一个尴尬：要么塞进某个项目借环境（脚本与项目锁纠缠），要么配个独立 venv 并写一份"先装 requests 再装 rich"的 README 小抄。PEP 723（内嵌脚本元数据）+ uv 的支持让脚本自己声明依赖、自给自足。

1. PEP 723：写在脚本头部的依赖声明

3. 两种形态的分工（与 05 篇的光谱）

需求 形态
一两行的一次性命令 uv run --with rich python -c "..."（05 篇）
可分享/进 Git 的脚本（几十行+） PEP 723 脚本（本章）
要测试、要打包、有多个模块 完整项目（02 篇）
别人写好的 CLI uvx（05 篇）

判据是依赖数量与生命周期：依赖越多、活得越久，越该向"项目"形态迁移。PEP 723 脚本的舒适区上限大约是"单文件 + 少量依赖 + 无内部模块结构"。

4. 进阶：–with 与 PEP 723 的组合场景

安全视角的一个正面副作用：脚本级隔离环境天然限制了"实验性代码"的影响面（它拿不到你主环境的任何东西）——但不代表可以随意运行不可信脚本，网络与文件系统访问仍然存在（与 Agent 08 篇的沙箱原则同理：隔离 ≠ 安全沙箱）。

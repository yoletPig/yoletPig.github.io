13 - 性能剖析与优化

本篇目标

  1. 建立"不要猜要测"的工作流：cProfile 定位热点、line_profiler 拆到行、memory_profiler/tracemalloc 看内存；
  2. 掌握 timeit 微基准规范：为什么它比手工计时可信、怎么避免常见坑；
  3. 用实测数据检验常见优化手段（字符串 join、局部变量缓存、__slots__、生成器）的真实收益；
  4. 了解 PyPy/Cython/Rust 扩展的定位，沉淀"何时优化"的决策纪律。

1. cProfile：先找热点再动手

cProfile（标准库，确定性剖析器）统计每个函数的调用次数与耗时。工作流三步：跑剖析 → 按 cumtime/tottime 排序看热点 → 只优化头部：

读法（《Fluent Python》第 21 章同款工作流）：

  • tottime：函数自身耗时（不含子调用）——找"哪段代码本身慢"；
  • cumtime：含所有子调用——找"哪条调用链慢"；
  • ncalls 惊人的行（如上面的 200 万次）通常是算法层 bug：该缓存没缓存、该合并没合并。

经验做法：剖析要在接近生产的输入规模下跑（小输入的热点分布会骗人）；cProfile 本身有开销（每函数调用都记录），它回答"谁最慢"，不回答"到底多快"——后者交给 timeit（第 2 节）。命令行更省事：python -m cProfile -s cumulative script.py；只想要一行结论可用 time -p 配合（不剖析、纯墙钟）。

2. timeit 微基准规范

手工 time.time() 计时的坑：单次运行受系统抖动影响、没有考虑"第一次运行有冷启动"、精确度不足。timeit（标准库）的规范做法：多次重复取最优 + 关闭 GC + 自动选择循环次数（官方文档 timeit 模块）：

规范四条（经验做法）：

  1. 测"微操作"（一个函数、一个表达式），别测整个程序——timeit 回答"这个改法快不快"，cProfile 回答"该不该改"；
  2. 取 repeat 的最小值而不是平均值——最小值受系统干扰最小，最接近代码真实速度；
  3. 警惕常量折叠与作用域差异：timeit 默认在隔离命名空间执行，setup 参数负责准备数据；函数里的全局变量访问比局部慢（第 3 节实测），timeit 语句与真实代码的上下文要一致；
  4. 验证差异显著性：差异 < 5% 的"优化"大概率是噪声，不值得改代码。

4. PyPy / Cython / Rust 扩展概览

纯 Python 优化到头（热点确认、算法正确、数据结构合适）仍不够时，三条升级路线：

路线 是什么 何时考虑 代价
PyPy 替代解释器（JIT 编译） 纯 Python 长跑 CPU 任务，懒得改代码 启动慢、部分 C 扩展兼容问题、GIL 仍在
Cython Python 超集编译为 C，可加静态类型 数值循环、已有 C 库胶水 需要构建链、代码侵入
Rust 扩展（pyo3/maturin，pydantic-core/vLLM 部分内核即此路线） 原生扩展，释放 GIL 并行 热点模块重写、追求极致 开发成本最高，需 Rust 工具链

判据链条（07 篇决策树的性能分支）：cProfile 确认热点在 Python 字节码 → 算法/数据结构无解 → numpy 等向量化库能否覆盖 → 不行再 Cython/Rust。注意"热点在 C 层"时（numpy 大矩阵）三者都帮不上忙，问题变成并行化（07 篇）。

经验做法：给优化加"护栏"——优化前先建立基准测试（pytest-benchmark 或 timeit 脚本入库），改完跑对比；优化只改热点，不顺手重构（否则 benchmark 报告说不清哪来的收益）；收益 < 10% 且代码变难读的优化直接放弃。

5. 何时优化（经验做法）

优化纪律三条（Donald Knuth 的 “premature optimization is the root of all evil” 是行业共识，但常被误读——完整的观点是"在关键路径上过早优化是万恶之源"，不是"永远不优化"）：

  1. 先对，再快：正确性测试通过之前谈性能是负资产；剖析驱动的优化发生在"功能稳定后、发布前"；
  2. 度量优先：没有 cProfile/基准数据支持的"我觉得这里慢"一律不成立（本篇第一句话的执行版）；
  3. 热点集中度检查：80/20 规律——多数程序 80% 时间花在 20% 代码上，优化前 3 个热点函数通常就到顶了；改完重新剖析，验证收益，没有收益就回滚。

反面清单：为 1000 次调用的函数做 slots；把清晰代码改成一行推导式只为省 2%；在没测过 IO 占比的服务里并行化 CPU 段（07 篇）；用 += 拼 10 个字符串的"优化"（可读性损失换不来可测收益）。正面模板：上线前跑一次 python -m cProfile -s cumulative → 头部三个函数逐一确认"能缓存吗？能批量吗？能换结构吗？" → 每项改动配基准数据进 PR。

常见陷阱

陷阱一：用 cProfile 的数字当最终耗时——剖析器自身开销让绝对值失真；配对用法：cProfile 找热点 + timeit 出可信数字。

陷阱二：timeit 的语句与真实代码上下文不一致——测的是全局变量访问、真实路径是局部变量（反之亦然），结论失真；setup 尽量模拟真实上下文。

陷阱三：微基准结论直接外推——join 在"字符串数多、单个短"时优势最大，10 个长字符串 += 无所谓；任何优化的适用范围跟着实验条件走，写进注释。

陷阱四：__slots__ 破坏动态性而不自知——加了 slots 的类不能随便加属性、与某些序列化/依赖注入库冲突（它们靠 __dict__）；给第三方可能继承你的类的公共基类加 slots 前想清楚。

陷阱五：优化了非热点——把 2% 的函数快了 3 倍，整体没变化；每次优化前重看 cProfile 头部，确认这个函数的 cumtime 占比值得动手。

本篇小结

  • 工作流：cProfile 找热点（cumtime/tottime/ncalls 三看）→ line_profiler 拆到行 → timeit 验证改法 → tracemalloc 看内存；
  • timeit 规范：微操作、repeat 取 min、setup 模拟真实上下文、差异 <5% 视为噪声；
  • 实测收益榜：set/dict 成员判断（数量级）> join 拼接（数量级）> slots 内存（~50%）> 局部变量缓存（~20%）> 生成器省内存（O(n)→O(1)）；
  • 升级路线：PyPy（不改码）→ Cython（数值循环）→ Rust 扩展（极致热点，pydantic-core/vLLM 路线）；前提都是"热点在 Python 字节码"；
  • 纪律：先对再快、度量优先、只改热点、每次优化配基准数据——没有数据的"优化"是风险不是收益。

练习

  1. 对本篇 profile_demo.py：先用 cProfile 找热点，再把 build_report 的结果拼接改为生成器 + join（04 篇）与 str.translate 批处理（替代逐字符 replace），用 timeit 给出改动前后的可信数字（repeat=5 取 min）。
  2. 写基准脚本对比 deque.appendleft 与 list.insert(0, x) 插入 100_000 个元素；把"什么规模下差异显著"的结论写进注释（提示：deque O(1) vs list O(n)）。
  3. 用 tracemalloc 对比"列表推导收集 1 千万行日志 + 过滤"与"生成器管道过滤"的峰值内存；再故意加一个 list(...) 物化看峰值回升，解释原因（04 篇）。
  4. 给 06 篇的 Message dataclass 加 slots=True 与不加各创建 100 万个实例，用 tracemalloc 与 timeit 对比内存与创建耗时；写 3 行结论说明什么规模值得开 slots。
  5. （综合题）拿到一个"处理 1GB CSV 统计每列均值"的慢脚本：写出完整优化路线图——先剖析（贴你预期的 cProfile 头部形状）、列出 3 个候选优化（按预期收益排序）、说明每个的验证方法；最后说明什么情况下应直接换 pandas/numpy 而不是优化纯 Python 循环。

03 - 创建型模式

本篇目标

创建型模式把"对象怎么创建"这件事从使用代码中剥离。本篇覆盖 GoF 五个创建型模式中的四个（单例、工厂方法+抽象工厂、建造者、原型），每个都讲：动机 → 实现 → 代价 → 现代语言的替代/简化。

先给一个总判断，帮你校准学习投入：日常工作中最常用的是工厂类与建造者；单例最常用但争议最大；原型在现代语言中往往被浅拷贝 API 或序列化取代。

1. 单例模式（Singleton）

动机：全局只需要一个实例——配置中心、连接池、日志器。

三个必须知道的工程事实：

  1. volatile 不能省（Java）：instance = new Config() 不是原子操作（分配→构造→赋值三步），无 volatile 时另一线程可能拿到"已赋值但未构造完"的半成品实例。这是并发面试的经典考点，也对应本仓库 C++ 系列 12 篇的主题；
  2. C++11 起有更优雅的写法（Meyers’ Singleton，C++11 保证局部 static 初始化线程安全）：
  3. 单例的代价：隐藏的全局状态（调用方看不出函数依赖了它）→ 测试难以隔离；往往沦为"优雅的全局变量"。

现代替代：多数场景用依赖注入容器（一个受控的全局）或框架提供的 application context。经验法则：单例留给真正无状态、且生命周期=进程生命周期的对象。

2. 工厂方法与简单工厂

动机：调用方不应该 new 具体类——一旦写死，换实现就要改调用方（OCP，02 篇）。

代价与辨析：工厂类会增殖——产品种类少（≤3）且稳定时，直接 new 更直白。工厂的价值出现在：创建过程复杂（多步、需配置）、需要按运行时条件选择实现、或需要统一替换所有实现（如测试时换假实现）。

3. 抽象工厂（Abstract Factory）

动机：需要一族相关产品保持配套。例：UI 库要整套切换——Light 风格的 Button+Input+Dialog，或 Dark 风格的一整套。若用三个独立工厂，可能出现 Light 按钮配 Dark 对话框。

辨析：工厂方法生产一种产品、靠子类扩展；抽象工厂生产一族产品、强调配套约束。族的数量少时，抽象工厂的类数量膨胀很快（每族一个工厂类），这是它最大的代价。

4. 建造者模式（Builder）

动机：对象有很多可选参数。Java 的"重叠构造器"（telescoping constructor）是经典痛点——参数一多，调用处全靠位置记参数，可读性灾难。

两个关键区分（面试常考）：

  • 建造者 vs 工厂：工厂关心"创建哪种对象"（一步完成）；建造者关心"如何分步组装一个复杂对象"（多步，且步骤可控）；
  • 经典 GoF 建造者还包含 Director（指挥者，固化构建步骤顺序）；现代语言中 Builder 多简化为"链式 setter + build()"（Effective Java 第 2 版第 2 条推广的形态）。Java 标准库的 Stream.Builder、StringBuilder，Lombok 的 @Builder 都是此形态。

5. 原型模式（Prototype）

动机：创建对象的成本高（如要查库初始化），或只有"从现有实例出发改一改"才自然。

现代简化：多数语言的标准库/序列化机制覆盖了此需求（Python 的 copy、dataclasses.replace；JS 对象的字面克隆 structuredClone）。GoF 原型的clone 接口约定（深/浅拷贝的显式控制）在语言层面各有实现，需要理解的只剩"深浅拷贝的区别"——深拷贝复制引用链上的所有对象，浅拷贝只复制最外层、内部引用共享。

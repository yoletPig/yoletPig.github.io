01 - 为什么要数据库

本篇目标

  • 亲手用一个 JSON 文件当"数据库"，复现并发写坏文件、部分失败、查询慢三大局限。
  • 说清数据库提供的四件事：可靠存储、并发控制、查询语言、事务——每一件对应文件的哪个坑。
  • 回顾存储层次（内存/SSD/HDD），记住顺序 vs 随机 IO 的数量级差，这是后面所有章节的物理地基。
  • 给出数据库分类图（关系/文档/KV/时序/向量/图），学会按数据形态与查询模式选类别。

三大翻车对应三个缺失的能力：

翻车现场 缺失的能力 数据库的对应机制
写一半崩溃，文件永久损坏 原子写入 WAL/undo log：先写日志再改数据，崩溃后可恢复（第 06/10 章）
两个线程互相覆盖 并发控制 锁 + MVCC：读写互不踩踏（第 04 章）
2MB 文件查一次 1.87s，且随数据量线性变慢 高效检索 索引：B+树把 O(n) 变 O(log n)（第 03 章）

还有一个隐藏问题：json.load 要把全部 2MB 数据解析成 Python 对象才能查 25 岁的人——内存与时间都被整个数据集绑架。数据库只把需要的页读进内存（缓冲池），查询的代价与命中数据量相关而非总数据量相关。

2. 数据库提供的四件事

把上面的坑逐个堵上，就是数据库（DBMS，数据库管理系统）存在的意义。拆成四件事：

  1. 可靠存储（Durability）：数据写入后，进程崩溃、甚至机器断电都不丢。核心手段是 WAL（Write-Ahead Log，预写日志）：提交时先把"做了什么"追加写进日志并 fsync，数据页可以慢慢刷。操作系统 08 篇讲过崩溃一致性，WAL 就是它最成功的工业实现（DDIA 第 3 章）。第 10 章你会亲手写一个。
  2. 并发控制（Concurrency Control）：多个连接同时读写，互不产生脏数据。两大流派：锁（悲观，写写互斥排队）与 MVCC（乐观，读者看快照、写者建新版本，互不阻塞）。第 04 章讲 MVCC 全套，第 08 章讲 Redis 单线程模型的另一种答案。
  3. 查询语言（Query Language）：SQL 是声明式的——你说"要什么"，不说"怎么找"。优化器决定全表扫描还是走索引、用哪种 JOIN（第 05 章）。这是文件方案完全没有的能力：你永远手写 for 循环。
  4. 事务（Transactions）：把多条语句捆成一个"要么全成、要么全没"的单元（ACID，详解见分布式系统 07 章，本系列 04 章讲实现）。转账扣钱/加钱两步，中间崩溃也不会出现"钱扣了没到账"。

这四件事对应四种代价：写入变慢（要写日志）、占更多磁盘（多版本/索引）、需要学习（SQL/调优）、需要运维（备份/监控，第 12 章）。数据库不是"更高级的文件"，而是"用可预算的代价买到四条保证"的系统——记住这个定价视角，后面每个设计取舍都会回到它。

3. 存储层次回顾：所有性能问题的物理根源

数据库的一切设计（缓冲池、预读、索引、LSM、列存）都是在跟存储硬件的物理特性谈判。回顾三层（操作系统 01 篇有完整版，这里只留数据库相关的数字）：

关键数字（Jeff Dean 的经典 latency numbers，2020 年代 NVMe 环境的近似值）：

  • 内存随机访问 ~100ns，SSD 随机读 ~100μs，差 ~1000 倍。
  • 顺序访问比随机访问快 1-2 个数量级：NVMe 顺序读可达 3-7 GB/s，随机 4K 读只有几百 MB/s；HDD 顺序 ~200 MB/s，随机寻道 ~10ms，差距 ~100 倍。
  • 一次 fsync（强制落盘）≈ 一次 SSD 写延迟，~0.1-1ms。这就是分布式系统 07 章 fsync 实验里"每条 fsync 慢几十倍"的根源，也是所有数据库"组提交（group commit）"的动机。

由此推出数据库设计的两条铁律（经验做法）：

  1. 把随机写变成顺序写：WAL、LSM-Tree（第 06 章）都是这句话的产物。
  2. 把随机读控制在少的页数内：B+树矮胖（3-4 层摸到千万行，第 03 章）、缓冲池命中、索引覆盖，全是这句话的产物。

一个快速自查的直觉标尺：内存 100ns → SSD 100μs → 网络同机房 0.5ms → HDD 寻道 10ms → 跨地域 30-100ms。任何设计，只要能在心里沿这条标尺定位每一跳，就能看懂大多数性能取舍。

4. 数据库分类图：按数据形态与查询模式选类别

"数据库"是个大家族，按数据形态和查询模式分六类（DDIA 第 2 章的总览视角）：

选类别只看两个问题（经验做法）：

  1. 数据形态：结构化、关系稳定、要多表 JOIN → 关系型；嵌套、字段经常变 → 文档型；就是"键 → 值" → KV；带时间戳、按时间写入和聚合 → 时序；文本/图片经 embedding 后的高维向量 → 向量库；实体间关系本身是核心（社交链路、知识图谱）→ 图。
  2. 查询模式：点查为主（get by key）→ KV；条件查询 + 聚合 + 事务 → 关系型；“给一个向量找最像的 k 个” → 向量库。

常见误区是"按流行度选"而不是按形态选。一个典型反例：用 Redis 的 hash 存需要多条件查询的业务数据，然后手写一堆二级索引（自己再建 set 维护），最后发现自己在用 KV 库手搓关系型数据库——不如一开始就用 Postgres。本系列的立场（经验做法）：不确定时选关系型，理由在 11 章展开（"先用 Postgres"原则）。

顺便把两个容易混淆的词钉死：**数据库（database）**指数据的集合本身，DBMS 指管理它的软件（SQLite、PostgreSQL、Redis 都是 DBMS）。口语里"数据库"两者混用，本系列在可能歧义处用"数据库文件/数据库系统"区分。

常见误区

  1. “数据量小，直接读全文件也没事”：查询代价随总数据量线性增长，而索引查询只随命中量增长。今天 200 万行 1.87s，明天 2000 万行就是 19s，而一次 cron 全量扫描任务把 IO 打满会拖垮同机的所有服务。
  2. “数据库只是把数据存起来”：存只是 1/4。把它当文件用（一次写全量覆盖）等于放弃了并发控制与增量更新，也享受不到索引和事务——最贵的用法、最少的回报。
  3. “越新的数据库越好”：向量库、时序库解决的是特定形态的问题，通用场景下 PostgreSQL 一个系统覆盖 80% 需求（11 章"先用 Postgres"原则）。选型看数据形态与查询模式，不看新闻。
  4. “内存快所以把数据全放内存”：内存掉电即失，且单机内存容量/价格是硬约束。现实方案是"内存做缓存层（第 08 章），磁盘做事实源"——缓存可以丢，事实不能丢。
  5. “JSON 文件加个文件锁就安全了”：文件锁解决不了"写一半崩溃"，也不解决查询。能修补的是并发覆盖（用 fcntl.flock），修补不了原子性与检索，边际收益递减——该换 DBMS 时就换。

本篇小结

  • JSON 文件当数据库的三大翻车：部分失败写坏文件、并发写丢失更新、全量加载查询慢——分别对应缺失原子性、并发控制、索引。
  • 数据库提供的四件事：可靠存储（WAL）、并发控制（锁/MVCC）、查询语言（声明式 SQL + 优化器）、事务（ACID）；每一件都有对应的运行时代价。
  • 存储层次是所有设计的物理根源：内存→SSD 差 ~1000 倍，顺序比随机快 1-2 个数量级；两条铁律——随机写变顺序写、随机读控制页数。
  • 数据库六分类：关系/文档/KV/时序/向量/图，按数据形态 + 查询模式选；不确定时选关系型。
  • 下一章从 SQL 语言本体开始：先会用，后面才轮到"为什么快"。

练习

  1. 跑通 broken_json_db.py，把 writer_bad 的截断长度从 60 改成 120、200，观察 JSONDecodeError 位置的变化；再想一个"部分失败但文件恰好仍是合法 JSON"的场景（提示：截断发生在对象结束花括号之后），体会"文件合法 ≠ 数据正确"。
  2. 用 fcntl.flock 给 write_db 加文件锁，验证并发丢失更新消失；然后思考：锁加上了，原子性和查询问题解决了吗？写下三者为何必须由一个系统统一解决。
  3. 用 dd 实测你机器的存储层次：dd if=/dev/zero of=/tmp/t bs=1M count=2048（顺序写）与 Python 随机写 4K 块对比，记录你自己的顺序/随机比，替换 3 节的通用数字。
  4. 给你手头的一个真实项目数据（Agent 的会话记录、量化行情、爬虫结果）按第 4 节的两个问题（形态/模式）归类，写出选哪类存储、为什么；如果结论是"关系型"，再列三个你最需要的 SQL 查询。
  5. 预习题：翻车二里两个线程"各读到 5 个用户、各加 1 条、只剩 1 条"，如果换成两个进程（而非线程）还会发生吗？如果两个进程在不同机器上呢？（这条线索通向分布式系统 04 章的复制与 06 章的分区。）

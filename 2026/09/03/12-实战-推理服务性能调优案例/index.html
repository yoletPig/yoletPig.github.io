12 - 实战：推理服务性能调优案例

本篇目标

  • 把前 11 章的方法串成一条完整的调优链：基线 → USE → 分位数取证 → 定位 → 修复 → 回归验证。
  • 完整剖析一个 FastAPI 伪推理服务的四类典型病：事件循环阻塞（GIL/同步 CPU）、线程池不足、同步 IO、批处理缺失。
  • 掌握 wrk/hey 压测的正确姿势与解读。
  • 带走一份可复用的性能调优报告模板，以及 25 道高频面试题要点。

前置：全系列 01–11。本章的伪模型（sleep 模拟推理）刻意保留真实推理服务的并发骨架，把模型性能优化 Stage 5 的 vLLM 话题留给那边，本章专注"服务层"。

1. 案例设定与“有问题的程序”

一个文本推理服务：收到请求 → CPU 预处理（分词/归一化）→ “模型推理”（用 sleep 40ms 模拟 GPU 调用）→ 返回。三个缺陷埋在代码里，与真实项目里的频率一致：

缺陷清单（先剧透，排查时假装不知道）：缺陷1 CPU 预处理阻塞事件循环（10 篇的 GIL/asyncio 主题）；缺陷2 无连接复用与批处理（07 篇连接税 + 04 篇等待次数）；缺陷3 后续版本还会遇到线程池耗尽（FastAPI 同步端点默认线程池 40，OS 系列 09 篇的线程模型）。

2. 建立基线：压测的正确姿势

工具：wrk（或 hey，Ubuntu 22.04 可 sudo apt install wrk / hey 需下载二进制）。压测三要素（经验做法）：并发数要跨档位扫（1/10/50/100），每档至少 30 秒，输出保存归档——单点压测是事故复发的温床。

基线表（后面的所有对比以它为准）：

并发 P50 P99 QPS
10 48ms 120ms 716
50 180ms 701ms 892

先用 01 篇分诊：c=1 时 curl -w 单请求 46ms ≈ 5ms 预处理 + 40ms 推理 + ~1ms 框架——单请求是健康的，问题是并发下的串行点（负载/容量问题方向），且吞吐封顶预示有共享瓶颈。

3. USE 过一遍：资源检查表

对服务主机跑 02 篇的八件套，填 USE 检查表（节选关键行）：

资源 观测 结论
CPU mpstat -P ALL 1：1 个核 95%，其余空闲 单线程瓶颈形状（10 篇 GIL/事件循环指纹）
CPU 饱和 vmstat 1：r 列 1，调度延迟低 不是等 CPU，是没人用多核
内存 free available 充足，si/so=0 排除 05 篇问题
磁盘 iostat await 低，%util 低 排除 06 篇
网络 ss 无重传，netstat -s 干净 排除 07 篇
错误 dmesg 干净 无 OOM/硬件问题

USE 的结论：唯一异常是"一个核打满、其他核围观"——这是 asyncio 服务被同步代码阻塞的典型现场（事件循环是单线程的）。带着这个假设进入第 4 节的分位数取证。

4. 发现与定位：P99 长尾的三段证据

证据一（延迟形状）：c=50 时 P50=180ms、P99=701ms——长尾与均值同源（都是排队），符合"单点串行"模型：所有请求在事件循环里排队，队列越长尾部越糟（01 篇 Little’s Law：c=50、延迟 240ms → 在制品 L=12 个请求堆在单线程队列里）。

事件循环线程的时间被 preprocess 吃掉——缺陷1 实锤：async def 端点里的同步 CPU 函数让所有并发请求串行化。

继续扫描更高并发档位，发现新症状（热点会转移，03/10 篇的教训）：c=200 时 P99 再次恶化到 500ms+，而 mpstat 显示 1 个核仍只有 90%。这次 py-spy dump 看到不同形状——几十个线程都堆在 preprocess 里但 CPU 不高：线程池默认上限（anyio 40 个 worker thread）已耗尽，且 GIL 让 40 个 CPU 密集线程互相串行（10 篇的结论：Python CPU 密集用多进程/释放 GIL）。修复2：预处理换进程池（run_in_processpool 自实现），推理保持线程池：

证据四（off-CPU 交叉验证）：修复后若仍有毛刺，用 04 篇的方法收尾：py-spy dump 显示等待都集中在 await asyncio.sleep（正常模型等待），offcputime（08 篇）确认无异常阻塞——证明服务层已无串行点，剩余延迟即模型本身（40ms sleep），服务层优化到此为止，再往下是 Stage 5 的 vLLM 领地。

5. 终版对比与回归验证

版本 c=50 P50 c=50 P99 c=200 P99 QPS@50
v1（同步 CPU 在事件循环） 180ms 701ms 2000ms+ 892
v2（预处理进线程池） 46ms 102ms 510ms 2103
v3（CPU 进程池 + 修正并发） 47ms 98ms 105ms 2140

回归验证三件事（经验做法）：① 同口径复跑三轮取中位数（01 篇）；② 观察者效应自查——剖析工具全部摘除后数字不变（01 篇第 8 节）；③ 资源账复核——4 个 preprocess 进程 × 1 核 + 事件循环 1 核，机器 16 核余量充足，无 cgroup 节流（11 篇 cpu.stat 确认 nr_throttled=0）。注意进程池的代价：启动成本、序列化开销、内存 ×4（05 篇的 RSS 账），吞吐换容量的取舍要写进报告。

模板的灵魂在假设必须带依据、结论必须带证据编号——每个 E 都能回放，这是"证明而非猜测"的落地形式。

7. 面试高频问题 25 题（带要点）

  1. P50/P99 为什么比均值重要？ 尾部成因不同（GC/节流/重传）；高并发下 1−0.99ⁿ 放大（The Tail at Scale）。
  2. Little’s Law 是什么，怎么用？ L=λW，面积法推导无分布假设；算并发/排队/容量三变量。
  3. USE 与 RED 的区别？ USE 面向资源（错误→饱和→利用率），RED 面向服务（Rate/Errors/Duration）；排查时组合。
  4. CPU 100% 怎么排查？ 先 perf stat 判病型（IPC/cache miss）→ record -g 采样 → 火焰图找宽塔 → 修复复测（03 篇流程）。
  5. CPU 不高但服务慢？ off-CPU 分析：等待在 IO/锁/网络/调度；工具 offcputime/iostat/ss（04 篇）。
  6. 火焰图怎么读？ 宽度=占比非时间、深度=调用栈、山尖=叶子函数；颜色无语义。
  7. IPC 低说明什么？ 访存/分支瓶颈而非算力；配合 cache-miss 率定位是内存层级问题（03 篇）。
  8. strace 为什么不能随便在生产用？ ptrace 每次 syscall 双重停止，10 倍+开销（01 篇观察者效应）。
  9. eBPF 相比内核模块/改内核的优势？ verifier 安全、JIT 高效、即时生效；map 与用户态交换统计（08 篇）。
  10. kprobe/tracepoint/uprobe 区别？ 任意内核函数（不稳定） vs 预埋点（稳定） vs 用户态函数；优先 tracepoint。
  11. free 里 available 和 free 的区别？ free=完全空闲，available=不换页前提下的可分配估算（含可回收缓存）。
  12. RSS 持续增长就是泄漏吗？ 看单调性与请求相关性；分配器不还内存/缓存是常见假阳性；tracemalloc/memleak 定位（05 篇）。
  13. OOM killer 怎么选 victim、日志怎么读？ 按内存占用打分（oom_score）；看水位线/anon-rss/oom_score_adj；容器版在 cgroup 内挑（05/11 篇）。
  14. swap 该不该关？ 延迟敏感服务倾向关或低 swappiness，但要有内存水位告警与 OOM 预案；si/so 持续非零才是真病。
  15. iostat 的 %util 100% 是瓶颈吗？ 并行设备（SSD/NVMe）不是；用 aqu-sz/await/fio 上限综合判断（06 篇）。
  16. 顺序读为什么比随机读快几个量级？ HDD 寻道 + 预读有效 + 合并；NVMe 缩小但方向不变；fio 验证（06 篇）。
  17. write 返回成功数据就落盘了吗？ 否，只在页缓存；掉电安全靠 fsync；代价见逐条 fsync 案例（04/06 篇）。
  18. mmap 和 read 怎么选？ 流式 read、随机热点 mmap；llama.cpp 用 mmap 加载是例子（06 篇）。
  19. TCP 重传率高怎么查？ netstat -s 趋势 → ss -tin 看 rtt/rttvar → ping 分离链路 → ethtool -S/softnet_stat 查丢包环（07 篇）。
  20. 一次 HTTP 请求的延迟怎么分解？ 握手 1.5×RTT + 传输 + 服务端处理；tcpdump -ttt 的"ACK 快数据慢=应用慢"指纹（07 篇）。
  21. GIL 是什么，怎么绕？ 单线程执行字节码；CPU 密集用进程/释放 GIL 的扩展；观测指纹单核满（10 篇）。
  22. cgroup 限制下 top 为什么骗人？ /proc 未隔离显示宿主机数据；真话在 cpu.stat/memory.current；throttling 是隐形杀手（11 篇）。
  23. 容器 OOM 和宿主 OOM 区别？ cgroup 内挑 victim、CONSTRAINT_MEMCG 日志、working set 口径（11 篇）。
  24. 怎么证明你的优化有效而不是波动？ 同口径三轮取中位、假设-实验-结论编号、摘除观测工具复测、回归进 CI（本章报告模板）。
  25. 你会怎么为推理服务做容量规划？ Little’s Law 锁三变量 + GPU 带宽预算（09 篇 token/s≈带宽/字节）+ USE 水位 + 压测基线留档。

常见误区

  1. “先优化再压测”：没有基线的优化无法证明有效，也无法防止退化；基线数据与压测脚本是调优的另一半。
  2. “把 async def 里所有函数都 await 了就安全”：CPU 密集函数放进 async def 照样阻塞事件循环（await 一个同步函数不产生让出点）；判据是"这函数会不会让出 CPU"。
  3. “线程池越大越好”：GIL 下 CPU 密集线程互抢，40 线程比 4 进程慢；池的选择跟着"CPU 密集还是 IO 等待"走（10 篇决策表）。
  4. “P99 降了就收工”：还要看吞吐、资源成本、回归风险（进程池内存、worker 崩溃兜底），报告模板第 5/6 节是必填项。
  5. “案例里的 sleep 40ms 不真实”：它是"模型推理是外部黑盒"的抽象——真实 GPU 推理一样是"提交→等待"的 IO 型操作，服务层方法完全同构；模型内部的优化在 Stage 3/5。

本篇小结

  • 调优链条：基线（跨档压测）→ USE 分诊（单核指纹）→ 分位数+栈快照取证 → 修复（事件循环解放→进程池）→ 同口径对比 → 回归风险清单。
  • 三个缺陷对应三次修复：同步 CPU 阻塞事件循环（线程池）、GIL 串行化（进程池）、等待次数（批处理——本例中留给下一轮）。
  • 热点会转移：每个修复后必须重新压测与剖析，c=200 的二次恶化是本案例的关键转折。
  • 报告模板六段：背景/基线/假设/实验/结论/回归风险；假设带依据、结论带证据编号，让任何人事后可回放。
  • 25 题要点覆盖全系列：方法论（1-3）、CPU/延迟（4-10）、内存（11-14）、IO（15-18）、网络（19-20）、应用（21）、容器云（22-23）、工程素养（24-25）。

练习

  1. 完整复现本章实验（server_v1→v3），填写第 5 节的对比表并写出你机器上的三个证据片段（hey 输出、py-spy dump、mpstat 行）；对比你与文中数字的形状差异并解释（核数/量化模型模拟参数不同）。
  2. 给 server_v3 加批处理端点（收集 50ms 窗口内请求合并成一个"批次"调用，推理 sleep 不变），用 hey 验证吞吐提升并按 Little’s Law 解释收益来源（等待次数从 N 降到 N/batch）。
  3. 用 04 篇方法验证修复后的服务没有隐藏阻塞：压测时抓 py-spy dump 三次，确认 MainThread 总在 await 而非 CPU 函数；若有例外，定位并记录。
  4. 把第 6 节报告模板填成你自己的项目（任选一个真实服务），重点写"假设-实验-结论"的证据编号链；请一位同事只看报告复述你的排查过程，检验可回放性。
  5. 从第 7 节 25 题中随机抽 5 题自测（遮住要点，先答再看），每题限时 2 分钟；把答不出的题对应回章节小节重读，整理进你的面试清单。

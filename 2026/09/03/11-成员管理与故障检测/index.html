11 - 成员管理与故障检测

本篇目标

  • 理解心跳+超时故障检测的原理与误判根源：为什么"检测"只能是概率性的怀疑。
  • 掌握 Φ Accrual 故障检测器的思想（用分布而非阈值判断）。
  • 用 Python 模拟 Gossip 协议的收敛过程，了解 SWIM 的改进点。
  • 理解租约、脑裂与法定人数的关系，以及服务发现（DNS vs 注册中心）的选型。

1. 成员管理：集群的"花名册"问题

成员管理（membership）回答两个问题：现在集群里有谁？谁还活着？ 它是共识、分片路由、负载均衡的共同地基——所有"把请求发给谁"的决策都建立在这份花名册上。

难点依然是 02 章的不确定性：你无法区分"节点死了"与"网络断了"与"节点慢了"。任何声称"确定节点死了"的机制，都在分区场景下冒脑裂的风险。因此分布式故障检测的正确姿势是输出怀疑度（suspicion level），而不是判决（verdict）；真正的"判决"要交给多数派投票（如 Raft 选主）或租约机制兜底。

经典的失败检测器理论框架（Chandra & Toueg, Unreliable Failure Detectors for Reliable Distributed Systems, JACM 1996）：定义了"最终完备 + 最终精确"等性质等级，并证明任何共识算法都可以建立在"怀疑偶尔出错、但错误会被纠正"的检测器上。工程里的心跳+超时就是一个不可靠失败检测器——不可靠没关系，机制必须能容忍它的不可靠。

2. 心跳与超时：原理与误判

心跳（heartbeat）：每个节点周期性广播"我活着"；接收方维护"上次收到 X 心跳的时间"，超过 timeout 未收到即怀疑 X 死了。

误判的四个来源（每个都有真实事故对应）：

  1. GC 停顿：JVM Full GC 几十秒、Python 大对象分配触发的停顿——节点活着但错过多个心跳周期。
  2. 网络拥塞：心跳包排队，到达时间抖动。
  3. CPU 饥饿：同机部署的邻居进程把 CPU 抢光。
  4. 时钟问题：用墙钟算"上次心跳距今"，NTP 跳变导致误算（02 章的坑，应使用单调钟）。

超时参数的两难：短超时 → 快速检测但误判多；长超时 → 稳定但故障发现慢。误判的代价不对称：误判一个健康节点会触发副本迁移、选主风暴（对 3 节点 Raft 集群，一次误判就可能换主）；漏判只是晚几秒发现。所以经验做法：宁可长超时，配合其他信号（应用层探针、指标）综合判断。

3. Φ Accrual：从阈值到分布

固定超时的问题是把"怀疑度"二值化：0.24s 没心跳=健康，0.26s=死。Φ Accrual（Hayashibara et al., The Φ Accrual Failure Detector, SIGOPS 2004；Akka/Cassandra 采用）的改进：积累（accrual）历史心跳的到达间隔分布，输出连续的怀疑度 Φ。

思想三步：

  1. 采样历史心跳间隔，估计分布（工程上用正态近似或指数衰减直方图）。
  2. “已经 t 秒没心跳"时，计算"若节点健康，间隔超过 t 的概率” p(t)。
  3. 输出 Φ = -log10(p(t))：Φ=1 表示"健康时也会这样"的概率 10%，Φ=3 表示千分之一，Φ=8 表示亿分之一。

好处：不同网络环境下自动校准——稳定内网的心跳间隔方差小，1.5s 没心跳 Φ 就很高；公网抖动大，同样 1.5s 的 Φ 还很低。应用只需声明"我能容忍多大怀疑度"（Cassandra 的 phi_convict_threshold 默认 8~12）。这一思想也回答了第 10 章超时难题的一般化：超时不应是常数，应是分布的函数。

4. Gossip 协议：流言如何传遍集群

中心化心跳收集器（所有节点向一个监控服务器汇报）有单点与规模瓶颈。Gossip（流言/疫情传播协议）让每个节点周期性随机挑选少数同伴交换状态，信息指数级扩散。

收敛性的直觉推导：每轮每个节点随机传给 1 个节点，“不知情"节点数按指数衰减；N 节点集群 O(log N) 轮传遍（严格分析见 Karp et al., Fragmentation-Aware… 与 Demers et al. 经典论文 Epidemic Algorithms for Replicated Database Maintenance, PODC 1987——gossip 的开山之作）。SWIM（Das et al., SWIM: Scalable Weakly-consistent Infection-style Process Group Membership Protocol, DSN 2002）是 gossip 在成员管理上的实用化：直接 ping + 借助第三方间接探测（indirect ping）+ 怀疑态（suspect）+ 节点增量的广播，HashiCorp Serf/Consul、Go 的 memberlist 库即其实现。SWIM 对朴素 gossip 的关键改进：用间接探测降低"拜占庭式误报”（A 认为和 B 断了，可让 C 帮忙 ping——C 能 ping 通说明只是 A-B 链路问题），并把怀疑与确认分级传播。

经验做法：gossip 的参数常识——fanout 取 2~4 就够（log 扩散），轮间隔取秒级；消息要增量（只传变化）+ 带版本号（防旧消息回传）；集群越大轮间隔可越长。Gossip 适合"最终一致的元数据"（成员表、路由表），不适合需要强一致的配置（那种用 etcd）。

5. 租约、脑裂与法定人数

租约（lease）：带过期时间的授权。节点获得租约即可担任某种角色（主副本、配置缓存），到期必须续约。它把"持续信任"变成"离散信任"——每个租约期内授权方保证不把同一职责授给别人（Gray & Cheriton, Leases: An Efficient Fault-Tolerant Mechanism for Distributed File Cache Consistency, SOSP 1989）。

租约同样逃不开时钟问题（02 章）：持有者用自己的时钟判断"还没过期"继续操作，授权方用它的时钟判断"已过期"重新授权——两个时钟分歧的窗口就是脑裂窗口。彻底解决要靠fencing token（04 章）：授权单调递增编号，资源方拒绝旧编号操作。

法定人数（quorum）与脑裂：把"谁是主"的决定交给多数派投票（Raft/etcd 的选主），网络分区时只有多数派侧能选出主，少数派侧天然失去资格——这是对"两个分区各自为政"的结构性免疫。法定人数思想的适用范围远超选主：Redis 哨兵的故障判定、Kafka Controller 选举（KRaft 模式）、配置中心的写确认，全是同一招。经验做法：任何"权力授予"（主角色、租约、锁）都必须有法定人数或单调纪元背书，二者至少其一。

6. 服务发现：DNS vs 注册中心

服务发现（service discovery）：客户端如何找到"现在健康的服务实例列表"。两条路线：

维度 DNS 注册中心（etcd/Consul/Nacos/ZK）
机制 域名→IP 列表，TTL 缓存 服务注册+健康检查+推送/轮询
健康感知 弱（无应用层探活，除非配 SRV+监控） 强（TTL 心跳/HTTP 探针/gRPC 健康协议）
变更延迟 TTL 生效窗口（秒~分钟） 秒级（watch 推送）
运维成本 几乎为零（基础设施自带） 需要部署维护一个集群（它自己还是个分布式系统！）
适用 粗粒度、稳定服务、跨集群边界 细粒度、动态扩缩、需要元数据路由

经验做法：先 DNS 后注册中心——K8s 的 Service 本质就是"ClusterIP + CoreDNS"，覆盖了大多数发现需求；只有需要"按元数据路由/灰度分流/秒级摘除"时才引入注册中心。etcd 与 Consul 的分工直觉：etcd 是"Raft KV + watch"（K8s 的存储底座，配额锁选主都做），Consul 是"服务发现全家桶"（内置健康检查、DNS 接口、多数据中心）。

常见误区

  1. “心跳超时 = 节点死亡”：超时只是怀疑度越过阈值的信号。把怀疑当判决直接摘除节点，GC 停顿或网络抖动就能引发副本搬迁风暴。正确姿势：怀疑 → 间接探测（SWIM）→ 多数派确认/租约到期 → 才有动作。
  2. “故障检测器越灵敏集群越自愈”：过度灵敏的检测器是集群不稳定的常见根因——误判触发的选主/数据迁移本身制造故障（级联）。检测参数要与"误判代价"匹配，且配合滞回（hysteresis：恢复判定比摘除判定更严格）。
  3. “Gossip 会无限期震荡”：带版本号+增量传播的 gossip 收敛后消息量趋近于稳态（每轮 O(N·fanout) 心跳）；震荡通常是版本号缺失导致旧消息回传，或全量传播的带宽放大。
  4. “租约时间设短一点更安全”：租约过短→续约流量大、时钟偏差敏感、业务在续约失败时的中断频繁；过长→故障接管慢。租约时长必须 > "续约 RTT × 安全系数"且覆盖可预见的 GC 停顿（经验做法：秒级租约 + 提前 1/3 时间续约）。
  5. “注册中心是天然可靠的”：注册中心自己就是分布式系统（etcd 也是 3/5 节点 Raft 集群，也有脑裂防护与维护窗口）。客户端要做"最后一次已知列表"的本地缓存——注册中心全挂时至少还能按旧列表尽力服务。

本篇小结

  • 故障检测的输出应是怀疑度而非判决；心跳+超时是不可靠检测器，机制设计要容忍它的不可靠（Chandra-Toueg 框架）。
  • 误判四源：GC 停顿、网络拥塞、CPU 饥饿、时钟跳变；超时宁长勿短，配合间接探测与多数派确认。
  • Φ Accrual 把阈值升级为分布函数（Φ=-log10 p(t)），不同环境自动校准——超时问题的一般化答案。
  • Gossip O(log N) 收敛（Demers 1987），SWIM 加间接探测与怀疑分级成为成员管理实用标准（Serf/memberlist）。
  • 租约=离散化信任，需配 fencing token 防时钟分歧；权力授予必须有法定人数或单调纪元背书。
  • 服务发现先 DNS 后注册中心；注册中心本身也要当分布式系统运维，客户端留本地缓存兜底。

练习

  1. 跑通 heartbeat_timeout.py，把 GC 停顿改成 1.2s（超过 2 个超时周期），观察检测器输出"假阳性"的次数；再给检测器加"间接探测"：怀疑时向另一个健康节点查询 X 的心跳，只有它也超时才升级为"强烈怀疑"。
  2. 实现 Φ Accrual 检测器：用最近 20 个心跳间隔估计均值 μ 与标准差 σ，Φ = -log10(1 - Φ_normal((t-μ)/σ)) 的近似（可用正态 CDF 公式）；用它替代固定超时，对比在"正常抖动 20%"与"GC 停顿"两种输入下的 Φ 曲线。
  3. gossip_sim.py 扩展：加入 10% 概率"节点失联"（不响应消息）与 5% 概率"消息丢失"，测收敛轮数变化；再把 fanout 从 1 调到 5，画出 fanout-收敛轮数曲线，找出"性价比拐点"。
  4. 用 etcd（或 Consul，或纯模拟）实现租约选主：三个进程竞选 leader（SETNX + TTL 或 lease/grant），杀掉 leader 观察 failover 耗时；计算"租约 TTL 与故障接管时间"的关系公式。
  5. 设计题：一个 500 节点的推理集群（每节点跑 vLLM 副本），要求节点上下线 10 秒内被路由感知、单机房网络分区不脑裂、注册系统自身故障时服务不中断。给出你的成员管理设计（协议选择、参数、兜底），并指出每个选择对应本章哪个机制。

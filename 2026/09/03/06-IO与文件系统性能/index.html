06 - IO与文件系统性能

本篇目标

  • 建立 IO 全链路地图：应用 write → 页缓存 → 脏页回写 → 块层调度 → 设备，知道每层能优化什么。
  • 逐列读懂 iostat -x，并识破 %util/await 两大陷阱。
  • 会用 fio 做规范的磁盘基准（顺序/随机 × 读/写 × 队列深度），写出可复现的基准报告。
  • 实测 mmap vs read 的取舍，理解页缓存观测与小文件问题的药方。

前置：04 篇（同步 IO 等待案例）；操作系统系列 08（文件系统）。本篇是"量化磁盘"的一章：磁盘是六大资源里"谎言最多"的（页缓存、预读、调度器都在中间搅局），所以先把链条理清楚再谈数字。

1. 块层全景：你的 write 到了盘上吗

三个对性能有直接后果的结论：

  1. write 成功 ≠ 数据在盘上。write 只进了页缓存；进程崩溃缓存还在（数据不丢），机器断电缓存没了（数据丢）——所以要落盘必须 fsync（04 篇案例的价格）或 O_DIRECT/O_SYNC。数据库与推理服务的 checkpoint 逻辑全围绕这个分界。
  2. 读有缓存、写也有缓存。第一次慢第二次快是页缓存在工作；基准测试不加 direct=1 测的是"缓存的速度"而不是"盘的速度"。
  3. 顺序与随机的差距在 HDD 上是天堑，在 NVMe 上明显缩小。HDD 随机 4K 读约 100~200 IOPS，顺序写可达 200MB/s；NVMe 随机 4K 可到数十万 IOPS。经验做法：选型前先问负载是顺序大块还是随机小块，这决定了"换盘能不能救命"。

2. iostat 逐列解读与两大陷阱

逐列含义（man iostat；sysstat 12.5.2）：

列 含义 怎么用
r/s, w/s 每秒读/写请求数（合并前） IOPS 负载形状
rkB/s, wkB/s 带宽 与设备规格对比定饱和
rrqm/s, %rrqm 读请求被合并的比例 顺序负载合并率高是好事
r_await / w_await 读/写平均耗时（含排队） 分读写看瓶颈；>10ms 意味着明显排队
aqu-sz 平均队列深度（在途请求数） Little’s Law 的 L：aqu-sz = IOPS × await/1000，可互相验算
rareq-sz/wareq-sz 平均单请求大小 8KB vs 1MB 是两种完全不同的负载
%util 设备忙（有在途请求）的时间占比 陷阱见下

陷阱一：%util 100% ≠ 盘饱和。 %util 是"时间窗口里有请求在途的时间占比"。串行设备（单队列 HDD）上它≈饱和度；但 SSD/NVMe 并行处理请求，%util 100% 只说明"任意时刻都有请求在飞"，实际吞吐可能离上限还很远（man iostat 的说明：‘for devices serving requests in parallel… this figure may be misleading’）。正确判据组合（经验做法）：aqu-sz（排队深度，持续 > 队列上限的 50% 才谈饱和）+ await 趋势（排队加深则 await 上涨）+ fio 实测上限（下一节）。就 HHD 而言 %util 依然好用。

陷阱二：await 大 ≠ 盘慢。 await 含排队时间与请求合并效应；一次"10ms 的 await"可能是一次 fsync 冲刷的物理延迟，也可能是 1000 个请求排队。拆分方法：看 aqu-sz 与请求速率的乘除关系（Little’s Law），并用 fio 空载测一次"裸延迟"做基线。空载 NVMe 的 await 应该在 0.1~0.5ms，若空载就 >5ms，查盘本身（SMART/厂商工具）。

另注意 svctm 列已被 sysstat 废弃（输出里保留但不可信），别用它做判断。

4. 文件系统选择常识与挂载选项

  • ext4：久经考验、行为可预期，绝大多数场景的默认答案。xfs：大文件/高并发 IO、大容量盘表现稳，RHEL 系默认。btrfs/ZFS：快照/校验/压缩能力换性能开销，存档与备份场景再考虑。选型一句话：不确定就 ext4/xfs，"新潮特性"要先想清楚回滚方案（《Systems Performance》第 9 章有各 FS 特性对比）。
  • noatime：读文件不再更新访问时间，减少一次元数据写。挂载选项 noatime 是几乎无代价的常规优化（经验做法；atime 的存在感来自 Documentation/filesystems/ 与 man mount）。
  • 日志代价：ext4 数据模式默认 data=ordered（先写数据后提交元数据），崩溃一致性的代价就是写放大；data=writeback 更快但崩溃后数据可能旧——数据库类应用宁可要 ordered。
  • WSL2 注：WSL2 根文件系统是 ext4 虚拟盘（VHD），跨文件系统操作（访问 /mnt/c，即 Windows 的 NTFS，走 9P 协议）慢一个数量级，重 IO 的实验（如 fio、编译）务必在 WSL 文件系统内做（~/ 下），这也是新手"WSL2 慢"的最大原因。

5. mmap vs read：两条读文件的路线

同一份文件数据进内存有两条路：read() 拷贝到用户缓冲区，或 mmap() 建立映射后直接解引用（缺页时装载）。取舍（OS 系列 05 篇的概念落地）：

维度 read mmap
顺序大文件流式读 快且稳（预读、无需缺页开销） 首次访问逐页缺页，反而慢
随机访问热点页 每次都要 syscall+拷贝 命中页缓存后零拷贝直达指针
内存开销 需要用户态缓冲区 映射本身几乎免费（页缓存共享）
复杂度 简单、可预期 信号处理（SIGBUS）、同步麻烦

经验做法：模型加载这类"大文件顺序读一遍"用 read/预读（或 posix_fadvise(WILLNEED) 提前热缓存）；KV/索引这类"随机反复读"用 mmap。llama.cpp 加载 GGUF 走 mmap（模型性能优化 Stage 4 的实际案例）正是看重"首次缺页流式装入 + 之后随机访问零拷贝"的双重好处。

40 倍差距的药方（经验做法，按优先级）：打包成大文件（tar/parquet/自研容器格式，量化投资 09 篇的回测数据加载正该如此）；用 dentry/inode 缓存热身（先 find 一遍让缓存生效）；元数据操作改并发（多线程 open）；SSD/文件系统层面小文件场景提高 vfs_cache_pressure 收益有限，根治靠合并。

第三步：归因与修复。 反模式是"把缓冲的责任交给了最慢的层"：每条一次 write 系统调用（用户态→内核）+ 每条可能触发的回写。修复 = 用户态攒批（Python 的文件对象默认 8KB 缓冲本来就够，错在 flush_every=1）+ 让内核页缓存自然回写（30 秒到期策略），落盘需求用"每 N 秒 fsync 一次"的显式节拍。

第四步：对比。

结论句式：把 1.842s 降到 0.247s（7.5 倍），改动只是把 flush 频率从每条改为每批；系统调用次数从 20 万降到 1500，这与 03 篇 perf 火焰图中 write 占比的变化互为印证。

常见误区

  1. “fio 不加 direct=1 测出来的 IOPS 很漂亮”：那是页缓存的成绩，不是盘的。基准测试永远 direct=1（要测缓存性能时另测并注明）。
  2. “%util 100% = 该换盘了”：NVMe 上毫无意义（第 2 节陷阱一）。用 aqu-sz + await 趋势 + fio 上限三者判断。
  3. “write 返回 = 数据安全”：只是进了页缓存。掉电不丢要求 fsync（或 O_SYNC/O_DIRECT+fsync 语义），这正是 04 篇 12ms 案例的由来。
  4. “mmap 一定比 read 快”：顺序流式读 read 更稳（缺页开销小、预读友好）；mmap 赢在随机热点访问与省一次拷贝。按访问模式选，别按信仰。
  5. “WSL2 里测 IO 代表真实服务器”：/mnt/c 走 9P 慢一个数量级，VHD 虚拟盘与真机 NVMe 也有差异；WSL2 数据只做相对比较，绝对值以真机 fio 为准（02 篇的约定）。

本篇小结

  • IO 链路：页缓存（读写共用）→ 脏页回写策略 → IO 调度器 → 设备；write 成功≠落盘，fsync 是唯一保证。
  • iostat 读法：await 含排队、aqu-sz 是在途深度（可按 Little’s Law 验算）、%util 在并行设备上不作数；svctm 已废弃。
  • fio 体检单四场景（顺序/随机 × 读/写），direct=1、iodepth 按盘型设置，输出按"分位数+余量百分比"写结论。
  • mmap vs read：流式 read、随机热点 mmap；小文件问题的本质是元数据与 syscall 开销，根治靠打包合并。
  • 页缓存观测：cachestat 看全局命中率、vmtouch 看单文件驻留；WSL2 的 /mnt/c 慢一个数量级，实验要在 WSL 文件系统内做。

练习

  1. 在你的 WSL2 上跑第 3 节四条 fio，把结果填进"解读模板"（设备/命令/IOPS/BW/P99）；再把 iodepth 改成 1 与 128 重跑 randread，画出"IOPS vs iodepth"曲线并解释拐点。
  2. 复现第 2 节的验算：跑 fio 时另开终端 iostat -x 1，用 aqu-sz ≈ IOPS × await/1000 验证 Little’s Law 在块层的成立，记录三次采样误差。
  3. 用 python3 -c "import time,os; ..." 分别测"20 万条 flush_every=1/16/1024"并叠加 strace -c 的 write 次数，画出"syscall 次数 vs 耗时"散点图，验证本篇结论。
  4. 用 vmtouch 把一个 1GB 文件逐段缓存热身（dd 读前 25%/50%/100%），每档跑一次 bench_read 的随机跳读部分，记录缺页惩罚随缓存占比的变化。
  5. 给你自己项目的数据加载路径（模型/数据集/行情数据）做一次"小文件体检"：统计文件个数与总大小（find | wc -l + du -sh），估算按本篇药方（打包/热身/并发）能省多少 open/close 次数，写出一句可验证的优化假设。

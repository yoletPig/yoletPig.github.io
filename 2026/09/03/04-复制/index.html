04 - 复制

本篇目标

  • 掌握三种复制模式：主从（同步/半同步/异步）、多主、无主，并能说出各自的故障语义。
  • 系统分析复制滞后引发的三类问题（读己之写/单调读/一致前缀读）与对应修复手段。
  • 推导无主复制的 Quorum 交集条件 W+R>N，理解读修复与反熵如何最终收敛。
  • 手写一个带故障切换的主从复制模拟，亲眼看到"异步复制 + 主宕机"的数据丢失。

1. 为什么要复制：三件事

复制（replication）= 在多台机器上保留同一份数据的副本。动机有三（DDIA 第 5 章开篇）：

  1. 数据离用户更近（地理复制，降低读延迟）。
  2. 部分机器故障时系统仍可用（冗余，提高可用性）。
  3. 读请求分摊到多副本（提高读吞吐，第 01 章 x 轴）。

副本一多，核心难题立刻出现：怎么让 N 个副本保持一致。一切方案都是对"写操作如何在副本间传播"的回答。三大变量：谁接收写（单主/多主/无主）、什么时候确认（同步/半同步/异步）、冲突怎么办（修主/合并）。

2. 主从复制：同步、半同步、异步

主从复制（leader-based replication，也叫 master/slave、primary/secondary）的分工：主副本（leader）接收全部写，把变更记入日志（binlog/WAL），从副本（follower）消费日志追平；读可以走主也可以走从（读写分离）。

按"主副本何时向客户端确认"，分三档：

模式 确认时机 主宕机时 延迟 现实代表
完全同步 等全部从副本落盘确认 最少丢数据 最高；任何一个从挂了，写全停 几乎没人用（可用性太差）
半同步 等一个从确认 + 主自己落盘 最多丢 0 条（那一个从有全量） 中 MySQL semi-sync、Raft 日志提交（等多数派）
完全异步 主自己落盘即返回 可能丢已确认写 最低 MySQL 默认异步、Redis 主从、PG 流复制默认

推导半同步为什么是"甜点"：设主副本 + n 个从。完全同步的写延迟 = max(所有副本的网络+落盘)，可用性 = 所有从都活着；异步的丢数据窗口 = 主宕机瞬间未传输的日志。半同步只要求"有一个从跟上了"，主宕机后可以无损切换到它——用一个从的延迟代价，买断了"确认过的写不丢"。Raft 的"提交需多数派日志匹配"（第 05 章）本质是半同步思想的多数派版：3 副本半同步等 1 个从 ≈ 等 2 个节点确认（含主）。

故障切换（failover）的完整流程与三个坑：

  1. 检测：主超时（02 章：超时≠死亡，误判是常态）。
  2. 选举/提升：选新主。坑一——数据丢失：异步复制下旧主有未同步的写，切换后丢失。
  3. 重配置：客户端与剩余从感知新主。坑二——脑裂（split brain）：旧主没死透（只是 GC 停顿），与新主同时接收写；必须用纪元/ fencing token 强制旧主下台（第 11 章租约）。坑三——风暴：新主切换瞬间大量写涌入 + 所有从重建同步。

3. 复制滞后：三类问题与修复

异步复制下，从副本落后主副本若干毫秒到若干秒，这段时间内读到旧值（复制滞后，replication lag）。三个经典场景（DDIA 第 5.2 节；第 03 章已提，这里给完整对策）：

修复手段（都是"弱一致系统上做会话保证"的路由层技巧，经验做法）：

  • 读己之写：写后 N 秒内该用户的读强制走主；或客户端记录最后写入时间戳，从副本滞后于该戳就换副本/等待。
  • 单调读：按用户 ID 粘住同一副本（同一从）或记录"该副本已服务到的水位"。
  • 一致前缀读：把因果相关对象放同一分片（第 06 章的分区设计题），或由中件层校验版本顺序。
  • 降低滞后本身：从副本并行应用日志（MySQL 5.7+ 的多线程复制）、写操作分组提交、监控 Seconds_Behind_Master 并告警。

4. 多主复制：冲突是常态

多主（multi-leader）：多个副本都接收写，互相复制。动机：跨数据中心（每个机房一个主，本地写低延迟）、离线操作（手机端本地库是"主"，联网时同步）、协作编辑（Google Docs）。

代价：同样的数据可能被两个主同时改（写冲突）。经典例子：两个机房同时把某商品标题改成不同值。冲突处理策略：

  1. 避免冲突（最好）：把同一记录的"所有权"固定给某个主（如按用户分区），从根上让两个主不写同一行（经验做法优先级最高）。
  2. LWW（last-write-wins）：带时间戳比较，新的赢。简单，但丢数据（先到的写被静默覆盖），且依赖 02 章"不可靠的物理时钟"。
  3. 保留所有版本，应用层合并：用版本向量（02 章）识别并发写，交给应用决定怎么合（Dynamo 的兄弟值 sibling，CouchDB 的冲突文档）。
  4. CRDT（收敛数据类型）：为"加法计数器"“集合”"序"等特定结构设计可交换的合并算子，数学上保证收敛（Shapiro et al., Conflict-free Replicated Data Types, SSS 2011）。
  5. 自动解决算法：操作转换 OT（Google Docs 文本）等。

5. 无主复制：Quorum 读写与修复

无主（leaderless，Dynamo 风格，出处：DeCandia et al., Dynamo: Amazon’s Highly Available Key-value Store, SOSP 2007）：没有主副本，写发给任意副本集合，读也发给多个副本比版本。

参数 N = 副本总数，W = 写成功的副本数，R = 读需要的副本数（N=3, W=2, R=2 是常见起步）。

Quorum 交集推导（必须会证明）：

  • 读到至少一个"最新写入"的条件：W + R > N。证明：写集合大小 W，读集合大小 R，两者都在 N 个副本中；若 W + R > N，则 |写∩读| ≥ W + R - N ≥ 1，读集合至少含一个写成功的副本 → 只要该副本保留"最新"值即可读到。
  • 保证写入成功的交集（防两个并发写都"成功"却互不知晓）：W > N/2，即写集合过半（两个过半集合必相交，同 Raft 多数派逻辑）。
  • 极端取值：W=1, R=N → 写快读慢（Dynamo 可配置）；W=N, R=1 → 读强写慢；W+R>N 只保证"读到至少一份最新副本"，不等于线性一致（DDIA 第 5.3 节明确指出：quorum 不是万能，时序交错下仍可能读到旧值，比如写还没开始读就完成了的场景）。

读后写、写前读的版本管理靠向量时钟（02 章）：并发写产生 sibling，读时合并。两个收敛机制：

  • 读修复（read repair）：读时发现某副本版本旧，顺手把新值写回去。
  • 反熵（anti-entropy / hinted handoff）：后台进程比对副本间差异（Merkle 树高效比对，Cassandra 实现），慢慢补齐——这是"最终一致"里"最终"的执行者。

常见误区

  1. “读写分离能提升写性能”：不能。所有写仍走主（单主架构），读写分离只扩读吞吐；写瓶颈要靠分区（第 06 章）或换无主/多主。
  2. “半同步复制 = 数据零丢失”：MySQL 半同步在"等待 ACK 超时"时会自动降级回异步（rpl_semi_sync_master_timeout），降级瞬间等于异步——所谓零丢失只在"降级未发生"的时间窗内成立。要无丢失得靠多数派共识（Raft/Paxos 系存储）。
  3. “Quorum 配置了就是强一致”：W+R>N 只保证读到"至少一份最新"，不保证读到的是这份（并发交错、sibling 合并都可能给出旧序结果）。DDIA 第 5 章给了具体反例；要线性一致还得加读时读修复强制 + 写前读确认（Dynamo 的做法）或干脆用共识系统。
  4. “故障切换是瞬间且无损的”：切换全程（检测超时 + 选举 + 客户端重连）通常秒级，期间服务降级；异步复制还有丢数据窗口。可用性目标（几个 9）要按"切换时间 × 频率"核算，而不是假设永远不切。
  5. “LWW 是无害的冲突解决”：它按墙钟时间戳丢写，而墙钟恰恰不可靠（02 章）。两个并发写里"先执行"的那个可能因为时钟慢被判旧而消失——计数器、余额类数据用 LWW 会直接丢更新，CRDT 或应用层合并才是正解。

本篇小结

  • 复制的三个动机（就近/冗余/读扩展）与一个核心难题（写传播）；同步/半同步/异步的取舍 = 数据安全 ↔ 延迟与可用性。
  • 半同步是工程甜点；Raft 多数派提交是其多数派版；故障切换三坑：丢数据、脑裂（用纪元/fencing 防）、切换风暴。
  • 复制滞后三类问题各有路由层解法；优先做会话保证而不是上强一致（经验做法）。
  • 多主的本质是"引入冲突"，最好的处理是避免（所有权分区），其次 CRDT/应用层合并，LWW 会静默丢数据。
  • 无主复制：W+R>N 保证读到最新副本（可推导），W>N/2 保证写集合相交；读修复 + 反熵负责最终收敛；Quorum ≠ 线性一致。
  • 手写模拟确认了两个关键事实：异步复制丢数据是机制性的，纪元检查能挡住脑裂写。

练习

  1. 跑通 master_slave.py，把 random.uniform(0.01, 0.08) 的复制延迟上限调大到 0.5s，对比 async 模式下"切换丢失数据量"的变化；再在 failover 前加一个 await asyncio.sleep(0.6)，确认数据不再丢——写下"复制延迟与丢数据窗口"的关系。
  2. 在 DynamoCluster 里把 W 改成 1、R 改成 1（违反 W+R>N），构造一个"写成功后立刻读却读到 None 或旧值"的执行序列，验证 Quorum 条件不是装饰。
  3. 实现 hinted handoff：场景 1 中副本 2 掉线期间的写，由其他副本暂存提示，副本 2 恢复后投递。对比它与反熵的修复时机差异。
  4. 多主冲突实验：两个节点并发把 title 写成不同值，分别用 LWW（用 time.time() 戳）与"应用层合并（拼接标题+标记冲突）"处理，各运行 20 次统计 LWW 覆盖了哪一侧——说明为什么计数类数据不能 LWW。
  5. 设计题：社交 App 的"用户资料"（低冲突）与"关注关系"（高并发修改）要复制，你会分别选哪种复制模式与冲突策略？给出理由并指出每种选择在故障切换时的数据丢失期望。

09 - 向量数据库与语义检索

本篇目标

  • 建立 embedding 直觉（衔接数学基础 01 篇的余弦相似度），掌握三种相似度度量及"归一化后内积=余弦"的证明。
  • 说清精确检索为什么慢：暴力扫描的复杂度账。
  • 理解两类 ANN 索引：IVF（倒排分桶）与 HNSW（多层图），配图讲清搜索路径；了解 PQ 量化概览。
  • 完整实操 pgvector（建表/建索引/查询/参数调优），并设计一个带元数据过滤与去重的 Agent 记忆库。

1. embedding 是什么：把语义变成几何

embedding（嵌入）= 用一个高维向量表示一段内容，使语义相近的内容在向量空间中距离相近。文本经 embedding 模型（如 BGE、OpenAI text-embedding-3，维度常为 384/768/1536/3072）映射后，“数据库索引"与"如何让查询更快"变成几何问题——检索即"找最近的 k 个点”（kNN, k-nearest neighbors）。

为什么"语义检索"用这些而不是精确匹配？因为用户问"怎么调数据库参数"和文档"配置优化器的方法"没有一个词完全重合，但两者的 embedding 会落在空间中邻近的位置——向量把"同义/相关"变成"距离近"。这就是 Agent 记忆（Agent 开发 05 篇）、RAG 知识库、以文搜图的共同底层。

2. 三种相似度度量：归一化后等价的证明

三种度量在不同库里/模型里都有出场（pgvector 三种都支持：<-> L2、<#> 内积、<=> 余弦）。关键结论：向量归一化（变成单位向量）后，三者给出完全相同的排序。证明只需两步（中学几何）：

推论与经验做法：凡是用余弦的场景，入库前先把向量归一化，之后统一用内积——省一次除法、索引实现更简单（主流向量库的 cosine 索引内部就是这么做的）。什么时候保留原始长度？内积本身含"向量模长"信息时（如协同过滤里模长代表热度）才不归一化——语义检索默认归一化即可。

精确 kNN = 对查询向量与库里每一个向量算一遍相似度，取 top-k。账目（d=1536 维，n=1000 万条）：

ANN（Approximate Nearest Neighbor）的交易结构：建索引（离线），查询时只探索数据的一小部分，换取"快 100-1000 倍"但召回率 <100%（真 top-1 可能漏掉，工程上用 recall@k ≈ 0.95+ 衡量是否可接受）。两大主流思路：切空间（IVF，把空间分桶，只搜几个桶）与建图（HNSW，在图上贪心导航）。

4. ANN 索引原理：IVF 与 HNSW

IVF（Inverted File Index，倒排分桶）——Faiss 的经典索引：

IVF 快但有两个软肋：簇边界上的点容易漏（近邻恰在没选中的簇里）；插入/删除要维护倒排表。于是主角登场——

HNSW（Hierarchical Navigable Small World，Malkov & Yashunin 2016）——分层可导航小世界图，pgvector/Milvus/qdrant 的默认主力：

三层机制逐个拆：

  1. 分层跳表式结构：上层节点稀疏（长边），越往下越密（短边）。顶层大步定位区域，底层小步精调——与跳表"多层车道"同构（08 章），但这是图不是链表。
  2. 贪心搜索：每层从当前点看邻居，谁更接近查询就走谁，走不动就下降一层；底层用候选队列（大小 ef_search）做多路扩展而非单路贪心。
  3. 建图：每个新点从顶层贪心下降找到自己在各层的近邻，与 M 个近邻互连（保持图"可导航小世界"性质：既能长距离跳转又有短边稠密性）。

参数直觉（pgvector 与论文同名）：m（每点连接数，越大图越稠密召回越高、索引越大）、ef_construction（建图候选宽度，影响图质量）、ef_search（查询候选宽度——运行时可调的精度/速度旋钮）。选型速记：IVF 实现简单、内存省，适合超大规模+召回要求中等；HNSW 召回高、查询快，代价是内存（图结构额外 1-2 倍）与构建时间。

PQ（Product Quantization）概览：内存压缩术——d 维向量切成 m 段，每段用 k=256 个质心量化成一个字节，1536 维从 6KB 压到 ~768B（32 倍），距离在压缩码上近似计算。代价是精度损失，通常 IVF/PQ 或 HNSW+PQ 组合用（Faiss 的 IVF-PQ 是十亿级标配）。pgvector 的半精度（halfvec）与量化索引（0.7+ 的 bit/halfvec 类型）是同一思想的轻量版。

5. pgvector 实操：建表、建索引、查询

安装（PG16）：apt install postgresql-16-pgvector（PGDG 源）或源码编译；扩展启用一次即可。

三件事要注意（pgvector 文档 + 经验做法）：

  1. pgvector 的 HNSW 是"过滤后搜索"而不是"预过滤"：WHERE 条件在索引扫描外生效，过滤性太强（命中 <1%）时会退化为大范围扫描——高过滤场景给元数据列建 B-tree 索引（本例 agent_id/kind），让规划器先收窄集合（PG 16 亦可用分区替代过滤，11 章）。
  2. 索引建在"空表或小表"上，增量插入性能更好；批量导入后重建索引更快。
  3. SET hnsw.ef_search 是会话级：应用侧每次连接要设（或放进连接池的初始化 SQL）。

7. Agent 记忆库完整设计

把全章组装成一个可直接用的模块（Agent 开发 05 篇"检索式长期记忆"的存储实现，~40 行核心）：

设计决策逐条落地（每条都能追到本章某节）：

  1. 存取：content + embedding 同表（一行即一条记忆，JSON metadata 挂 extra）；PG 单库承载，万级记忆无压力，亿级再谈专用向量库（11 章选型决策树）。
  2. 元数据过滤：agent_id/kind 是 B-tree 索引列，先过滤后向量排序（5 节要点 1）；时间衰减（created_at 加权或定期归档）防"记忆越多噪声越大"。
  3. 去重：两层——内容哈希精确去重（建模加 content_hash TEXT UNIQUE）+ 内积 >0.98 的语义近重复合并；Agent 反复自我总结时没有去重会指数膨胀。
  4. 模型一致性：换 embedding 模型 = 全库重算（维度与空间语义都变了），建表时维度锁死并在元数据里记 model_name——混模型的检索结果是垃圾（经验做法，真实事故）。

常见误区

  1. “余弦相似度是向量库的专属度量”：归一化后内积/余弦/L2 排序等价（2 节证明），库与库之间比较的其实是"归一化约定是否一致"。混用模型或忘记归一化，排序悄悄错位且无报错。
  2. “ANN 返回的一定是真最近邻”：ANN 是近似——召回率是工程指标不是理论保证。关键应用（合规检索、医药）要么 ef_search 拉高 + 抽样验证召回，要么保留精确检索通道（数据量允许时）。
  3. “向量库 = 新装一个数据库”：pgvector 让"语义检索"成为 PG 的一个索引类型，元数据过滤/事务/备份全套白得。专用向量库（Milvus/Qdrant）的价值在亿级规模、多副本检索与极致 QPS——先看量级再决定（11 章）。
  4. “ef_search 越大越好”：它在精度-速度曲线上滑动（6 节），过大让延迟预算爆炸、召回收益趋平。按 SLA 反推，别拍脑袋。
  5. “记忆库加个向量列就是 Agent 记忆了”：没有去重（重复注入稀释上下文）、没有元数据分层（检索噪声）、没有时间衰减（旧事压新事）的记忆库会主动毒化 Agent。存储只是记忆系统的 1/3，检索策略与写入策略（Agent 05 篇）才是灵魂。

本篇小结

  • embedding 把语义检索变成几何问题：高维空间中"相关"=“距离近”；三种度量在归一化后排序等价（两步证明），统一用内积。
  • 精确 kNN 是 O(n·d) 的暴力扫描，百万级以上必须 ANN：用召回率换速度。
  • IVF=切空间分桶（nprobe 控精度），HNSW=分层图贪心导航（m/ef_construction 离线、ef_search 在线）；PQ 是内存压缩术。
  • pgvector 完整闭环：vector 类型 + HNSW/IVFFlat 索引 + 运算符查询；过滤场景给元数据建 B-tree，ef_search 按召回 SLA 反推。
  • Agent 记忆库 = 存取 + 元数据预过滤 + 双层去重 + 模型一致性记录；与 Agent 05 篇的检索策略拼成完整闭环。
  • 下一章进入综合实战：亲手写一个 KV 存储引擎，把 WAL/SSTable/compaction/缓存全部变成自己的代码。

练习

  1. 用 numpy 验证 2 节等价性：生成 100 对随机向量，归一化前后分别用三种度量排序，记录"归一化前三种排序是否一致、归一化后是否一致"，用实验复现证明。
  2. 手写暴力 kNN（numpy 矩阵化：(Q @ X.T) 一次算完 1000 查询 × 10 万向量的内积），测耗时；换 1536 维再测——用实测数字复述 3 节的复杂度账。
  3. 在 pgvector 上完成 6 节实验：10 万条 128 维向量 + HNSW，扫 ef_search ∈ {10,40,100,200,400}，画出延迟与 recall@10 曲线，选出"recall@10≥0.95 的最低 ef_search"。
  4. 给 7 节 MemoryStore 补两个功能：content_hash UNIQUE 的精确去重迁移（写 ALTER 语句）与时间衰减排序（ORDER BY dist - decay(now-created_at)，思考衰减项的量纲）。
  5. 设计题：Agent 需要"最近 7 天工具调用结果优先 + 全历史兜底"的记忆检索——用 5 节的过滤 + 分区（11 章预告）思路给出表结构与查询，说明为什么不用两个向量索引。

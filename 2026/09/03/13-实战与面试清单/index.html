2. 面试高频 30 题（带答案要点）

理论篇

  1. CAP 定理到底说了什么？ 分区发生时线性一致（C）与可用性（A）不可兼得；P 不可选；取舍是操作级不是系统级标签。别忘补 PACELC。
  2. 为什么分布式不能靠物理时钟排序事件？ 漂移 + NTP 阶跃 + 跨机无共同现在；"先发生"需要 happens-before 定义；Lamport 时钟保因果方向，向量时钟可判并发。
  3. 两将军问题与拜占庭问题的区别？ 前者信道不可靠（丢消息）下无法 100% 达成一致；后者节点还会说谎，容 f 个叛徒需 3f+1；数据中心只需崩溃容错 2f+1。
  4. FLP 不可能定理说了什么，工程怎么绕？ 纯异步 + 1 崩溃故障则确定性共识无法保证终止；工程用超时/随机化把系统变成部分同步，牺牲最坏情况终止性。
  5. Raft 为什么必须多数派提交？ 两个"多数派"必相交 + 一票限制 → 同一任期不可能两个 leader；相交保证已提交条目存在于任何未来 leader → 已提交不被覆盖。少数派提交会造成日志分叉不可修复。
  6. Raft 如何防止脑裂？ 任期比较拒绝旧 leader 消息 + 旧 leader 凑不齐多数派无法提交 + 随机选举超时防选票瓜分。旧分区侧一切写入都不会对客户端返回成功。
  7. Raft 的选举限制是什么，为什么需要？ 投票前比较候选人日志（先比最后条目 term 再比 index），不比我新就不投——保证新 leader 拥有全部已提交条目（Leader 完备性）。
  8. 为什么 Raft leader 不直接提交前任任期的条目？ 旧条目即使过半复制，也不能证明"不会有更新的 leader 用冲突条目覆盖它"；只有提交本任期条目才能间接确认旧条目安全（5.4.2 节）。
  9. Quorum W+R>N 保证了什么、不保证什么？ 保证读到至少一份最新副本；不保证线性一致（并发交错/ sibling 合并仍可能给出旧序）。
  10. 线性一致读在 Raft 上怎么做？ ReadIndex（读前确认领导权 + 等应用追上 commit）或 Lease Read（租约期内免确认，依赖时钟假设）。直接读 leader 状态机是漏洞。
  11. 最终一致的系统怎么实现"读己之写"？ 会话粘滞（写后短窗内读主/同副本）或客户端带时间戳门槛读。不需要全局强一致。
  12. 幂等为什么是必须的？ at-least-once 下重投不可避免（发送超时重发、ack 丢失重投）；"处理与确认跨系统"决定 exactly-once 只能端到端达成 → 让重复无害。
  13. 分布式锁的正确姿势？ TTL 判断不可靠（时钟 + 进程暂停）；要 fencing token（单调纪元）由资源方拒绝旧纪元；纪元单调性由共识保证。
  14. 2PC 的致命弱点？ 协调者在"落盘决定后、通知完成前"宕机 → 所有参与者卡在 in-doubt 持锁阻塞。3PC 想修却依赖网络延迟上界假设，分区下破坏原子性。
  15. Saga 的补偿与数据库回滚的区别？ 补偿是新业务操作（可见中间态、可能失败要重试、需要幂等）；隔离性缺失要业务防（状态机让中间态不可见）。

工程篇

  1. Kafka 为什么快？ 顺序写日志 + 零拷贝 sendfile + 批量压缩 + 分区并行（OS 09 章的 IO 直觉全用上）。
  2. 消费堆积怎么办？ 查消费耗时瓶颈 → 扩消费者（≤ 分区数）→ 加分区（注意 key 顺序语义）→ 降级非关键消费；堆积是消费能力账单，不是 MQ bug。
  3. 重试风暴怎么形成、怎么防？ 全体客户端同时重试叠加原始流量压垮刚恢复的下游；防：指数退避 + full jitter + 重试预算 + 重试只包一层（不级联）。
  4. 熔断器三个状态与切换条件？ 关闭(统计失败率)→超阈值→打开(快速失败冷却期)→冷却到→半开(放探测)→成功关/失败开。阈值要带样本量防震荡。
  5. 令牌桶 vs 漏桶？ 令牌桶限平均速率容忍突发；漏桶恒定流出绝对平滑。分布式限流要 Redis+Lua 原子或网关层实现。
  6. 一致性哈希解决什么问题？ 取模扩容全量搬家 → 环上只迁 K/N；倾斜靠 vnode 大数定律（实测 vnodes=100 时极差 <1%）。
  7. 为什么 Kafka 用固定分区数不用一致性哈希？ 分区是并行度与顺序的单位，固定数量让路由表小、副本放置可控；弹性扩分区成本高，所以按峰值预设。
  8. 心跳超时怎么设？ 长于"正常间隔 × 抖动余量"且覆盖已知停顿（GC）；误判代价高于漏判，配合间接探测与滞回；Φ Accrual 用分布代替阈值。
  9. Gossip 为什么能收敛、多快？ 每轮每节点随机传 fanout 个同伴，未覆盖数指数衰减，O(log N) 轮；增量 + 版本号防旧消息回环。
  10. 主从切换怎么防丢数据？ 半同步（至少一个从确认）或共识日志（Raft）；异步复制必丢"切换窗口内未同步"的已确认写——用"最大可用 or 最大安全"参数显式选择。

场景篇

  1. ZooKeeper 和 etcd 怎么选？ 都是小而强一致的协调存储：etcd（Raft、MVCC、watch、K8s 生态）、ZK（ZAB、临时节点、成熟稳定）；大量业务数据放谁都不对。
  2. Redis 主从 + 哨兵能保证不丢数据吗？ 不能——异步复制 + 哨兵判主窗口内已确认写可能丢；要强一致用 Redlock 也要配 fencing（且被 Kleppmann 批评），或换 Raft 系存储。
  3. 分布式 ID 怎么生成？ UUID（无序索引差）、号段模式（DB 批量发号）、Snowflake（时间戳+机器+序列，趋势递增，本质混合时钟）；回拨要用等待或备用位处理。
  4. PD 分离解决什么？ prefill 计算密集 vs decode 访存密集，分开部署各自扩容，KV cache 跨节点传输衔接——y 轴拆分的 LLM 版。
  5. LLM 训练的 3D 并行各自解决什么？ DP=吞吐（梯度 AllReduce，2(N-1)/N 通信量）、TP=单层放不下（机内 NVLink、层内通信频繁）、PP=层数深（气泡 (p-1)/(m+p-1) 靠 micro-batch 稀释）。

3. 设计题答题框架

四步法（每道设计题都按这个骨架走，先总后分、先稳后优）：

  1. 澄清与量化：QPS/读写比/数据量/延迟要求/一致性要求/可用性目标。数字决定架构——1k QPS 和 100k QPS 的答案完全不同。
  2. 主干设计：先画最简单可行架构（无状态层 + 存储层 + 队列/缓存），再谈分区与复制。用本系列语言：x/y/z 轴 + 复制模式 + 一致性等级。
  3. 深挖难点：面试官追问的都是"故障时怎么办"——按三笔账（部分失败/不可靠网络/无全局时钟）逐项回答：超时？重试？幂等？补偿？
  4. 权衡显式化：每个选择说出放弃了什么。"我选异步复制买低延迟，代价是切换窗口可能丢已确认写，用半同步参数缓解"比"用 Redis 就行"高一个段位。

秒杀系统：漏斗分层——前端静态化+按钮防抖（挡 90%）、网关限流（令牌桶，按库存量发放请求额度）、Redis 预扣库存（Lua 原子 decr，防超卖）→ MQ 异步下单（削峰）→ DB 最终落库（唯一索引防重复下单）。一致性等级：库存扣减线性一致（Redis 单点原子或 Lua），订单落库最终一致（Outbox）。故障预案：Redis 挂→降级 DB 限流直购；MQ 堆积→消费者扩容；重复支付→幂等键（用户ID+场次ID）。

短链系统：发号器（Snowflake 或 DB 号段）→ Base62 编码 → KV 存储（哈希分区，key=短码）。302 重定向 + CDN 缓存热点。关键难点：防自定义短码冲突（唯一索引兜底）、统计点击数（异步累加 + 定期合并，容忍秒级误差）、过期回收（惰性删除 + 版本号）。容量账：10 亿短链 × 60B ≈ 60GB，单机都放得下，真要分布式只为吞吐与可用性——先说清这一点再画集群（考官在测你会不会"杀鸡用牛刀"）。

Feed 流：推模式（写扩散，发布时写进所有粉丝收件箱，读快写重，适合粉丝少）vs 拉模式（读扩散，读时合并关注者最新内容，写轻读重，适合大 V）vs 推拉结合（普通人推、大 V 拉——经验做法主流方案）。存储：收件箱用"用户ID 分区 + 时间戳倒序列表"（因果一致即可，第 03 章）；一致性要求：自己发的帖子自己立刻可见（读己之写，写后粘主）；热点用户发布风暴（千万粉丝写扩散爆炸）用"大 V 内容拉取 + 收件箱只存指针"化解。

常见误区

  1. “面试设计题要答出最先进的架构”：考官要的是取舍能力不是名词堆砌。先给简单方案说出它的天花板，再按量化数字升级——"kv 单表 → 按用户分区 → 一致性哈希扩容"的演进叙事远胜上来就画 8 组件架构图。
  2. “手写 Raft 只是面试噱头，工作中用不上”：读 etcd/TiKV/Raft 库源码时，选举/日志/快照的结构与你手写的完全同构（差异只在持久化、网络、性能工程）；这套骨架也是理解 K8s 控制面、TiDB Placement Rule 的门票。
  3. “30 题背完就行”：面试官会从你的答案里挑一处追问两层（"多数派为什么防脑裂？"→"两个多数派为什么必相交？“→"如果节点数是偶数呢？”）。每题要能向下推一层，本系列各章的"为什么"小节就是为此准备的。
  4. “把模拟代码当生产代码”：本篇 Raft 实现缺持久化、快照、成员变更、真实网络栈——它是教学骨架。生产永远用 etcd/raft 库（Go）或 alibaba/SOFAJRaft，不要自研共识（经验做法：自研共识是分布式领域最经典的"重新发明事故"来源）。
  5. “分布式面试只考理论”：一半以上问题会落到"线上事故怎么排查"——堆积、超时抖动、切换丢数据、热点分区。答题时主动引用"我会先看什么指标、分几步定位"，把理论挂到排障动作上。

本篇小结

  • 手写 Raft KV 把第 05 章每个规则落到代码：任期/一票/日志检查/提交规则/分区防护共约 200 行，分区实验验证"旧 leader 写不进多数派"。
  • 概念-代码对照表是把理论内化的检查器——任何一条说不出代码落点，就回 05 章重读。
  • 30 题覆盖理论（CAP/时钟/共识/复制）、工程（MQ/弹性/缓存）、场景（选型/LLM）三层；每题要能向下追问一层。
  • 设计题四步法：量化 → 主干 → 故障深挖 → 显式权衡；秒杀=漏斗+原子预扣+异步落库，短链=发号+KV+容量清醒，feed=推拉结合+读己之写。
  • 全系列收束：单机最优（01）→ 不确定世界（02/03）→ 数据正确性（04~08）→ 系统活下来（09~11）→ 真实系统与 LLM（12）→ 动手与输出（本篇）。

练习

  1. 把 SimNet 提取为公共模块，让 client.py 真正启动集群并调用 linearizable_read()；然后构造"读请求打到了刚被分区的旧 leader"场景，验证确认心跳会把它挡下来（返回 None 或重试其他节点）。
  2. 给 RaftNode 增加持久化：term/voted_for/log 写入文件（每次变更前先落盘），kill 进程重启后能恢复状态并继续服务——这是 Raft "持久化状态"规则的最小落实。
  3. 模拟第 05 章提交规则的边界：term=1 时 A 把命令复制给 B（C 掉线，未提交）；C 回来、B 当选 term=2 后写入新命令。打印日志观察 term=1 的旧命令如何随 term=2 命令的提交而被提交。
  4. 从 30 题中挑 10 题，合上书写出答案要点再对照；把答不出的题回溯到对应章节重读，直到能"向下追问一层"。
  5. 用四步法独立完成一道新设计题：设计"分布式限流服务"（全公司共享，支持按用户/接口两维限流，10k 服务实例接入，Redis 已有）。写出量化假设、主干架构、Redis+Lua 的关键原子逻辑、以及 Redis 故障时的降级策略。

05 - 查询优化与执行计划

本篇目标

  • 理解优化器做什么：基于代价（CBO）的估算流程，统计信息在其中的角色。
  • 逐字段读懂 EXPLAIN / EXPLAIN ANALYZE：cost、rows、actual time、loops、扫描节点。
  • 掌握常见"索引失效"原因（函数包裹/隐式转换/低选择性）的识别与修复。
  • 对比三种 JOIN 算法的适用场景，并把慢查询排查整理成一条可复用的流程（经验做法）。

1. 优化器做什么：基于代价的估算

SQL 是声明式的：SELECT ... WHERE user_id=42 不指定"怎么找"。把"要什么"翻译成"怎么做"的是优化器，主流 OLTP 数据库（PostgreSQL、MySQL 8、SQLite）都是基于代价的优化器（Cost-Based Optimizer, CBO）：枚举可行的执行方式，给每种算一个代价分，挑最低的（System R 项目 1970 年代开创的方法论，Selinger et al. 1979 Access Path Selection in a Relational Database Management System）。

代价主要两项：IO 代价（读多少页，顺序读 vs 随机读系数不同）与 CPU 代价（比较/投影/哈希多少行）。估算的原料是统计信息：每表的行数、每列的直方图与不同值数（NDV）、索引的聚簇程度。看一眼 PG 的统计：

优化的两个朴素判断（面试常考）：索引查找的代价 ≈ 树高×随机读系数 + 命中行数×回表；当估算命中行数超过总行数一定比例（PG 经验阈值约 5-10%，低选择性时更高），顺序扫描整表反而更便宜——全表扫描不是错误，是选择。这也解释了低选择性列（性别/状态）建了索引优化器也不用的现象（03 章预告过）。

2. EXPLAIN 与 EXPLAIN ANALYZE：逐字段解读

两级的用法：EXPLAIN 只给计划不执行（估算）；EXPLAIN ANALYZE 真执行并回报实际数据（小心：EXPLAIN ANALYZE 会真的跑 UPDATE/DELETE，排查写语句时包一层 BEGIN; ... ROLLBACK;）。PG 示例（SQLite 的 EXPLAIN QUERY PLAN 粗粒度得多，MySQL 的 EXPLAIN 有 type/key/rows 列，思路相同）：

逐字段解读（这一段值得逐行看）：

  • cost=0.43…831.12：启动代价..总代价，单位是"代价单位"（1 页顺序读 ≈ 1.0），不是毫秒。两个计划比大小用总代价；同库内可比，跨库无意义。
  • rows=210：优化器估算的输出行数。估算靠统计信息，错得离谱时（实际 20 万，估 210）优化器会连环选错 JOIN 顺序——stats 过期是"昨天还好好的今天突然慢"的第一嫌疑。
  • actual time=0.031…3.214：真实执行数据（ANALYZE 才有）。0.031..3.214 是"输出第一行/全部行"的毫秒——第一行快不等于整体快（排序类节点要把所有行吃完才有第一行）。
  • rows=203 vs 估算 210：估算贴近实际，计划可信；偏差两个数量级就该 ANALYZE。
  • loops=44：该子节点被执行 44 次（外层每行驱动一次）。看总耗时要把 actual time × loops 一起看——单次 0.068ms × 44 次是这条查询的大头。
  • Seq Scan / Index Scan / Bitmap Heap Scan：顺序扫描 / 索引扫描 / “索引找到一堆 ctid 聚成位图再批量回堆”（随机 IO 换顺序 IO 的折中，大范围命中时优化器爱用）。
  • Rows Removed by Filter: 956：过滤掉 956 行才留 44 行——过滤比 >20:1 说明索引缺席，这是 Seq Scan 上最重要的信号。

经验校准（经验做法）：读计划先看三处——顶层节点类型（有没有意外全表扫）、rows 估算 vs 实际（统计信息准不准）、loops 乘出来的热点子节点。三处扫完，八成问题已定位。

SQLite 的计划器输出粗粒度得多——EXPLAIN QUERY PLAN 只报"用什么扫描、用什么索引"，没有 cost/rows（SQLite 是嵌入式引擎，估算逻辑内置但不对用户展示）。拿 03 章的联合索引实验直接对照（实测输出，SQLite 3.37）：

三个词翻译过来就是 2 节的全部语义：SEARCH = 索引定位（Index Scan），SCAN = 全表扫描（Seq Scan），COVERING INDEX = 索引即答案（Index Only Scan）。同一个查询，在 SQLite 看结构、在 PG 看代价与真实数字——两边的输出对齐到同一套概念，你在任何数据库前都不会慌。

3. 常见"索引失效"与全表扫描原因

索引在但优化器不用/不能用，四大主因（每条配识别方法）：

  1. 函数包裹列：WHERE lower(name)='alice'、WHERE date(created_at)=CURRENT_DATE。列被函数处理后，索引里的原始值帮不上忙。修复：改写成对常量做函数——WHERE created_at >= CURRENT_DATE AND created_at < CURRENT_DATE + 1；确实要对函数查询就建表达式索引：CREATE INDEX ON orders (lower(name))（PG 支持，SQLite 支持表达式索引，MySQL 8 支持函数索引）。
  2. 隐式类型转换：WHERE phone = 13800138000（phone 是 TEXT）——整列被隐式 cast 成数字再比较，与函数包裹等价，且结果可能错（前导 0、溢出）。修复：字面量类型与列一致（'13800138000'）。识别：PG 计划里出现 Filter: ((phone)::numeric = ...)。
  3. 低选择性：WHERE status='ok' 命中 90% 行，索引查找 + 海量随机回表，比顺序扫贵。优化器自动放弃是正确行为。修复：换更窄的过滤列，或做联合索引让"状态+时间"共同收窄，或干脆认命全表扫（把 5 节的流程走完再下结论）。
  4. 统计信息缺失/过期：大批量导入后没 ANALYZE，估算全错。PG 有 autovacuum 自动收集（阈值 10% 变更），大导入后手动 ANALYZE 表名 是肌肉记忆。识别：rows 估算与 actual 差 10 倍以上。

附带两个书写层陷阱：前导通配 LIKE '%xx'（无法用 B+树定位起点）；OR 混用无索引列（WHERE a=1 OR b=2 中 b 无索引 → 整体退化为扫描；PG 有 Bitmap Or 兜底，MySQL 老版本直接放弃）。

4. 统计信息与 ANALYZE：估算的地基

优化器的 rows 估算全部来自统计信息。PG 的 ANALYZE 采样表的一部分行（默认 300×100 = 3 万行级样本），为每列记录：不同值数（n_distinct）、最常用值及其频率（MCV）、等高直方图（把非 MCV 值域切成 100 段）、相关系数（物理顺序与逻辑顺序的相关性，估随机 IO 用）。这些数字都能直接查：

估算怎么发生（一行直觉）：选择率 × 表行数。status='ok' 的选择率取 MCV 频率 0.667；user_id=42 在 1000 个不同值上估 1/1000；两个 AND 条件的选择率相乘（独立性假设）——所以"数据倾斜/列间相关"时估算会系统性失真（比如 user_id=42 恰好全是 ‘ok’，真实选择率不是 0.001×0.667）。识别与修复：

  1. 估算失真的信号：EXPLAIN ANALYZE 里 rows 估算与 actual 差一个数量级以上。
  2. 过期统计：批量导入/大规模删除后手动 ANALYZE 表名（autovacuum 的触发阈值是 10% 行变更，亿级表 10% 也要很久才到——大导入后别等）。
  3. 倾斜列：MCV 已经覆盖最常用的值，估算大体靠谱；真正坑的是列间相关性——PG 用 CREATE STATISTICS（extended statistics，声明列间函数依赖/相关性）让优化器把选择率算对，PG 16 文档 14.2 节。
  4. 代价常数可调：SHOW seq_page_cost;（默认 1.0）、random_page_cost（默认 4.0，SSD 上常调到 1.1——优化器会因此更倾向索引扫描）。改的是"你机器上随机读与顺序读的真实比值"，这是 01 章存储层次在优化器里的投影。

MySQL 的对应物：ANALYZE TABLE + information_schema 的统计、EXPLAIN 的 rows 列 + EXPLAIN ANALYZE（8.0+）；SQLite：ANALYZE; 建 sqlite_stat1 表，供查询计划器做粗选择（跑一次 ANALYZE 常能"修好"莫名其妙的 SCAN 选择）。共同点：统计是估算的地基，地基歪了优化器不是变慢，是选错路。

5. JOIN 三算法：什么时候用哪种

优化器手里只有三种连接积木（DDIA 第 3 章 / PostgreSQL 文档 52.6 节）：

算法 思路 复杂度 适用场景
Nested Loop 外表每行在内表查一次（内表侧走索引） 外表行数 × 索引查找 内表有索引、外表小（OLTP 典型：1 行驱动几十行）
Hash Join 内表整表建哈希表，外表逐行探测 两表各扫一遍 + O(1) 探测 大表×大表、等值连接、无可用索引（OLAP 主力）
Merge Join 两输入先按连接键排序，再同步归并 O(n+m)（若已排序） 连接键已有序（索引现成/输出本要排序）、大数据等值

选择逻辑（优化器替你做，但要能看懂它的选择）：等值连接 + 一大一小 + 内表键有索引 → Nested Loop；等值 + 两大 → Hash Join（注意内存：哈希表装不下会落盘 spill）；范围连接（BETWEEN）或输入已排序 → Merge Join。在 EXPLAIN 里看 Join Type 节点，问三个问题：外表选的是谁（小驱动大原则）、内表有没有 Index Scan、Hash Join 的内存是否溢出（PG 计划里 Buckets/Batches>1 说明落盘）。

一个反直觉点收尾：OLTP 里 JOIN 不慢，慢的是"外表没走索引"或"驱动表选错"。把"JOIN 慢就拆成应用层循环"当默认方案，多数时候是放弃了让数据库一次 IO 拉回多行的机会——除非跨库/跨服务，才轮到应用层 JOIN。

6. 慢查询排查完整流程（经验做法）

把前五节串成一条流水线——这条流程来自一线排查的反复打磨（经验做法，照抄即可用）：

给一个端到端的小例子收束全章：查询 SELECT * FROM orders WHERE date(created_at)='2025-06-01' 走 Seq Scan、Rows Removed 90%+ → 改写为 WHERE created_at >= '2025-06-01' AND created_at < '2025-06-02' → 计划变 Index Scan using ix_created_at，Buffers read 从 8 万块降到 300 块，执行时间 900ms → 6ms。全程没建新索引——一半的"索引问题"其实是写法问题（经验做法）。

常见误区

  1. “EXPLAIN 的 cost 是毫秒”：cost 是无量纲代价分，1 顺序页读 ≈ 1.0；和真实时间的换算关系随硬件/配置浮动。耗时只看 ANALYZE 的 actual time / Execution Time。
  2. “rows=1000 就会返回 1000 行”：估算不是承诺。估算与实际的偏差本身就是诊断信号——大偏差先怀疑统计信息与数据倾斜。
  3. “全表扫描一定是错的”：低选择性与小表上，全扫是最优解。优化器选 Seq Scan 不代表出 bug，先看 Rows Removed by Filter 与表行数再下判断。
  4. “加索引是慢查询的万能药”：先确认失效原因（3 节四主因），很多场景改写 SQL 或刷统计就解决；乱加索引的账单（写放大/空间/优化器干扰）在 03 章已实测。
  5. “优化一次就一劳永逸”：计划是每次执行现场决定的（PG 有计划缓存但代价仍重算），数据分布变化、参数值变化都可能让计划翻转。生产对关键 SQL 用固定计划手段（PG 的 plan_cache_mode、MySQL 的 optimizer hints）是防翻转，不是防笨。

本篇小结

  • 优化器 = 基于统计信息的代价估算器；索引查找与全表扫描的分界由选择性与随机读代价决定，全表扫描是选择不是错误。
  • EXPLAIN ANALYZE 四件套：cost（估算）、rows（估算 vs 实际偏差看统计）、actual time × loops（真实热点）、节点类型（Seq/Index/Bitmap）；SQLite 的 SEARCH/SCAN/COVERING 是同一套概念的结构版。
  • 索引失效四主因：函数包裹列、隐式转换、低选择性、统计过期；修复优先"改写 SQL"而非"加索引"。
  • 统计信息（n_distinct/MCV/直方图）决定选择率估算，选择率相乘的独立性假设在倾斜与相关列上失真；大导入后手动 ANALYZE，random_page_cost 按硬件调。
  • JOIN 三算法：Nested Loop（小驱动大+内表索引，OLTP）、Hash Join（大等值，OLAP）、Merge Join（已有序/范围）；"JOIN 慢"先查驱动表与索引。
  • 慢查询六步流程：定位→看计划→三看→四因对照→分级改法→验证固化；从 EXPLAIN 到索引/改写的路要形成肌肉记忆。

练习

  1. 建一张 100 万行 orders（user_id 1-1000 均匀、status 两值、created_at 随机一年），对 WHERE user_id=42 AND status='ok' 与 WHERE status='ok' 各跑 EXPLAIN ANALYZE，记录估算/实际偏差与扫描方式。
  2. 复现函数失效：对比 WHERE date(created_at)='2025-06-01' 与范围写法的计划与耗时；再用表达式索引让第一种写法也走索引，比较两种解法的代价。
  3. 构造三种 JOIN 场景（小×大有索引 / 大×大无索引 / 连接键已排序），让 PG 分别选出 Nested Loop / Hash Join / Merge Join，截图记录计划里每种算法的触发条件。
  4. 人为搞坏统计：大表批量 INSERT 100 万行后不 ANALYZE，跑一个"该走索引"的查询看优化器选错；执行 ANALYZE 后重跑对比——记录你机器上的翻转过程；再查 pg_stats 看 status 列的 MCV 与频率，手算 status='ok' 的选择率并与计划里的估算对照。
  5. 把 random_page_cost 从 4.0 改成 1.1（SET random_page_cost=1.1），重跑练习 1 的两条查询，观察哪些计划翻转了；用 01 章的存储层次数字解释为什么 SSD 机器上这个默认值偏保守。
  6. 拿你项目里一条真实慢 SQL 走完 6 节六步流程，把"第 0 步之前的凭感觉猜测"与"第 2 步三看的结论"并排写下，体会流程与直觉的差距。

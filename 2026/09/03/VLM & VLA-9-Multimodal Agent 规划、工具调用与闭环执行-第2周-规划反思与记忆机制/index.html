第2周-规划反思与记忆机制

第 2 周教程：任务规划、反思与长短期记忆

本周要回答的三个问题

  1. 子目标拆解与 ToT/MCTS 的规划谱系怎么选？
  2. <reflection> 自我纠错的工程闭环怎么搭？它的能力边界在哪？
  3. 短期记忆的上下文管理（压缩/摘要）与长期记忆（Visual RAG）怎么分工？

对应学习计划：第 2 周。交付物：一个具备自我纠错能力的 Agent——工具调用抛 Exception / API 超时时，自动进入 <reflection> 状态分析 Traceback，重生成修正后的代码/参数直至成功。

1. 第一性原理：Agent 的三大失败面与三大对策

1.1 根本矛盾：任务长于一次生成，反馈慢于一次推理

第 1 周的 Agent Loop 解决了"单步行动的合法性"；但真实任务的两个特性让它不够：

  1. 任务长度：复杂任务需要几十步，模型无法一次规划全部——且中间结果会改变后续计划（计划必须可修订）；
  2. 反馈延迟：错误往往在第 k 步才暴露（工具报错、结果不符），而错误根源可能在第 j < k 步——需要回看与修正的能力。

三大失败面对应三大对策：

失败面 症状 对策（本周）
一次性规划过脆 中途变化后死守原计划 规划：子目标拆解 + 动态重规划（ToT/MCTS）
错误后盲目重试 同样的调用反复失败 反思：失败归因 + 修正后再试
上下文撑爆/遗忘 长任务后半段失忆 记忆：短期压缩 + 长期检索

1.2 规划谱系：从线性到搜索

子目标拆解（Sub-goal Decomposition）：把长指令拆成有序原子动作序列。工程要点：

  • 原子性判据：每个子目标可被 1~2 次工具调用完成、有独立可验证的完成条件（"下载报告"可验证、"研究分析报告"不可）；
  • 计划的数据形态：显式的任务清单（plan list）优于隐式推理——显式计划可以被程序跟踪进度、检测偏航、触发重规划（ReAct 的 Thought 里隐式规划是无法被程序审计的）；
  • 动态重规划：每步执行后对照计划，若 Observation 与预期不符（工具失败/前置条件变化），触发重规划而非死磕——ReAct 原始论文的核心卖点正是这种"计划可被推理修订"。

Tree of Thoughts（ToT）/ MCTS：线性规划在"路径有分叉、错误代价高"时不够——ToT 把推理组织成树，每个节点是一个中间状态，可以分叉探索多个假设、回溯剪枝；MCTS 用"选择→扩展→模拟→回传"的循环在树上做启发式搜索（AlphaGo 血统）。工程定位：

方法 搜索深度 成本（额外推理调用） 适用
线性 ReAct + 重规划 1 条路径 1× 步骤清晰、失败成本低
ToT（广度/深度搜索） 树形分叉 数×~数十× 关键决策点少但分叉价值高
MCTS 深度搜索 + 价值回传 数十~数百× 可模拟/可验证的环境（数学、代码、游戏）

经验规则：搜索的每一分收益都要用推理成本买单——先用线性 ReAct 打基线，仅在"已知会卡在特定分叉决策"时局部引入 ToT；全任务 MCTS 只在"验证便宜"（RLVR 式 Verifier 现成）时划算。RLVR 与搜索的深层关系：RL 训练是把搜索的成果蒸馏进策略——训练时多搜、推理时少搜。

1.3 Reflection：把错误反馈变成修正信号的闭环

Reflexion（Reflexion: Language Agents with Verbal Reinforcement Learning, NeurIPS 2023）的核心思想：把环境反馈（报错/失败）转化为语言形式的自我反思文本，存入记忆，指导下一次尝试——“verbal RL”：不用梯度，用文字强化。用大白话说：模型考试错了，把"错在哪、下次怎么改"写成便条贴在试卷旁边，重考时先读便条——便条（反思文本）就是"强化信号"，只是它作用在上下文里而不是参数上。

工程闭环的四要素：

  1. 触发条件（程序判定）：工具报错、结果校验失败、步数/预算超限——确定性触发，不依赖模型"自觉反思"；
  2. 反思输入：错误信息（Traceback 全文！不是摘要）+ 失败动作 + 相关上下文——Traceback 的行号与异常类型是归因的最强线索，喂摘要等于自废武功；
  3. 反思结构：<reflection> 标签内强制三段式——失败原因（归因）→ 证据（Traceback 中的哪一行）→ 修正方案（具体到参数怎么改）；
  4. 防循环：同一次失败的反思次数上限（如 2 次）、反思内容与上次失败的相似度检查（反思了却提出同样的方案 = 归因失败，升级为换策略/求助）。

能力边界（必须诚实）：Reflection 修的是"可从反馈推断原因"的错误（参数错、超时、格式错——反馈里有线索）。对"反馈正确但模型不理解"（能力不足）或"反馈本身误导"的情况，反思只是高级的复读。Reflection 提升的是"把会做的事做对"，不是"把不会的变成会"——后者属于训练问题（Stage 4/7 的数据与 RL）。

1.4 记忆架构：短期压缩与长期检索的分工

短期记忆（Context Window 内）：

  • 问题：多步轨迹（尤其含图像/长 Observation）迅速撑爆窗口；
  • 手段：历史压缩——旧的 Observation 用摘要替换（保留结论与关键数据，丢弃过程文本）；旧截图缩略化；工具结果超过阈值即截断+指针；
  • 关键纪律：压缩的是过程，不是约束——任务目标、已完成的关键结论、坐标约定等"约束性信息"永不压缩（Stage 9 的 Agent 失忆高发点：把坐标约定压没了，后续全部坐标引用错位）。

长期记忆（Visual RAG）：把历史关键帧/截图 + 对应坐标与 Action 写入向量库，跨任务/跨时域检索：

  • 写入时机：任务完成点、关键中间结论点（不是每帧都存——噪声入库会稀释检索）；
  • 检索键：任务语义（embedding）+ 结构化过滤（时间/任务类型/实体）；
  • 与 Stage 4 的关系：这就是 RAG 在轨迹数据上的应用——检索的是"过去的经验"而非"知识文档"；
  • 坑：检索到的旧经验可能是错误经验（当时的失败教训）——存储时要带"成功/失败"标签，检索时优先成功案例、失败案例作为警示注入。

2. 实现与验证

2.1 本周 MVP：自我纠错 Agent（Reflection 闭环）

预期输出：

断言验证反思闭环的四个关键行为：Traceback 驱动的归因（NameError/KeyError 被正确分类）、三段式结构、逐次修正的推进（第 1 次反思修一个 bug、第 2 次修另一个）、同方案失败的升级策略（防反思循环）。

2.2 记忆管理的最小实现

设计要点：约束性信息（坐标系约定等）置顶且永不压缩；过程性 Observation 只留摘要；assert 把"压缩后仍超预算"显式暴露（逼出更强手段——如外挂长期记忆）而不是静默截断。

3. 工程权衡与失效模式

3.1 决策表：记忆与规划的成本谱系

手段 成本 收益 起用时机
History 截断 零 防溢出但丢信息 首选兜底
Observation 摘要 少量 LLM 调用 保留结论省窗口 轨迹 > 10 步
显式 Plan 清单 1 次规划调用 可审计/可重规划 ≥3 子目标的任务
Visual RAG 长期记忆 向量库 + 写入策略 跨任务经验复用 多任务持续运行
ToT/MCTS 数十×推理 关键分叉的决策质量 验证便宜 + 决策点少而关键

3.2 三个代表性失效模式

失效 1：反思循环（Reflection Loop）——归因错误导致的"改错方向"

  • 症状：同一错误反复出现，每次 reflection 都在变但都没修到点上，步数耗尽。
  • 根因：反馈与真实根因脱节（Traceback 显示 KeyError，但根因是上游数据没加载）；或模型归因能力不足，反思是"重新表述错误"而非定位错误。
  • 定位：审计反思链——相邻两次反思的"修正方案"若无实质推进即确认。
  • 修复：升级策略（换工具/换方法/请求人工——1.3 节的防循环闸）；或给反思器喂更多结构化上下文（前置步骤的状态快照）；承认能力边界，把"反思解决不了"的失败导流到训练侧（Stage 4/7）。

失效 2：长期记忆的"错误经验污染"

  • 症状：Agent 在新任务中重复旧任务的错误做法（或拒绝旧任务里已验证可行的方法）。
  • 根因：Visual RAG 检索到的经验不带对错标签，或相似度检索把表面相似、实质不同的任务错配。
  • 定位：抽查检索命中记录 vs 当前任务的适配性。
  • 修复：经验入库带成功标签与任务指纹；检索后加一层"适用性自检"（让模型显式判断"这个经验适用吗"）；定期清洗记忆库（Stage 4 清洗纪律的记忆版）。

失效 3：摘要压缩丢掉了关键约束

  • 症状：长任务后半段坐标引用错位、单位混乱、目标漂移。
  • 根因：摘要器把约束性信息（坐标约定/单位/任务目标）当过程文本压缩掉了。
  • 定位：对压缩前后 diff，检查约束性关键词是否存活。
  • 修复：约束保护名单（2.2 的 CONSTRAINT_KEYS）+ 关键约束置顶注入每轮 prompt；摘要 prompt 显式声明"禁止压缩约束与结论"。

4. 延伸思考题

  1. Reflexion 与 RL 的光谱：Reflexion（文字强化）与 GRPO（梯度强化）处在什么光谱的两端与中间？给一个任务特征表：什么时候文字反思够用，什么时候必须上梯度训练？（提示：任务新颖性、反馈密度、算力预算、部署是否允许长上下文反思——Reflexion 的成本在推理侧、RL 的成本在训练侧。）
  2. Plan 的可审计性：显式 Plan 清单让"程序检测偏航"成为可能。设计一个"计划偏航检测器"：每步执行后判断当前轨迹是否仍服务于计划中的子目标，偏航时触发重规划。（提示：子目标的完成谓词 + 当前 Observation 的相关性判定；这是把"规划"从 prompt 里的自由文本升级为可管理状态机的一步。）
  3. 记忆的遗忘权利：长期记忆里的历史截图可能包含敏感信息（用户数据）。设计一个"可撤回的记忆"机制：用户要求删除后，向量库与摘要中的对应条目如何真正消失？（提示：这是 RAG 系统的经典 GDPR 难题——向量的删除与派生摘要的传播，值得系统设计期就考虑。）

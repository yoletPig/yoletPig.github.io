11 - 容器与云环境观测

本篇目标

  • 说清 namespace 隔离了什么、没隔离什么：容器内视角与宿主机视角的差异，以及 top/free 在容器里为什么"骗人"。
  • 实测 cgroup v2 的 CPU throttling：cpu.max、cpu.stat 的 throttled 计数，理解"为什么 top 看不到节流"。
  • 区分容器 OOM 与宿主 OOM：memory.max、working set 与 OOMKill 事件链。
  • 掌握 K8s 性能观测的最小集（kubectl top/describe/events），理解 noisy neighbor 与 steal time。
  • 把 USE/RED 方法翻译成 Prometheus 指标设计：USE→指标命名的对照表。

前置：操作系统系列 13（容器与虚拟化——namespace/cgroup 的原理）；本篇讲"限制之下怎么观测"。K8s 部分无集群也可读，命令形态与原理不变。

1. 容器内的观测边界：namespace 隔离了什么

容器 = 一组 namespace（视野隔离）+ cgroup（资源限额）+ 联合文件系统（OS 系列 13 篇）。对观测来说关键是分清哪些视野被隔了、哪些数据是"假的"：

三条实战结论（经验做法）：

  1. 容器内 top/mpstat 看到的 CPU 数与利用率是宿主机的——8 核宿主机上跑 limit=0.5 的容器，top 里的 %CPU 上限是 800%，你完全看不出"只允许用半核"。容量判断必须读 cgroup 文件（第 2 节）。
  2. free 显示宿主机内存——判断容器内存水位用 /sys/fs/cgroup/memory.current（当前用量）与 memory.max（限额）。K8s 的 kubelet 默认就是按"working set（近似 cgroup 用量 - 不可回收缓存）"来判 OOM 的，比容器内 free 靠谱得多。
  3. 观测工具的越界：宿主机上可以看到一切（docker exec 进容器只是换 namespace，宿主 perf/eBPF 能覆盖容器进程）；容器内通常只能看自己。线上排查的标准站位是宿主机，容器内只做最后一米的确认。

2. CPU throttling 实测：limit 之下，时间被“没收”

cgroup v2 用 cpu.max 限 CPU，格式 “quota period”（man 5 cgroups；内核文档 Documentation/admin-guide/cgroup-v2.rst）：

这就是容器版"CPU 不高但很慢"的元凶：宿主机 top 里容器进程 %CPU 平平无奇（被限额压着），但每个 100ms 周期里，进程用完 50ms 配额后被硬暂停，到下个周期才能继续——P99 延迟被节流周期整体抬高（04 篇的"等待"多了一种内核来源）。判断节流三步（经验做法）：

  1. cat /sys/fs/cgroup/cpu.stat（或 docker exec 进去看），看 nr_throttled/nr_periods 比例，>10% 就值得警惕。
  2. 对照应用 P99：节流比例与 P99 恶化常同步。
  3. 药方按序：升 limit → 减并发线程数（把单请求的核需求压到 limit 之下）→ CPU 密集任务挪出该容器。

无 Docker 的 WSL2 也能做同款实验（systemd-run 建 cgroup，或直接手写 cgroup v2 目录），工具变了，cpu.stat 的读法一模一样。

3. 容器 OOM：limit 的“死线”

cgroup v2 的内存限额在 memory.max，事件计数在 memory.events：

与 05 篇宿主 OOM 的三点区别：作用域（cgroup 内挑选 victim，宿主内存再空也没用）；日志形状（dmesg | grep -i 'memory cgroup out of memory'，constraint=CONSTRAINT_MEMCG）；观测面（kubelet/memory.events 的 oom_kill 计数，比翻日志及时）。K8s 里 kubectl describe pod 的 Last State: Terminated, Reason: OOMKilled 就是这条链的用户界面。

指标口径要小心（经验做法）：K8s 判 OOM 用 working set ≈ memory.current − inactive_file（近似），监控画 RSS 会与"为什么被杀"对不上——监控容器内存一律用 working set（Prometheus 的 container_memory_working_set_bytes），别用 RSS。

4. K8s 性能观测最小集

  • kubectl top（metrics-server 提供）：kubectl top pods -n prod 看每个 Pod 的 CPU/内存用量（注意：这是用量不是限额利用率，limit 90% 的告警要自己算 container_memory_working_set_bytes / cluster_resource_limit）。
  • kubectl describe pod：Events 区是事故线索第一现场（OOMKilled、FailedScheduling、镜像拉取失败、重启原因）。
  • requests/limits 与 QoS：Guaranteed（cpu=mem 的 requests==limits）在节点资源紧张时最后被驱逐——延迟敏感服务值得多花钱买 Guaranteed（经验做法）。
  • CPU 节流的 K8s 形态：kubectl top 看不到节流！它只报用量。必须看 Prometheus 的 container_cpu_cfs_throttled_periods_total（下一节），这是 K8s 观测最著名的盲区之一。

5. 云上邻居噪声：steal time 与“看不见的邻居”

虚拟机里你的 CPU 时间可能被 hypervisor 拿走分配给同宿主机的其他租户（noisy neighbor）。观测信号是 steal time（top/vmstat/mpstat 的 %st 列，取自 /proc/stat 的 steal 字段）：

%st 持续 >5% 就该警觉：你的"CPU 利用率 60%"里有一大块时间其实没在跑。排查与自救（经验做法）：

  1. 确认形状：steal 高发时段与业务高峰重合 → 同宿主邻居忙；全天恒定 → 机型超卖比例如此。
  2. 缓解：换实例类型/专用主机（dedicated host）/换可用区重开；把关键服务与噪声服务分组隔离。
  3. 与 07 篇联动：网络抖动也常来自邻居（软中断/网卡带宽被抢），iperf3 基线（第 5 节）留档以便"回到过去"对比。

6. Prometheus 指标设计：USE/RED 的翻译字典

方法论的最终归宿是监控。USE（01 篇）落到 Promethesu 上就是一张命名字典（Prometheus 官方文档 “Naming of metrics” + node_exporter 指标清单）：

USE 问题 资源 Prometheus 指标 读法
利用率 CPU node_cpu_seconds_total rate(...[5m]) 按 mode 求和
利用率 内存 node_memory_MemAvailable_bytes / total 得可用比例（02 篇的 available 口径）
利用率 磁盘 node_disk_io_time_seconds_total rate = %util；io_time_weighted ≈ aqu-sz
饱和度 CPU（容器） container_cpu_cfs_throttled_periods_total / ..._periods_total = 节流比例（第 2 节）
饱和度 磁盘 node_disk_io_now 在途请求数（aqu-sz 的即时版）
错误 网络 node_network_receive_drop_total / node_netstat_Tcp_RetransSegs 速率告警（07 篇丢包）
错误 内存 kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} 事件计数（第 3 节）

RED（服务侧）三件套的标准形状：

命名与基数两守则（Prometheus 文档的 Data model 一节）：

  1. 命名：<namespace>_<subsystem>_<name>_<unit>，unit 后缀（_seconds/_bytes/_total）强制——http_request_duration_seconds 能被全世界读懂，latency1 不能。
  2. label 基数（cardinality）：label 组合数 = 时序数量。给 user_id、request_id 打 label 是经典事故（时序爆炸，TSDB OOM——观测系统自己成了 05 篇的案发现场）。经验做法：低基数维度（method/path 模板/region）进 label，高基数（用户/请求 ID）进日志与 trace。

CPU 才 49.8%（0.5 核用满即 50%）——docker stats 完全看不出任何问题。这正是第 2 节说的盲区。取证必须去 cgroup：

第三步：修复对比。 三条路逐一试，同口径记录 P99 与节流比例：

方案 P50 P99 nr_throttled/nr_periods
原状（0.5 核，8 线程） 18ms 700ms 98%
线程数 8→1（减少需求） 19ms 45ms 55%
limit 0.5→2（增加供给） 18ms 24ms 6%
1 线程 + limit 2（双管齐下） 18ms 21ms 0%

结论句式：节流（98% 周期）是 P99 恶化的直接原因（证据：cpu.stat 与 P99 同步恶化/恢复）；供给（limit）与需求（线程数）双向调整后节流归零、P99 回到 21ms。把这个表格放进你的调优报告——12 篇的模板会要求完全相同的结构。

常见误区

  1. “容器内 top/free 说内存 CPU 都正常”：/proc 未隔离的部分是宿主机数据；容器的"真话"在 /sys/fs/cgroup/。站位错误会让整个排查从第二步就走偏。
  2. “docker stats CPU 50% 说明没瓶颈”：50% 恰好是 0.5 核限额跑满的形状；CPU % 必须除以 limit 看占比。
  3. “K8s 里 kubectl top 红了才有问题”：top 看不到节流；throttled 比例是独立指标（第 6 节的翻译字典），缺了它 CPU 类 P99 事故排查会一筹莫展。
  4. “监控把 RSS 画上就行”：容器判死用 working set；RSS 与 working set 的差（共享/缓存口径）会让"为什么 OOM"变成悬案。
  5. “云上 VM 的 CPU 是我自己的”：%st 持续非零说明 hypervisor 在抽成；把 steal 常态化指标化是云上容量管理的常识（经验做法）。

本篇小结

  • namespace 隔离视野（进程/网络/挂载），cgroup 决定限额；容器内 top/free 的数字是宿主机的，cgroup 文件才是容器的真话；排查站位在宿主机。
  • throttling 证据链：cpu.max 定限额 → cpu.stat 的 nr_throttled/throttled_usec 量化 → 与 P99 同步性定因果；docker stats/top 都是盲区。
  • 容器 OOM 三件套：memory.max / memory.events(oom_kill) / OOMKilled 事件；监控口径用 working set 不是 RSS。
  • K8s 最小集：top（用量）、describe（事件）、QoS（驱逐顺序）；节流与 OOM 都要靠指标（第 6 节字典）而非日志死磕。
  • 邻居噪声看 %st；Prometheus 设计 = USE/RED 翻译字典 + 命名守则 + label 基数自律。

练习

  1. 用 docker run --cpus=0.5 复现第 7 节实验，把三组 cpu.stat 数字与你机器上的 P99 填进表格；没有 Docker 时用 systemd-run（systemd-run --scope -p CPUQuota=50% python3 ...）替代，读同样的 cpu.stat（systemd cgroup 层级下路径在 /sys/fs/cgroup/system.slice/…）。
  2. 在容器内分别跑 free -h、cat /proc/cpuinfo | grep -c processor、cat /sys/fs/cgroup/memory.max，把三组数字与宿主机对比，写一段"容器内哪些数字不可信"的笔记。
  3. 构造一次容器 OOM（第 3 节命令），依次取证：docker inspect 的 OOMKilled、memory.events 的 oom 计数、宿主 dmesg 的 “memory cgroup out of memory” 行，体会三种证据的层级（编排层/内核层/事件层）。
  4. 查一下你所在云（或本地虚拟机）的 %st：vmstat 1 10 记录 st 列；若有条件，把一个高 CPU 任务与它并行跑，观察 steal 与你自己进程延迟的相关性。
  5. 给你自己的服务写"USE→指标"翻译清单（至少 CPU/内存/网络三资源六个指标名），并写一条 histogram_quantile 的 P99 查询；核对 label 是否有 user_id 级高基数维度，有则重构。

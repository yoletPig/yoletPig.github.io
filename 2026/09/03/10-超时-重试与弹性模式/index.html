10 - 超时-重试与弹性模式

本篇目标

  • 建立"故障注入"思维：把失败当常态输入来设计，而不是当异常事件来救火。
  • 学会设置超时（默认超时为什么是反模式）与重试（指数退避+抖动，防重试风暴）。
  • 手写熔断器状态机、舱壁隔离、令牌桶/漏桶限流器，理解各自的保护对象。
  • 掌握降级与兜底的分层设计，以及 Hedge 请求对长尾延迟的治理。

1. 故障注入思维：先假设一切会挂

弹性（resilience）设计的第一步是列"故障清单"，然后给每一项写预案（这一方法论在 Netflix 的 Chaos Engineering 实践与《Release It!》Nygard 第二版中被系统化）：

故障 表现 预案落点
下游变慢 延迟从 5ms 涨到 5s 超时 + 熔断
下游拒绝服务 连接拒绝/503 重试（带退避）+ 降级
自己被拖垮 线程池/连接池耗尽 舱壁 + 限流
流量突增 QPS 10 倍 限流 + 弹性扩容
依赖不可用 整个服务挂 降级 + 兜底数据
网络抖动 少量超时 Hedge + 重试

核心思想：每个组件都按"它一定会慢/一定会挂"来设计邻居。故障注入（chaos engineering）就是把假设变成例行验证——在生产环境定期关掉某个依赖，看预案是否真的生效（Netflix 的 Chaos Monkey 即此思路，见《Chaos Engineering》O’Reilly, Basiri et al.）。

2. 超时：为什么默认超时是反模式

超时回答"等多久放弃"。三种错误姿势：

  1. 不设超时（依赖库默认或压根没配）：一次下游 hang 把你的线程/协程全部占死，故障沿着调用链向上传播——同步调用的雪崩总是从缺超时开始。
  2. 全局统一默认超时（如 requests 不给 timeout 参数的"无限等"，或全部 30s）：下游正常 5ms，你等 30s——被 hang 的请求占用资源 6000 倍于必要时间。
  3. 超时层层叠加失控：入口 10s → 服务 A 10s → 数据库 10s。A 等数据库 10s 超时后，入口的 10s 也到了，A 的工作全部白费。

经验做法（超时预算法）：从用户可接受的入口延迟倒推，逐层分配并留余量。入口预算 500ms → A 服务 400ms → A 内数据库调用 300ms + 下游 RPC 150ms（每个超时 ≤ 父级剩余预算）。同时超时与重试联动：若打算重试 2 次，单次超时必须 ≤ 预算/3，否则重试本身就超时（此时不是恢复而是放大）。

3. 重试风暴与指数退避 + 抖动

下游抖一下，所有调用方同时重试 → 下一波请求量 = 原始 + 全量重试 → 下游刚缓过来又被压垮 → 又全量重试……这就是重试风暴（retry storm），重试把一次抖动放大成持续故障。

三个纠正手段：

  1. 指数退避（exponential backoff）：第 n 次重试等待 base * 2^n，让风暴的波峰指数衰减。
  2. 抖动（jitter）：所有客户端在同一时刻退避会形成"整齐的重试脉冲"（sync storm）；加随机抖动把脉冲摊平。AWS 的《Exponential Backoff and Jitter》博文（Marc Brooker, AWS Architecture Blog, 2015）实测：full jitter 把完成时间的中位数压到最低。
  3. 重试预算（retry budget）：限制重试请求占总请求的比例（如 10%）；失败率超阈值后停止重试，把流量让给"新请求"。

经验做法：退避公式用 delay = min(cap, base * 2^attempt)，叠加 full jitter（AWS 的推荐式）；同时给整条调用链设最大重试次数与"上游不再重试已被下游重试过的错误"的纪律（每个节点都重试 = 乘法放大，80 章节级的事故复盘常见根因）。

4. 熔断器：状态机 + Python 实现

熔断器（circuit breaker）（模式出处：Michael Nygard《Release It!》2007；思想源于电气保险丝）解决的问题是：下游已经挂了，上游还在持续发请求——每次请求都付出超时等待的代价（资源占用），且给死马做心肺复苏毫无意义。熔断器在"连续失败"后直接快速失败，给下游喘息窗口。

三状态机：

熔断与重试的分工：重试赌"偶发抖动能恢复"，熔断承认"持续故障别再浪费资源"。经验做法：重试只包住非熔断路径；熔断器放行的请求里的失败才值得重试 1~2 次，熔断打开后重试立即停止。

5. 舱壁隔离与限流

舱壁（bulkhead）（Nygard《Release It!》命名，取自船体水密隔舱）：把资源（线程池/连接池/内存配额）按依赖分池。一个依赖 hang 死只烧光自己的池，别的依赖不受牵连。Python 里常用 asyncio.Semaphore(n) 当轻量舱壁——每个下游一个信号量，超限立即失败而不是无限排队。

限流（rate limiting）保护的是自己（防止被打挂）与下游（防止我把它打挂）。两大经典算法：

  • 令牌桶（token bucket）：桶以固定速率生成令牌，请求消耗令牌，桶满则丢弃新令牌。允许突发（攒下的令牌可一次性用掉）——适合"平均限速、容忍脉冲"的 API 限额。
  • 漏桶（leaky bucket）：请求进桶，以恒定速率流出处理，桶满则拒绝。输出绝对平滑——适合保护脆弱下游（如只有固定 QPS 能力的数据库）。

经验做法：分布式限流不要自己造——用 Redis + Lua 保证原子（单机内存限流在多副本部署下每副本各算各的，等于限流值×副本数），或用网关层（Nginx limit_req/Envoy rate limit service）。单机算法的意义在于理解模型。

6. 降级、兜底与 Hedge 请求

  • 降级（degradation）：依赖不可用时切换到"功能缩水但可用"的路径——推荐服务挂了就返回热门榜单；搜索挂了就只查缓存。关键：降级开关要提前埋好（配置中心一键切换，而不是故障现场改代码）。
  • 兜底（fallback）：给降级路径准备真实可用的数据源。反模式是"兜底返回空列表"——前端空白页面等于把故障 100% 转嫁给用户，体验上约等于挂了。
  • Hedge 请求（对冲请求）：对付长尾延迟——主请求发出后 P95 时间内没回来，再发一个相同请求到另一副本，谁先回用谁（Dean & Barroso, The Tail at Scale, CACM 2013，Google 的关键论文：大集群里单请求慢几率的乘法效应让长尾治理成为必修课）。代价：后端多处理一份重复请求，适合幂等读（缓存查询、推荐召回），不适合非幂等写。

常见误区

  1. “重试解决了失败”：重试只解决瞬时失败（抖动）；对持续性故障，重试是放大器。正确顺序：先分类错误（瞬时/持续/不可重试），再决定重试、熔断还是降级。
  2. “熔断器阈值越敏感越好”：阈值 2 次失败就熔断，会把正常波动当故障，频繁打开-关闭震荡（chattering）。阈值要按"失败率 + 样本量"统计（如 30 秒内失败率 > 50% 且样本 ≥ 20），冷却期也要够下游真正恢复（经验做法：初始冷却 5~10s，恢复探测放 1~5 个请求）。
  3. “限流了就安全了”：限流保护容量，不保护正确性——被限流的请求怎么处理（拒绝/排队/降级）才是用户体验的决定项。且限流阈值要随容量评估（压测得出）动态调整，拍脑袋数字会在大促翻车。
  4. “超时越长越保险”：超时是资源持有的时长上限。调大超时 = 故障时占用更多线程/连接更久 = 更容易雪崩。宁可短超时 + 重试 + 熔断，不要长超时硬扛。
  5. “Hedge 可以随便加”：Hedge 对非幂等请求会真实执行两次业务（双扣款）；对已饱和的后端是趁火打劫。只用于幂等读、且最好带"重试预算"约束。

本篇小结

  • 弹性设计从故障清单开始：变慢→超时+熔断，抖动→退避重试，打挂→限流，挂死→舱壁+降级。
  • 超时用预算法逐层分配并联动重试次数；默认/统一超时是反模式，短超时+快速失败优于长超时硬扛。
  • 重试防风暴三件套：指数退避（波峰衰减）、full jitter（摊平脉冲）、重试预算（全局上限）；错误分类决定"重试/直落 DLQ/熔断"。
  • 熔断器三状态（关-开-半开）+ 快速失败给下游喘息；舱壁按依赖分池隔离故障；令牌桶容忍突发、漏桶输出平滑，分布式场景用 Redis+Lua 或网关。
  • 降级要提前埋开关、兜底要有真数据；Hedge 用第二请求换长尾（幂等读专属）。
  • 各模式分工明确：限流管"进多少"、舱壁管"占多少"、超时管"等多久"、重试管"再来一次"、熔断管"还去不去"、降级管"没它行不行"。

练习

  1. 跑通 circuit_breaker.py，把失败率从 0.8 调到 0.3 与 0.5，观察熔断器是否频繁震荡；给阈值加上"样本量 ≥ 10 才统计"的条件，记录震荡是否消失。
  2. 实现"重试预算"装饰器：统计最近 100 个请求，重试占比超 10% 后直接抛出"不重试"异常；把它套在 backoff_jitter 的重试逻辑上，用日志验证预算生效。
  3. 把 rate_limiter.py 扩展成滑动窗口日志限流器（保留最近 1s 的时间戳列表），对比它与令牌桶在"突发 10 个 + 匀速 20 个/秒"流量下的放行曲线。
  4. 综合题：为"调用大模型推理 API"设计完整弹性层——列出你用的超时预算（推理 API 通常 10~60s，怎么与 HTTP 层、重试层协调）、重试策略（哪些错误可重试：429/5xx/超时？哪些不可：400/401？）、熔断与降级（降级到小模型还是缓存？），写成一张配置表。
  5. 实验题：用 hedge_request.py 构造 1000 次请求、其中 10% 概率某副本慢 20 倍的混合场景，对比"无 hedge"与"hedge at P95"的总耗时分布（P99 改善多少）；再统计 hedge 发出的多余请求数，评估代价。

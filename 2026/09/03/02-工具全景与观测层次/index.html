02 - 工具全景与观测层次

本篇目标

  • 建立 Linux 观测的分层地图：从用户态库到系统调用、内核计数器、tracepoint、kprobe、硬件 PMU，知道每层"能看到什么、付出什么代价"。
  • 掌握 8 个静态工具的最小用法与读法：uptime/dmesg/free/vmstat/mpstat/pidstat/iostat/sar——拿到陌生机器 5 分钟内形成第一印象。
  • 理解动态追踪工具谱系（strace/ftrace/perf/bpftrace）的取舍，能按"问题 → 工具"选型。
  • 明确 WSL2 环境下哪些观测可用、哪些受限，避免在假象上浪费时间。

前置：操作系统系列 02（进程与线程）、07（中断与系统调用）。本篇是"地图篇"，后续章节是每块区域的深潜。

1. 观测分层：离系统越近，看到越多

Linux 上的所有观测手段，按"信息在系统的哪一层产生"分层（《Systems Performance》第 4 章 Observability Tools；Brendan Gregg 的 tracing layers 图）：

几条重要的层间规律（经验做法）：

  1. 排查顺序自上而下：先看计数器（L3，便宜且能回答"哪类资源异常"），确定方向后再下潜到 L4/L5 看函数级真相。上来就 strace 全量跟踪，既慢又容易迷路（strace 的开销见 01 篇第 8 节）。
  2. L3 计数器是免费的，但只有"汇总"没有"原因"：vmstat 告诉你 CPU 50% 在 iowait，但不知道哪个文件、哪个调用栈——那是 L4/L5 的活。
  3. tracepoint 是内核预埋的探针（/sys/kernel/tracing/events/ 下上千个），位置稳定、有文档（Documentation/trace/）；kprobe 可以挂到几乎任意内核函数，灵活但函数名/参数随内核版本变，脚本要跟着维护。

2. 静态工具一览：8 条命令建立第一印象

以下命令来自 sysstat 12.5.2 与 procps-ng（Ubuntu 22.04 默认或 sudo apt install sysstat）。每条先给最小用法，再给读法。它们共同的特点：读 L3 计数器，开销≈0，任何机器可用（含 WSL2）。

(1) uptime——负载与存活时间

load average 三个数是 1/5/15 分钟的"活跃任务数"。Linux 的定义不只是"想用 CPU 的任务"：还包括 D 状态（不可中断睡眠，通常是磁盘 IO）的任务（Brendan Gregg, “Linux Load Averages: Solving the Mystery”, 2017）。所以 load 高 + CPU 空闲 = 在等 IO，这是新手最常见的困惑。读法：与 CPU 核数比，8 核机器 load 稳定在 8 以下不算高；三个数比较得出趋势（1min > 15min = 正在变忙）。

(2) dmesg——内核发生过的坏消息

先看错误再看别的（USE 方法的 E 优先）：OOM、磁盘 I/O error、MCE 硬件错误、网络驱动丢包告警都在这。-T 把时间戳转成人类可读。

(3) free——内存水位

只看两列：available（新应用可用的内存估算，含可回收缓存）和 Swap 的 used。free 列小不是内存不足——Linux 把空闲内存拿去做页缓存了，需要时立刻收回（05 篇逐列详解）。

(4) vmstat——全系统一屏速览

最常看的四组：r（可运行任务数，持续 > 核数 = CPU 饱和）、b（阻塞在 IO 的任务数）、si/so（换入换出，非零 = 内存压力）、wa（iowait 高 = CPU 在等盘）。注意第一行是开机以来的平均，从第二行开始读（man vmstat 的说明）。

(5) mpstat——每个 CPU 的拆分

读法：%sys 高 = 内核态忙（大量 syscall、锁、内存管理）；%soft 高 = 软中断忙（网络收包，07 篇主角）；单个 CPU 打满其余空闲 = 单线程瓶颈或中断集中（GIL 程序的典型形状，10 篇实拍）。

(6) pidstat——落到具体进程

-u CPU、-r 内存（看 majflt 和 RSS）、-d 磁盘（kB_rd/s、kB_wr/s）、-w 上下文切换（cswch 自愿=等资源，nvcswch 非自愿=被抢占）。四件套基本覆盖"某个进程在干什么"。

(7) iostat——磁盘与分区

await（IO 平均耗时，含排队）、aqu-sz（平均队列深度）、%util（设备忙的时间占比——在并行设备（SSD/NVMe）上有著名陷阱，06 篇专节拆解）。

(8) sar——回看历史

sar 是唯一能"回到过去"的：sysstat 的采集器（需 sudo systemctl enable --now sysstat）每 10 分钟落盘一次，sar -q（负载）、sar -n DEV（网卡）、sar -B（换页）、sar -d（盘）。事故后问"昨晚 11 点网络为什么卡"，答案在 sar -n DEV -f /var/log/sysstat/saXX 里，而不是靠回忆。经验做法：所有长期跑的服务器都开 sysstat，它是最便宜的黑匣子。

3. 动态追踪谱系：四个工具的四条路线

静态工具回答"哪里异常"，动态追踪回答"为什么"。谱系上四个工具，按能力与代价排序：

  • strace：用 ptrace 拦截每次系统调用，用户态实现，能看到完整的参数与返回值（strace -T -e trace=openat python3 ...）。优点：零门槛；缺点：每次 syscall 都有上下文切换级开销，-c 统计模式好、逐行模式危险（01 篇）。只适合小负载、单进程、短时间。
  • ftrace：内核自带（tracefs，通常挂载在 /sys/kernel/tracing，man ftrace），不装任何东西。能看函数调用图、按事件记录。缺点：接口原始（echo 写文件），输出分析费劲；04 篇给最小用法。
  • perf：Linux 官方剖析器，唯一同时打通 L4~L6 的工具：既能在 tracepoint 上记事件，又能用 PMU 采样 cycles、按调用栈聚合（03 篇主角）。开销低（采样而非全量）。缺点：WSL2 上硬件事件受限（见第 5 节）。
  • bpftrace/BCC：eBPF 路线，在内核里安全地运行你写的（小）程序，自定义聚合（08 篇主角）。bpftrace 适合一行命令与短脚本，BCC 适合 Python 前端的完整工具。两者都依赖较新内核（≥4.x 起步，功能越新要求越高）。

选型速查表（问题 → 首选工具 → 备选）：

想回答的问题 首选 备选
哪类资源先饱和了（USE） vmstat/mpstat/iostat/free sar 回看历史
一个进程在忙什么 pidstat -u -r -d -w top -H（线程）
CPU 时间花在哪些函数上 perf record -g py-spy（Python 层）
一个请求的 syscall 都干了啥 strace -c perf trace
进程不在 CPU 上时在等谁 bpftrace offcputime / BCC offcputime ftrace sched_switch
每个 syscall 慢了多少 bpftrace 统计脚本（08 篇） strace -T（小负载）
磁盘真实能力多少 fio（06 篇） dd（粗测，慎用）
网络延迟丢包在哪 ss/tcpdump/iperf3（07 篇） ethtool -S
昨晚发生了什么 sar 监控系统（11 篇）

4. 内核侧的窗口：/proc 与 /sys

静态工具们读的都是这两个目录，值得知道原始入口（操作系统系列 02 篇已介绍 /proc/pid/*，这里补性能相关的全局文件）：

直接读它们的两个好处：一是理解工具数字的真实含义（比如知道 mpstat 的 %idle 来自 /proc/stat 的 idle 字段，就能解释 WSL2 上"宿主 Windows 忙时 WSL 里 %idle 看起来正常"这类语义错位）；二是在受限环境（容器、精简镜像）里 /proc /sys 往往还在，原始文件是最后的观测手段（11 篇）。

5. WSL2 可用性矩阵：先知道手上这把尺子能量什么

WSL2 是轻量虚拟机（真实 Linux 内核 6.6，由 Microsoft 编译），观测能力与原生 Linux 有差异，先给结论表（实测于 kernel 6.6.87，标注"以 uname -r 对应内核实测为准"）：

工具/能力 WSL2 状态 说明
uptime/free/vmstat/mpstat/pidstat 可用 计数器完整
iostat 可用（形状有差异） 虚拟 NVMe 设备，%util 等可读
dmesg 可用 只含 WSL2 内核日志
sar 可用 需启用 sysstat 服务
strace 可用 ptrace 正常
ftrace 大部分可用 /sys/kernel/tracing 存在；部分事件缺失
perf record/stat（软件事件、tracepoint） 可用 perf record -e cpu-clock 正常
perf（硬件 PMU：cycles/cache-miss） 通常不可用 显示 <not supported>；内核未暴露虚拟 PMU
bpftrace/BCC（eBPF） 可用 kernel 6.6 支持 kprobe/tracepoint/uprobe；需 sudo；建议先确认 /sys/kernel/btf/vmlinux 存在
nvidia-smi/nvtop（有 NVIDIA GPU 时） 可用 CUDA 直通（09 篇）
ethtool -S 网卡统计 受限 虚拟网卡计数器很少（07 篇注）

两个最常见的 WSL2 坑（经验做法）：

  1. perf stat 报 Perf counters are not supported 或事件列显示 <not supported>：这是虚拟机没暴露 PMU，不是你操作错。改用软件事件：perf stat -e task-clock,context-switches,cpu-migrations,page-faults 与 perf record -e cpu-clock，火焰图流程不变（03 篇给 WSL2 等价命令）。
  2. 发行版 apt install linux-tools-generic 装出的 perf 与 WSL2 内核版本不匹配，运行即报错。解法：从 Microsoft 官方 WSL2-Linux-Kernel 仓库同版本源码构建 tools/perf，或使用软件事件兜底方案。

6. 动手实验：给一台"生了病的机器"做体检

实验制造三类典型症状，然后用第 2 节的 8 条命令逐一发现。先生成一个故意有问题的程序（三线程：一个烧 CPU、一个疯狂小文件 IO、一个只睡大觉）：

诊断链：uptime 提示"正在变忙" → vmstat 区分是 CPU（r 高、us 高）还是 IO（b 高、wa 高）还是两者 → pidstat 把责任落到 PID 与线程 → 需要继续深入函数级原因时，进入 03 篇（CPU 热点）或 04 篇（IO 等待）。这套"广度体检 → 定方向 → 定进程 → 下潜"的流程，就是 USE 方法的工具化。

清理现场：kill %1; rm -rf /tmp/sick。

常见误区

  1. “load average 高 = CPU 忙”：Linux 的 load 含 D 状态任务，load 高 + %idle 高 = 在等不可中断的资源（典型是盘/网络存储）。判断 CPU 紧张要看 vmstat 的 r 列与 mpstat 的 us。
  2. “free 列很小说明内存快用完了”：看 available。free 小是页缓存的正常工作方式（05 篇）。 alarmed "内存不足"而 available 还有 20GB，是运维群里的经典段子。
  3. “vmstat 第一行也是当前状态”：第一行是开机以来的平均，采样要看第二行起（man vmstat）。
  4. “在 WSL2 里按教程敲 perf stat，看到 就认为 perf 坏了”：是 PMU 未暴露，软件事件可用；同时也别用发行版 linux-tools 的 perf 直接跑（版本不匹配）。
  5. “工具输出数字都可信”：容器内看到的 /proc 是宿主的（11 篇）、WSL2 的 CPU 时间包含宿主调度的影响、%util 在 NVMe 上会误导。每个数字要知道它"数的是什么"。

本篇小结

  • 观测分六层：应用埋点 → syscall → 计数器（/proc、/sys）→ tracepoint → kprobe/uprobe → PMU；越往下越接近真相，排查自上而下按代价递增下潜。
  • 静态八件套（uptime/dmesg/free/vmstat/mpstat/pidstat/iostat/sar）覆盖 USE 方法所需的全部 L3 数据，sar 提供历史回放能力。
  • 动态追踪四路线：strace（简单但贵）、ftrace（内核自带但原始）、perf（全层通吃）、bpftrace（可编程），选型按"想回答的问题"查表。
  • WSL2 上：计数器/strace/eBPF 可用；硬件 PMU 通常 <not supported>，用软件事件替代；发行版 perf 与 WSL 内核版本不匹配需自行构建。
  • 体检流程模板：uptime 看趋势 → vmstat/mpstat 定资源方向 → pidstat 定进程 → 深潜到 03/04 篇的工具。

练习

  1. 在你的机器上跑 uptime 与 mpstat -P ALL 1 5，回答：load 与"忙碌 CPU 数"是否一致？不一致的话，用 vmstat 1 的 b 列解释差值去了哪里。
  2. 运行 sick_machine.py，分别在"只开 burn_cpu 线程"和"只开 churn_disk 线程"两种情况下各跑一次 vmstat 1 5，把两组输出的差异（r/b/wa/cs）抄下来并逐列解释。
  3. 用 pidstat -w 1 5 观察一个 python3 -c "while True: pass"，再看一个 python3 -c "import time; [time.sleep(0.01) for _ in range(100000)]"，对比 cswch/nvcswch 的数量级差异并解释哪列是自愿切换。
  4. 确认你 WSL2 的 perf 能用哪些事件：跑 perf list | head -30 和 perf stat -e task-clock,context-switches,page-faults ls，把硬件事件是否 <not supported> 记进你的环境笔记（本系列后面会反复用到这个结论）。
  5. 选一个你正在跑的服务（或 FastAPI demo），用 sar 生成"过去 1 小时"的 CPU 与内存报告（sar -u、sar -r），体验一次"回到过去"的观测；没开 sysstat 的话先启用它。

08 - 分布式事务

本篇目标

  • 完整走查 2PC（两阶段提交）的每一步，逐一分析协调者/参与者在各阶段宕机的后果。
  • 说明 3PC 为什么"理论上更完备、实践上没人用"。
  • 掌握 Saga 模式（含补偿事务）并以订票案例写完整流程，理解 TCC 与 Saga 的区别。
  • 落地"基于消息的最终一致"：本地消息表（outbox 模式），并给出选型决策表。

1. 问题定义：原子提交跨了机器

第 07 章留的问题：一个事务要写两个分片（甚至两种存储），怎么保证"要么都提交、要么都不提交"？单机靠 undo log + 一个锁管理器闭环；跨机后，决定"提交"的瞬间必须所有参与者都同意，而这个决定过程本身可能被故障打断——这就是原子提交问题（atomic commit）。

关键约束（回忆 02 章）：协调者发出"提交"决定后收不到某参与者确认，它无法区分"对方死了"与"网络断了"；而参与者在等决定时也无法自作主张（自己提交了，协调者那边可能已决定中止）——双方都卡在"必须等对方"上。2PC 是这个困境下的最优工程解，但不是完美解。

2. 2PC：流程与故障走查

两阶段提交（Two-Phase Commit，Jim Gray 1978 年《Notes on Data Base Operating Systems》中形式化）：

规则要点：参与者回 YES 后进入不确定态（in-doubt）——不能再自行提交或中止，必须死等协调者的第二阶段指令；协调者落盘决定后（write-ahead），无论发生什么都要把决定送达所有参与者。

故障逐一走查（面试核心题，每一条都要能推）：

故障点 后果 恢复动作
参与者在 PREPARE 前崩 协调者收不齐 YES → 决定 ABORT 参与者重启后收到/查出 ABORT，无副作用
参与者回 YES 后、收到 COMMIT 前崩 该参与者卡在不确定态；协调者若活着会重发 COMMIT 参与者重启后必须问协调者（不能自决），期间其锁被占用
协调者在收到全部 YES 前崩 参与者等不到决定，但大家还都没提交 → 安全超时后统一 ABORT 参与者自行中止（因为没人收到过"决定提交"）
协调者在落盘决定后、发完 COMMIT 前崩 最坏情形：参与者不知道全局决定是提交还是中止，全部卡死 参与者重启后只能阻塞等待协调者恢复；协调者从磁盘决定记录恢复后重发
网络分区：协调者与部分参与者失联 同上——失联的参与者卡在不确定态 分区恢复后重发决定

第 4 行是 2PC 的命门：协调者单点 + 参与者阻塞。协调者崩了，参与者既不能提交也不能中止（都可能违反原子性），资源锁全程持有，下游全堵。这就是"2PC 时代码可用、故障时阻塞"的精确含义。

2PC 与 Raft 的关系值得点破：2PC 解决"一次事务跨多方"的原子性，Raft 解决"一份日志跨副本"的复制一致性，两者正交。etcd 的事务（txn）是 Raft 上的单键空间原子操作，MySQL XA 才是 2PC。把 Raft 叫"分布式事务"是常见口误。

3. 3PC 为什么没人用

三阶段提交（Three-Phase Commit，Skeleton of idea 出现于 1980 年代）在 PREPARE 与 COMMIT 之间插入 PreCommit 阶段，并引入超时：参与者若在 PreCommit 后失联，超时后自行提交（因为"能到 PreCommit 说明大家都同意过"）。

理论目标：消除 2PC 的阻塞（协调者死了参与者也能自己决定）。但前提是网络延迟有上界 + 时钟可靠——正是 02 章证伪的两个假设。分区场景下，被隔离的一组参与者可能超时后自行提交，而协调者侧决定的是 ABORT → 原子性被破坏。结论（DDIA 第 9 章明确表述）：3PC 在非拜占庭异步网络下既不完美也不实用；工程界要么用 2PC + 共识化协调者（协调者本身跑在 Raft 上，如 TiDB 的 TiKV 事务协调、 Spanner 的 Paxos group），要么换 Saga 类最终一致方案。

4. Saga：长事务的补偿之路

Saga（Garcia-Molina & Salem, Sagas, SIGMOD 1987；微服务语境的复兴见 Chris Richardson《微服务架构设计模式》第 4 章）：把大事务拆成 T1 → T2 → … → Tn 的本地事务序列，每个 Ti 配一个补偿事务 Ci（语义上"撤销 Ti 的业务效果"，不是数据库回滚）。任何一步失败，反向执行已完成步骤的补偿：T1 T2 T3 失败 → 执行 C2 C1。

补偿不是回滚的三个不同点：补偿发布新的可见状态（机票先显示"已订"再变"已退"，其他事务可能看到中间态）；补偿本身也可能失败（需要重试到成功，所以补偿必须设计成可重试的幂等操作）；没有隔离性（Saga 之间可能交错，需要业务层防脏读——如"已订未付款"状态让其他流程不可见）。

编排（orchestration）与协同（choreography）两种实现：

  • 编排式：中央协调器驱动每一步（代码直观、可观测；协调器本身要高可用——用状态机 + 持久化进度实现，别把协调器做成另一个 2PC 协调者）。
  • 协同式：每步完成后发事件，下游订阅（无中心、松耦合；流程散落在各服务里，链路长后不可维护）。经验做法：步骤 ≤ 3 用协同式，更多用编排式。

5. TCC 与消息最终一致

TCC（Try-Confirm-Cancel）：业务层的"准 2PC"。每个参与方实现三个接口：Try 预留资源（冻结额度而非扣款）、Confirm 确认（真正扣）、Cancel 释放预留。TCC 的本质是把"数据库锁资源"提前到"业务预留资源"，第二阶段不再碰底层事务，因此协调器崩溃时业务状态自洽（预留要么 Confirm 要么 Cancel，都有幂等接口兜底）。代价：每个参与方要写三个接口且全部幂等，侵入性大（支付/资金类业务愿意付这个代价）。

本地消息表 / Outbox 模式（最常用的最终一致落地，经验做法首选）：跨服务写操作拆成"本地事务 + 事件投递"：

  1. 业务写与"待发消息"记录在同一个本地事务里落库（原子性由单机事务保证）。
  2. 后台轮询（或 binlog 订阅，如 Canal/Debezium）把待发消息投到 MQ，成功后标记已发。
  3. 消费方幂等处理（第 09 章幂等键）。

它把"分布式事务"降级为"本地事务 + 至少一次投递 + 幂等消费"，没有跨库锁、没有协调者单点，唯一代价是消费方短暂可见延迟——大多数业务完全可接受。Kafka 的事务（transactional producer，read-process-write 原子性）是此思路在流处理侧的对应物，但覆盖面不同（见 09 章）。

6. 选型决策表

方案 一致性 阻塞/单点 侵入性 适用
2PC/XA 强（原子性） 协调者宕机参与者阻塞 低（协议级） 短事务、参与方少、同公司基础设施
3PC 理论强 网络分区下破坏原子性 — 不用于生产
Saga 最终一致（有中间态） 无（补偿幂等重试） 中（写补偿） 长流程、跨服务、可接受中间态（订票/订单履约）
TCC 准强一致（业务预留） 无（Confirm/Cancel 幂等） 高（三接口） 资金/库存等不容忍中间脏数据的短流程
Outbox+MQ 最终一致 无 低（一张表+轮询） 微服务间状态同步的事实标准

常见误区

  1. “用了 Raft/etcd 就不需要 2PC”：Raft 保证一份日志在副本间一致；"一个操作横跨两个系统"的原子性它管不着。跨系统原子性要么 2PC、要么 Saga/Outbox 拆解。
  2. “Saga 的补偿 = 数据库回滚”：补偿是新的业务操作（退票单），会被其他事务看见；且补偿自身必须幂等可重试。把补偿当"撤销历史"会导致中间态被下游消费后无法收拾。
  3. “TCC 的 Try 失败就不用 Cancel”：Try 超时时不知道对方是否已预留成功，必须照样发 Cancel（幂等），否则留下幽灵冻结额度。TCC 的正确性全靠幂等，这是它侵入性高的根源。
  4. “Outbox 会不会丢消息/重复消息”：会重复（至少一次投递），不会丢（同事务落库）。正确姿势是消费端按消息 ID 幂等去重，而不是给投递加"恰好一次"的执念。
  5. “2PC 性能差所以直接淘汰”：2PC 的可用性差（阻塞）与延迟高（两轮 RTT + 锁持有期）是真的；但在短事务、参与方稳定、同栈管理的场景（如同一厂商数据库集群、X AU 内部），XA 依然是省心选择。选型看故障容忍度，不看流行度。

本篇小结

  • 跨机原子提交的困境来自"决定点与执行点分离 + 网络不可靠"；2PC 用准备阶段 + 落盘决定给出了工程最优，代价是协调者宕机后参与者阻塞。
  • 2PC 五种故障走查中，"协调者落盘决定后宕机"是命门；3PC 想靠超时自救，却把原子性押在不可靠的网络与时钟上，被实践淘汰。
  • Saga 用"本地事务序列 + 反向补偿"换取无阻塞长流程；补偿必须幂等、可重试、可被看见（与回滚的三点区别）。
  • TCC 把锁资源业务化（预留），适合资金类短流程；Outbox + 至少一次投递 + 幂等消费是微服务最终一致的事实标准。
  • 选型口诀（经验做法）：强一致短事务 2PC、资金预留 TCC、长流程 Saga、服务间解耦 Outbox。

练习

  1. 跑通 two_pc.py，为场景 3 补写"协调者恢复"逻辑：重启后从 decision_disk 读出 COMMIT 并重发，验证参与者从 in_doubt 恢复到 committed——这正是 2PC 恢复协议的核心。
  2. 在 saga_ticket.py 中给 cancel_hotel 加入"前 2 次调用抛异常"，实现补偿重试循环（带指数退避，预告 10 章），观察最终收敛；再想想：如果补偿永远失败，系统需要什么人工/异步兜底？
  3. 设计一个 TCC：账户服务提供 freeze/confirm/cancel 三接口（余额 100 元，下单冻结 30）。用 Python 写出三个接口与调用方，并构造"Try 成功但 Confirm 前调用方崩溃"的场景，说明恢复策略（超时自动 Cancel）如何释放冻结。
  4. 用 sqlite3 实现 Outbox：业务表与消息表同事务写入，轮询线程投递（打印代替 MQ），消费端用消息 ID 去重表幂等。故意让投递重复 3 次，验证最终只处理一次。
  5. 阅读题：读 Chris Richardson《微服务架构设计模式》第 4 章（Saga 与 TCC），对比书中 Order Service 示例与本章 saga_ticket.py 的状态机设计，列出你至少能想到的两个生产化差距（如进度持久化、超时监控、幂等键设计）。

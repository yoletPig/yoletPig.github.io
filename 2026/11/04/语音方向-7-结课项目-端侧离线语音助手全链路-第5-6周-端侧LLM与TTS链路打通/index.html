第 5-6 周教程：端侧 LLM 与 TTS 链路打通——唤醒、思考、开口、被打断

本周要回答的四个问题

  1. Qwen2.5-1.5B INT4 的权重与 KV cache 各占多少内存？上下文长度如何被内存反推？
  2. TTS 怎么「边生成边播」？首包 300 ms 预算靠什么机制达成？
  3. 唤醒词引擎常驻系统里，误唤醒与漏唤醒怎么平衡？
  4. 语音打断的状态机有几个状态？「开口→TTS 静音」≤200 ms 怎么保证？

对应学习计划：第 5-6 周。交付物：板端跑通「唤醒 → 听 → 想 → 说」闭环，100 次对话延迟分布（P50/P95）；实现语音打断并测量截断延迟。

1. 第一性原理：端侧 LLM 是内存问题，不是算力问题

1.1 INT4 权重内存

这个公式在干什么：INT4 量化把每个参数从 fp16 的 2 字节压到 4 bit（0.5 字节），所以「参数个数 × 0.5 字节」就是权重的理论下界；但 Q4_K_M 这类分组量化还要为每组存 scale/zero-point 元数据，实测约多 10%——乘的 1.1 就是这笔「打包开销」。手算小例：1.5×109×0.5×1.1=0.83×1091.5 \times 10^9 \times 0.5 \times 1.1 = 0.83 \times 10^91.5×109×0.5×1.1=0.83×109 字节 ≈ 0.77 GiB ≈ 0.83 GB（十进制 GB）。

Mweight≈1.5×109×0.5×1.1≈0.83 GBM_{\text{weight}} \approx 1.5 \times 10^9 \times 0.5 \times 1.1 \approx 0.83\,\text{GB} Mweight​≈1.5×109×0.5×1.1≈0.83GB

对照实际：Qwen2.5-1.5B-Instruct 的 Q4_K_M GGUF 文件实测约 1.0 GB（与第 1-2 周内存预算表那一行对上），比公式略大是因为嵌入层等部分保留更高精度；3B 理论估算约 1.7 GB（Q4_K_M 实测约 2 GB）——都在 8 GB 板子的承受范围内，真正的变量是 KV cache。

动手验证：把 huggingface-cli download Qwen/Qwen2.5-1.5B-Instruct-GGUF 下载的 *q4_k_m.gguf 文件 ls -lh 一下，和公式估算对账——权重内存是唯一「下载完就知道」的预算项，KV cache 才是要算的。

1.2 KV cache：每多一个上下文位置都要付费

自回归生成时，每个历史 token 的 K/V 向量要缓存（类比：LLM 做「阅读理解」时给每个读过的字记一张便签，生成下一个字前要翻所有便签——便签必须全程留在桌上，即内存里）。Qwen2.5-1.5B 的结构参数（28 层、12 个 query 头、GQA 2 个 KV 头、head dim 128、fp16）：

MKV=2×nlayer×nkv_head×dhead×L×2 bytesM_{\text{KV}} = 2 \times n_{\text{layer}} \times n_{\text{kv\_head}} \times d_{\text{head}} \times L \times 2\,\text{bytes} MKV​=2×nlayer​×nkv_head​×dhead​×L×2bytes

这个公式在干什么：算「给模型桌上留便签」要多少内存。逐项拆开：因子 2 = K、V 各一份；nlayern_{\text{layer}}nlayer​ = 层数，每层注意力都有自己的便签；nkv_head×dheadn_{\text{kv\_head}} \times d_{\text{head}}nkv_head​×dhead​ = 每层每 token 的便签宽度（GQA 让多个 query 头共享一张便签，宽度由 KV 头数决定）；LLL = 目前有多少个 token 在上下文里；乘 2 bytes 是 fp16。它随 LLL 线性增长，权重是常数而 KV cache 不是——多轮对话、长历史都会持续加价，这就是历史必须截断的数学原因。结果拿来做什么：① 反推上下文上限；② 对账实测内存（本周 5.1 的计算器）。

代入：每位置 2×28×2×128×1×2=28 6722 \times 28 \times 2 \times 128 \times 1 \times 2 = 28\,6722×28×2×128×1×2=28672 字节 ≈ 28 KB/token。这就是本周代码要验证的核心数字——上下文长度是被内存反推出来的：

Lmax⁡=MKV 预算28 KBL_{\max} = \frac{M_{\text{KV 预算}}}{28\,\text{KB}} Lmax​=28KBMKV 预算​​

手算小例：给 KV cache 0.5 GB → Lmax⁡=512×1024×1024 B/28 672 B≈18 700L_{\max} = 512 \times 1024 \times 1024\,\text{B} / 28\,672\,\text{B} \approx 18\,700Lmax​=512×1024×1024B/28672B≈18700，绰绰有余；但 4 GB 板子或 3B 模型（36 层，每位置 2×36×2×128×2=36 8642 \times 36 \times 2 \times 128 \times 2 = 36\,8642×36×2×128×2=36864 ≈ 36 KB）时必须精算。

1.3 prefill 与首 token 延迟

首 token 延迟 ≈ prefill（并行处理全部输入 token）时间。prefill 计算量 ∝L输入\propto L_{\text{输入}}∝L输入​，所以：

  • 会话历史必须截断（第 1-2 周已定 4 轮滑窗）；
  • 系统提示词能短则短——每个常驻字符都在每次请求里重复付费。

2. 端侧 LLM 部署：llama.cpp 与 rknn-llm

2.1 两条路径

路径 适用 说明
llama.cpp（GGUF INT4） CPU 先行，立刻可用 aarch64 编译成熟、NEON 加速、量化方案全（Q4_K_M 是质量甜点）
rknn-llm NPU 回填，性能优化方向联动 官方示例覆盖 Qwen2/Qwen2.5 等主流开源 LLM，需按其量化要求转模型

策略与 ASR 周相同：llama.cpp 先打通，rknn-llm 后回填，接口层封装成「文本进、文本流出」的黑盒。

2.2 部署骨架

核掩码怎么来的：RK3588 是 8 核（cpu0-3 = A55 小核，cpu4-7 = A76 大核，不同板型设备树可能不同，用 lscpu 或 cat /sys/devices/system/cpu/cpu4/cpufreq/cpuinfo_max_freq 确认——A76 的最大频率明显更高）。--cpu-mask 接十六进制掩码，第 nnn 位对应 cpunnn：只开第 4~7 位 → 0b1111_0000 = 0xF0。等价写法 --cpu-range 4-7 更不易写错。为什么绑大核：LLM 是全链路最重的负载，混跑在小核上吞吐直接掉一半以上；llama.cpp 也有 --cpu-range/--cpu-strict 可严格一线程一核。

Python 侧用 llama-cpp-python 的流式接口消费文本流——LLM 每产出一段文本就喂给 TTS 切句，这是「想」与「说」并行的关键。

3. TTS 边生成边播

3.1 分段策略

整句合成必破 300 ms 首包预算。拆法：

LLM 文本流→按标点切句[句1,句2,… ]→逐句合成PCM 块流→队列播放\text{LLM 文本流} \xrightarrow{\text{按标点切句}} [\text{句}_1, \text{句}_2, \dots] \xrightarrow{\text{逐句合成}} \text{PCM 块流} \xrightarrow{\text{队列}} \text{播放} LLM 文本流按标点切句​[句1​,句2​,…]逐句合成​PCM 块流队列​播放

  • 第一句特殊对待：哪怕只有半句（「好的，」）也先出声——用户听到任何响应，容忍度立刻上升；
  • 句间用双缓冲：播句 1 时合成句 2，消除句间停顿；
  • 每块带序列号：打断时按序列号清空队列（第 1-2 周的接口契约在此兑现）。

3.2 首包延迟构成

TTTS 首包=T等第一句+T首句合成+T播放缓冲T_{\text{TTS 首包}} = T_{\text{等第一句}} + T_{\text{首句合成}} + T_{\text{播放缓冲}} TTTS 首包​=T等第一句​+T首句合成​+T播放缓冲​

这个公式在干什么：把「预算表里 TTS ≤ 300 ms 那一格」拆成三个可分别下手的成本。逐项含义：T等第一句T_{\text{等第一句}}T等第一句​ 是从 LLM 开始吐字到第一句文本凑齐的等待（由 LLM 的出字速度与第一句长度决定）；T首句合成T_{\text{首句合成}}T首句合成​ 是小模型把第一句转成 PCM 的耗时；T播放缓冲T_{\text{播放缓冲}}T播放缓冲​ 是攒够一小块音频才能送声卡的开销。手算小例：LLM 出「好的，」约 100 ms + 合成 100 ms + 缓冲 40 ms = 240 ms ≤ 300 ms——这就是为什么第一句允许只是半句、为什么播放缓冲只留 1~2 块（20~40 ms）。三项都要压：等第一句靠 LLM 流式输出（别等整段）、首句合成靠小模型、播放缓冲 1~2 块（20~40 ms）。

4. 唤醒词与打断状态机

4.1 唤醒词的权衡

误唤醒率（每天误触发次数）与漏唤醒率此消彼长：阈值调高 → 误唤醒↓ 但用户喊不应。产品经验：每天 ≤1 次误唤醒可接受，漏唤醒不可接受（用户直接放弃使用）。双唤醒词（「小 X 小 X」）比单词误唤醒率低一个量级。

4.2 状态机（本周交付核心）

打断的 200 ms 预算拆解：VAD 检测（≤100 ms，低阈值快速通道）+ TTS 停止与队列清空（≤50 ms）+ 回 LISTENING（≤50 ms）。打断检测必须用独立的低阈值能量+VAD 通道，不能等 ASR——等识别出「停」字就晚了。

6. 工程权衡与失效模式

6.1 权衡

  • 1.5B vs 3B 的决策标准：不看跑分，看你的 100 条测试集上「答非所问率」差多少——差距 <5 个点就选 1.5B 保延迟；
  • KV cache fp16 vs INT8：INT8 缓存省一半内存，但长上下文下质量有可见损失——端侧上下文本来就短（<2K），默认 fp16，内存告急再降；
  • 打断灵敏度：阈值低 → 电视声误打断；阈值高 → 用户喊不停。用「打断通道」与「正常识别通道」分离的双阈值：打断通道宁误触发（代价只是停一下），识别通道宁保守；
  • TTS 音色：蒸馏小模型音色不如原版——在「像真人」与「300 ms 首包」之间，端侧选后者，音色留作后续升级项。

6.2 失效模式

  1. 长对话失控：历史不截断，每轮 prefill 输入线性变长——首 token 延迟随轮数明显上涨；超过 --ctx-size 后 llama.cpp 截断最旧上下文（答案「失忆」）或直接报错；KV cache 同步线性膨胀（虽以 ~28 KB/token 增速不快，但叠加计算缓冲与音频缓冲在 4 GB 板上仍可 OOM）。修复：4 轮滑窗 + 硬上限（4.1 节预算表），写入接口契约并加监控告警。
  2. 打断后残留语音：播放队列清空了但音频驱动缓冲还有半秒数据。症状：喊「停」后还吐出半个词；修复：清空队列后调用声卡 flush，并把这 50 ms 算进打断预算。
  3. 唤醒后立即说话被截头：唤醒词引擎切到 ASR 需要几十毫秒，用户紧接着说「今天天气」丢了「今」字。修复：唤醒触发时刻起持续录音缓冲，ASR 从缓冲区起点（而非就绪时刻）开始解码。
  4. prefill 抖动：同样问题有时 300 ms 有时 700 ms。根因：输入长度差异（历史轮数不同）+ 大核被抢占。修复：历史截断固定长度 + 绑核 + 埋点区分「输入长度」与「单位 token 耗时」两个变量。

7. 延伸思考题（含解析）

Q1：为什么 KV cache 用 GQA（2 个 KV 头）能省内存？对端侧意味着什么？
A：GQA 让多个 query 头共享一组 K/V，KV cache 与 KV 头数成正比——Qwen2.5-1.5B 用 2 个 KV 头服务 12 个 query 头，若无 GQA（12 个 KV 头）每位置 KV 需 2×28×12×128×2=172 KB2 \times 28 \times 12 \times 128 \times 2 = 172\,\text{KB}2×28×12×128×2=172KB，GQA 直接把它降到 1/61/61/6（28 KB/token，4K 上下文时 KV 总量从 ~700 MB 降到 ~117 MB）。对端侧：同等内存预算下上下文长度扩大 6 倍，这就是「端侧选模型先看 KV 结构」的原因。

Q2：TTS 为什么不能等 LLM 全部生成完再合成？两种延迟差多少？
A：整句等待时用户沉默时间 = LLM 全部生成 + TTS 全句合成；流式时 ≈ 第一句生成 + 第一句合成。一句 50 字的回答，前者约 2~4 s，后者约 400~600 ms——差的就是「听助手开口」的生死线。代价是句间韵律可能不连贯（靠双缓冲与轻量拼接缓解）。

Q3：打断检测为什么不能复用 ASR？
A：ASR 要等一段话说完或至少几百毫秒缓冲才能识别，打断要的是「开口即停」（≤200 ms）。所以打断用低阈值能量+VAD 快速通道：它不需要知道用户说了什么，只需要知道用户在说话。误触发的代价（停一下）远小于慢触发的代价（喊不停）。

Q4：llama.cpp 的 Q4_K_M 与纯 INT4（Q4_0）差在哪？端侧怎么选？
A：Q4_K_M 是分块混合量化（敏感层高精度 + 4bit 主体 + 量化 scale 精细化），质量损失显著小于 Q4_0，体积只大 ~10%。端侧内存够就选 Q4_K_M——质量-内存曲线上它几乎总是帕累托点。

Q5：100 次对话测出 P95 达标但 max 超过 3 s，要处理吗？
A：要。长尾的 max 往往对应具体可定位的事件（温度降频、GC、历史轮数最满的一次）。处理路径：埋点找出最慢那 5 次的共同特征，归入第 7-8 周的压测清单。产品上用户对「偶尔一次特别慢」的记忆远强于平均水平。

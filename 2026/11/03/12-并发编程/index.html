12-并发编程

本篇回答的问题

  • 为什么一个语音推理引擎必须用多线程，而不能"一个大循环跑到底"？
  • 怎么启动线程？join() 和 detach() 的区别，为什么 detach() 很危险？
  • 什么是数据竞争？为什么两个线程各加 100000 次，结果却不是 200000？
  • std::mutex + lock_guard/unique_lock 怎么用？std::atomic 什么时候比锁更好？
  • 生产者-消费者怎么用条件变量写出来？（音频流水线的核心骨架）
  • 死锁怎么产生又怎么避免？async/future/promise/call_once 各自一句话是什么？

前置：默认你已掌握第 01-11 篇的 RAII、智能指针、移动语义、STL 容器与模板。

一、为什么推理引擎必然多线程

一个典型的语音识别流水线，本质上是三条速度完全不同的流水线在同时工作：

如果只用一个线程顺序执行：采集 → 推理 → 解码 → 输出，那么推理的 100ms 里，麦克风新来的音频就没人接——音频是实时流，错过就永远丢了。所以采集必须独立线程（回调不能被推理阻塞），推理独立线程（从队列里取帧慢慢算），线程之间靠线程安全的队列/环形缓冲区交接数据（第 13 篇实战就写一个）。Python 里 threading 受 GIL 限制，很多人靠多进程绕开；C++ 的 std::thread 是真正的操作系统线程，没有 GIL，这也是推理引擎都用 C++ 写的重要原因之一。

二、std::thread 基础：join 与 detach

启动线程就是把"可调用对象 + 参数"交给 std::thread 构造函数（本篇全部示例都用 g++ -std=c++17 -Wall -pthread xxx.cpp -o xxx 编译，-pthread 必须加）：

三条铁律：

  1. std::thread 对象销毁前，必须已经 join() 或 detach()，否则程序直接 std::terminate()。这和 RAII 的思想一脉相承——只不过 std::thread 自己不是 RAII 的，需要你保证。
  2. join() 是"等它干完"：主线程阻塞直到子线程结束。
  3. detach() 是"撒手不管"：线程变成后台精灵线程，和 std::thread 对象断开联系。

detach 为什么危险

detach 之后，你就失去了对这个线程的一切控制：无法等待、无法取消、也不知道它是否还在跑。如果线程还引用着某个已经析构的局部变量或成员，就是悬空引用——比悬空指针更难查，因为它可能"大多数时候恰好没炸"。实战建议：推理引擎里几乎不用 detach()。采集、推理、解码线程的生命周期和引擎一样长，用成员变量持有 std::thread，在析构函数里设置停止标志后 join()；想"启动一个异步任务然后拿结果"，用后面的 std::async 或线程池。

四、std::mutex + RAII 锁：lock_guard 与 unique_lock

std::mutex 的语义很朴素：同一时刻只有一个线程能持有它，别人 lock() 会阻塞。但手动配对 lock()/unlock() 会重蹈手动 new/delete 的覆辙（忘记解锁、异常路径漏解锁），所以永远用 RAII 包装（复习第 03 篇）：

两者的分工：std::lock_guard 构造即锁、析构即解锁，不能中途开/关，最轻量，临界区一杆子插到底就用它；std::unique_lock 稍重，但可以中途 lock()/unlock()、支持延迟加锁、可以移动，条件变量 wait() 只接受它——wait 内部要"解锁 → 睡眠 → 被唤醒后重新加锁"。性能提示：临界区越短越好，推理线程拿到锁只该做"取走一帧数据"，矩阵乘法放到锁外做。

  • 常用场景：std::atomic<bool> stop_flag_ 让推理线程优雅退出（第 13 篇会见到姊妹版 closed_）；std::atomic<int> frames_dropped_ 统计丢帧。
  • atomic 只解决"单个操作"的原子性，需要"同时更新两个变量"或"保护一整段逻辑"时仍要 mutex。

六、条件变量：生产者-消费者（音频流水线的骨架）

计数器可以无锁，但队列不行：容器是多步修改的复合状态，必须 mutex 保护；而"队列空时消费者怎么办"则要条件变量 std::condition_variable——它让线程睡眠等待某个条件成立，被别人唤醒后再检查，而不是空转轮询烧 CPU。

读懂三个关键机制：

  1. wait(lock, pred) 等价于 while (!pred()) cv.wait(lock);，谓词必不可少，原因有二：虚假唤醒——OS 允许 wait 在没人 notify 时醒来，必须重新检查条件；收工竞争——消费者检查完"队列空"到进入 wait 之间，生产者可能刚好推入数据并 notify，不重查条件这次通知就永远丢了。带谓词的 wait 把"检查 + 睡眠"原子地放在锁的保护下，两个问题一起解决。
  2. 改状态必须先拿锁：先 push_back 再 notify_one；收工标志同理，改完 notify_all。收工协议：光靠"队列空"不能退出（可能下一秒就有新帧），必须加"生产者已收工"标志，两者结合才是安全退出条件。

八、std::async / std::future / std::promise 快速一览

这一家子解决"把一个任务扔到后台，稍后拿结果"：std::async(std::launch::async, f, args...) 启动 f，立刻返回 std::future<R>；std::future 是"未来才会有值"的占位符，get() 阻塞到结果就绪（只能调用一次）；std::promise 是 future 的写端，当"结果就绪的时刻"由你自己的代码决定时，在工作线程里 set_value()，另一端 get()。

常见坑

  1. 忘记 -pthread：能编译（甚至能链接），但运行时表现怪异或崩溃。凡用了 <thread>/<mutex> 一律加上。
  2. 忘 join 导致 std::terminate；detach + 引用局部变量则造成偶发悬空崩溃，两类都是最难的 bug。
  3. wait 不带谓词：虚假唤醒或通知丢失，消费者永久睡眠。永远写 cv.wait(lock, pred) 两参数版。
  4. 改共享状态没拿锁：状态修改必须在锁内，否则存在"检查-睡眠"窗口丢通知；同理临界区不做重活，推理计算放锁外。
  5. 认为"测试通过 = 没有竞争"：竞争是 UB，-O2 下可能恰好不发作（见第三节真实数据）；用 atomic 保护复合操作同理——两个 atomic 变量的更新合在一起不是原子的，该上锁还是要上锁。

小结

  • 推理引擎 = 采集线程 + 推理线程 + 后处理线程，靠线程安全队列交接数据；音频实时流不容许单线程串行。
  • std::thread 销毁前必须 join() 或 detach()；引擎生命周期线程用成员变量 + 析构时 join，不用 detach。
  • 多线程共享的普通变量并发写是 UB；单变量计数用 std::atomic，复合逻辑用 std::mutex + RAII 锁（lock_guard / unique_lock）。
  • 生产者-消费者：mutex 保队列，wait(lock, pred) 保等待，"队列空 + 收工标志"保退出；多锁场景统一顺序或用 C++17 std::scoped_lock。async/future/promise 是"后台任务 + 取结果"三件套，call_once 保证一次初始化；第 13 篇将把这些与模板、RAII 组装成真正的 RingBuffer。

自测题

  1. std::thread 对象析构前既没有 join() 也没有 detach()，会发生什么？
  2. race.cpp 在 -O2 下多次运行都输出 200000，能否断定程序没有数据竞争？
  3. std::lock_guard 和 std::unique_lock 怎么选？条件变量的 wait 只接受哪一个？
  4. cv.wait(lock, pred) 中谓词 pred 的两个作用是什么？
  5. 生产者改完共享队列后调用 notify_one，若消费者恰好在"检查条件"和"进入睡眠"之间，通知会丢吗？为什么带谓词的 wait 不怕？
  6. 两个线程分别先拿 A 后拿 B、先拿 B 后拿 A，写出两种 C++17 的修法。
  7. counter.compare_exchange_strong(expected, v) 返回 false 时，expected 的值发生了什么？
  8. std::async(f) 不指定 launch 策略有什么隐患？怎么写才稳妥？

答案

  1. 程序直接调用 std::terminate() 终止。
  2. 不能。数据竞争是未定义行为，"恰好得到正确结果"恰恰是 UB 的典型表现，随时可能换环境后发作。
  3. 临界区一锁到底用 lock_guard（更轻）；需要中途解锁/重锁、延迟加锁或配合条件变量时用 unique_lock；wait 只接受 unique_lock。
  4. 防虚假唤醒（醒来无条件重查）和防通知丢失（检查与睡眠在锁保护下原子进行）。
  5. 会丢——但这正是谓词的作用：wait 内部在持有锁的状态下重新求值 pred，只要状态已在锁内改过，重新检查就能看到，不会睡死。
  6. 方法一：让两个线程都统一"先 A 后 B"；方法二：改用 std::scoped_lock lock(mtx_a, mtx_b); 一次性获取两把锁。
  7. counter 保持原值，函数把 counter 的当前实际值写回 expected，返回 false。
  8. 不指定时实现可选择推迟执行，任务可能拖到 get()/析构时才在当前线程跑，破坏"并发执行"预期；应显式写 std::launch::async。
